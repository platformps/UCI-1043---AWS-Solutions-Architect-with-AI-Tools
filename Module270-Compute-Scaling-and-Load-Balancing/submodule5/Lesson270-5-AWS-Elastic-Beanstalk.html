Lesson Overview

In this module, you learned the pieces of a scalable web tier: the load balancer (lessons 270.1 and 270.2), the Auto Scaling group, and the launch template (lesson 270.4). 1. Elastic Beanstalk Fundamentals

Problem Statement

FlashCart’s small web team has written a new storefront in Python. The team knows that a production site needs a load balancer, an Auto Scaling group, and monitoring, and it has no time to build and maintain them by hand before the next sale.

The team wants to upload its code and let AWS set up the rest, and it still wants to see and control the instances that run the application.

Your challenge:

  • Name the AWS service that does this, and list the resources that it builds.
  • Explain how an application, a version, and an environment relate to each other.
  • Choose between a web server environment and a worker environment for a background job.

1.1 What AWS Elastic Beanstalk Is

  • AWS Elastic Beanstalk is a platform as a service (PaaS). You upload your application code, and Elastic Beanstalk provisions the capacity, load balancing, automatic scaling, and health monitoring for it.
  • You keep control. The resources that it creates are normal AWS resources in your account, so you can see and change them.
  • There is no additional charge for Elastic Beanstalk. You pay for the AWS resources that your application uses, such as Amazon EC2 instances and the load balancer. Check the pricing page for details.
  • It supports Go, Java, .NET, Node.js, PHP, Python, Ruby, and Docker applications.

1.2 What It Builds for You

  • Amazon EC2 instances that run your application, and the security groups for them (lesson 269.1).
  • An Auto Scaling group (lesson 270.4), so the environment adds and removes instances with the load.
  • A load balancer, an Application Load Balancer by default (lesson 270.2), in a load-balanced environment.
  • Amazon CloudWatch alarms for scaling and health (lesson 274.1), and an Amazon S3 bucket that stores the application versions (lesson 271.2).
  • Elastic Beanstalk creates and updates these resources through AWS CloudFormation (lesson 296.1).

1.3 Applications, Versions, Environments, and Platforms

ConceptWhat it is
ApplicationA logical collection of Elastic Beanstalk components: versions, environments, and configurations. It works like a folder.
Application versionA specific, labeled iteration of deployable code. A version is stored in Amazon S3, and you can deploy any version again.
EnvironmentThe set of AWS resources that runs one application version. An application can have several environments, for example development, test, and production.
PlatformThe operating system, the language runtime, the web server, and the Elastic Beanstalk components that run the application, for example Python on Amazon Linux 2023.
Saved configurationA set of environment settings that you can save and use to create or update an environment.

1.4 Environment Types and Tiers

ChoiceOptionsUse it for
Environment typeSingle instance: one EC2 instance and no load balancer. Load balanced: a load balancer and an Auto Scaling group across several Availability Zones.Single instance for development and testing. Load balanced for production.
TierWeb server environment: serves HTTP requests from users.A website or an API.
TierWorker environment: reads messages from an Amazon SQS queue (lesson 273.3) and sends each one to your application for processing.Background jobs, such as sending a report or resizing images.

1.5 Platforms and Their Life Cycle

  • Each platform is released in platform branches, for example a Python version on an operating system. Elastic Beanstalk retires a branch when one of its components reaches end of life.
  • Current Linux platforms run on Amazon Linux 2023. Elastic Beanstalk set the status of all Amazon Linux 2 branches to retired on August 6, 2026, after Amazon Linux 2 reached end of life. Elastic Beanstalk retired the Amazon Linux AMI branches on July 18, 2022.
  • Check the platform release schedule before you choose a platform branch, because the dates change.

Exam Trap

Remember these points:

  • Elastic Beanstalk is not serverless. Your application runs on EC2 instances that you pay for.
  • There is no charge for the service itself. The charge is for the resources.
  • A database inside the environment is deleted when the environment is terminated (section 2.4).
  • Elastic Beanstalk is for applications. AWS CloudFormation is for describing any set of resources.

Memory Hook

2. Deployments, Configuration, and Operations

Problem Statement

FlashCart’s storefront now runs on Elastic Beanstalk with six instances. The team must release a fix before the next flash sale. A release that takes the site offline, or that leaves it with half its capacity, is not acceptable.

The team also stores the order data in a database that it created inside the environment, and it asks whether that is wise.

Your challenge:

  • Compare the deployment policies for downtime, capacity, and rollback.
  • Explain how a blue/green deployment works.
  • Say where the production database should live.

2.1 The Five Deployment Policies

PolicyHow it worksAvailable in
All at onceDeploys the new version to every instance at the same time. It is the fastest, and the environment is briefly unavailable.Load-balanced and single-instance environments
RollingDeploys in batches. Each batch is out of service while it updates, so capacity drops during the deployment.Load-balanced environments
Rolling with an additional batchLaunches a new batch of instances first, so full capacity stays in service, and then deploys in batches.Load-balanced environments
ImmutableLaunches a second Auto Scaling group with the new version. When the new instances pass health checks, they replace the old ones. To roll back, Elastic Beanstalk ends the new group.Load-balanced and single-instance environments
Traffic splittingLaunches new instances like an immutable deployment, and sends a set percentage of traffic to them for a set time. It is a canary test.Load-balanced environments with an Application Load Balancer

Source: AWS Elastic Beanstalk Developer Guide, Deploying applications to Elastic Beanstalk environments.

2.2 Blue/Green Deployments

  • A blue/green deployment is not one of the five policies. You clone the environment, deploy the new version to the clone (the green environment), and test it.
  • When the new version works, you swap the environment URLs (the CNAMEs), so the DNS name points to the green environment. To roll back, swap again.
  • It avoids any mix of old and new versions on one environment, and it costs a second environment while both run. DNS records are covered in lesson 269.9.

2.3 Configuration, Updates, and Health

  • Configuration options set the instance type, scaling limits, load balancer, and environment properties. Use the .ebextensions folder or saved configurations to keep settings with the application.
  • Managed platform updates apply platform updates in a maintenance window that you choose.
  • Health reporting shows the state of the environment. Enhanced health reporting adds detail about the instances and the application.
  • Instances use an IAM instance profile (lesson 267.5) to call other AWS services, such as Amazon S3.

2.4 Keep the Production Database Outside the Environment

  • You can add an Amazon RDS database to an environment, but its life cycle is tied to the environment. Terminate the environment, and the database is deleted.
  • For production, create the database outside Elastic Beanstalk (lesson 272.1), and give the application its connection details with environment properties. A blue/green swap then keeps the data.

2.5 Pricing

  • Elastic Beanstalk has no charge. You pay for the EC2 instances, the load balancer, the storage, and the other resources of the environment.
  • Immutable, traffic-splitting, and blue/green deployments run extra instances while they deploy, so they cost more for that time. Check the Elastic Beanstalk and EC2 pricing pages for current prices.

Exam Trap

Remember these points:

  • All at once causes downtime. Use it for development only.
  • Rolling reduces capacity during the deployment. Rolling with an additional batch and immutable keep full capacity.
  • Immutable rolls back fastest, because Elastic Beanstalk only ends the new Auto Scaling group.
  • Traffic splitting needs an Application Load Balancer.
  • Blue/green is done by swapping CNAMEs between two environments. It is not a deployment policy setting.

3.3 Lesson Summary

This lesson covered the following points:

  • AWS Elastic Beanstalk deploys and runs an application on a load balancer, an Auto Scaling group, and EC2 instances that it builds for you. There is no charge for the service, only for the resources.
  • An application has versions and environments. An environment runs one version on a platform, as a single-instance or a load-balanced environment, in a web server or a worker tier.
  • The five deployment policies are all at once, rolling, rolling with an additional batch, immutable, and traffic splitting. Blue/green is done by swapping the URLs of two environments.
  • Current Linux platforms run on Amazon Linux 2023, and the Amazon Linux 2 branches were retired on August 6, 2026.
  • Keep the production database outside the environment, because a database inside it is deleted with the environment.

Memory Hook

Pick Elastic Beanstalk when the team wants to ship code and keep the instances.

4. Knowledge Check

Answer each question in your own words before you open the model answer. The questions were written for this course.

Question 1: Define AWS Elastic Beanstalk, and list the resources that it builds.

Maps to: Objective 1 (Comprehension).

Elastic Beanstalk is a platform as a service. You upload your code, and it provisions the capacity, load balancing, scaling, and health monitoring. It builds EC2 instances and their security groups, an Auto Scaling group, a load balancer in a load-balanced environment, CloudWatch alarms, and an S3 bucket for the versions, and it manages them with CloudFormation. There is no charge for the service, only for the resources.

Question 2: Explain how an application, an application version, an environment, and a platform relate to each other.

Maps to: Objective 2 (Comprehension).

An application is a logical collection of versions, environments, and configurations. A version is a labeled iteration of deployable code that is stored in S3. An environment is the set of AWS resources that runs one version. The platform is the operating system, runtime, and web server that the environment uses.

Question 3: When do you use a worker environment, and when a single-instance environment?

Maps to: Objective 3 (Analysis).

Use a worker environment for background jobs, because it reads messages from an SQS queue and sends each one to the application. Use a single-instance environment for development and testing, because it has one instance and no load balancer, so it costs less. Use a load-balanced web server environment for production.

Question 4: Compare the five deployment policies by downtime, capacity, and rollback.

Maps to: Objective 4 (Analysis).

All at once is the fastest and causes brief downtime. Rolling deploys in batches and reduces capacity. Rolling with an additional batch keeps full capacity. Immutable launches a second Auto Scaling group, keeps full capacity, and rolls back by ending the new group. Traffic splitting sends a share of traffic to new instances as a canary test, and it needs an Application Load Balancer.

Question 5: Which platform branches should a new environment use, and how do you operate it safely?

Maps to: Objective 5 (Application).

Choose a current platform branch on Amazon Linux 2023, because Elastic Beanstalk retired the Amazon Linux 2 branches on August 6, 2026. Check the platform release schedule for retirement dates. Keep settings in .ebextensions or saved configurations, turn on managed platform updates for a maintenance window, and use enhanced health reporting to watch the environment.

Question 6: A team needs a production web application with fast, safe releases and a database that keeps its data. Design the setup, and say when Elastic Beanstalk is the wrong choice.

Maps to: Objectives 6 and 7 (Evaluation and Synthesis).

Use a load-balanced web server environment with an immutable deployment policy, or blue/green deployments for the safest switch. Create the RDS database outside the environment, and pass its connection details as environment properties, so that the data survives a terminated environment. Elastic Beanstalk is the wrong choice when the workload is event-driven code, which fits Lambda, when it is built from containers and microservices, which fits ECS or Fargate, or when the team needs infrastructure that it cannot express in Elastic Beanstalk settings.

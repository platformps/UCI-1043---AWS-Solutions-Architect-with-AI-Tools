Introduction

Software changes all the time. One developer adds a feature while another fixes a bug, and a third tries a new idea. Without a record of each change, a team cannot tell who changed what, cannot go back to a version that worked, and cannot combine work safely. Version control solves these problems, and Git is the most widely used version control system. Infrastructure code follows the same rules as application code, so the skills in this lesson support the later lessons on automation and DevOps.

1. Version Control Systems

Problem Statement

FlashCart Inc. has developers, testers, designers, and consultants in several offices. They all work on the same website and infrastructure code, and they pass files around by email and shared folders.

Last week, two developers edited the same file at the same time, and one of them overwrote the other’s work. The checkout page then broke, and nobody could say which change caused it or which version had worked. Yesterday a laptop failed, and a week of work on it was lost.

The engineering manager asks for a system that records every change, lets the team return to any earlier version, and lets people work at the same time without overwriting each other.

Your challenge: Explain to the manager how a version control system solves these problems. Your answer should:

  • Name the benefits that match each problem.
  • Say which type of system fits offices in several countries.
  • Name at least two tools that the team could use.

1.1 What Version Control Is

A version control system (VCS) is software that records every change to a set of files over time. The place where the files and their history are kept is called a repository.

  • A team can see who changed what, when, and why.
  • Any earlier version of the project can be recovered.
  • Several people can work at the same time without overwriting each other.
  • The history is a record that the team can search and trace.

1.3 Distributed and Centralized Systems

The two most common types of version control systems are distributed and centralized. They differ in where the history lives and in what a developer can do without a network connection. This section explains each type, compares them step by step, and shows how to choose.

1.3.1 Distributed Version Control Systems

A distributed version control system (DVCS) lets users access a repository from multiple locations. Developers who collaborate from several computers, or remotely with team members, widely use it.

  • Each user has a complete copy, or clone, of the repository, including its full history.
  • Users work independently, offline if needed, and synchronize changes with others later.
  • No single computer is the only holder of the history. If a developer loses a repository, another clone can restore it.
  • Teams usually still agree on one shared remote repository, such as one on GitHub, so that everyone knows where the current version lives.
  • This decentralized design gives flexibility, offline access, and strong collaboration.
  • Git and Mercurial are distributed systems.

1.3.2 Centralized Version Control Systems

A centralized version control system (CVCS) uses a single central repository for all collaboration, file access, changes, and revision tracking.

  • All team members use the central repository, which sits on a server or a designated machine.
  • A developer gets a working copy from the central repository, changes the files, and sends the changes back to it.
  • History management and access control are simple, because everything is in one place.
  • Software teams commonly use it for centralized code sharing and version control.
  • Offline access and scalability are more limited than in a distributed system, because actions such as saving a change depend on reaching the server.
  • Subversion, Perforce Helix Core, and the Concurrent Versions System (CVS) are centralized systems.

1.3.5 Which Type Fits FlashCart?

FlashCart has developers in several countries. Some of them travel and work on trains and planes, so they need to commit offline, work in separate branches, and keep the full history on every laptop. Those needs point to a distributed system, and FlashCart chooses Git. A small team in one office, on a fast network, with strict access rules for each folder, might still run a centralized system.

1.4 Lock-Based and Optimistic Systems

Two less common types manage concurrent access in different ways. You need to recognize them, not use them.

  • Lock-based: the system uses locks so that two users cannot change the same file at the same time.
  • Optimistic: each user has a private workspace. A user submits changes to the server, and the server merges the changes that do not conflict.

Common Mistake

Version control is not the same as a backup. A backup copies files so that you can restore them after a failure. Version control records the history of changes. A distributed system does keep many copies, but you still need to push your work to a shared remote so that the team can reach it.

Memory hook

Centralized means one library that everyone borrows from. Distributed means every developer owns a copy of the whole library.

2. Installing and Configuring Git

Problem Statement

FlashCart hires a new developer, Priya. On her first day she opens a terminal on her Windows laptop and types a Git command, but the terminal does not recognize it.

When her team later reviews the history, her first commits show a blank author name, because nobody set her identity. She also asks why her edits are not saved after she changes a file, since she saved the file in her editor.

Her lead asks her to install Git, set her identity, and explain the path that a change takes from her editor to the shared server.

Your challenge: Get Priya ready to work with Git. Your plan should:

  • Install Git and check that it works.
  • Set the name and email address that Git records.
  • Name the four areas that a change passes through, and the command that moves a change between them.

2.1 What Git Is

  • Git is a free, open-source, distributed version control system.
  • It handles projects from small to very large with speed and efficiency.
  • Linus Torvalds created it in 2005 for the Linux kernel.
  • It is one of the most widely used version control systems.
  • Git records a project as a series of snapshots, called commits, and each snapshot has a message, an author, and a date.
  • Most Git actions run on your own computer, so they are fast and work without a network connection.
  • Branching is built into Git, so developers can work on several tasks in parallel and merge them later.
  • Git tracks any text file, so teams use it for application code, infrastructure templates, scripts, configuration, and documentation.
  • You can use Git from the command line, from a graphical tool, or from a code editor that includes Git support.
  • Hosting services such as GitHub, GitLab, and Bitbucket store shared Git repositories and add collaboration tools.

In the DevOps life cycle, Git stores and tracks the code at the Code stage. A shared repository is where builds and tests start, so Git connects the work of developers to the pipeline that tests and deploys it.

  • On Windows, complete GLAB 302.1.1. On macOS and Linux, use the Terminal to run Git commands.

2.4 Configure Your Identity

Every commit records its author, so set your name and email address once. The --global option applies the values to every repository on your computer.

git config --global user.name "YOUR_USERNAME"
git config --global user.email "your_email_address@example.com"
git config --global --list
  • The first two commands set your name and your email address.
  • The third command shows your settings, so that you can check them.
  • Leave out --global inside a project to set values for that project only.

2.6 How a Change Moves Through Git

  1. Edit a file in the working directory.
  2. Stage the change, which chooses it for the next commit.
  3. Commit the staged changes, which saves them in the local repository.
  4. Push the commit, which sends it to the remote repository.

A commit includes only the staged changes, not every modified file. That is why saving a file in an editor does not save it in Git. You will learn the commands for these steps in tab 3 and tab 8.

2.7 Roles in Version Control: Developer and Cloud Engineer

Developers and cloud engineers both work in Git repositories, but they keep different things in them and care about different risks. At FlashCart, Priya is a developer who builds the checkout service, and Jordan is a cloud engineer who builds the AWS infrastructure that runs it.

2.7.1 The Developer Role

  • Writes and changes application code, and commits it in small steps with clear messages.
  • Creates a branch for each feature or fix, so that unfinished work does not reach the main code.
  • Pulls often, so that the work builds on the latest changes from the team.
  • Pushes branches and opens pull requests, and reviews the pull requests of teammates.
  • Resolves merge conflicts, and keeps secrets and generated files out of the repository.

2.7.2 The Cloud Engineer Role

  • Keeps infrastructure code, such as templates, scripts, and configuration, in repositories, so that every environment is built the same way from a recorded definition.
  • Uses pull requests so that a second person reviews an infrastructure change before it reaches production.
  • Tags versions of infrastructure code, so that the team can tell exactly what was deployed and when.
  • Connects repositories to automated pipelines that test and deploy changes, so that a merge can trigger a deployment.
  • Controls who can push or merge, for example by protecting the main branch, and keeps credentials out of repositories.
  • Uses the history to audit changes and to roll back a faulty change with git revert.

2.7.3 The Roles Side by Side

TopicDeveloperCloud engineer
What goes in the repositoryApplication code, tests, and documentation.Infrastructure templates, scripts, configuration, and diagrams.
BranchingOne branch for each feature or fix.One branch for each infrastructure change, often matched to an environment.
ReviewPull requests that review code quality and behavior.Pull requests that review cost, security, and the effect on live systems.
ReleaseTags mark application releases.Tags mark versions of the infrastructure that was deployed.
SecurityKeeps secrets out of the code.Keeps secrets out of templates and controls access to the repository.
RecoveryReverts a faulty change to the application.Reverts a faulty change to the infrastructure, then redeploys.

The two roles share the same Git skills. Lesson 296.2 covers Git workflows for infrastructure code in more depth.

3. Local Repositories, Commits, and Hashes

Problem Statement

Priya now has Git installed and configured. Her first task is to put FlashCart’s checkout service under version control. The project folder holds source files, but it also holds log files, compiled output, and a file named .env that contains local settings and secrets.

She runs a commit and is surprised that it contains only some of her changes. Later, a teammate asks which commit introduced a bug and sends a long string of letters and numbers that Priya does not recognize.

Her lead asks her to create the repository, keep the clutter and the secrets out of it, and explain what a commit and its ID really are.

Your challenge: Set up the repository correctly. Your answer should:

  • Create a local repository in the project folder.
  • Keep logs, compiled files, and .env out of Git.
  • Explain what a commit is and what the long ID means.

3.1 The Local Repository

A local repository is a private working copy with the full history. You can add, remove, rename, and move files, and commit changes. It can hold any file type that your project needs. Nothing is shared until you push.

3.2 Create a Local Repository

When you start a new local repository, you need only one Git command: git init. If you have a project directory that is not under version control and you want to control it with Git, first go to that project’s directory, and then run the command.

Open a terminal and go to the project folder with cd. Then run git init.

Operating systemExample command
Windowscd C:/Users/user/my_project
macOScd /Users/user/my_project
Linuxcd /home/user/my_project

git init creates a hidden .git folder that holds the repository data. The .git folder is a directory, not a file. Many other Git commands do not work outside an initialized repository, so git init is usually the first command in a new project.

3.3 Check Status and History

  • git status lists untracked, modified, and staged files.
  • git log lists the commits, newest first.
  • git log --oneline shows one line for each commit.

Example output from git status in a new repository. The wording varies a little between Git versions.

On branch main

No commits yet

Untracked files:
  (use "git add <file>..." to include in what will be committed)
        newfile.txt

nothing added to commit but untracked files present (use "git add" to track)

Run git status often. It tells you what to do next.

3.4 The README File

A README file is often the first thing a visitor sees in a repository. It describes what the project does and why it is useful, and it tells readers how to get started, where to get help, and who maintains the project. Name it README.md. The .md ending means Markdown, a simple text format.

3.5 The .gitignore File

A .gitignore file lists files and folders that Git should not track. Place it in the root folder of the repository. Each line is a pattern.

PatternWhat it ignoresWhy
*.logEvery file that ends in .log.Log files are output, not source.
node_modules/The folder with that name.Downloaded packages can be rebuilt.
.envThe file named .env.It often holds local settings and secrets.

A .gitignore file affects only files that Git is not yet tracking. A file that is already tracked stays tracked, so add secrets to .gitignore before the first commit.

3.6 What Is a Commit? (Save Snapshots)

3.6.1 Working Directory and Staging Area (Index)

  • The working directory is the place where files are checked out: the files that you see and edit in the project folder.
  • The staging area is also called the index. It holds the changes that you have chosen for the next commit.
  • When you run a commit, Git looks at the files in the staging area. Only the staged files, not every modified file, go into the commit.

The workflow has these parts:

  1. Modify a file in the working directory.
  2. Add the file to the staging area: git add file.txt.
  3. Commit the staged changes: git commit -m "Describe the change". This moves them into the local repository.
  4. Later, git push sends the commits to the remote repository, where the team can reach them. Tab 8 covers pushing.

3.6.2 Stage Changes With git add

git add moves changes from the working directory to the staging area. You can run it as many times as you like before a commit.

CommandWhat it stages
git add newfile.txtOne named file.
git add .All changes in the current folder and the folders below it, including new files.
git add -AAll changes in the whole repository: new, modified, and deleted files.
git add -uChanges to files that Git already tracks, which are modified and deleted files. It does not stage new files.
  1. Create or edit a file, for example newfile.txt.
  2. Run git add newfile.txt.
  3. Run git status. The file now appears under “Changes to be committed.”
  • If you edit a file after you stage it, run git add again to stage the latest edits.
  • If a file name is wrong, Git reports that the path did not match any files. Check the spelling and the folder.
  • Know what you are staging. git add . stages everything, so check git status first, and use .gitignore to keep unwanted files out.

3.6.3 Commits Save Snapshots

  • A commit saves the staged changes in the local repository. It does not send anything to a remote server.
  • Each commit is a snapshot of the tracked files at that moment. A file that did not change is stored only once.
  • Each commit records an author, a date, and a message.
  • git commit -m "Describe the change" creates a commit.

Git does not add changes to a commit automatically. You choose them with git add, and a clear message tells the team why the change was made.

3.7 What Git Stores

CommitA pointer to a tree, plus the author, date, message, and parent commit.

3.7.1 What Are Binary Large Objects (BLOBs) and Content Addressing in Git?

  • A blob, short for binary large object (BLOB), is the object type that stores the contents of one file in a repository.
  • A blob holds only the contents of the file. It does not hold the file name, the log message, the author, or the date. The tree holds the names, and the commit holds the author, date, and message.
  • In the Git database, each blob is named by the Secure Hash Algorithm 1 (SHA-1) hash of its contents.
  • Git is content-addressed: it finds a file by the hash of its contents, not by its name. Two files with identical contents share one blob.
  • Together, the commits, trees, and blobs hold everything that Git needs to rebuild any revision or branch of the project.

Learn more in the Pro Git chapter on Git objects.

3.8 What Are Git Hashes (SHA-1)?

Git names every object with a hash, a 40-character hexadecimal ID calculated with Secure Hash Algorithm 1 (SHA-1). The hash comes from the content, so the same content gives the same hash. A hexadecimal ID uses only the digits 0 to 9 and the letters a to f.

e83c5163316f89bfbde7d9ab23ca2e25604af290

git log --oneline shows the first seven characters of each commit hash. You can use that short form in other commands.

Common Mistake

A .gitignore file does not stop Git from tracking a file that you already committed. If a secret is already in the history, ignoring it later does not remove it. Treat the secret as exposed and replace it (tab 5, section 5.6).

Memory hook

Add chooses. Commit saves. The hash names what was saved.

4. Branching and Merging

Problem Statement

Two FlashCart developers need to change the same project. Marcus is adding a coupon feature that will take several days, and Dana has to fix a checkout bug today. If both commit to the same line of work, Dana’s urgent fix would ship with Marcus’s unfinished coupon code.

The team lead wants each task isolated, so that the main code always stays in working order. When a task is done, it must be combined into the main code. Last month two developers changed the same lines of one file, and the combination stopped with an error that nobody understood.

The lead asks you to show the team how to work in separate lines of development and bring them back together.

Your challenge: Explain the workflow to the team. Your answer should:

  • Show how to create a branch and switch to it.
  • Show how to merge it into main and clean up.
  • Explain what a merge conflict is and how to resolve it.

4.1 Branches Isolate Work

  • A branch is a separate line of development.
  • Create a branch for each new feature or fix. The main branch stays in working order.
  • The default branch is usually called main. Older repositories may call it master.
  • When the work is ready, merge the branch back into main.

4.2 Create and Switch Branches

CommandWhat it does
git branch my-new-branchCreates a branch.
git branchLists the branches. An asterisk marks the current one.
git switch my-new-branchSwitches to the branch.
git checkout my-new-branchAlso switches branches. It is the older command, and GLAB 302.1.2 shows both.
git branch -d my-new-branchDeletes a branch that has been merged.

4.3 Merge a Branch

  1. Switch to the branch that receives the work: git switch main.
  2. Run git merge my-new-branch to combine the branch into main.
  3. After a successful merge, delete the branch with git branch -d my-new-branch.
SituationWhat Git does
Main has not changed since the branch startedGit moves main forward to the branch’s latest commit. This is called a fast-forward.
Main has new commits of its ownGit creates a merge commit that joins the two lines.

4.4 Merge Conflicts

A conflict happens when two branches change the same lines of a file. Git stops the merge and marks the conflict inside the file.

<<<<<<< HEAD
price = 19.99
=======
price = 18.50
>>>>>>> my-new-branch
  1. Open the file, choose the final text, and remove the conflict markers.
  2. Run git add on the file.
  3. Run git commit to finish the merge.

git status lists the files that still have conflicts.

Common Mistake

A merge always combines the named branch into the branch that is checked out. If you run git merge main while you are on the feature branch, you bring main into the feature branch, which is the opposite of what you wanted. Switch to the receiving branch first.

Memory hook

Switch to where the work should land, then merge what you built.

Scenario Triggers

Trigger 1: “Work on a feature without affecting the main code”
→ create a branch

Trigger 2: “Combine a finished branch into main”
→ git merge from the main branch

Trigger 3: “Two branches changed the same lines”
→ merge conflict

Trigger 4: “The default branch name in new repositories”
→ main. Older repositories use master.

5. HEAD, Tags, Undo, and Compare

Problem Statement

FlashCart’s release 1.0 went out last week. A developer pushed a faulty commit to the shared main branch yesterday, and the team now needs to undo it without disturbing the teammates who already pulled it.

A different developer wants to know exactly which lines changed before staging a file. Another developer proposes using git reset to remove a database password that was committed by mistake, and says that it will make the password disappear.

The lead asks you to explain which command to use in each case, and to warn the team about the risks.

Your challenge: Advise the team. Your answer should:

  • Name the safe way to undo a commit that others already have.
  • Show how to compare changes before and after staging.
  • Explain what to do about a committed secret.

5.1 HEAD

  • HEAD is a pointer to what you have checked out now.
  • Usually HEAD points to the current branch, and the branch points to its latest commit.
  • Switching branches moves HEAD to the new branch.
  • Checking out a tag or a commit puts Git in a detached HEAD state, where HEAD points to a commit directly.

5.2 Tags

  • A tag gives a fixed, readable name to one commit. Developers often tag releases.
  • A tag does not move when new commits are made. A branch moves forward with each commit.
  • git tag v1.0 tags the latest commit. git tag v1.0 abc1234 tags an earlier commit.
  • git tag lists the tags.

5.3 Compare Changes With git diff

CommandWhat it compares
git diffThe working directory with the staging area.
git diff --stagedThe staging area with the last commit.
git diff main feature/loginTwo branches.
git diff main feature/login index.htmlOne file in two branches.

git diff main..feature/login gives the same result as separating the two branches with a space. In the output, a line that starts with - was removed, and a line that starts with + was added.

5.4 Undo With git revert

  • git revert undoes a commit by creating a new commit that applies the opposite changes.
  • The history stays intact, so revert is safe for commits that other people already have.
  • Run git log --oneline to find the commit ID. Then run git revert <commit-id>.

5.5 Undo With git reset

git reset moves the branch pointer to an earlier commit. It rewrites history, so use it only on commits that no one else has.

OptionWhat happens to the changes
--softThe changes stay staged.
--mixed (the default)The changes stay in the working directory, unstaged.
--hardThe changes are discarded. This can lose uncommitted work, so commit or save first.

5.6 Leaked Secrets

  • If a password, key, or token was committed, treat it as exposed.
  • Revoke or replace the credential first.
  • A reset does not remove copies that were already pushed or cloned.
  • Removing a secret from history takes extra tools and a plan for the team.
  • Lesson 296.2 covers keeping secrets out of repositories.
Common Mistake

Using git reset to remove a secret is a mistake. It moves a pointer on your computer, but the secret is still in every copy that was pushed or cloned. Revoke the credential first. Never reset commits that teammates already have.

Memory hook

Revert adds a new commit that says sorry. Reset pretends the commit never happened.

Scenario Triggers

Trigger 1: “Undo a commit that is already on the shared branch”
→ git revert

Trigger 2: “See which lines changed before staging”
→ git diff

Trigger 3: “A password was committed”
→ revoke the credential first

Trigger 4: “Give a release a fixed name”
→ a tag

  1. Run git switch main. You return to the branch that receives the work.
  2. Look at the folder. coupon.txt is not there, because the file exists only on the feature branch.
  3. Run git merge feature-coupon. It combines the branch into main. Main has not changed since the branch started, so Git moves main forward. You should see: Fast-forward.

6.9 Part 8: Create and Resolve a Merge Conflict (Tab 4)

  1. Create a file named price.txt with the text price = 19.99. Run git add price.txt and git commit -m "Add price".
  2. Run git branch branch-a and git branch branch-b. Both branches start from the same commit.
  3. Run git switch branch-a. Change price.txt to price = 18.50, save it, and run git add price.txt and git commit -m "Lower price in branch A".
  4. Run git switch branch-b. Change price.txt to price = 17.00, save it, and run git add price.txt and git commit -m "Lower price in branch B". Both branches now change the same line.
  5. Run git switch main, and then git merge branch-a. This merge is a fast-forward.
  6. Run git merge branch-b. Git cannot combine the two changes to the same line. You should see: CONFLICT in price.txt and a message that the automatic merge failed.
  7. Run git status. You should see: price.txt under “Unmerged paths” as both modified.
  8. Open price.txt. Git marked the conflict inside the file:
<<<<<<< HEAD
price = 18.50
=======
price = 17.00
>>>>>>> branch-b
  1. Replace the whole content of price.txt, including the marker lines, with price = 17.50, and save it. You choose the final text.
  2. Run git add price.txt, and then git commit -m "Resolve price conflict". Staging marks the conflict as resolved, and the commit finishes the merge.
  3. Run git log --oneline, and then git branch -d branch-a branch-b. You see the merge commit, and you delete the two merged branches.

6.10 Part 9: Tags and HEAD (Tab 5)

  1. Run git tag v1.0. It gives a fixed name to the latest commit.
  2. Run git tag. It lists the tags. You should see: v1.0.
  3. Open README.md, add the line Version 1.0 is ready., and save it. Run git add README.md and git commit -m "Update README". The branch moves forward, and the tag stays where it was.
  4. Run git log --oneline. You should see: (HEAD -> main) on the newest commit and (tag: v1.0) on an earlier one.
  5. Run git switch --detach v1.0. It checks out the tagged commit. Older Git versions can use git checkout v1.0, which also prints a longer note about the detached HEAD state. You should see: HEAD is now at, followed by the commit that carries the tag.
  6. Run git status, and open README.md. HEAD points to a commit, not a branch, and the README does not have the new line. You should see: HEAD detached at v1.0.
  7. Run git switch main. It returns HEAD to the branch.

6.11 Part 10: Undo With git revert (Tab 5)

  1. Create a file named oops.txt with the text This file was added by mistake. Run git add oops.txt and git commit -m "Add oops file by mistake". This is the faulty commit.
  2. Run git revert HEAD --no-edit. It creates a new commit that undoes the latest commit. The option keeps Git from opening an editor.
  3. Run git log --oneline. The faulty commit is still in the history, and a new Revert commit sits on top of it.
  4. Look at the folder. oops.txt is gone. The history stays intact, which is why revert is safe for shared commits.

6.12 Part 11: Try git reset on a Private Commit (Tab 5)

Warning

Run these steps only in this practice repository, on commits that nobody else has. A hard reset discards work.

  1. Create a file named temp.txt with any text. Run git add temp.txt and git commit -m "Temporary commit".
  2. Run git reset --soft HEAD~1, and then git status. HEAD~1 means the commit before HEAD. The commit is gone, but the change stays staged. You should see: temp.txt under “Changes to be committed.”
  3. Run git commit -m "Temporary commit" again, and then git reset --mixed HEAD~1 and git status. The commit is gone, and the change stays in the working directory, unstaged. You should see: temp.txt under “Untracked files.”
  4. Run git add temp.txt and git commit -m "Temporary commit" one more time. Then run git reset --hard HEAD~1 and git status. The commit and the file are both discarded. You should see: a clean working tree, and no temp.txt in the folder.

  2. Run git log --oneline. This is your finished history.

Priya has her repository and a GitHub account. She runs git push, and Git asks for a password. She types her GitHub password, and Git refuses it.

8.1 Sign In With a Personal Access Token

  • GitHub no longer accepts your account password for Git commands over Hypertext Transfer Protocol Secure (HTTPS), the secure web protocol.
  • Use a personal access token or a credential manager instead.
  • When Git asks for a password during a push or pull, enter the token.
  • Treat a token like a password. Do not share it, post it in a screenshot, or save it in a repository.

8.2 Create a Personal Access Token

  1. In GitHub, open your profile settings, and then open Developer settings.
  2. Select Fine-grained tokens, and then select Generate new token.
  3. Name the token, set a short expiration such as 60 days, and choose the repository it can reach.
  4. Grant only the permissions you need, such as access to repository contents.
  5. Select Generate token, and copy it. GitHub does not show it again.

8.3 Push Your Commits

  • A push copies commits from your local repository to a remote repository.
  • git push origin main pushes the main branch to origin.
  • git push -u origin main also remembers the target, so later you can run git push alone.
  • The first time, Git asks for your user name and token.

8.4 Pull Changes

  • A pull copies changes from a remote repository into your local repository and merges them.
  • git pull origin main pulls the main branch. git pull alone works once the target is set.
  • A pull is a fetch followed by a merge.
  • Pull before you start work, so that you build on the latest changes.

8.5 Pull Requests

A pull request is a GitHub feature. It asks the team to review a branch and merge it into another branch, often main. It is not the same as git pull.

Reviewers comment on the changes, and the team merges the request when it is approved. A pull request lets a team discuss work before it joins the main code.

Typing your GitHub account password when Git asks for a password during a push will fail. GitHub expects a personal access token. Also, a pull request is not a command: you open it on GitHub after you push a branch.

Memory hook

Push sends. Pull receives. A pull request asks for review.

Scenario Triggers

Trigger 1: “Git refuses the account password over HTTPS”
→ use a personal access token

Trigger 2: “Bring a teammate’s change into your local repository”
→ git pull

Trigger 3: “Ask the team to review a branch before it joins main”
→ open a pull request on GitHub

Trigger 4: “Send local commits to GitHub”
→ git push

9. Clone, Remote Add, and Forks

Problem Statement

FlashCart has two situations. In the first, Priya joins a project that already lives on GitHub, and she has nothing on her laptop. In the second, Marcus built a prototype in a local folder for two weeks, and now he wants it on a new, empty GitHub repository.

FlashCart also relies on an open-source library. A developer finds a bug in it and wants to propose a fix without changing the library’s own repository. Another team wants to take the library in a new direction that the original owners do not plan to follow.

The lead asks you to match each situation to the right command or feature.

Your challenge: Choose the right approach for each situation. Your answer should:

  • Pick clone or remote add for Priya and for Marcus.
  • Say when to fork a repository, and what to do after the fork.
  • Explain how a branch differs from a fork.

9.1 Clone a Repository

  • git clone <repository-url> creates a local copy of a remote repository, with all commits and branches.
  • Git sets the remote name origin for you.
  • Open a terminal, go to the folder where the copy should go, and run the command.
  • Find the address on the repository page, in the HTTPS option of the Code button.

9.2 Link an Existing Project With Remote Add

  1. Go to the project folder with cd.
  2. Run git init if the folder is not yet a repository.
  3. git remote add origin <repository-url> links the folder to the remote.
  4. git pull origin main brings in the remote files. Resolve any conflicts.

9.3 Clone or Remote Add?

9.4 Forks

  • A fork is your own copy of someone else’s repository on GitHub.
  • Fork to propose changes: change a branch in your fork, and open a pull request to the original.
  • Fork to start a separate project that goes its own way.
  • A fork lives on GitHub. A clone lives on your computer.

9.5 Branch or Fork?

BranchFork
Where it livesInside one repository.In a separate repository under your account.
Usual purposeA line of work that merges back.Contributing back through a pull request, or starting a separate project.
After a mergeDeleting the branch removes the pointer. The commits stay in the history.The fork can stay as your own copy.

9.6 Fork and Contribute

  1. Fork the repository on GitHub.
  2. Clone your fork to your computer.
  3. Create a branch, make a change, and commit it.
  4. Push the branch to your fork.
  5. Open a pull request to the original repository.
Common Mistake

Running git clone inside a project that already exists creates a second copy and does not link the first one. If the project is already on your computer, use git remote add. Also, a fork is not a clone: a fork is a copy on GitHub, and a clone is a copy on your computer.

Memory hook

Clone when you have nothing. Remote add when you already have something. Fork when it belongs to someone else.

Scenario Triggers

Trigger 1: “No local project yet, and you want a full copy of a remote”
→ git clone

Trigger 2: “A local project exists and needs a remote”
→ git remote add origin

Trigger 3: “Propose a change to a repository you do not own”
→ fork, branch, and open a pull request

Trigger 4: “Start a separate project from an existing one”
→ fork

10.4 Lesson Summary

  • Version control records every change to a project, so a team can see who changed what, return to an earlier version, and work at the same time. A distributed system, such as Git, gives every developer a complete copy. A centralized system keeps the history in one place.
  • Git moves a change through four areas: the working directory, the staging area, the local repository, and the remote repository. Set your name and email address once with git config.
  • In a local repository, git init starts tracking a folder, git add stages changes, git commit saves a snapshot, and git status and git log show where you are. A .gitignore file keeps files out of the repository, and each commit is named by a 40-character hash.
  • Branches isolate work. Merge a finished branch into main from the main branch, and resolve a conflict by choosing the final text, staging the file, and committing.
  • HEAD points to what is checked out, and a tag gives a fixed name to a commit. Use git diff to compare changes. Undo a shared commit with git revert, avoid git reset on commits that others have, and treat a committed secret as exposed.
  • GitHub hosts Git repositories and adds collaboration tools. Sign in over HTTPS with a personal access token. git push sends your commits, git pull brings others in, and a pull request asks the team to review a branch before it is merged. GitHub Copilot is an AI assistant that helps, but you review and decide.
  • Use git clone when the project is not on your computer yet, and git remote add when it already is. A fork is your own copy of a repository on GitHub, and a branch lives inside one repository.
  • Developers and cloud engineers use the same Git skills. Developers keep application code in repositories, and cloud engineers keep infrastructure code there and connect it to reviewed, automated deployments.
Memory hook

Edit, stage, commit, push. Branch to try, merge to keep, revert to undo safely.

11. Knowledge Check

Answer each question in your own words before you open the model answer.

  1. Explain how version control solves FlashCart’s problems of overwritten work, lost versions, and a failed laptop.

    Show the model answer

    It records every change, so the team can see who changed what and return to any earlier version. Branching and merging let people work at the same time without overwriting each other. A distributed system also gives every developer a complete copy, and pushing to a shared remote keeps the work safe if a laptop fails.

  2. Compare a distributed system and a centralized system. Which fits a team in several countries that works offline, and why?

    Show the model answer

    A centralized system keeps all history in one central repository, which makes access control simple but limits offline work. A distributed system gives every user a complete clone, so users can commit and review history offline and synchronize later. The distributed system fits the team, and Git is a distributed system.

  3. Name the four areas that a change passes through in Git, and the command that moves a change from each area to the next.

    Show the model answer

    The working directory holds your edits, and git add stages them. The staging area holds the changes chosen for the next commit, and git commit saves them. The local repository holds the history on your computer, and git push sends commits to the remote repository. git pull brings remote changes back.

  4. A developer changes two files, stages one, and commits. What does the commit contain, and why?

    Show the model answer

    It contains only the staged file. A commit takes the changes in the staging area, not every modified file. The other file stays in the working directory until it is staged and committed.

  5. Why do you set your name and email address with git config, and what does --global do?

    Show the model answer

    Every commit records its author, so Git needs your name and email address. The --global option applies the values to every repository on your computer. Without it, the values apply only to the current project.

  6. What does a .gitignore file do, and what is one limit of it?

    Show the model answer

    It lists patterns of files and folders that Git should not track, such as log files and local settings. Its limit is that it affects only untracked files. A file that was already committed stays tracked, so a secret must be added to .gitignore before the first commit.

  7. Describe what a blob, a tree, and a commit hold in Git’s data model.

    Show the model answer

    A blob holds the contents of one file. A tree lists the files and folders in a directory. A commit points to a tree and holds the author, date, message, and parent commit. Each object is named by a 40-character hash.

  8. Walk through creating a feature branch, merging it into main, and cleaning up. What happens if the same lines changed in both branches?

    Show the model answer

    Run git branch my-new-branch and git switch my-new-branch, then commit your work. Switch back with git switch main, run git merge my-new-branch, and delete the branch with git branch -d my-new-branch. If the same lines changed in both branches, Git reports a conflict and marks it in the file. You choose the final text, run git add, and run git commit to finish.

  9. A faulty commit is already on the shared main branch. Which command do you use to undo it, and why not git reset?

    Show the model answer

    Use git revert with the commit ID. It adds a new commit that applies the opposite changes and keeps the shared history intact. A reset rewrites history, which breaks the copies that teammates already have, and a hard reset can discard work.

  10. A password was committed and pushed. Why is git reset not the fix, and what do you do first?

    Show the model answer

    A reset moves a pointer on your computer, but the password remains in every copy that was already pushed or cloned. First revoke or replace the credential, because the password is exposed. Then use extra tools and a team plan if the secret must be removed from history, and keep secrets out of the repository in future.

  11. Explain the difference between Git and GitHub, and name two things that GitHub adds.

    Show the model answer

    Git is the version control software that tracks changes, usually on your computer. GitHub is a web-based hosting service for Git repositories. It adds a shared remote repository, pull requests, code review, and issue tracking.

  12. Why does a push over HTTPS to GitHub ask for a personal access token, and how should you treat it?

    Show the model answer

    GitHub no longer accepts account passwords for Git operations over HTTPS, so Git needs a personal access token or a credential manager. Enter the token when Git asks for a password. Treat it like a password: do not share it, post it in a screenshot, or save it in a repository.

  13. Explain the difference between git pull and a pull request.

    Show the model answer

    git pull is a command that copies changes from a remote repository into your local repository and merges them. A pull request is a GitHub feature that asks the team to review a branch and merge it into another branch. You pull to receive changes, and you open a pull request to propose them.

  14. For each case, choose git clone or git remote add and justify the choice: (a) a new hire with an empty laptop, (b) a local prototype that needs a remote.

    Show the model answer

    (a) Use git clone, because the project is not on the computer yet. Clone copies the whole remote repository with its history and sets origin. (b) Use git remote add origin, because the project already exists locally. Clone would make a second copy and would not link the original.

  15. Describe how a developer and a cloud engineer each use version control, and what they share.

    Show the model answer

    A developer keeps application code in the repository, works in a branch for each feature or fix, pulls often, and uses pull requests to share and review code. A cloud engineer keeps infrastructure templates, scripts, and configuration in repositories, reviews changes before they reach production, tags deployed versions, connects the repository to pipelines, controls access, and uses the history to audit changes and roll them back with git revert. Both rely on the same skills: commits, branches, merges, pull requests, and keeping secrets out of the repository.

  16. Differentiate a branch from a fork, and describe how a pull request proposes a change from a fork.

    Show the model answer

    A branch is a line of development inside one repository, and it usually merges back. A fork is a separate copy of a whole repository under your account. To propose a change, fork the repository, clone your fork, create a branch, commit, push the branch to your fork, and open a pull request to the original repository so that its owners can review and merge it.

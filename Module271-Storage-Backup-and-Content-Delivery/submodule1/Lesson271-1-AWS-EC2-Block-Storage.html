Introduction

Every EC2 instance needs storage for its operating system and its data. The storage choice decides whether data survives a stop, a replacement, or a failure, how fast the data is reached, and what the storage costs. Architects who pass SAA-C03 questions on storage need to know which block storage option fits which workload.

This lesson assumes basic AWS knowledge, such as launching an EC2 instance and recognizing Regions and Availability Zones. It covers block storage for EC2 only.

Two terms appear often in this lesson:

  • Block storage: storage that an instance uses like a hard drive, to hold an operating system, applications, and databases.
  • Persistent storage: storage whose data remains after the instance stops. Ephemeral storage: storage whose data can be lost.

1. EC2 Block Storage Options

Problem Statement

A team runs a web application on Amazon EC2. The application needs very fast scratch space for temporary files and caches, and it also needs a safe place for its database files that survives a stopped or replaced instance. The team must decide which storage belongs to which job before it launches the instances.

1.1 Two Types of EC2 Block Storage

EC2 instances can use two primary types of block storage:

  • Instance store: temporary block storage physically attached to the EC2 host. It is available only with supported instance types.
  • Amazon Elastic Block Store (Amazon EBS): persistent, network-attached block storage that is separate from the physical host that runs the EC2 instance.

1.2 Overview of Amazon EC2 Instance Store

An EC2 instance store provides temporary block storage that is physically attached to the host computer that runs an EC2 instance. It offers fast access to data, but it is designed for temporary information, not long-term storage. Instance store data is wiped out if the instance is stopped and started.

Instance store volumes are available only with EC2 instance types that support them.

1.2.1 Key Characteristics

  • Physically attached to the EC2 host.
  • Provides high-speed temporary storage.
  • Included with the price of the supporting EC2 instance.
  • Cannot be detached and attached to another instance.
  • Does not support EBS snapshots.
  • Data normally remains during an instance reboot.
  • Data is lost if the instance is stopped, hibernated, terminated, or moved to another physical host because of a hardware failure.

1.2.2 Appropriate Uses

Instance store is suitable for data that can be recreated, such as:

  • Temporary files.
  • Application caches.
  • Buffers.
  • Scratch data.
  • Replicated data.
  • Intermediate processing results.

Instance store should not be the only location for important business data.

Exam-Style Question

Scenario: A company runs a video rendering job on EC2. The job needs the highest possible local I/O for temporary working files, and the final output is copied to Amazon S3 when the job ends. The temporary files can be recreated at any time. Which storage should the company use for the temporary files?

  • A. An EBS Provisioned IOPS volume with Multi-Attach.
  • B. An instance store volume.
  • C. An EBS snapshot restored with fast snapshot restore.
  • D. An EBS Cold HDD (sc1) volume.
Show Answer and Explanation

Correct answer: B. Instance store is physically attached to the host and gives fast temporary storage. The data can be lost when the instance stops, which is acceptable because the files can be recreated.

2. Amazon EBS Basics

Problem Statement

A company runs a customer database on an EC2 instance and stores the database files on an EBS volume. One night the instance fails. The team must recover the stored data on a replacement instance, protect the data against loss, and keep a copy for disaster recovery in another Region.

2.1 What Amazon EBS Is

  • Amazon Elastic Block Store (Amazon EBS) is a cloud storage service for EC2 instances.
  • An EC2 instance has a root volume, which contains the operating system, and can optionally have one or more data volumes.
  • Amazon EBS provides persistent block storage volumes for Amazon EC2 instances. An EBS volume works like a virtual hard drive that can store an operating system, applications, databases, and other files.
  • Unlike instance store data, EBS data normally remains available when an instance is stopped or restarted.
  • The volume size is the storage capacity of an EBS volume, measured in gibibytes (GiB).
  • An EBS volume can be encrypted with keys from AWS Key Management Service (AWS KMS).

EBS volumes can be used for:

  • Operating system storage.
  • Application data.
  • Databases.
  • Log files.

2.2 Overview of an EBS Volume

An EBS volume has these characteristics:

  • It is a network drive, not a physical drive. It uses the network to communicate with the instance, so there might be a small amount of latency.
  • It can be detached from an EC2 instance and attached to another one quickly.
  • It is locked to an Availability Zone. An EBS volume in us-east-1a cannot be attached to an instance in us-east-1b. To move a volume across zones, first create a snapshot of it.
  • It has a provisioned capacity, which is its size in gibibytes (GiB) and its input/output operations per second (IOPS). You are billed for all of the provisioned capacity, and you can increase the capacity of the volume over time.

Notice these points in the image:

  1. More than one volume can be attached to a single EC2 instance.
  2. A volume can exist without being attached to any instance.
  3. EBS volumes are specific to an Availability Zone. You can migrate the data between zones with snapshots, but a volume cannot be attached to an instance in a different zone.

2.3 Example: Real-World Scenario

A company runs a customer database on an EC2 instance. It attaches an EBS volume to store the database files.

If the EC2 instance fails, the company can launch a replacement instance and attach the EBS volume to recover the stored data. The company can also create snapshots to protect the data, and copy those snapshots to another Region for disaster recovery.

2.4 EBS Key Details

  • EBS volumes can be created on their own, be attached to one EC2 instance, or be attached to several EC2 instances with EBS Multi-Attach.
  • EBS volumes are elastic. You can increase the size of a volume as required.
  • Each EBS volume is automatically replicated within its Availability Zone to protect against component failure.
  • You can back up EBS volume data with point-in-time snapshots. A snapshot writes a copy of the data in the volume to Amazon Simple Storage Service (Amazon S3), where it is stored redundantly in multiple Availability Zones.
  • An EBS snapshot reflects the contents of the volume at one concrete instant in time.
  • You can change EBS volumes while they are in use, including their size and storage type.

2.5 Elastic Volumes and Cost

  • With Elastic Volumes, you can increase the size of a volume, change its type, and adjust its performance while the volume stays attached. On supported instance types you do not detach the volume or restart the instance.
  • You can only increase the size of a volume. You cannot decrease it.
  • If you change a volume from gp2 to gp3 and do not specify IOPS or throughput, EBS provisions equivalent performance or the gp3 baseline, whichever is higher.
  • A volume that is not attached to an instance still incurs charges for its provisioned capacity.
  • An EBS-optimized instance has dedicated bandwidth between the instance and its volumes, so storage traffic does not compete with other network traffic.

3. EBS Volume Types

Problem Statement

FlashCart Inc. runs a high-traffic online store with a PostgreSQL database and an image processing engine on Amazon EC2. Before the Black Friday peak, three problems appear. Under high sales volume the database runs out of burst credits on a gp2 volume, so IOPS drop and checkout pages time out. The web servers use older gp2 volumes that cost more than necessary. Large analytics log files sit on SSD volumes and cost too much, although they need only sequential reads. The team must match each workload to the right EBS volume type.

3.1 EBS Volume Types

EBS volumes come in six variations: gp2, gp3, io1, io2, st1, and sc1. Each type is optimized for specific use cases and is priced accordingly. EBS volume types fall into two primary categories:

  • SSD-backed (solid state drive): optimized for transactional workloads, low latency, and high IOPS, for example databases and boot volumes.
  • HDD-backed (hard disk drive): optimized for throughput-intensive, sequential access workloads, for example big data, log processing, and archives.
Volume typeCategoryWhat the lesson uses it for
gp2SSDOlder general purpose volume. Ties performance to volume size and uses burst credits.
gp3SSDThe default choice for general workloads and boot volumes.
io1 and io2SSDLow latency, consistent high IOPS, and mission-critical databases.
st1HDDLarge, sequential data streams such as logs, big data, and data warehouses.
sc1HDDInfrequently accessed data.

Exam Rule of Thumb

  • Default choice: pick gp3 for general workloads unless the question says otherwise.
  • Boot volumes: only SSD types (gp2, gp3, io1, io2) can be EC2 root or boot volumes. HDD types (st1 and sc1) cannot be boot volumes.

3.2 Real-World Scenario: Scaling an E-Commerce Platform for Black Friday

Company: FlashCart Inc.

Application: a high-traffic online store that runs a PostgreSQL database and an image processing engine on Amazon EC2.

3.2.1 The Problem

In October, the engineering team prepares for peak holiday traffic. It faces three major blockages with its default EBS setups:

  1. Database lag: the database uses a gp2 volume. Under high sales volume, the database runs out of burst credits, IOPS drop, and checkout pages time out.
  2. Boot volume cost: the web application servers use older gp2 volumes, which cost more than necessary to maintain the target throughput.
  3. Log processing cost: large analytics log files are stored on SSD volumes, which causes high monthly storage costs although the files need only sequential reads.

3.2.2 The Architectural Solution

The team matches each EBS type to its workload:

DatabaseMigrate the PostgreSQL data drive from gp2 to an io2 Provisioned IOPS volume (io2 Block Express).io2 delivers consistent, low-latency performance with 99.999 percent durability and guaranteed IOPS that do not run out during traffic spikes.No transaction timeouts during peak checkout hours.
Application web serversConvert all EC2 root boot volumes from gp2 to gp3.gp3 provides baseline performance of 3,000 IOPS and 125 MB/s throughput at a 20 percent lower cost per GB than gp2. 3.2.3 Key Takeaways for the SAA-C03 Exam

  • Rule 1: use io1 or io2 when a question emphasizes low latency, consistent high IOPS, or mission-critical databases.
  • Rule 2: use gp3 as the default recommendation for general-purpose web applications and boot volumes.
  • Rule 3: use st1 for large, sequential data streams such as big data, log processing, and data warehouses. HDD volumes (st1 and sc1) cannot be EC2 boot volumes.
  • Rule 4: to back up all these volumes, FlashCart configures Amazon Data Lifecycle Manager to take automated incremental EBS snapshots and store them in Amazon S3 behind the scenes.

3.3 IOPS, Throughput, and Limits

  • IOPS counts input/output operations per second and matters for small, random operations such as database transactions.
  • Throughput is the amount of data moved per second, in MiB/s, and matters for large, sequential operations such as log processing.
  • SSD types are sized by IOPS, and HDD types are sized by throughput.
Volume typePerformance facts
gp2Baseline of 3 IOPS per GiB (minimum 100), up to 16,000 IOPS. Small volumes can burst to 3,000 IOPS, and performance depends on volume size.
gp3Baseline of 3,000 IOPS and 125 MiB/s at any volume size. You can provision IOPS and throughput above the baseline, independently of size. The ModifyVolume API reference lists gp3 IOPS up to 80,000.
io1Up to 64,000 IOPS per volume.
io2 and io2 Block ExpressUp to 256,000 IOPS and 4,000 MB/s per volume on Nitro-based instances, with 99.999 percent durability.
st1Throughput Optimized HDD. High sequential throughput, up to 500 MiB/s, for volumes of 125 GiB to 16 TiB.
sc1Cold HDD. Lowest cost, for infrequently accessed data, for volumes of 125 GiB to 16 TiB.

Limits change over time, so check the current Amazon EBS volume types page before relying on a number.

4. EBS Snapshots

Problem Statement

A company stores business-critical data on EBS volumes. An engineer accidentally deletes a snapshot, a new volume restored from a snapshot is slow the first time each block is read, and the finance team asks to lower the cost of snapshots that nobody has opened for a year. The team needs a backup approach that is automated, recoverable, and affordable.

4.1 EBS Snapshots

  • Snapshots are point-in-time backups of EBS volumes.
  • Snapshots are stored in Amazon S3 and are highly durable within a Region.
  • Snapshots are incremental. The first snapshot is a full copy, and later snapshots store only the data that changed.
  • Snapshots can be shared with other AWS accounts and copied to other AWS Regions.
  • You can copy a snapshot across Availability Zones or Regions.
  • You can delete snapshots and retain them in the Recycle Bin for a retention period that you choose.
  • Amazon Data Lifecycle Manager (DLM) automates EBS snapshot creation and retention.
  • You do not have to detach a volume to take a snapshot, but detaching it is recommended.

4.2 EBS Fast Snapshot Restore

  • Amazon EBS fast snapshot restore (FSR) lets you create a volume from a snapshot that is fully initialized at creation.
  • This removes the latency of input/output (I/O) operations on a block when it is accessed for the first time.
  • Volumes created with fast snapshot restore deliver all of their provisioned performance instantly.

4.3 EBS Snapshot Features

4.3.1 EBS Snapshot Archive

  • Move a snapshot to an archive tier that is about 75 percent cheaper than the standard tier. Check the pricing page for current rates.
  • Restoring from the archive takes 24 to 72 hours.

4.3.2 Recycle Bin for EBS Snapshots

  • Set up rules to retain deleted snapshots so you can recover them after an accidental deletion.
  • Specify the retention period, from one day to one year.

4.4 Snapshots and AMIs

  • You can use a snapshot to create EBS volumes or Amazon Machine Images (AMIs).
  • An AMI built from a snapshot lets you launch new instances with the same data and configuration.

5. Multi-Attach and Delete on Termination

Problem Statement

A company runs a highly available clustered application that needs several instances to read and write the same block storage at the same time. In a separate project, a team terminates instances to rebuild them and loses the root volumes, although it needs to inspect the data on them. The team must share one volume safely and control what happens to a volume when its instance terminates.

5.1 EBS Multi-Attach

EBS Multi-Attach works as follows:

  • EBS supports a feature called Multi-Attach for Provisioned IOPS SSD volumes (io1 and io2 Block Express).
  • You can attach the same EBS volume to several EC2 instances in the same Availability Zone.
  • You must create the volume with Multi-Attach enabled. A volume that was not created this way cannot be converted to Multi-Attach later.
  • A single volume can be shared by up to 16 EC2 instances (Linux) within the same Availability Zone.
  • Each EC2 instance has full read and write access.
  • Use Amazon CloudWatch metrics and EBS performance monitoring tools to find and address performance issues in a timely manner.

Use cases:

  • Highly available clustered applications, such as Oracle RAC and SAP.
  • Zero-downtime applications.
  • Analytics or rendering applications where nodes process shared input and output files in parallel.

Key considerations:

  • A Multi-Attach volume cannot be used as an EC2 boot volume.
  • Applications must handle concurrent writes safely to keep the data consistent.

5.2 EBS Delete on Termination Attribute

  • You can control what happens to an EBS volume when an EC2 instance terminates.
  • The volume attribute DeleteOnTermination defines whether the volume is deleted or retained when the instance terminates.
  • You can change the value of this attribute in the AWS Management Console or with the AWS Command Line Interface (AWS CLI).

5.2.1 DeleteOnTermination Attribute Settings

SettingWhat happens
DeleteOnTermination = trueBy default, the root EBS volume is permanently deleted when the EC2 instance terminates.
DeleteOnTermination = falseThe EBS volume remains in the AWS account after the instance terminates.

Use case: preserve the root volume when the instance is terminated.

  • B. An instance store volume shared by the three instances.
  • C. An io2 volume attached to instances in two different Availability Zones.
  • D. An io2 volume created with Multi-Attach enabled, attached to the three instances.

Correct answer: D. Multi-Attach works with io1 and io2 volumes that are created with Multi-Attach enabled, for instances in the same Availability Zone.

6. Data Protection and Encryption

Problem Statement

A company must show auditors that its data is encrypted at rest and in transit. Some existing EBS volumes were created without encryption, and one team disabled a key by mistake and lost access to a volume. The company needs to know how EBS encryption works, how to encrypt an existing volume, and what happens if an encryption key is disabled or deleted.

6.1 EBS Encryption

Amazon EBS supports encryption with AWS Key Management Service (AWS KMS). You encrypt EBS volumes in one of two ways:

  1. Encryption by default. This is a Region-level setting. In every Region, AWS creates a default KMS key with the alias aws/ebs.
  2. Manually, when you create the volume. This uses customer managed keys (CMKs) from AWS KMS.

When you create an encrypted EBS volume and attach it to a supported instance type, these types of data are encrypted:

  • Data at rest inside the volume.
  • All data that moves between the volume and the instance.
  • All snapshots created from the volume.
  • All volumes created from those snapshots.
  • Copying an unencrypted snapshot allows encryption.
  • Snapshots of encrypted volumes are encrypted.

6.2 EBS Encryption Scenarios

  • Snapshots of encrypted volumes are also encrypted. To create a new volume from such a snapshot, you need access to the encryption key.
  • You cannot directly encrypt an existing unencrypted volume or snapshot. To encrypt an unencrypted volume, create a snapshot of the volume, and then use the snapshot to create a new encrypted volume.
  • If a customer managed key is disabled, the encrypted EBS volume becomes temporarily inaccessible. If the key is deleted, the result is permanent data loss, because the data can no longer be decrypted.

6.3 Sharing an Encrypted Snapshot

  • You cannot share an encrypted EBS volume directly with another account. Share a snapshot of it instead.
  • You can share only snapshots that are encrypted with a customer managed AWS KMS key. A snapshot that uses the default AWS managed key cannot be shared.
  • When you share an encrypted snapshot, you must also share the customer managed key that encrypts it.
  • In the target account, create a copy of the shared snapshot, and then create a new volume from the copy.
  • To share a snapshot with another Region, copy the snapshot to that Region and then share the copy.

Exam-Style Question

Scenario: A company has an unencrypted EBS volume that holds production data, and a new policy requires encryption at rest. The volume must stay in service with the least disruption. What should the company do?

  • A. Enable encryption on the existing volume in the console.
  • B. Create a snapshot of the volume, copy it with encryption, and create a new encrypted volume from it.
  • C. Detach the volume and attach it to an instance that uses KMS.
  • D. Enable Multi-Attach to encrypt the volume.
Show Answer and Explanation

Correct answer: B. You cannot encrypt a volume in place. A snapshot copy can be encrypted, and a new volume created from it is encrypted.

OptionResultReason

BCorrectSnapshot, encrypted copy, and a new volume is the supported path.

DIncorrectMulti-Attach shares a volume. It does not encrypt it.

Exam Trap

You cannot encrypt a volume in place. A question that asks how to encrypt an existing unencrypted volume needs a snapshot and a new encrypted volume created from it. Deleting the key makes the data permanently unreadable.

Encrypt = snapshot, then new volume. Disable a key = locked. Delete a key = gone.

7. EBS Pricing and Cost Optimization

Problem Statement

FlashCart Inc. sees its Amazon EBS bill grow after Black Friday, although the number of instances did not change. The bill includes volumes that belonged to terminated instances, many old snapshots, and provisioned IOPS that nobody uses. The finance team asks the engineers to explain what EBS charges for and where they can lower the cost.

7.1 What You Pay For

Prices change often and differ by Region. Always check the current rates on the Amazon EBS pricing page, and estimate your own cost with the AWS Pricing Calculator.

Amazon EBS billing has several parts:

ChargeWhat it billsKey points
Volume storageThe size you provision, per GB-month.You pay for provisioned capacity, whether you use it or not, until you release the volume. Billing is per second, with a 60-second minimum. A volume that is not attached to an instance still bills.
Provisioned IOPSIOPS you provision, per IOPS-month.gp3 includes 3,000 IOPS and charges only above that. io1 and io2 charge for all provisioned IOPS. gp2 includes its IOPS in the storage price.
Provisioned throughputThroughput you provision, per MB/s-month.gp3 includes 125 MB/s and charges only above that.
Snapshot storageThe data that the snapshots store, per GB-month.Snapshots are incremental, so you pay for stored data, not for the size of the volume. The standard tier costs more than the archive tier.

Fast snapshot restorePer DSU-hour, for each snapshot in each Availability Zone where you enable it.Enable it only for the snapshots and zones that need it.
Recycle BinRetained snapshots, at the snapshot storage rates.Set retention rules that match your recovery needs.
Data transferCopying a snapshot to another Region.Cross-Region copies add data transfer cost.
Instance storeNothing extra.It is included with the price of the supporting EC2 instance.

7.4 Ways to Lower the Cost

  • Migrate gp2 volumes to gp3. You save on storage and you can set IOPS and throughput independently of size. The change works on a volume in use with Elastic Volumes.
  • Match the size to the data. You pay for provisioned capacity, so do not provision far more than you need.
  • Delete unattached volumes you no longer need. A volume bills even when no instance uses it.
  • Review DeleteOnTermination. Volumes that were created with an instance and are not needed after it ends can be deleted with it.
  • Clean up snapshots. Snapshots are not deleted when you delete their volume or terminate their instance, so use Amazon Data Lifecycle Manager to enforce retention.
  • Archive old snapshots. Use Snapshot Archive for snapshots you keep for more than 90 days.
  • Use fast snapshot restore sparingly. Enable it only for the snapshots and zones that need it.
  • Choose the cheapest type that meets the workload. Use st1 for sequential data and sc1 for cold data, instead of SSD.
  • Use instance store for temporary data that can be recreated, because it is included in the instance price.

8.6 Lesson Summary

This lesson covered the following points:

  • Instance store is fast, temporary storage that is physically attached to the host. Amazon EBS is persistent, network-attached storage that is separate from the host.
  • An EBS volume is locked to one Availability Zone, and a snapshot is the way to move its data to another zone or Region.
  • Use gp3 by default, io1 or io2 for low latency and consistent IOPS, and st1 for large sequential data. Only SSD types can be boot volumes.
  • Snapshots are incremental. Amazon Data Lifecycle Manager automates them, Snapshot Archive lowers their cost, Recycle Bin protects against deletion, and fast snapshot restore removes first-read latency.
  • Multi-Attach shares one io1 or io2 volume among instances in one zone, and DeleteOnTermination controls whether a volume survives its instance.
  • EBS encryption with AWS KMS protects data at rest, data in transit, and snapshots, and an unencrypted volume is encrypted by creating a snapshot and a new volume.

Choose instance store for fast, temporary data that can be recreated. Choose Amazon EBS when the data must persist after an instance is stopped or replaced.

Memory Hook

Instance store is a scratch pad. EBS is a hard drive on the network. A snapshot is its backup. A key protects it.

9. Knowledge Check

Answer each question in your own words before you open the model answer.

Question 1: Compare instance store and Amazon EBS, and say when you choose each.

Maps to: Objectives 6 and 7 (Analysis).

Instance store is temporary block storage physically attached to the host. It is fast, it is included with the instance price, and its data is lost when the instance is stopped, hibernated, or terminated. Amazon EBS is persistent, network-attached storage that remains after a stop and can move to another instance. Choose instance store for data that can be recreated, such as caches and buffers, and choose EBS when the data must persist.

Question 2: Explain why an EBS volume cannot be attached to an instance in another Availability Zone, and how to use its data there.

Maps to: Objective 1 (Comprehension).

An EBS volume exists in one Availability Zone and can attach only to instances in that zone. To use the data in another zone, create a snapshot of the volume, and then create a new volume from the snapshot in the target zone.

Question 3: A team runs a database on gp2 volumes and checkout pages time out under heavy load. Identify the likely cause and recommend a volume type.

Maps to: Objective 5 (Application).

A gp2 volume ties performance to its size and relies on burst credits, so under sustained load the credits run out and IOPS drop. Recommend an io2 Provisioned IOPS volume, which delivers consistent low latency and guaranteed IOPS for a mission-critical database.

Question 4: Recommend EBS volume types for a boot volume and for sequential log processing, and justify them.

Maps to: Objective 5 (Evaluation).

Use gp3 for the boot volume. Boot volumes must be SSD types, and gp3 is the cost-effective general purpose choice. Use st1 for the log volume, because it provides high throughput for sequential reads and writes at a lower cost than SSD. An HDD type such as st1 cannot be the boot volume.

Question 5: Describe how snapshots work and how you protect and lower the cost of them.

Maps to: Objective 2 (Comprehension).

Snapshots are incremental point-in-time backups stored in Amazon S3. Amazon Data Lifecycle Manager automates their creation and retention. A Recycle Bin retention rule lets you recover a deleted snapshot, and Snapshot Archive stores rarely used snapshots at a lower cost, with a restore time of 24 to 72 hours. Fast snapshot restore makes a volume created from a snapshot fully initialized at creation.

Question 6: Explain when you use EBS Multi-Attach and the limits that apply.

Maps to: Objective 3 (Comprehension).

Use Multi-Attach for clustered applications that need several instances to read and write the same volume at once. It works with io1 and io2 volumes created with Multi-Attach enabled, in one Availability Zone, for up to 16 Linux instances. The volume cannot be a boot volume, and the application must handle concurrent writes safely.

Question 7: A team terminated an instance and lost its root volume, although it needed the data. Explain the cause and the fix.

Maps to: Objective 3 (Application).

By default the root volume has DeleteOnTermination set to true, so it is deleted when the instance terminates. Set DeleteOnTermination to false, in the console or with the AWS CLI, so that the volume remains in the account after termination.

Question 8: A company needs to encrypt an existing unencrypted volume and asks what happens if the key is disabled or deleted. Explain the steps and the effects.

Maps to: Objective 4 (Application and Evaluation).

You cannot encrypt a volume in place. Create a snapshot of the volume, and then create a new encrypted volume from the snapshot, using the default key or a customer managed key. If the customer managed key is disabled, the encrypted volume is temporarily inaccessible. If the key is deleted, the data can no longer be decrypted and is permanently lost.

Question 9: Explain how you change the size or type of an EBS volume that is in use, and the limits that apply.

Maps to: Objective 1 (Application).

Use Elastic Volumes. On supported instance types you can increase the size, change the type, and adjust the performance of a volume without detaching it or restarting the instance. You can only increase the size, and a change to the type must stay within the limits of the target type.

Question 10: Describe how a company shares an encrypted EBS snapshot with another AWS account.

Maps to: Objective 4 (Application).

The snapshot must be encrypted with a customer managed AWS KMS key, because a snapshot that uses the default AWS managed key cannot be shared. The company shares the snapshot and also shares the customer managed key. In the target account, create a copy of the snapshot and then create a new volume from the copy.

Question 11: Explain what Amazon EBS charges for, and recommend three ways to lower the cost.

Maps to: Objective 8 (Evaluation).

EBS charges for the provisioned size of a volume per GB-month, for provisioned IOPS and throughput where they apply, and for snapshot storage per GB-month. Fast snapshot restore and snapshot archive retrieval add separate charges. To lower the cost, migrate gp2 volumes to gp3, delete unattached volumes and old snapshots with Amazon Data Lifecycle Manager, and move long-retained snapshots to Snapshot Archive.

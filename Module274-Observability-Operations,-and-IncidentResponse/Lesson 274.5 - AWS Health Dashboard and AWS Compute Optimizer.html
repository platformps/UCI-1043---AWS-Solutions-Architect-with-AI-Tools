AWS Health Dashboard and AWS Compute Optimizer

How AWS tells you about events that affect your account with the AWS Health Dashboard, how to react to those events automatically, and an overview of how AWS Compute Optimizer recommends the right size for your resources.

Lesson Overview

The earlier lessons of this module watch your own resources. This lesson covers two services that look at your account from the side of Amazon Web Services (AWS): AWS Health, which tells you about AWS events that affect you, and AWS Compute Optimizer, which tells you whether your resources are the right size. It builds on EventBridge (lesson 273.3), alarms (lesson 274.2), and the CloudWatch agent (lesson 274.1). In this lesson, you will study:

  • Service Health and Account Health: the two views of the AWS Health Dashboard, the event categories, and how long events stay.
  • Health Events and Automation: Amazon EventBridge rules, targets, the organizational view, and the Health application programming interface (API) and support plans.
  • AWS Compute Optimizer: an overview of what it recommends, the resources it covers, and the data it needs.
  • Where AWS Health and Compute Optimizer Fit: how both tools connect to the tools in the earlier lessons.
  • Comparison and Scenarios: comparison tables and a cheat sheet for the AWS Certified Solutions Architect – Associate (SAA-C03) exam.
  • Knowledge Check: open-ended questions with model answers.

Learning Objectives

By the end of this lesson, you will be able to:

  1. Define service health, account health, issue, scheduled change, and account notification.
  2. Describe what each view of the AWS Health Dashboard shows, and how long events stay visible.
  3. Explain how AWS Health events reach Amazon EventBridge, and which targets can respond.
  4. Compare the Health Dashboard, EventBridge, the Health API, and the organizational view.
  5. Describe the resources that AWS Compute Optimizer covers and the data that it needs.
  6. Differentiate the findings under-provisioned, over-provisioned, and optimized.
  7. Apply an EventBridge rule to send a Health event to a notification or a runbook.
  8. Evaluate which tool answers a question: AWS Health, CloudWatch, CloudTrail, AWS Config, or Compute Optimizer.
  9. Design an operational awareness setup that combines Health events, automatic responses, and a right-sizing review.

1. Service Health and Account Health

Problem Statement

On a Sunday morning, FlashCart’s canaries from lesson 274.4 start to fail in the US East (N. Virginia) Region. The on-call engineer spends 50 minutes reading the application logs and rolling back the last release before a colleague asks whether AWS itself has a problem. It does: an operational issue is raising API error rates in that Region. The 50 minutes were wasted because nobody checked.

The week before, an email from AWS about a scheduled retirement of the hardware under the standalone reporting server went to a shared mailbox that nobody reads. On Monday, the reporting server stopped, and the finance team could not run its reports.

The CTO asks how the team finds out quickly whether AWS is the cause of a problem, how it finds out about events that touch only FlashCart’s own resources, and what the difference between the two is.

Your challenge:

  • Choose the place to check first when you suspect that AWS itself has a problem.
  • Choose the place that shows events affecting only FlashCart’s own resources, and name the three kinds of account events.
  • Explain what each view shows, and whether either one needs any setup.
  • State how long events stay visible, and what old names learners may still see.

1.1 What AWS Health Is

AWS Health gives you ongoing visibility into the state of AWS services and of the resources in your account. It delivers alerts and notifications when the health of AWS resources changes. The AWS Health Dashboard is powered by the AWS Health application programming interface (API), it is available to all signed-in AWS users, and it needs no setup. It has two views: service health for everyone, and account health for you.

1.2 Service Health

AWS Health Dashboard – Service health shows the current and historical status of all AWS services. You can view it without an AWS account, because it lists public events.

  • It shows open and recent issues, such as an operational issue that raises API error rates in a Region.
  • Its service history table shows the status of each service, by Region, for the past 12 months.
  • It is general: it tells you what AWS is experiencing, not which of your resources are affected.

1.3 Your Account Health

AWS Health Dashboard – Your account health is a personalized view of events that affect your AWS account or organization. It gives you alerts and remediation guidance when AWS is experiencing events that may affect you, and it gives proactive notice so that you can plan for scheduled activities. Older materials call it the Personal Health Dashboard.

  • The page has tabs for open and recent issues, scheduled changes, notifications, and an event log.
  • Each event shows the service, the Region or Availability Zone, the status, the start and end time, the category, whether the event is specific to your account, the affected resources, and a description.
  • You can sign in and open it from the Service health page.

1.4 Event Categories and Status

CategoryWhat it meansExample
IssueAn unplanned problem with an AWS service that may affect you.Increased launch failures for Amazon Elastic Compute Cloud (Amazon EC2) instances in one Availability Zone.
Scheduled changeA planned activity that AWS announces in advance.Maintenance, or the retirement of the hardware under an instance.
Account notificationA notice about your account rather than about the service in general.A notice about quotas or limits.
  • Each event has a status of open, closed, or upcoming.
  • You can view Health events in the Health Dashboard or through the Health API for up to 90 days.
  • Each event lists the affected resources, so you can find the instance, the database, or the volume that needs action.
Exam trap

Service health is general, and your account health is personal. A question about events that affect your own resources, such as a scheduled retirement, points to your account health, not to the public service health page. The Health Dashboard does not measure the performance of your resources. CloudWatch does that (lesson 274.1). Also expect the older names “Service Health Dashboard” and “Personal Health Dashboard” in practice tests.

Memory hook

Service health is the weather report. Your account health is the warning with your name on it.

2. Health Events and Automation

Problem Statement

After the missed retirement notice, FlashCart wants AWS Health events to reach people and systems automatically. The security team wants an email for every scheduled change and issue that affects Amazon EC2 or Amazon Relational Database Service (Amazon RDS). The operations team wants an OpsItem to be created for each one, and wants a Systems Manager Automation runbook to stop and start the reporting server before a retirement date.

FlashCart now has 14 AWS accounts. Checking the Health Dashboard of each account is not realistic, and the team asks whether one place can show the events of all accounts.

An engineer also writes a script that reads Health events through the API from a development account. The script fails with an error that says a subscription is required, and she asks what the error means and whether the Dashboard has the same limit.

Your challenge:

  • Choose how to receive Health events automatically, and write the event pattern for scheduled changes to EC2.
  • Name the targets for the email, the ticket, and the runbook (lessons 273.3 and 268.8).
  • Choose how to see the events of all 14 accounts in one place.
  • Explain the subscription error, and say which access methods need a support plan.

2.1 Health Events in Amazon EventBridge

AWS Health automatically publishes service health events to Amazon EventBridge (lesson 273.3). An EventBridge rule can filter the events by service, Region, or event type, and send the matching events to targets that act on them:

  • Amazon Simple Notification Service (Amazon SNS), to notify people (lesson 273.3).
  • AWS Lambda, to run code.
  • Systems Manager Automation runbooks and OpsItems, to start a response (lesson 268.8).
  • Amazon Simple Queue Service (Amazon SQS) or Amazon Kinesis Data Streams, to pass the event on to other systems (lessons 273.3 and 273.6).
{
  "source": ["aws.health"],
  "detail-type": ["AWS Health Event"],
  "detail": {
    "service": ["EC2"],
    "eventTypeCategory": ["scheduledChange"]
  }
}

This pattern matches scheduled changes for Amazon EC2. Confirm the exact fields in the AWS Health documentation before you use it. You can also receive Health notifications through AWS User Notifications.

2.2 The Organizational View

If your account is part of an AWS Organizations organization, you can turn on the AWS Health organizational view. It collects Health events from all accounts in the organization in one place, so a central team does not need to open 14 dashboards. A delegated administrator can manage it for the organization.

2.3 The Health API and Support Plans

  • Service health is public. Your account health is available to every signed-in AWS user and needs no setup.
  • To use the AWS Health API, you need a paid AWS Support plan: Business Support+, Enterprise Support, or Unified Operations. With Basic Support, the call fails with a SubscriptionRequiredException error.
  • AWS describes the Health API, but not EventBridge, as requiring AWS Premium Support.
  • Older study materials may use different plan names, so match the idea (a paid plan) and not the name.
Exam trap

The Health Dashboard needs no support plan and no setup, but the Health API does need a paid AWS Support plan. A question that says “automatically react to Health events” points to an EventBridge rule, not to a script that polls the API. Remember to write a narrow rule, because a rule that matches everything creates noise.

Memory hook

The dashboard is for looking, EventBridge is for acting, and the API is for scripting.

3. AWS Compute Optimizer

Problem Statement

After the sale, the finance team asks why the compute bill is so high. A quick look at the dashboards from lesson 274.1 shows that many instances average 6 percent central processing unit (CPU) use, an order-confirmation function (lesson 273.1) uses a fraction of its configured memory, and several volumes are far larger than their traffic needs. Engineers choose sizes by feel, and each one remembers a different rule of thumb.

The team wants recommendations based on real utilization, not guesses, and it wants to know which resource types are covered, what data the service needs, and whether memory can be included, because memory is not a default instance metric.

Your challenge:

  • Choose the AWS service that recommends optimal resource sizes from utilization data.
  • Name the resource types that it covers.
  • Describe what data it uses, and how much data it needs before it recommends anything.
  • Explain how memory data gets in (lesson 274.1, tab 4), and name the findings that it reports.

3.1 What Compute Optimizer Does

AWS Compute Optimizer recommends optimal AWS resources for your workloads, to reduce cost and improve performance. After you opt in, it analyzes the specifications of your running resources, such as virtual CPUs, memory, and storage, and their CloudWatch metrics. Its findings also appear in the consoles of the supported services, such as the Amazon EC2 console.

3.2 Resources It Covers

ResourceWhat it recommendsRelated lesson
Amazon EC2 instancesAn instance type that fits the measured use.Lesson 274.1
Amazon EC2 Auto Scaling groupsInstance types for the group.Lesson 270.2
Amazon Elastic Block Store (Amazon EBS) volumesVolume type and size settings.Lesson 271.1
AWS Lambda functionsA memory size for the function.Lesson 273.1
Amazon Elastic Container Service (Amazon ECS) services on AWS FargateTask-level CPU and memory sizes.Lesson 273.5
Other resourcesCommercial software licenses, Amazon Aurora and Amazon RDS DB instances, and idle resources, such as idle network address translation (NAT) gateways.Lessons 272.1 and 269.2

3.3 Findings and Data

  • Findings: for each resource, Compute Optimizer reports whether it is under-provisioned (it needs more capacity), over-provisioned (it has more than it needs), or optimized.
  • Data it uses: specifications and CloudWatch metrics from the last 14 days. It uses the maximum utilization point in each five-minute interval.
  • Data it needs: at least 30 hours of CloudWatch metric data in the past 14 days for Amazon EC2 instances and Auto Scaling groups, and at least 24 hours for Amazon ECS services on Fargate.
  • Memory: memory is not a default EC2 metric. If the CloudWatch agent publishes memory utilization (lesson 274.1, tab 4), Compute Optimizer analyzes it automatically. Collecting memory with the agent is charged.
  • Longer history: enhanced infrastructure metrics is a paid option that extends the look-back period to 93 days.
  • Cost: Compute Optimizer is free to use, apart from the enhanced option. Check the pricing page.

Compute Optimizer only recommends. It does not resize anything for you. Trusted Advisor, covered in lesson 275.1, reports low-utilization checks, but Compute Optimizer recommends specific sizes.

Exam trap

Compute Optimizer is opt-in and needs enough metric data before it recommends anything. Without the CloudWatch agent, it has no memory data for instances. It recommends changes but does not make them, and for Lambda functions it recommends a memory size.

Memory hook

Metrics in, right size out.

4. Where AWS Health and Compute Optimizer Fit

Problem Statement

After the lessons on AWS Health and AWS Compute Optimizer, the operations manager asks the team for a one-page map. She lists five situations: AWS reports an issue in a Region; a scheduled change affects the team’s own instances; the team wants an email and a ticket for every Health event; the compute bill is high and nobody knows which instances are too large; and a customer reports a slow page, and nobody knows whether the cause is the application or AWS.

A junior engineer proposes a CloudWatch alarm for the Health events, and asks why the memory advice from Compute Optimizer is missing for some instances.

Your challenge:

  • Match each situation to the view or service that answers it.
  • Explain why Health events use an EventBridge rule and not a CloudWatch alarm.
  • Explain what Compute Optimizer needs before it can recommend a size based on memory.
  • Name the earlier lesson that provides each connected tool.

4.1 Two Lanes

AWS Health is an event flow from AWS to you, and Compute Optimizer is an analysis of your own metrics. Both connect to tools from the earlier lessons.

4.3 Alarms and Actions

AWS Health events arrive as EventBridge events, not as metrics, so you react with an EventBridge rule and not with a CloudWatch alarm (lesson 274.2, tab 7). Compute Optimizer produces recommendations that people review, so the follow-up is a decision, such as a new instance type, which you can then apply through your normal change process.

Exam trap

AWS Health events arrive as EventBridge events, not as metrics, so a CloudWatch alarm is the wrong answer. Compute Optimizer recommends sizes but does not resize anything. Service health is public, and your account health lists the events that affect your own resources.

Memory hook

AWS Health is the news from AWS. Compute Optimizer is the advice for your resources.

6. Knowledge Check

Answer each question in your own words before you open the model answer.

  1. Compare the Service health and Your account health views of the AWS Health Dashboard. Which would you open for a scheduled instance retirement?

    Show the model answer

    Service health shows the current and historical status of all AWS services, including public events, and you can view it without an account. Your account health is a personalized view of events that affect your account or organization, with the affected resources.

    Open Your account health for a scheduled retirement, because it lists scheduled changes and the instances that are affected.

  2. Name the three kinds of account events, give an example of each, and say how long events stay visible.

    Show the model answer

    An issue is an unplanned problem with a service, such as higher launch failures for instances. A scheduled change is a planned activity, such as maintenance or the retirement of the hardware under an instance. An account notification is a notice about your account, such as a quota notice.

    Events stay visible in the Health Dashboard or through the Health API for up to 90 days.

  3. Design an automatic response to scheduled changes for Amazon EC2 and Amazon RDS.

    Show the model answer

    Create an EventBridge rule that matches events from aws.health with the category scheduledChange and the services EC2 and RDS. Send the events to an Amazon SNS topic for the email, to an OpsItem for the ticket, and to a Systems Manager Automation runbook for the stop and start steps.

    Keep the rule narrow, so that only the events that need action trigger it.

  4. FlashCart has 14 accounts. How can one team see the Health events of all of them, and what does an engineer need to call the Health API?

    Show the model answer

    Turn on the AWS Health organizational view for the AWS Organizations organization, so that events from all accounts appear in one place. A delegated administrator can manage it.

    To call the Health API, the account needs a paid AWS Support plan, such as Business Support+, Enterprise Support, or Unified Operations. With Basic Support, the call fails with SubscriptionRequiredException. The Health Dashboard itself needs no plan.

  5. What resources does AWS Compute Optimizer cover, and what data does it need?

    Show the model answer

    It recommends sizes for Amazon EC2 instances, Auto Scaling groups, Amazon EBS volumes, Lambda functions, and Amazon ECS services on Fargate, and it also covers commercial software licenses, Aurora and RDS DB instances, and idle resources.

    After you opt in, it analyzes specifications and CloudWatch metrics from the last 14 days. EC2 instances and Auto Scaling groups need at least 30 hours of metric data. Memory is included only when the CloudWatch agent publishes it.

  6. Explain the findings under-provisioned, over-provisioned, and optimized, and say what Compute Optimizer does after it makes a recommendation.

    Show the model answer

    Under-provisioned means the resource lacks capacity and risks poor performance. Over-provisioned means it has more capacity than it uses and could be smaller and cheaper. Optimized means the size fits the measured use.

    Compute Optimizer only recommends. People decide, and they apply the change through their normal process, such as changing an instance type.

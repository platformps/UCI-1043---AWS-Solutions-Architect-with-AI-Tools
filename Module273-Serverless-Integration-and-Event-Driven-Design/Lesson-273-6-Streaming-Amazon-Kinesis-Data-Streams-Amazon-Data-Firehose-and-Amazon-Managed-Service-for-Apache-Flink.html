Introduction

A queue holds a message until one worker processes it, and a topic pushes a message to many subscribers. A stream is different: it keeps an ordered, time-limited record of events that several applications can read, and re-read, at their own pace. Exam questions often describe a firehose of clicks, logs, or sensor readings and ask which service ingests it, which one delivers it to Amazon S3 with no code, and which one calculates rolling results while the data moves.

1. Streaming Data Fundamentals

Problem Statement

FlashCart’s analysts receive website clicks and payment events in a nightly batch file. Fraudulent payments are found the next morning, and a product that sells out stays on the home page all day. Marketing wants to see what shoppers do within seconds, and three teams want to use the same events for different purposes.

The architect proposes a streaming pipeline, and the team asks what streaming means and which AWS services fit.

Your challenge:

  • Explain how streaming data differs from batch data.
  • Name the three stages of a streaming pipeline and the AWS services for each stage.
  • Describe the roles of producers and consumers.

1.1 What Streaming Data Is

  • Streaming data is data that arrives continuously from many sources, in small records, and is processed as it arrives.
  • Typical sources are website clickstreams, IoT devices, banking transactions, and metrics and logs.
  • A batch job collects data first and processes it later, for example every night. A streaming pipeline processes each record within seconds or minutes.
  • Streaming suits cases where the value of the data falls quickly with time, such as fraud detection and live monitoring.
FeatureBatch processingStreaming
When data is processedAfter it is collected, on a schedule.As it arrives, continuously.
Delay before resultsHours or a day.Seconds to minutes.
Typical FlashCart exampleA nightly sales report.A fraud alert while the payment is in progress.
Typical AWS servicesAmazon S3 with a scheduled job.Kinesis Data Streams, Amazon Data Firehose, and Managed Service for Apache Flink.

1.2 The Three Stages of a Streaming Pipeline

  • Ingestion: collect the records from the sources and hold them.
  • Processing and analytics: filter, join, aggregate, or analyze the records.
  • Delivery: load the records, or the results, into a destination.
StageAWS servicesWhat the service does
IngestionAmazon Kinesis Data Streams
Amazon MSK		Collects and stores records in real time.
Processing and analyticsAmazon Managed Service for Apache Flink
AWS Lambda, Amazon EC2, Amazon ECS, Amazon EKS		Runs stream-processing code, such as aggregations and joins.
DeliveryAmazon Data FirehoseLoads records into Amazon S3, Amazon Redshift, Amazon OpenSearch Service, partners, and HTTP endpoints.

1.3 Producers, Consumers, and Records

  • A record is one unit of data in a stream, such as one click event.
  • A producer writes records into the stream, for example a web server, an IoT device, or a log agent.
  • A consumer reads records from the stream, for example an AWS Lambda function, Amazon Data Firehose, or a Flink application.
  • Producers and consumers work independently, so a slow consumer does not slow down the producers.

1.4 Streaming Use Cases

Use caseWhat the stream carries
Fraud detection in financial servicesPayment events, checked while the payment is in progress.
Real-time customer behaviorClicks and searches, used for recommendations, offers, and discount codes.
Log monitoring and alertingApplication and infrastructure logs.
IoT data processingDevice readings, used to detect malfunctions or anomalies.
Connected vehiclesDriving data, used to detect risky driver behavior.
Home security and smart camerasVideo streams, for motion detection and face detection with Amazon Kinesis Video Streams.
  • Amazon Kinesis Data Streams ingests real-time records such as logs, metrics, and events.
  • Amazon Kinesis Video Streams securely ingests, stores, and processes real-time video and media streams from devices and cameras. This lesson does not cover it further.

1.5 Amazon MSK as an Alternative

  • Amazon Managed Streaming for Apache Kafka (Amazon MSK) is fully managed Apache Kafka on AWS, and an alternative to Kinesis Data Streams.
  • AWS creates and manages the Kafka broker nodes and the cluster coordination nodes, and recovers automatically from common Kafka failures.
  • You deploy an MSK cluster in your VPC, across up to three Availability Zones for high availability. Data is stored on Amazon EBS volumes for as long as you want.
  • MSK Serverless runs Apache Kafka without capacity management.
  • It is compatible with open-source Kafka APIs and tools, so it suits teams that already use Kafka.
  • Consumers include Managed Service for Apache Flink, AWS Glue streaming ETL jobs, AWS Lambda, and applications on Amazon EC2, Amazon ECS, and Amazon EKS.

Exam Trap

Remember these points:

  • Streaming is for a continuous flow of records. A queue or a topic (lesson 273.3) delivers messages to workers or subscribers.
  • Kinesis Data Streams and Amazon MSK ingest and store the stream. Firehose delivers it. Managed Service for Apache Flink processes it.
  • Kinesis Data Firehose is now named Amazon Data Firehose, and Kinesis Data Analytics for Apache Flink is now named Amazon Managed Service for Apache Flink.

Memory Hook

Ingest, process, deliver: Kinesis or MSK takes it in, Flink works on it, Firehose drops it off.

2. Amazon Kinesis Data Streams

Problem Statement

FlashCart’s checkout service produces thousands of events per second during a sale. The fraud team, the inventory team, and the analytics team each need to read every event. After a bug, the analytics team must reprocess the last two days of events. Events for one order must stay in order.

Your challenge:

  • Describe how a Kinesis data stream stores and orders the events.
  • Explain how the team can reprocess two days of events, and how long a stream can keep them.
  • Choose a capacity mode, and explain how several consumers can read the same stream.

2.1 What Amazon Kinesis Data Streams Is

  • Amazon Kinesis Data Streams collects and stores streaming data in real time.
  • Producers write records into a stream, and consumers read and process them.
  • Producers include the Kinesis Producer Library (KPL), the Kinesis Agent, the AWS SDK, and AWS services such as Amazon CloudWatch Logs and AWS IoT. Third-party tools such as Fluentd and Kafka Connect can also write to a stream.
  • Consumers include applications that use the Kinesis Client Library (KCL) or the AWS SDK on Amazon EC2, AWS Lambda, Amazon Data Firehose, and Amazon Managed Service for Apache Flink.

2.2 Shards, Partition Keys, and Ordering

  • A stream is made of one or more shards. The number of shards sets the capacity of the stream.
  • Each producer chooses a partition key for each record. Kinesis uses the key to decide which shard stores the record.
  • Records with the same partition key go to the same shard, so Kinesis keeps them in order within that shard.
  • Kinesis does not guarantee order across different shards.
Per-shard limitValue
Write throughputUp to 1 MB per second, or 1,000 records per second.
Read throughputUp to 2 MB per second, shared by all standard consumers.
Read callsUp to 5 read transactions per second.
  • If producers write more than a shard accepts, Kinesis throttles the writes. Add shards, or use on-demand mode.
  • The data payload of one record can be up to 10 MiB before encoding. Kinesis handles intermittent large records (1 to 10 MiB) with burst capacity, but the typical use case is many small records.

2.3 Data Retention and Replay

  • Records stay in a stream for 24 hours by default. You can raise the retention period to 365 days.
  • You cannot delete records from a stream. They are removed only when they expire.
  • Consumers can replay data, which means they read the records again and reprocess them. This is how FlashCart’s analytics team can recover from the bug.
  • Keeping data longer adds cost, so extend retention only when a use case needs replay.

2.4 Capacity Modes

FeatureProvisioned modeOn-demand mode
CapacityYou choose the number of shards.No capacity to provision or manage.
ThroughputEach shard gives 1 MB per second (or 1,000 records per second) in and 2 MB per second out.A new stream starts with 4 MB per second of write and 8 MB per second of read throughput.
ScalingManual: you split or merge shards to change the capacity.Automatic, based on the observed throughput peak during the last 30 days.
PricingYou pay per shard per hour.On-demand Standard: you pay per stream per hour, and per GB written and read. On-demand Advantage: you pay per GB written and read, with no per-stream hourly charge.
Best forPredictable, steady workloads.Unpredictable or highly variable workloads.
  • On-demand mode has two billing options: On-demand Standard and On-demand Advantage. On-demand Advantage lets you warm a stream for sudden traffic increases.
  • An on-demand stream scales up to 200 MB per second of write throughput in most Regions, and up to 10 GB per second in US East (N. Virginia), US West (Oregon), and Europe (Ireland).
  • You can switch a stream between provisioned and on-demand mode twice within 24 hours.

2.6 Security

  • Kinesis encrypts data at rest with AWS KMS, and in flight with HTTPS.
  • Access is controlled with IAM policies for producers and consumers.

3. Amazon Data Firehose

Problem Statement

FlashCart wants every application log and click event stored in Amazon S3 as compressed Parquet files, so analysts can query them with SQL. A copy of the logs must also reach Amazon OpenSearch Service for dashboards. The team has no spare engineers to run servers, and some records must be cleaned before they are stored.

Your challenge:

  • Describe how Firehose delivers data to Amazon S3 and Amazon OpenSearch Service without servers.
  • Explain how Firehose controls how often it delivers.
  • Explain how Firehose cleans records, converts them to Parquet, and handles failures.

3.1 What Amazon Data Firehose Is

  • Amazon Data Firehose, formerly named Kinesis Data Firehose, is a fully managed service that loads streaming data into data stores and analytics tools.
  • It is serverless: it scales automatically, and you pay for what you use.
  • Delivery is near real-time, because Firehose buffers records by size and time before it delivers them.
  • Firehose does not store data for later reads, and it does not support replay.
  • A Firehose record can be as large as 1,000 KB.

3.2 Sources and Destinations

SourcesDestinations
Kinesis Data Streams and Amazon MSKAmazon S3
Direct PUT, with the AWS SDK or the Kinesis AgentAmazon Redshift (through an Amazon S3 bucket and the COPY command)
Amazon CloudWatch Logs and eventsAmazon OpenSearch Service
AWS IoTSplunk, and partners such as Datadog, Dynatrace, MongoDB, and New Relic
Amazon Managed Service for Apache Flink (through its Firehose sink)Custom HTTP endpoints, Apache Iceberg tables, and Snowflake

3.3 Buffering

  • Firehose holds incoming records in memory until a buffer size or a buffer interval is reached, and it delivers when the first condition is met.
  • For Amazon S3, the buffer size is 1 to 128 MiB with a default of 5 MiB. The buffer interval is 0 to 900 seconds with a default of 300 seconds.
  • A larger buffer makes fewer, larger files and lowers cost, but it adds delay. A smaller buffer lowers the delay.
  • With a buffer interval of zero seconds, Firehose does not buffer and delivers within a few seconds.
  • The course slides describe Firehose delivery as near real-time, with a delay of about one minute. Use “near real-time” on the exam, and check the Firehose documentation for current buffering values.

3.4 Transforming, Converting, and Compressing Data

  • Transformation: Firehose can call an AWS Lambda function on each batch of records before delivery, for example to convert CSV to JSON or to remove sensitive fields.
  • Format conversion: Firehose can convert JSON to Apache Parquet or Apache ORC before delivery, with no code.
  • Compression: Firehose can compress data with GZIP, Snappy, or ZIP, to reduce storage cost. Only GZIP is supported if the data is then loaded into Amazon Redshift.
  • Input formats: Firehose handles JSON, CSV, Parquet, Avro, raw text, and binary data.

3.5 Backup and Error Handling

  • Firehose can save failed deliveries, failed transformations, or all source records to an Amazon S3 backup bucket.
  • This backup lets you inspect and reprocess records that could not be delivered or transformed.

3.6 Use Cases

Use caseFirehose delivers to
Application logs for long-term storage and analyticsAmazon S3
Clickstream or event data for near real-time reportingAmazon Redshift
Operational logs for search and visualizationAmazon OpenSearch Service
Metrics and traces for monitoring toolsSplunk or Datadog
Streaming data converted and compressed before storage, for example JSON to Parquet with GZIPAmazon S3

4. Amazon Managed Service for Apache Flink

Problem Statement

FlashCart’s fraud team wants an alert when one card has more than a set number of failed payments in any five-minute window. The check must also look up the customer’s risk level in a reference table. The results must reach a Kinesis data stream for the alerting service and Amazon S3 for audit.

Your challenge:

  • Explain which service calculates counts over time windows on streaming data.
  • Identify the sources the service reads, and the sinks it writes to.
  • Explain why the team does not use Firehose as the input.

4.1 What Amazon Managed Service for Apache Flink Is

  • Amazon Managed Service for Apache Flink, formerly named Kinesis Data Analytics for Apache Flink, runs Apache Flink applications for real-time stream processing.
  • Apache Flink is an open-source framework for processing data streams. You write applications in Java, Scala, Python, or SQL.
  • AWS runs your application on a managed cluster, with provisioned compute resources, parallel computation, and automatic scaling.
  • You can use any Apache Flink programming feature to transform the data.
  • AWS backs up the application state as checkpoints and snapshots, so an application can recover.
  • You define the input sources and the output sinks.

4.2 Sources and Sinks

RoleExamples
Source (input)Kinesis Data Streams, Amazon MSK (Apache Kafka), and files.
Sink (output)Kinesis Data Streams, a Firehose stream, a Kafka topic, Amazon S3, Amazon DynamoDB, and a relational database.
  • AWS lists a Firehose connector as a Flink sink, and it does not list Firehose as a source. Firehose is a delivery service, so use it as an output and not as an input.
  • To run in the service, you package the application code, upload it to an Amazon S3 bucket, and create the application.

4.3 Use Cases

5.3 Choosing a Service

5.4 Pricing Models

  • Kinesis Data Streams, provisioned mode: you pay per shard per hour, and for the data that producers write (PUT payload units).
  • Kinesis Data Streams, on-demand mode: with On-demand Standard, you pay per stream per hour, and per GB written and read. With On-demand Advantage, you pay per GB written and read, with no per-stream hourly charge. Longer retention costs extra.
  • Amazon Data Firehose: serverless, and you pay for the volume of data that you ingest, with optional charges for format conversion, VPC delivery, and dynamic partitioning.
  • Amazon Managed Service for Apache Flink: you pay for the duration and the number of Kinesis Processing Units (KPUs), billed in one-second increments, plus running application storage.
  • Check each service’s pricing page for current prices. Prices differ by Region.

5.5 Common Streaming Patterns

5.5.1 Big Data Ingestion Pipeline

  • AWS IoT Core harvests data from IoT devices.
  • Kinesis collects the data in real time.
  • Firehose delivers the data to Amazon S3 in near real time, and AWS Lambda can transform it first.
  • Amazon Athena queries the data with SQL, and the results go to a reporting bucket.
  • Amazon QuickSight, or Amazon Redshift, builds the reports.

5.5.2 Amazon CloudWatch Logs Subscriptions

  • A subscription filter streams log events from a CloudWatch Logs log group to another service in near real time.
  • The destinations are Kinesis Data Streams, Amazon Data Firehose, or AWS Lambda.
  • Subscription filters can send logs across accounts, and can combine logs from several accounts and Regions into one destination.
  • For a Firehose destination in another account, you also need a resource policy that allows access.

5.5.3 Streaming Into Amazon OpenSearch Service

  • For near real-time loading, use Firehose, with an optional Lambda transformation, to Amazon OpenSearch Service.
  • For real-time loading, use Kinesis Data Streams with an AWS Lambda function that writes to Amazon OpenSearch Service.

6.3 Lesson Summary

  • Streaming data arrives continuously and is processed in seconds or minutes, in three stages: ingestion, processing and analytics, and delivery.
  • Kinesis Data Streams stores ordered records in shards, keeps them for 24 hours to 365 days, and lets consumers replay them. Provisioned mode needs shards, and on-demand mode scales on its own.
  • Amazon Data Firehose buffers, transforms, converts, and delivers streaming data to Amazon S3, Amazon Redshift, Amazon OpenSearch Service, partners, and HTTP endpoints. It does not store or replay data.
  • Amazon Managed Service for Apache Flink runs Apache Flink to aggregate, enrich, and analyze streams. It reads from Kinesis Data Streams and Amazon MSK, and it can write to Firehose.
  • Amazon MSK is managed Apache Kafka. Amazon SQS and Amazon SNS handle messages that are consumed once or pushed to subscribers.

7. Knowledge Check

Answer each question in your own words before you open the model answer.

Question 1: Explain what streaming data is, and describe the three stages of a streaming pipeline with an AWS service for each stage.

Maps to: Objective 1 (Knowledge).

Streaming data arrives continuously in small records and is processed as it arrives. The first stage is ingestion, where Kinesis Data Streams or Amazon MSK collects and holds the records. The second is processing and analytics, where Amazon Managed Service for Apache Flink, AWS Lambda, or code on Amazon EC2, Amazon ECS, or Amazon EKS works on the records. The third is delivery, where Amazon Data Firehose loads the records into Amazon S3, Amazon Redshift, Amazon OpenSearch Service, partners, or HTTP endpoints.

Question 2: Explain how shards, partition keys, and retention work in Kinesis Data Streams, and how a team can replay data after a defect.

Maps to: Objective 2 (Comprehension).

A stream is made of shards, and each shard accepts up to 1 MB per second of writes and serves up to 2 MB per second of reads. A producer’s partition key decides the shard, so records with the same key go to the same shard and stay in order there. Records are kept for 24 hours by default and up to 365 days, and they cannot be deleted before they expire. A consumer can read the retained records again, so a team can reprocess data after a defect.

Question 3: Compare provisioned and on-demand capacity modes, and explain when to use enhanced fan-out.

Maps to: Objective 3 (Application).

In provisioned mode you choose the number of shards, scale them by splitting or merging, and pay per shard per hour, so it suits steady traffic. In on-demand mode there is no capacity to manage, the stream scales with the traffic peak of the last 30 days, and you pay per GB written and read (plus a per-stream hourly charge in On-demand Standard), so it suits variable traffic. Standard consumers share 2 MB per second per shard. Enhanced fan-out gives each consumer 2 MB per second per shard, so use it when several consumers each need full speed.

Question 4: Describe how Amazon Data Firehose delivers data, including buffering, transformation, format conversion, and backup.

Maps to: Objective 4 (Application).

Firehose reads from a source such as a Kinesis data stream, a CloudWatch Logs subscription, or a direct write. It buffers records until the buffer size or the buffer interval is reached, which makes delivery near real-time. An AWS Lambda function can transform records first, and Firehose can convert JSON to Parquet or ORC and compress the data with GZIP, Snappy, or ZIP. It then delivers to a destination such as Amazon S3, and it can back up failed deliveries, failed transformations, or all source records to an Amazon S3 bucket.

Question 5: Distinguish Kinesis Data Streams, Amazon Data Firehose, Amazon Managed Service for Apache Flink, Amazon SQS, and Amazon SNS.

Maps to: Objective 5 (Analysis).

Kinesis Data Streams stores ordered records, supports several consumers, and allows replay. Firehose loads streaming data into destinations in near real-time, with no storage and no replay. Managed Service for Apache Flink analyzes streams with time windows and joins, and it reads from Kinesis Data Streams or Amazon MSK. Amazon SQS holds messages for workers that pull them, and deletes each message after it is consumed. Amazon SNS pushes a message to many subscribers and does not keep it.

Question 6: FlashCart must keep events for a week, load logs into Amazon S3 with no servers, and calculate fraud alerts over time windows. Evaluate the services for each need, and justify your choice.

Maps to: Objective 6 (Evaluation).

Keeping events for a week with replay points to Kinesis Data Streams with extended retention, because Firehose and queues do not offer replay. Loading logs into Amazon S3 with no servers points to Firehose, which is managed and can convert and compress the data. Fraud alerts over time windows point to Managed Service for Apache Flink, which aggregates and joins streaming data. Amazon MSK would only be chosen if FlashCart already used Apache Kafka.

Question 7: Design a secure, scalable streaming pipeline for FlashCart’s checkout events, with several consumers, near real-time storage in Amazon S3, and fraud alerts.

Maps to: Objective 7 (Synthesis).

Producers write checkout events to a Kinesis data stream in on-demand mode, with KMS encryption at rest and HTTPS in transit, and IAM policies for producers and consumers. Retention is extended so teams can replay events. A Managed Service for Apache Flink application reads the stream, counts failed payments over a time window, enriches the events with a risk table, and writes alerts to another stream. Amazon Data Firehose reads the stream with enhanced fan-out and delivers compressed Parquet files to Amazon S3, with a backup bucket for failed records. Fraud, inventory, and analytics teams read through enhanced fan-out so that none slows another.

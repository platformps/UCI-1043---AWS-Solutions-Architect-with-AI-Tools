1. Orchestration and Step Functions

Problem Statement

FlashCart’s order fulfillment now spans six steps: validate the order, check the stock, charge the payment, reserve the stock, run a fraud review, and start the shipping job. In Lesson 273.3, the team connected these steps with events and queues, and each service reacts to the event before it.

Three months later, nobody can answer a simple question from customer service: "Where is order 48213, and why is it stuck?" The status lives in six services and six sets of logs. When the shipping job fails after the payment, a developer must refund the customer by hand. Each Lambda function also contains its own retry loop, written in a different way by a different team.

The architects want one place that defines the order of the steps, retries failed steps the same way, runs a refund when something fails after the payment, and shows the status of every order. They also want to avoid one Lambda function that calls all the others and waits, because that function would hit the 15-minute limit and pay for all the waiting time.

Your challenge:

  • Explain the difference between choreography, which FlashCart uses now, and orchestration, and decide which one fits the fulfillment process.
  • List what an orchestration service must provide to meet the architects’ goals.
  • Explain why one Lambda function that calls the other functions is the wrong orchestrator.

1.1 Orchestration

  • In choreography (Lesson 273.3), each service reacts to events and publishes new ones. No service is in charge, which is flexible, but the overall flow is hard to see and to change.
  • In orchestration, a central workflow calls each step in order, decides what happens next, retries failures, and keeps the status of each run.
  • Many systems use both: choreography between independent domains, and orchestration inside a business process that must run steps in a set order.

1.2 What AWS Step Functions Is

  • AWS Step Functions is a serverless orchestration service. You define a workflow as a state machine, a set of states and the transitions between them.
  • Each run of a state machine is an execution. Step Functions keeps the state of each execution, so you can see where every run is and what happened at each step.
  • It has built-in sequences, branches (conditions), parallel steps, waits, timeouts, retries, and error handling, so the business code in each step stays simple.
  • It integrates directly with AWS services, such as Lambda, ECS and Fargate, SQS, SNS, DynamoDB, EventBridge, and API Gateway, and with more than two hundred services through AWS SDK integrations.
  • It can also wait for a person or an outside system, for example a human approval.
  • Typical uses: order fulfillment, data processing, machine learning pipelines, and any business process with several steps.

1.3 How Workflows Start

  • An EventBridge rule or EventBridge Scheduler starts a workflow on an event or a schedule. S3 events reach Step Functions through EventBridge.
  • API Gateway starts a workflow from an API call, with an AWS service integration (Lesson 273.2).
  • Code starts a workflow with the StartExecution API, from Lambda or any application, and one state machine can start another.

2. State Machines and States

Problem Statement

The FlashCart team decides to build the fulfillment workflow in Step Functions and opens the console. Before they draw anything, they must learn how a state machine is described, which kinds of states exist, and how data moves from one state to the next.

The workflow has specific needs. Orders over 1,000 dollars must go through the fraud review, and smaller ones must skip it. The payment and the stock reservation do not depend on each other, so they should run at the same time. Customers who pay by bank transfer must wait up to two days for the money to arrive. When the stock is gone, the workflow must end with a clear failure that customer service can read.

Your challenge:

  • Choose the state type for each need: the amount check, the payment and the reservation together, the two-day wait, and the out-of-stock ending.
  • Explain how a state machine is written, and what tool helps the team design it visually.
  • Explain how the output of one state becomes the input of the next.

2.1 State Machines and the Amazon States Language

  • A state machine is written in the Amazon States Language (ASL), a JSON structure that lists the states, the start state, and the next state of each one.
  • Workflow Studio in the console lets you design the state machine visually, with drag and drop, and it writes the ASL for you.
  • Each state receives a JSON input and produces a JSON output, which becomes the input of the next state. You can filter and transform the data between states, with JSONPath or, in newer workflows, JSONata expressions.
  • Step Functions limits the size of the data passed between states, so store large data in S3 or DynamoDB and pass a reference.

2.2 The States

StateWhat it doesFlashCart example
TaskDoes one unit of work: calls an AWS service or an activity.Charge the payment with a Lambda function.
ChoiceChooses the next state with conditions on the data.Orders over 1,000 dollars go to the fraud review.
ParallelRuns several branches at the same time, and waits for all of them.Charge the payment and reserve the stock together.
MapRuns the same steps for each item of a list (tab 5).Process each line of an order.
WaitPauses for a time, or until a date and time.Wait two days for a bank transfer.
PassPasses its input to its output, optionally adding data. Useful for testing and shaping data.Add default values to the order.
SucceedEnds the execution successfully.The order is complete.
FailEnds the execution with an error name and a cause.OutOfStock, with a message for customer service.

2.3 A Small Example

{
  "StartAt": "CheckAmount",
  "States": {
    "CheckAmount": {
      "Type": "Choice",
      "Choices": [
        { "Variable": "$.amount", "NumericGreaterThan": 1000, "Next": "FraudReview" }
      ],
      "Default": "ChargePayment"
    },
    "FraudReview": {
      "Type": "Task",
      "Resource": "arn:aws:states:::lambda:invoke",
      "Parameters": { "FunctionName": "fraud-review", "Payload.$": "$" },
      "Next": "ChargePayment"
    },
    "ChargePayment": {
      "Type": "Task",
      "Resource": "arn:aws:states:::lambda:invoke",
      "Parameters": { "FunctionName": "charge-payment", "Payload.$": "$" },
      "End": true
    }
  }
}

Orders over 1,000 dollars go through the fraud review before the payment. Smaller orders go straight to the payment.

3. Standard and Express Workflows

Problem Statement

FlashCart now has two very different workflows to build. The order fulfillment workflow runs about 40,000 times a day. It can take up to three days, because of bank transfers and fraud reviews, and it must never charge a customer twice or skip a step. Auditors also want to see the full history of every order.

The second workflow handles clickstream events from the website: about 5,000 events per second at peak. Each run validates an event, enriches it with product data, and writes it to a stream, which takes less than a second. A duplicate run now and then is harmless, but the cost must stay low.

A developer suggests using the same workflow type for both, "to keep things simple".

Your challenge:

  • Choose the workflow type for each workflow, and explain the deciding factors: the duration, the execution guarantee, the volume, the history, and the cost.
  • Explain what goes wrong if the clickstream workflow uses the type of the order workflow, and the other way around.

3.1 Two Workflow Types

Standard workflowsExpress workflows
Maximum durationOne year.Five minutes.
Execution guaranteeExactly-once execution.Asynchronous: at-least-once. Synchronous: at-most-once.
VolumeDesigned for durable, long-running processes.Designed for high event rates, up to 100,000 state transitions per second.
Execution historyKept by Step Functions, with a visual view of each execution.Not captured by Step Functions. Send it to CloudWatch Logs.
Integration patternsRequest response, run a job (.sync), and wait for callback.Request response only.
PricingPer state transition.Per execution, and by duration and memory.
Use it forOrder processing, payments, approvals, and other long or critical processes.High-volume, short event processing, such as streaming data, IoT, and API backends.
  • You choose the type when you create the state machine, and you cannot change it later.
  • A synchronous Express workflow (StartSyncExecution) returns its result to the caller, which suits an API backend behind API Gateway. An asynchronous Express workflow returns at once and runs in the background.
  • The two types work together: a Standard workflow can start Express workflows as child workflows for its short, high-volume parts.

Exam-Style Question

Scenario: A workflow processes IoT sensor readings: 20,000 events per second, each processed in under one second, and an occasional duplicate is acceptable. The company wants the lowest cost. Which workflow type should a solutions architect choose?

  • A. An asynchronous Express workflow.
  • B. A Standard workflow.
  • C. A synchronous Express workflow called by each sensor.
  • D. A Standard workflow with a Map state.
Show Answer and Explanation

Correct answer: A. Express workflows are built for high-volume, short executions, priced by execution and duration, and asynchronous Express accepts at-least-once execution.

OptionResultReason
ACorrectIt fits the volume, duration, and cost goal.
BIncorrectStandard is priced per state transition and is not designed for this volume.
CIncorrectSensors do not need to wait for each result.
DIncorrectA Map state does not change the pricing or the volume limits.

Exam Trap

Remember these points:

  • Longer than five minutes, exactly-once, audit history, human approval = Standard.
  • High volume, short, lowest cost, duplicates acceptable = Express.
  • Express workflows do not support .sync or wait for callback.

Memory Hook

Standard is the long, careful marathon. Express is the short, cheap sprint.

→ Standard workflow

Trigger 2: "High-volume, short event processing at low cost"

4. Error Handling and Integrations

Problem Statement

The first runs of the FlashCart order workflow show three kinds of trouble. The payment provider sometimes returns a timeout error for a few seconds during busy periods. The shipping step starts a container task on Amazon ECS that runs for about 20 minutes, and the workflow moves on before the task has finished. When the stock reservation fails after the payment has succeeded, the customer is charged for nothing.

The fraud team adds a new requirement: for orders that look risky, a person must approve or reject the order in the fraud team’s web tool, which can take up to a day. The workflow must pause until the decision arrives, and must not run anything while it waits.

Your challenge:

  • Handle the short payment timeouts without failing the order.
  • Make the workflow wait until the 20-minute ECS task finishes.
  • Refund the customer when a step fails after the payment.
  • Pause the workflow until a person approves or rejects a risky order.

4.1 Retry and Catch

  • Errors are named, for example States.Timeout, States.TaskFailed, or a custom error such as PaymentDeclined. States.ALL matches any error.
  • A Retry rule on a Task, Parallel, or Map state retries the state when an error matches its ErrorEquals list, with IntervalSeconds before the first retry (1 second by default), MaxAttempts (3 by default), and a BackoffRate that multiplies the interval after each attempt (2.0 by default).
  • A Catch rule runs when the retries are used up or there are none. It sends the execution to a fallback state, for example a refund, and can keep the error information in the output.
  • A timeout on a Task stops a step that runs too long, and a heartbeat timeout fails a long task that stops reporting progress.
"ChargePayment": {
  "Type": "Task",
  "Resource": "arn:aws:states:::lambda:invoke",
  "Parameters": { "FunctionName": "charge-payment", "Payload.$": "$" },
  "Retry": [
    { "ErrorEquals": ["States.Timeout", "Lambda.ServiceException"],
      "IntervalSeconds": 2, "MaxAttempts": 3, "BackoffRate": 2.0 }
  ],
  "Catch": [
    { "ErrorEquals": ["States.ALL"], "ResultPath": "$.error", "Next": "RefundPayment" }
  ],
  "Next": "ReserveStock"
}

A timeout is retried after 2, 4, and 8 seconds. Any error that remains sends the order to the refund step, with the error details kept in $.error.

4.2 Service Integration Patterns

PatternResource suffixWhat Step Functions does
Request response (default)NoneCalls the service and moves to the next state as soon as it gets the HTTP response. It does not wait for a job to finish.
Run a job.syncStarts a job, such as an ECS task, an AWS Batch job, or an AWS Glue job, and waits until the job completes.
Wait for callback.waitForTaskTokenSends a task token to a service, such as SQS, SNS, or Lambda, and pauses until a system or a person calls SendTaskSuccess or SendTaskFailure with the token.
  • Standard and Express workflows support the same services, but Express workflows support only the request response pattern.
  • Human approval uses the callback pattern: the workflow sends the task token to the approver’s tool, for example in an email through SNS or a message in SQS, and the tool calls SendTaskSuccess or SendTaskFailure with the decision.
  • Activities let a worker on any server, including on premises, poll Step Functions for tasks and return the results.

Exam-Style Question

Scenario: A workflow must pause until a manager approves an expense in an internal web tool, which can take several days, and must not pay for compute while it waits. Which approach fits best?

  • A. A Lambda function that polls the tool every minute.
  • B. An Express workflow with a Wait state.
  • C. A Standard workflow with a Task that uses .waitForTaskToken and sends the task token to the tool.
  • D. A Standard workflow with a request response Task.
Show Answer and Explanation

Correct answer: C. The callback pattern pauses the Standard workflow until the tool returns the token with SendTaskSuccess or SendTaskFailure, with nothing running while it waits.

OptionResultReason
AIncorrectPolling adds code and cost.
BIncorrectExpress workflows last five minutes and do not support callbacks.
CCorrectThis is the human approval pattern.
DIncorrectRequest response does not wait for the decision.

Remember these points:

  • Transient errors = Retry with backoff. Compensation such as a refund = Catch to a fallback state.
  • Wait for a job (ECS, Batch, Glue) = .sync. Wait for a person or an outside system = .waitForTaskToken. Both need Standard workflows.

Retry the hiccups, Catch the failures, .sync for jobs, and a token for people.

5. Parallel Processing at Scale

Problem Statement

FlashCart is changing the look of its website, and every product image must be resized into three new formats. There are about one million images in an S3 bucket. A developer builds a workflow with a Map state that loops over a list of the images, but the list does not fit in the workflow input, and a test with 20,000 images fails with an error about the size of the execution history.

The marketing team also needs to run three independent checks on each new product, for price, description, and images, and it wants the results as soon as the slowest check finishes.

Your challenge:

  • Choose the right way to process one million S3 objects in parallel with Step Functions.
  • Explain why the first design failed, and how the fix avoids both problems.
  • Choose the state for the three independent product checks.

5.1 Parallel and Map

  • A Parallel state runs a fixed set of branches at the same time and waits for all of them. The output is a list with the result of each branch.
  • A Map state runs the same steps for each item of a list.
  • In inline mode, the Map state runs inside the parent execution, with up to 40 iterations at the same time. All iterations share the parent’s execution history, which can hold up to 25,000 events for a Standard workflow.

5.2 Distributed Map

  • In distributed mode, the Map state launches each iteration, or each batch of items, as a separate child workflow execution, with its own history.
  • It runs up to 10,000 child executions in parallel.
  • It can read the items directly from Amazon S3: a list of objects, a CSV or JSON file, or an S3 inventory, so the data does not need to fit in the workflow input. It can write the results back to S3.
  • The child workflows can be Standard or Express. Express fits short, high-volume items, and Standard fits long items or items that use .sync or callbacks.

Exam-Style Question

Scenario: A company must process 5 million CSV records stored in S3, with up to thousands of records processed in parallel, using Step Functions. Which approach fits best?

  • A. One Lambda function that loops over all the records.
  • B. A Map state in inline mode with the records in the workflow input.
  • C. A Parallel state with one branch per record.
  • D. A Map state in distributed mode that reads the CSV file from S3.
Show Answer and Explanation

Correct answer: D. Distributed Map reads the items directly from S3 and runs up to 10,000 child executions in parallel, each with its own history.

OptionResultReason
AIncorrectOne function is limited to 15 minutes and does not scale out.
BIncorrectThe records do not fit in the input, and inline mode runs at most 40 iterations at a time.
CIncorrectParallel has a fixed set of branches, not one per record.
DCorrectIt is built for large-scale parallel processing over S3 data.

Exam Trap

Remember these points:

  • Millions of S3 objects, thousands in parallel = Distributed Map. A few items = inline Map.
  • Parallel = a fixed set of different branches. Map = the same steps for each item.

Memory Hook

Parallel does different things at once. Map does the same thing many times. Distributed Map does it at S3 scale.

Trigger 2: "Run three different checks at the same time"

6. Security, Monitoring, and Pricing

Problem Statement

Before the order workflow goes live, three teams review it. The security team asks what the workflow is allowed to do, because it calls the payment function, the stock table, and the ECS cluster. The operations team asks how it will know that orders are failing, and how it will find the step where a slow order spends its time.

The finance team compares two designs of the clickstream workflow: a Standard workflow with eight states, and the same eight states in an Express workflow. It asks which one costs less at 5,000 events per second, and why the bill of the order workflow grew after a developer split one step into five smaller states.

Your challenge:

  • Describe how the workflow gets permission to call other services, following least privilege.
  • Choose how operations monitors failures and finds slow steps.
  • Explain how each workflow type is billed, and answer the finance team’s two questions.

6.1 Security

  • Each state machine has an IAM execution role. Step Functions assumes this role to call the services in the workflow, so give it only the actions and resources that the workflow needs.
  • Callers need IAM permission to start an execution (states:StartExecution), for example the role of API Gateway or an EventBridge rule.
  • Step Functions encrypts data at rest, and you can use a customer managed AWS KMS key.

6.2 Monitoring

  • For Standard workflows, the console shows the history and a graph of each execution: each state, its input and output, and where it failed.
  • CloudWatch metrics count started, succeeded, failed, and timed-out executions, and you can set alarms on them. Express workflows send their execution history to CloudWatch Logs.
  • AWS X-Ray traces an execution across Step Functions and the services that it calls, to find the slow steps.
  • EventBridge receives an event when an execution changes status, so another workflow or a notification can react to failures.

6.3 Pricing

  • Standard workflows are billed per state transition. More states, or more retries, mean more transitions, so splitting one step into five states raises the cost.
  • Express workflows are billed per execution and by duration and memory, which is usually much cheaper for high-volume, short workflows.
  • The services that the workflow calls, such as Lambda, are billed separately.
  • Check the Step Functions pricing page for the current prices.

Exam-Style Question

Scenario: A Standard workflow runs millions of times a day for short, simple event processing, and its cost is high. The workflow finishes in under a second, and an occasional duplicate is acceptable. How can a solutions architect lower the cost?

  • A. Add more states to split the work.
  • B. Recreate it as an Express workflow, billed by execution and duration.
  • C. Add retries to every state.
  • D. Give the execution role more permissions.
Show Answer and Explanation

Correct answer: B. Standard workflows are billed per state transition. For short, high-volume executions, Express workflows are billed by execution and duration and usually cost much less.

OptionResultReason
AIncorrectMore states mean more transitions and more cost.
BCorrectIt matches the pricing model to the workload.
CIncorrectRetries add transitions.
DIncorrectPermissions do not affect the price.

Exam Trap

Remember these points:

  • The workflow calls services with its execution role: least privilege applies.
  • Standard = billed per state transition. Express = billed per execution and duration.
  • Express history goes to CloudWatch Logs, not to the Step Functions console.

Memory Hook

A role to act, CloudWatch and X-Ray to watch, transitions or duration to pay.

7.4 Lesson Summary

This lesson covered the following points:

  • Step Functions orchestrates steps as a state machine, written in the Amazon States Language or drawn in Workflow Studio, with built-in state, retries, and error handling.
  • The states are Task, Choice, Parallel, Map, Wait, Pass, Succeed, and Fail.
  • Standard workflows run up to one year with exactly-once execution and are billed per state transition. Express workflows run up to five minutes, at high volume, and are billed per execution and duration.
  • Retry and Catch handle errors and compensation. The integration patterns are request response, run a job (.sync), and wait for callback with a task token. Express supports request response only.
  • Parallel runs different branches at once. Map repeats steps for each item, and Distributed Map runs up to 10,000 child executions over data in S3.
  • An IAM execution role controls what a workflow can do, and CloudWatch, CloudWatch Logs, and X-Ray monitor it.

Memory Hook

Order the steps, retry the hiccups, wait for people, and pick Standard or Express.

8. Knowledge Check

Answer each question in your own words before you open the model answer.

Question 1: Explain the difference between choreography and orchestration, and when Step Functions is the better choice.

Maps to: Objective 1 (Comprehension).

In choreography, each service reacts to events and publishes new ones, with no central control, which suits independent services. In orchestration, a central workflow runs the steps in order, retries failures, runs compensation, and keeps the status of each run. Step Functions is the better choice for business processes whose steps must run in a set order with error handling and visible status, such as order fulfillment, and it avoids a Lambda function that calls the others and waits.

Question 2: Describe the main state types and give an example of each.

Maps to: Objective 2 (Knowledge and Comprehension).

Task does one unit of work, such as invoking a Lambda function. Choice branches on the data, such as orders over 1,000 dollars. Parallel runs fixed branches at the same time, such as payment and stock reservation. Map runs the same steps for each item. Wait pauses for a time or until a date. Pass passes or shapes data. Succeed and Fail end the execution with success or a named error.

Question 3: Compare Standard and Express workflows, and explain how you choose between them.

Maps to: Objective 5 (Analysis).

Standard workflows run up to one year with exactly-once execution, keep the execution history, support .sync and callbacks, and are billed per state transition. Express workflows run up to five minutes, at up to 100,000 state transitions per second, with at-least-once (asynchronous) or at-most-once (synchronous) execution, history in CloudWatch Logs, only request response, and billing by execution and duration. Choose Standard for long, critical, or audited processes, and Express for short, high-volume, low-cost processing.

Question 4: Explain how Retry and Catch work, and how they protect the FlashCart order workflow.

Maps to: Objective 3 (Application).

A Retry rule retries a state for matching errors, with an interval, a maximum number of attempts, and a backoff rate, which handles short payment timeouts. A Catch rule runs after the retries are used up and sends the execution to a fallback state, such as a refund, keeping the error details in the output. Together they handle transient errors automatically and compensate for failures after the payment.

Question 5: Describe the three service integration patterns, and when to use each.

Maps to: Objective 3 (Application).

Request response calls the service and moves on when the HTTP response arrives, for quick calls. Run a job (.sync) starts a job such as an ECS task or a Batch or Glue job and waits for it to complete. Wait for callback (.waitForTaskToken) sends a task token and pauses until a system or a person calls SendTaskSuccess or SendTaskFailure, for human approvals and external systems. Express workflows support only request response.

Question 6: Explain when to use Distributed Map instead of an inline Map, and why.

Maps to: Objective 4 (Application).

Use Distributed Map for large datasets, such as millions of objects or records in S3. It reads the items directly from S3, so they do not need to fit in the workflow input, runs up to 10,000 child executions in parallel, each with its own execution history, and can write the results to S3. An inline Map runs inside the parent execution, with up to 40 iterations at a time, and shares the parent history, which has a limit of 25,000 events for a Standard workflow.

Question 7: Design the FlashCart order fulfillment with Step Functions: steps in order, a fraud review by a person, a 20-minute ECS shipping job, short payment timeouts, refunds after failures, and monitoring.

Maps to: Objective 6 (Synthesis).

Use a Standard workflow, because the process can take days, must run exactly once, and needs callbacks and .sync jobs. Validate the order, use a Choice state for stock and amount, and a Parallel state for payment and stock reservation. Add Retry with backoff for payment timeouts, and a Catch that sends failures after the payment to a refund Task and a Fail state. Use the callback pattern with a task token for the fraud review, and the .sync pattern for the ECS shipping task. Start the workflow from EventBridge or API Gateway, give it a least-privilege execution role, and monitor it with CloudWatch alarms, X-Ray, and status-change events.

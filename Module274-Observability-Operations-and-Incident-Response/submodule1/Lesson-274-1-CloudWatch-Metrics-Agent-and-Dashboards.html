CloudWatch Metrics, Agent, and Dashboards

How Amazon CloudWatch structures, stores, and displays metrics: monitoring intervals, custom metrics, metric math, Metric Streams, the CloudWatch agent for memory and disk data, dashboards, and the metrics that each AWS service publishes.

Lesson Overview

This lesson introduces metrics, the foundation of monitoring on Amazon Web Services (AWS). It is the first lesson of Module 274 and prepares you for logs and alarms (lesson 274.2). In this lesson, you will study:

  • Metrics Fundamentals: namespaces, metrics, dimensions, data points, statistics, periods, and the Regional scope of metrics.
  • Basic, Detailed, and High-Resolution Monitoring: how often metrics arrive, how long CloudWatch keeps them, and what each option costs you in detail.
  • Custom Metrics, Metric Math, and Metric Streams: publishing your own data, calculating new values from existing metrics, and streaming metrics out of CloudWatch.
  • CloudWatch Agent: collecting memory, disk, and other operating system metrics that Amazon Elastic Compute Cloud (Amazon EC2) does not report by default.
  • Dashboards: automatic and custom dashboards, cross-Region and cross-account views, and sharing.
  • Where CloudWatch Metrics Fit Across AWS Services: which metrics each AWS service publishes, with detail on Amazon Elastic Block Store (Amazon EBS) volumes and load balancers, and which AWS features use them.
  • Comparison and Scenarios: comparison tables and a cheat sheet for the AWS Certified Solutions Architect – Associate (SAA-C03) exam.
  • Knowledge Check: open-ended questions with model answers.

1. Metrics Fundamentals

Problem Statement

FlashCart Inc. runs its online store on six Amazon EC2 instances behind an Application Load Balancer (lesson 270.2) on a normal day, and Auto Scaling (lesson 270.4) grows the group to 40 instances during a flash sale. During the last sale, page response time rose from about 300 milliseconds to more than four seconds for 35 minutes.

On the incident call, the operations manager asked two questions: “Which instance is struggling?” and “How do we know?” Three engineers answered in three different ways. One looked at the Auto Scaling group, one looked at the load balancer, and one logged in to an instance and ran a command. None of them could say where the data came from, how it was organized, or how long CloudWatch keeps it.

A new engineer then asks two more questions. Why does a CPUUtilization graph for the second Region show nothing for the instances in the first Region? And why does a custom CheckoutLatency metric that she published with two dimensions return no data when she asks for only one of them?

Your challenge:

  • Describe how CloudWatch identifies a metric, using the terms namespace, name, and dimension.
  • Explain why the custom metric returns no data when only one dimension is requested.
  • Explain why metrics from one Region do not appear in another.
  • Choose a statistic that shows an unusually heavy instance without one spike distorting the result.

1.1 What Amazon CloudWatch Does

Amazon CloudWatch collects monitoring data from AWS resources and applications. It works with metrics (numbers measured over time), logs (text records), and alarms (actions that depend on a metric). This lesson covers metrics, the CloudWatch agent, and dashboards. Logs and alarms are covered in lesson 274.2. To follow one request across several services, use AWS X-Ray (lesson 274.6).

CloudWatch works as a metrics repository. An AWS service, an agent, or your own application puts data points into the repository, and you retrieve statistics about those data points.

1.2.1 How Dimensions Work

Dimensions follow these rules:

  • Each unique combination of dimensions is a separate metric, even when the metric name is the same.
  • You can retrieve statistics only for dimension combinations that were published.
  • For some AWS service metrics, such as Amazon EC2, CloudWatch can aggregate across dimensions. A request for CPUUtilization in AWS/EC2 with no dimensions returns an aggregate across instances.
  • CloudWatch does not aggregate across dimensions for custom metrics.

For example, FlashCart publishes a custom metric named CheckoutLatency with the dimensions Service and Stage. The four combinations it publishes are Payments and Prod, Payments and Beta, Cart and Prod, and Cart and Beta.

Statistics requestResult
Service = Payments and Stage = ProdReturns data, because this combination was published.
Service = Payments onlyReturns no data, because this combination was never published.
No dimensionsReturns no data, because this combination was never published.

The metric math SEARCH function is the exception. It can find and return several metrics at once (tab 3).

1.3 Statistics, Units, and Periods

CloudWatch supports these statistics:

  • Sum, the total of the values in the period.
  • Average, the mean of the values in the period.
  • Minimum and Maximum, the lowest and highest values.
  • SampleCount, the number of data points in the period.
  • Percentiles, such as p95.

Not every statistic is meaningful for every metric. For example, CPUUtilization in Amazon EC2 is meant to be read with Average, Minimum, and Maximum.

1.3.1 Why Percentiles Matter

The 95th percentile means that 95 percent of the values are lower than the result and 5 percent are higher. An average can hide an unusually heavy instance, while a maximum can be skewed by one spike. A percentile such as p95 shows how the load is distributed. Some service metrics support percentiles, including metrics from Amazon EC2, AWS Lambda, Amazon Relational Database Service (Amazon RDS), and Elastic Load Balancing. Percentiles are not available for a metric when any of its values is negative.

1.3.2 Periods and Units

  • The default period is 60 seconds.
  • Valid periods are 1, 5, 10, 30, or any multiple of 60 seconds. A period longer than 60 seconds must be a multiple of 60.
  • Only custom metrics stored at one-second resolution support sub-minute periods (tab 2).
  • Data points that use different units are aggregated separately. If two identical metrics use different units, CloudWatch returns two data streams.

1.4 Scope, Timestamps, and Expiry

  • Metrics exist only in the AWS Region where they are created. CloudWatch does not aggregate data across Regions automatically. Metric math (tab 3) and dashboards (tab 5) can combine metrics from different Regions.
  • You cannot delete metrics. A metric expires on its own after 15 months if no new data is published to it.
  • Each data point needs a timestamp. The timestamp can be up to two weeks in the past and up to two hours in the future. If you omit it, CloudWatch uses the time of receipt. Use Coordinated Universal Time (UTC).
  • Metrics with no new data for two weeks do not appear in the console. Retrieve them with the get-metric-data or get-metric-statistics commands in the AWS Command Line Interface (AWS CLI).
Exam trap

Metrics are Regional and cannot be deleted. A question that asks you to “remove old metrics” has no deletion answer. The data expires by itself, 15 months after the last data point.

Memory hook

A metric is its namespace, its name, and its dimensions. Change any one of the three, and you have a different metric.

SAA-C03 Keyword Triggers

Trigger 1: “Keep metrics from different applications from being mixed in the same statistics”
→ Use separate namespaces.

Trigger 2: “Look at the metric for one specific instance”
→ Filter by the InstanceId dimension.

Trigger 3: “Detect unusually heavy load without one spike skewing the result”
→ Use a percentile statistic such as p95.

Trigger 4: “Metrics from another Region do not show up”
→ Metrics are Regional. Use a dashboard or metric math across Regions (tabs 3 and 5).

2. Basic, Detailed, and High-Resolution Monitoring

Problem Statement

The sale creates a traffic spike that lasts about three minutes, when a popular product is announced. The central processing unit (CPU) graph on the team’s dashboard shows one data point every five minutes, so the spike is averaged away: the graph shows 55 percent while the instances actually reach 95 percent for three minutes. The Auto Scaling group (lesson 270.4) reacts only after the next data point, so new instances arrive after the spike is over.

The checkout team wants response-time data for every second during the first 10 minutes of future sales. The finance team asks how long CloudWatch keeps such detailed numbers, because they want to compare this sale with the sale of exactly one year ago on one graph.

The security lead adds one condition: nobody should pay for extra detail on the 40 development instances.

Your challenge:

  • Choose how to get one-minute CPU data for the production instances only, and say what it costs.
  • Choose how to publish response times for every second, and explain the limits of that data.
  • Explain what the graph for last year’s sale will look like, and at what resolution.
  • Explain how the period of an alarm must relate to the resolution of its metric.

2.1 Basic and Detailed Monitoring for Instances

Amazon EC2 sends metrics to CloudWatch in the AWS/EC2 namespace. You choose between two monitoring levels:

FeatureBasic monitoringDetailed monitoring
IntervalFive minutesOne minute
Turned onBy defaultManually, at launch or on a running instance
CostNo chargeCharged per metric that Amazon EC2 sends; check the pricing page
Metrics availableThe standard Amazon EC2 setThe same set at finer granularity
 
# Turn detailed monitoring on, and off again
aws ec2 monitor-instances --instance-ids i-0123456789abcdef0
aws ec2 unmonitor-instances --instance-ids i-0123456789abcdef0

Keep these details in mind:

  • Detailed monitoring does not add new kinds of metrics. It still does not report memory or disk space usage (tab 4).
  • Status check metrics, such as StatusCheckFailed_System, are available every minute by default at no charge.
  • Some metrics are five-minute only: NetworkPacketsIn and NetworkPacketsOut are available for basic monitoring only, and the CPU credit metrics are published only every five minutes.
  • The ImageId and InstanceType dimensions are available only for instances that have detailed monitoring enabled.
  • When you create an alarm (lesson 274.2, tab 6), choose a period that is at least as long as the metric’s resolution: 300 seconds or more for basic monitoring, and 60 seconds or more for detailed monitoring.

2.2 Standard and High-Resolution Metrics

Every metric has either standard or high resolution:

  • Standard resolution stores data at one-minute granularity. Metrics that AWS services publish use standard resolution by default.
  • High resolution stores data at one-second granularity. High resolution is available only for custom metrics.

You publish a high-resolution metric by setting the storage resolution to 1 in the PutMetricData call. You can then retrieve it with a period of 1, 5, 10, or 30 seconds, or any multiple of 60 seconds.

aws cloudwatch put-metric-data \
  --namespace FlashCart/Checkout \
  --metric-name CheckoutLatency \
  --unit Milliseconds --value 240 \
  --dimensions Service=Payments,Stage=Prod \
  --storage-resolution 1
  • Every PutMetricData call for a custom metric is charged, so publishing more often raises the cost.
  • A high-resolution alarm can use a period of 10, 20, or 30 seconds. It costs more than a regular alarm.
  • Do not start a custom namespace with AWS/. That prefix belongs to AWS services.

2.3 Retention and Rollup

CloudWatch keeps data points for different lengths of time, depending on their period:

Data point periodAvailable for
Under 60 seconds (high-resolution custom metrics)3 hours
60 seconds (one minute)15 days
300 seconds (five minutes)63 days
3,600 seconds (one hour)455 days (15 months)

Data points that are published with a shorter period are aggregated for long-term storage. One-minute data stays at one-minute resolution for 15 days. After that, you can retrieve it only at five-minute resolution. After 63 days, you can retrieve it only at one-hour resolution.

Exam trap

Detailed monitoring gives the same metrics at one-minute granularity. It does not add memory, disk space, or any other operating system metric. A question that needs memory data always points to the CloudWatch agent.

Memory hook

Five minutes by default, one minute when you pay for detailed monitoring, and one second only for custom metrics that you publish yourself.

3. Custom Metrics, Metric Math, and Metric Streams

Problem Statement

The finance team wants “orders per minute” and “revenue per product” on the same dashboards as the servers. These numbers exist only inside the order application, and no AWS service publishes them. The operations team also wants an “error rate” graph for the Application Load Balancer, but AWS publishes the count of failed requests and the count of all requests as two separate metrics.

The data team wants every CloudWatch metric from the production Region in an Amazon Simple Storage Service (Amazon S3) data lake (lesson 271.2), and a subset in a third-party monitoring tool, delivered within a few minutes and without polling the CloudWatch application programming interface (API) every minute. The tool that the data team prefers accepts the OpenTelemetry format.

A developer suggests publishing a custom metric for every customer ID, so that finance can see revenue for each customer. The finance team estimates two million customers.

Your challenge:

  • Describe how the application can publish orders and revenue, and what the namespace and dimensions should be.
  • Write the calculation that gives the error rate from the two AWS metrics.
  • Choose how to deliver all metrics to the data lake and a subset to the third-party tool, and name the destination service (lesson 273.6).
  • Explain the problem with a metric for every customer ID.

3.1 Custom Metrics

A custom metric is a metric that you or your application publish to CloudWatch. Use custom metrics for application and business data, such as orders placed or products sold. You publish data points with the PutMetricData operation in the AWS CLI or an AWS software development kit (SDK). The caller needs permission to perform cloudwatch:PutMetricData. The CloudWatch agent (tab 4) also publishes custom metrics.

aws cloudwatch put-metric-data \
  --namespace FlashCart/Store \
  --metric-name ProductsSold \
  --value 15 \
  --dimensions Product=Headphones
TopicAWS service metricsCustom metrics
NamespaceAWS/serviceYour own name, which must not start with AWS/
ResolutionStandard, one minuteStandard or high resolution
Aggregation across dimensionsAvailable for some services, such as Amazon EC2Not available
CostMany are free; some options cost extraCharged per metric and per PutMetricData call

3.1.1 Statistic Sets

For a large number of measurements, publish a pre-aggregated statistic set instead of every data point. A statistic set carries the Min, Max, Sum, and SampleCount of many measurements. For example, aggregate the response times of all page hits once a minute and send one statistic set. Percentile statistics need the raw, unsummarized data points, so a statistic set cannot provide them in most cases.

3.2 Metric Math

Metric math lets you calculate new time series from existing metrics. You use it in graphs and dashboards, and an alarm can also use a metric math expression (lesson 274.2, tab 6). CloudWatch computes the result from the source metrics when you request it. The result is not published as a new metric.

GoalExpression
Error rate as a percentage, where m1 counts failed requests and m2 counts all requests(m1 / m2) * 100
Total across all metrics shown in a graphSUM(METRICS())
Bytes per second from a byte count, where m1 is the metricm1 / DIFF_TIME(m1)
Average volume read latency in milliseconds, where m1 is the total time spent on reads and m2 is the number of read operations (section 6.3.1)(m1 / m2) * 1000
Find several metrics that match a patternSEARCH function
Return the band of expected values around a metric, where m1 is the metric and 2 is the number of standard deviations that sets the band widthANOMALY_DETECTION_BAND(m1, 2)

Metric math can also combine metrics from different Regions, which solves the Regional scope from tab 1.

3.2.1 A Preview of Anomaly Detection and Outlier Detection

CloudWatch can learn what normal looks like for a metric. It applies machine learning to the metric’s past data, up to two weeks of it, and builds a model of expected values that accounts for trends and for hourly, daily, and weekly patterns. The ANOMALY_DETECTION_BAND function returns the upper and lower edges of that band, and a graph can overlay the band so that values outside it stand out. An alarm can also use the band instead of a fixed threshold. Lesson 274.2, tab 6, covers those alarms.

This feature has two names. The course slides and many study materials call it anomaly detection. The current AWS documentation page for the feature is titled “Using CloudWatch outlier detection” and uses the term outlier detection. Both names refer to the same feature, and the metric math function keeps the name ANOMALY_DETECTION_BAND. Treat an exam question that uses either term as a question about this feature.

3.3 Metric Streams

A metric stream sends CloudWatch metrics continuously to a destination you choose, with near-real-time delivery and low latency. Without a stream, an external tool typically has to poll the CloudWatch application programming interface (API) for the data.

  • Custom setup with Amazon Data Firehose: you create a delivery stream that sends the metrics to an Amazon Simple Storage Service (Amazon S3) data lake or to any destination that Firehose supports, including third-party providers. Lesson 273.6 covers Firehose.
  • Quick Amazon S3 setup: CloudWatch creates the resources needed to stream to Amazon S3.
  • Quick partner setup: CloudWatch offers a fast setup for some third-party providers, such as Datadog, Dynatrace, New Relic, Splunk, and Sumo Logic.

Each stream uses one output format: JavaScript Object Notation (JSON), OpenTelemetry 1.0.0, or OpenTelemetry 0.7.0. A stream can include up to 1,000 filters that either include or exclude metric namespaces or specific metrics. A single stream can have include filters or exclude filters, but not both. Pricing depends on the number of metric updates, plus the Firehose charges for the delivery stream.

Note on source material

Some course slides still call the delivery service “Kinesis Data Firehose.” The current name is Amazon Data Firehose, and this lesson uses it.

Exam trap

A metric stream delivers metrics, not logs. To send logs to Amazon S3, Amazon Kinesis, or AWS Lambda, you use CloudWatch Logs features that lesson 274.2 covers.

Memory hook

Math happens at the graph; streams leave CloudWatch. Use math to calculate a value, and use a stream to move metrics somewhere else.

Problem Statement

During the last sale, the checkout instances froze three times for about two minutes each. The CPU graph looked normal at 40 percent, the network graph showed no change, and the Auto Scaling group (lesson 270.4) added no instances because it scales on CPU. The engineers suspected that the Java application ran out of memory, but they could not prove it, because memory is not on any CloudWatch graph.

The security team asks that the fix does not store access keys on any server, and that all 40 instances use the same configuration, which one engineer can change in one place. The warehouse in a rented building also runs one on-premises server for shipping labels, and it needs the same graphs.

The first engineer who tried a fix installed software on one instance and saw no new metrics after 10 minutes. He later found that the instance had no role attached. On a second instance, memory appeared but disk usage did not.

Your challenge:

  • Explain why memory and disk space do not appear among the standard EC2 metrics.
  • List the steps to get memory and disk metrics from an instance, including the permissions and where the metrics appear.
  • Describe how one engineer can change the configuration for all 40 instances in one place (lesson 268.8).
  • Explain how the on-premises server can send the same metrics.

4.1 Metrics That Amazon EC2 Does Not Report by Default

Amazon EC2 reports what it can measure about an instance from outside the operating system. Values that exist only inside the operating system need software running on the machine.

Reported by default (namespace AWS/EC2)Needs the CloudWatch agent
CPU utilization, network in and out, and status checksMemory used, free, cached, and total
Disk operations and bytes for instance store volumes onlyDisk space used, free, and total
Amazon Elastic Block Store (Amazon EBS) operations and bytes for attached volumes on Nitro-based instancesSwap space, processes, and Transmission Control Protocol (TCP) and User Datagram Protocol (UDP) connections
CPU credit metrics for burstable instancesDetailed CPU states, such as idle, user, system, and steal

The disk metrics DiskReadOps and DiskWriteOps cover instance store volumes only. If the instance has no instance store volumes, the value is 0 or the metric is not reported. Performance metrics for an Amazon EBS volume itself, such as queue length and burst balance, come from the AWS/EBS namespace (section 6.3.1).

4.2 What the CloudWatch Agent Does

The CloudWatch agent is software that you install on Linux or Windows servers. It runs on Amazon EC2 instances and on on-premises servers. It collects system-level metrics and log files and sends them to CloudWatch. Log collection is covered in lesson 274.2.

  • By default, the agent publishes its metrics in the CWAgent namespace. You can set a different namespace in the configuration file.
  • Metrics, logs, and traces that the agent collects are charged.
  • The agent replaces the older CloudWatch Logs agent, which could send only logs. Some course slides call the current agent the “unified agent.” This lesson uses its current name, the CloudWatch agent.

4.3 Setting Up the Agent

  1. Create an IAM role. Create an IAM role that includes the CloudWatchAgentServerPolicy managed policy, and attach the role to the instance. The role is delivered to the instance through an instance profile.
  2. Install the agent. Install the package on the instance, or use AWS Systems Manager to install it on many instances at once (lesson 268.8).
  3. Create the configuration file. Use the configuration wizard or write the file by hand. The file is JSON and has four sections: agent, metrics, logs, and traces.
  4. Store the configuration centrally (optional). Save the file as a Systems Manager Parameter Store parameter so that every instance reads the same configuration (lesson 268.8). AWS examples name such parameters with the prefix AmazonCloudWatch-.
  5. Start the agent and check the result. Start the agent with the configuration, and confirm that the CWAgent namespace appears in CloudWatch.
# Start the agent on Linux with a local configuration file
sudo /opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-ctl \
  -a fetch-config -m ec2 -s -c file:/opt/aws/amazon-cloudwatch-agent/etc/config.json

# Check that the agent is running
sudo /opt/aws/amazon-cloudwatch-agent/bin/amazon-cloudwatch-agent-ctl -a status
{
  "metrics": {
    "append_dimensions": { "InstanceId": "${aws:InstanceId}" },
    "metrics_collected": {
      "mem":  { "measurement": ["mem_used_percent"] },
      "disk": { "measurement": ["used_percent"], "resources": ["/"] }
    }
  }
}

The second block is a minimal example configuration that collects memory and root-volume disk usage. Test any configuration in a lab before you use it on a production instance.

Exam trap

Do not store access keys on the instance to let the agent publish data. The correct answer is an attached IAM role. Also remember that enabling detailed monitoring never produces memory metrics.

Memory hook

No agent, no memory. No role, no data.

At 2 a.m. during an incident, FlashCart’s on-call engineer opens five console pages: the instances, the load balancer, the database (lesson 272.1), the queue (lesson 273.3), and the billing page. She loses 12 minutes finding the page that shows the problem. Leadership wants one screen for the sale-day war room that shows all five.

The store runs in two Regions, and the payments team owns a separate AWS account with its own queue and database. The payments team will not give anyone access to its account, but it agrees to share its metrics. The CEO also wants a read-only view on a television in the office. The television has no AWS account.

An earlier dashboard that someone built showed a memory graph, but the line stayed flat at zero for the whole sale.

Your challenge:

  • Decide whether to use an automatic dashboard, a custom dashboard, or both, and explain how the dashboard covers two Regions.
  • Describe how to include the payments team’s metrics without giving anyone access to its account.
  • Choose how to show the dashboard on the television, and name two properties of a shared dashboard.

5.1 Automatic and Custom Dashboards

CloudWatch includes automatic dashboards and lets you build your own:

  • Automatic dashboards are preconfigured, service-level views that show the standard metrics for a service. Start with them, then copy useful metrics into a custom dashboard and remove the ones you do not need.
  • Custom dashboards are views that you design. You can create them in the console, with the AWS CLI, or with the PutDashboard API operation.

Widgets can show graphs such as line, stacked area, and number widgets, alarm status, and Logs Insights results (lesson 274.2). A dashboard body is a JSON document that lists the widgets and their positions, so you can copy one dashboard’s JSON as a template for another. To work with dashboards, a user needs the permissions cloudwatch:GetDashboard and cloudwatch:ListDashboards to view them, cloudwatch:PutDashboard to create or modify them, and cloudwatch:DeleteDashboards to delete them. Dashboards can incur a charge beyond a free allowance, so check the pricing page before you create many.

5.2 Cross-Region and Cross-Account Dashboards

Metrics are Regional (tab 1), but a dashboard can show metrics from several Regions in one view. Each widget names the Region of its metrics, so no extra configuration is needed.

To show metrics from other AWS accounts, use CloudWatch cross-account observability:

  • You enable at least one sharing (source) account and at least one monitoring account.
  • In the monitoring account, widgets can use the accountId and region properties to name where each metric comes from.
  • You can mix accounts and Regions inside one widget, for example in one metric math expression.

5.3 Sharing Dashboards

You can share a dashboard with people who do not have access to your AWS account:

  • Share it with specific people by email address, and they sign in with credentials that are generated for them.
  • Share it publicly through a URL, so that anyone with the link can view it without AWS access.

Shared dashboards are read-only, and you can revoke sharing at any time. Dashboards can also use variables and live data, which the CloudWatch documentation describes. Image 5c shows the Share dashboard option in a dashboard’s Actions menu.

6.3 Key Storage and Load Balancer Metrics

6.3.1 Volume Metrics for Block Storage

Amazon EBS publishes one-minute metrics for each volume in the AWS/EBS namespace at no charge, but only while the volume is attached to an instance. It does not report free disk space, which needs the CloudWatch agent (tab 4). Volume types are covered in lesson 271.1.

MetricWhat it tells you
VolumeReadOps, VolumeWriteOpsOperations in the period. Divide the Sum by the seconds in the period for operations per second.
VolumeQueueLengthRequests waiting to complete. A consistently high value means the volume cannot keep up.
VolumeTotalReadTime, VolumeTotalWriteTimeTotal time of completed operations. Divide by the operation count with metric math (tab 3) for average latency.
BurstBalanceBurst credits left on gp2, st1, and sc1 volumes. It falls toward zero under sustained load.

6.3.2 Load Balancer Metrics

Elastic Load Balancing (ELB) publishes metrics every 60 seconds, and only while requests flow through the load balancer (lesson 270.1). The Application Load Balancer uses AWS/ApplicationELB. The Network Load Balancer uses AWS/NetworkELB and has no HTTP response-code metrics.

MetricWhat it tells you
RequestCount, RequestCountPerTargetTraffic volume. Requests per target is a common scaling signal (lesson 270.4).
TargetResponseTimeAverage seconds for a target to respond. Read it with a percentile such as p95 (tab 1).
HTTPCode_ELB_5XX_CountErrors that the load balancer itself returns.
HTTPCode_Target_5XX_CountErrors that the targets, meaning your application, return.
HealthyHostCount, UnHealthyHostCountThe number of healthy and unhealthy targets.

8. Knowledge Check

Answer each question in your own words before you open the model answer.

  1. Explain how a namespace, a metric name, and dimensions together identify a metric. What happens when you add a new dimension to a metric?

    Show the model answer

    A metric is uniquely defined by its namespace, its name, and zero or more dimensions. The namespace keeps metrics from different applications apart, the name says what is measured, and the dimensions describe which resource or category the data belongs to.

    Each unique combination of dimensions is a separate metric. When you add a unique dimension name and value to a metric, you create a new variation of that metric.

  2. A team publishes a custom metric with the dimensions Service and Stage. They ask for statistics using only the Service dimension and receive nothing. Explain why, and name two ways to get the data they want.

    Show the model answer

    CloudWatch treats each published combination of dimensions as a separate metric and returns statistics only for combinations that were published. It does not aggregate across dimensions for custom metrics, so a request with only Service matches no published metric.

    The team can publish an additional metric that uses only the Service dimension, or use the metric math SEARCH function (or a sum across metrics) to find and combine the published combinations.

  3. Compare basic monitoring and detailed monitoring for Amazon EC2. A manager says that enabling detailed monitoring will also show memory usage. Respond to the manager.

    Show the model answer

    Basic monitoring sends instance metrics every five minutes at no charge. Detailed monitoring sends the same metrics every minute and is charged per metric. Both are turned on per instance, and basic monitoring is the default.

    The manager is incorrect. Detailed monitoring changes only the interval. Memory exists inside the operating system, so it needs the CloudWatch agent running on the instance.

  4. Describe what happens to a one-minute metric over 15 months, and name the retention period at each step.

    Show the model answer

    The data stays at one-minute resolution for 15 days. After that, it is aggregated and available only at five-minute resolution until day 63. After day 63, it is aggregated again and available at one-hour resolution for a total of 455 days, which is about 15 months. After that, the data expires.

  5. FlashCart wants per-second response times for its checkout service during a 90-minute flash sale. Which approach should it use, and what limits apply?

    Show the model answer

    It should publish a custom high-resolution metric by setting the storage resolution to 1 in PutMetricData. High resolution is available only for custom metrics, and data points under 60 seconds are kept for three hours, so the team must read the data during or soon after the sale.

    Every PutMetricData call is charged, so publishing every second raises the cost. A high-resolution alarm can use a period of 10, 20, or 30 seconds and costs more than a regular alarm.

  6. Outline the steps to get memory and disk utilization from a Linux Amazon EC2 instance into CloudWatch, and say where the metrics appear.

    Show the model answer

    First, create an IAM role that includes the CloudWatchAgentServerPolicy managed policy, and attach it to the instance. Second, install the CloudWatch agent. Third, create a configuration file that collects memory and disk metrics, using the wizard or by hand. Optionally, store the file in Systems Manager Parameter Store so many instances share it. Finally, start the agent with the configuration.

    The metrics appear in the CWAgent namespace by default, unless the configuration sets a different namespace.

  7. Design a dashboard for the FlashCart sale-day war room. The resources are in two Regions, and the payments team uses a separate AWS account. Which features do you use, and how do you let an executive without an AWS account watch it?

    Show the model answer

    Build a custom dashboard, starting from automatic dashboards for the services involved. Widgets can name different Regions, so one dashboard can show both. For the payments account, set up cross-account observability with a monitoring account and a sharing account, then name the account and Region in each widget.

    Use metric math if a widget needs combined values. To let the executive watch without an AWS account, share the dashboard by email address or through a public link. Shared dashboards are read-only, and sharing can be revoked at any time.

  8. FlashCart wants an error rate that no AWS service publishes, and wants all its CloudWatch metrics in a third-party analytics tool. Explain how to meet both needs.

    Show the model answer

    For the error rate, use metric math to divide a metric that counts failed requests by a metric that counts all requests and multiply by 100. The result is calculated when requested, so no new metric is published.

    For the third-party tool, create a metric stream. Use the quick partner setup if the provider supports it, or a custom setup with an Amazon Data Firehose delivery stream. Include or exclude namespaces with filters to control volume and cost.

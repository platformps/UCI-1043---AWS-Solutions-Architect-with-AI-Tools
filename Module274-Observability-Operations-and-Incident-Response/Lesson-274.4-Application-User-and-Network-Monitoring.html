Application, User, and Network Monitoring

How to monitor an application from the outside and at each layer: Synthetics canaries, real user monitoring, Container, Lambda, Database, and Application Insights, Application Signals, managed Prometheus and Grafana, and network monitoring.

Lesson Overview

The earlier lessons of this module watch resources on Amazon Web Services (AWS) from the inside: metrics, logs, alarms, and audit records. This lesson looks at the application from the outside and at its layers: scripted tests, real users, containers, functions, databases, whole applications, open-source monitoring, and networks. It builds on lessons 274.1, 274.2, and 274.3. In this lesson, you will study:

  • Synthetics Canaries: scripts that act like customers on a schedule, and the canary types.
  • CloudWatch RUM: real user monitoring (RUM), which collects data from actual browser sessions.
  • Container Insights and Lambda Insights: detailed metrics for containers and functions.
  • Database Insights and Application Insights: database load analysis, and automatic monitors for an application stack.
  • Application Signals and X-Ray: automatic instrumentation, service level objectives, and the relationship to tracing.
  • Managed Prometheus and Managed Grafana: managed open-source monitoring, which is on the exam list.
  • Network Monitoring: hybrid network probes, internet health, and connection flow monitoring.
  • Where Monitoring Tools Fit Across AWS Services: the layers of an application, the tool for each layer, and the alarms that go with them.
  • Comparison and Scenarios: comparison tables and a cheat sheet for the AWS Certified Solutions Architect – Associate (SAA-C03) exam.
  • Knowledge Check: open-ended questions with model answers.

Learning Objectives

By the end of this lesson, you will be able to:

  1. Define canary, app monitor, service level indicator, service level objective, and probe.
  2. Describe what CloudWatch Synthetics and CloudWatch RUM each measure, and where each one runs.
  3. Explain why standard metrics are not enough for containers, functions, and databases.
  4. Compare scripted monitoring with real user monitoring.
  5. Match each CloudWatch Insights feature to the kind of resource that it covers.
  6. Differentiate CloudWatch from Amazon Managed Service for Prometheus and Amazon Managed Grafana.
  7. Apply a canary, an app monitor, or an Insights feature to a described monitoring problem.
  8. Evaluate which monitoring tool and which alarm meet a requirement for the user, application, container, function, database, or network layer.
  9. Design a monitoring setup that covers every layer of an application, from the user to the database.

1. Synthetics Canaries

Problem Statement

At 3:10 a.m. on Saturday, FlashCart’s checkout page returns an error to every customer for 26 minutes. Every graph from lessons 274.1 and 274.2 stays green: the instances are healthy, central processing unit (CPU) use is normal, the load balancer shows healthy targets, and no alarm fires. The team learns about the outage at 3:36 a.m., when a customer in Europe posts about it. Almost nobody shops at that hour, so there was no traffic to produce errors that an alarm could count.

The cause turns out to be a login step that depends on a third-party service. The web servers answered every request, so the load balancer saw nothing wrong. The CTO asks for a “robot customer” that signs in, adds a product to the cart, and starts checkout every minute, from outside the servers.

The team also wants three more checks: a nightly scan for broken links on the product pages, an alert when the page layout changes after a release, and a check of the private application programming interface (API) from lesson 273.2. An engineer asks whether the Route 53 health checks from lesson 269.9 already do all of this.

Your challenge:

  • Choose the CloudWatch feature that behaves like a customer on a schedule, and explain why metrics and alarms did not catch the outage.
  • Choose the canary type for each of the four checks: the checkout flow, the broken links, the layout change, and the private API.
  • Describe what a canary produces, where the results and screenshots go, and which metric an alarm should watch.
  • Explain how a canary differs from a Route 53 health check.

1.1 What a Canary Is

Amazon CloudWatch Synthetics runs canaries: configurable scripts that run on a schedule to test your endpoints and APIs. A canary follows the same routes and performs the same actions as a customer, so it can find a broken flow before a customer does. Because it runs on a schedule, it works even when nobody is using the site, for example at 3 a.m. CloudWatch Synthetics runs each canary script on AWS Lambda behind the scenes.

1.2 Canary Blueprints

You can write a canary script yourself, in Node.js or Python, or start from a blueprint:

API canaryCalls web APIs. A multi-step canary can test several APIs, as HTTP steps, in one run. It can also test a private API in Amazon API Gateway (lesson 273.2).The private order API answers.

1.3 Schedules, Results, and Alarms

  • Schedule: run a canary at a regular rate, such as every minute, or at set times with a cron expression.
  • Results: a canary records a pass or fail result, per-step results, and artifacts such as screenshots, logs, and HTTP Archive (HAR) files. You choose the Amazon Simple Storage Service (Amazon S3) bucket for the artifacts (lesson 271.2), and you set how long CloudWatch keeps the run data.
  • Metrics: canaries publish metrics to CloudWatch in the CloudWatchSynthetics namespace, including SuccessPercent and Duration.
  • Alarms: alarm on SuccessPercent (lesson 274.2, tab 6) so that a failed run notifies the team through Amazon Simple Notification Service (Amazon SNS) or EventBridge.

FeatureWhat it testsChoose it when

Exam trap

A canary tests on a schedule and needs no real traffic, so it can catch an outage when nobody is online. It is proactive. Real user monitoring (tab 2) is the opposite: it measures actual users and sees nothing when nobody is there. Do not choose RUM for a question that says “detect a failure when no customers are using the site.”

Memory hook

A canary is a robot customer that never sleeps.

2. CloudWatch RUM

Problem Statement

After the canaries are in place, FlashCart still gets complaints that the product page “feels slow” on phones in Brazil, and a release causes a JavaScript error in one browser version. The canaries pass, because they run from one place on one fast connection. The operations team cannot see how real customers experience the site: which browsers, which devices, which pages, and how long a page takes to load.

Marketing wants page load times by device and browser, and developers want the JavaScript errors with their stack traces. The privacy team agrees to collect data from only a share of the sessions, and it does not want customers’ personal data in the monitoring. The finance team asks what will drive the cost, after a test month produced an unexpected bill.

The web developers also ask how a browser, which has no AWS credentials, is allowed to send data to AWS, and where the collected data is kept.

Your challenge:

  • Choose the CloudWatch feature that measures what real users experience, and explain how it differs from the canaries.
  • List the kinds of data that the feature can collect, and which of them can raise the bill.
  • Explain how to limit the amount of data collected, and how the browser is authorized to send it (lesson 273.2).
  • Describe where the data is stored and for how long, and how a slow page can be linked to a backend trace (lesson 274.6).

2.1 What Real User Monitoring Does

CloudWatch RUM performs real user monitoring (RUM). It collects client-side data about your web application from actual user sessions in near real time. The data includes page load times, client-side errors, and user behavior, and you can see it in total or broken down by the browsers and devices that your customers use.

2.2 How It Works

  • App monitor: you create an app monitor for your application. RUM generates a JavaScript snippet, or an installable module, that you add to your pages. The snippet loads the RUM web client.
  • What it collects: you choose performance telemetry, which covers page and resource load times and Core Web Vitals, JavaScript errors, and HTTP errors. More collected data means more charges.
  • Sampling: you set the percentage of user sessions to monitor. A lower percentage gives less data and a lower bill.
  • Authorization: a browser has no AWS credentials, so an Amazon Cognito identity pool (lesson 273.2) authorizes it to send data. You can use a new or existing pool, or another identity provider.
  • Cookies: if you allow the web client to set cookies, RUM can collect randomly generated user IDs and session IDs.
  • Storage: RUM events go to a CloudWatch Logs log group. By default it keeps the data for 30 days, and you can change the retention (lesson 274.2, tab 1).
  • Tracing: you can turn on AWS X-Ray tracing for the sampled sessions. RUM then adds a trace header to the allowed HTTP requests, so a slow page links to the backend trace (lesson 274.6).
  • Cost: you pay for every RUM event that CloudWatch receives, such as a page view, a JavaScript error, or an HTTP error.

If you load the web client from a content delivery network (CDN) instead of installing it as a module, ad blockers can block it.

2.3 Canaries and RUM Together

QuestionSynthetics canaryCloudWatch RUM

Exam trap

RUM needs a snippet in the web application and collects data only from sampled real sessions. Without an authorization setup, such as a Cognito identity pool, the browser cannot send data. RUM cannot detect an outage at 3 a.m. with no users, and it is charged for each event.

The canary is a robot user. RUM is the real user.

3. Container Insights and Lambda Insights

Problem Statement

FlashCart’s background workers run as three services on Amazon Elastic Container Service (Amazon ECS) with AWS Fargate (lesson 273.5). One of them leaks memory and is restarted every few hours. The standard CloudWatch graphs from lesson 274.1 show only service-level CPU and memory, so the team cannot tell which task or which container is the problem, or how much memory each container asks for compared with what it uses.

The order-confirmation function from lesson 273.1 has a different problem. It is set to 512 megabytes of memory, and customers complain about slow first requests after quiet periods. The standard Lambda metrics show invocations, errors, and duration. They do not show how much memory the function actually uses, how much processor time it consumes, or how long its cold starts take.

The finance team asks the team not to turn on extra monitoring everywhere, because custom metrics and extra logs cost money.

Your challenge:

  • Choose the feature for the container problem, and name the level of detail that it adds to the standard metrics.
  • Choose the feature for the function problem, and name three things it shows that the standard metrics do not.
  • Describe what must be set up for each feature, and where its metrics appear.
  • Decide where to turn the features on, and explain why.

3.1 Container Insights

CloudWatch Container Insights collects, aggregates, and summarizes metrics and logs from containerized applications. It works for Amazon ECS, Amazon Elastic Kubernetes Service (Amazon EKS), Kubernetes on Amazon Elastic Compute Cloud (Amazon EC2), and AWS Fargate. On Amazon EKS and Kubernetes, it uses a containerized version of the CloudWatch agent (lesson 274.1, tab 4) to discover the containers.

  • What it adds: more metrics than the standard Amazon ECS metrics, including network, storage, and ephemeral storage metrics, and a link between metrics and log entries in CloudWatch Logs.
  • Enhanced observability: an enhanced mode gives higher granularity at the task and container levels, so you can find the one container that uses too much or too little.
  • Where the metrics appear: for Amazon ECS, in the ECS/ContainerInsights namespace, with metrics such as CpuUtilized, MemoryUtilized, and ContainerInstanceCount.
  • Setup: you turn it on for each cluster. The metrics do not appear until setup is complete.
aws ecs update-cluster-settings \
  --cluster flashcart-workers \
  --settings name=containerInsights,value=enhanced

Confirm the setting name and values in the Amazon ECS documentation before you use the command.

3.2 Lambda Insights

CloudWatch Lambda Insights is a monitoring and troubleshooting solution for serverless applications that run on AWS Lambda (lesson 273.1). It collects and summarizes system-level metrics, including processor time, memory, disk, and network, and diagnostic information such as cold starts and Lambda worker shutdowns.

  • How you turn it on: Lambda Insights is provided as a Lambda extension layer that you add to the function.
  • Where the metrics appear: in the LambdaInsights namespace, with metrics such as memory_utilization, cpu_total_time, and init_duration (the time spent in the initialization phase, which shows cold starts).
  • Typical use: compare the memory that a function uses with the memory that it is set to, and right-size it. Lambda gives a function processor power in proportion to its memory.

3.3 Standard Metrics and Insights

Insights features are not automatic. Container Insights must be turned on for the cluster, and its metrics do not appear before setup is complete. Lambda Insights needs the extension layer on the function. Both produce extra metrics and logs that are charged, so turn them on where the detail is needed, not everywhere.

4. Database Insights and Application Insights

Problem Statement

Every weekday at 9 a.m., the Amazon Relational Database Service (Amazon RDS) database from lesson 272.1 slows down after a new reporting feature starts. CPU rises to 70 percent and the number of connections grows, but the team cannot tell which SQL statements or which waits cause the load. An engineer says that the old tool for this, Performance Insights, “is gone,” and a study note still tells her to use it.

The company also runs an older warehouse application on Amazon EC2. It is a .NET application on a web server with a Microsoft SQL Server database, and nobody monitors it beyond CPU. When it fails, the team learns about it from the warehouse staff. The security lead wants monitors and alarms for it that are set up automatically and that open a ticket in Systems Manager (lesson 268.8) when something goes wrong.

The CTO also asks which of the “Insights” features in CloudWatch apply to which kind of resource, because the names are confusing.

Your challenge:

  • Choose the CloudWatch feature for the slow database, and explain what happened to Performance Insights.
  • Name the two modes of that feature and what the second one adds.
  • Choose the feature that sets up monitors for the warehouse application automatically, and name what it creates when it finds a problem.
  • Match each Insights feature to the kind of resource that it covers.

4.1 Database Insights

CloudWatch Database Insights helps you monitor database load across your fleet of databases and analyze and troubleshoot performance at scale. It shows the database load and lets you slice it by waits, SQL statements, hosts, or users (lesson 272.1, tab 9).

  • It replaced Performance Insights. AWS ended Performance Insights on July 31, 2026, and the Performance Insights console now redirects to Database Insights. Older questions and documents may still use the old name.
  • Standard mode keeps the experience and pricing of Performance Insights, including flexible retention periods of 1 to 24 months.
  • Advanced mode adds fleet-level monitoring, lock diagnostics, execution plan capture, and on-demand analysis.

4.2 Application Insights

CloudWatch Application Insights helps you monitor applications that use Amazon EC2 instances and other resources. It identifies and sets up key metrics, logs, and alarms across the application’s resources and technology stack, for example a Microsoft SQL Server database, web servers on Internet Information Services (IIS), the operating system, load balancers, and queues.

  • It continuously monitors the metrics and logs to detect and correlate anomalies and errors.
  • It sets up dynamic alarms that update based on the anomalies found in the previous two weeks.
  • When it detects a problem, it generates CloudWatch events that you can use for notifications or actions (lesson 273.3), and it creates an OpsItem in Systems Manager OpsCenter (lesson 268.8).
  • It integrates with AWS Launch Wizard, so that a SQL Server high-availability deployment can have monitoring set up in one step.

5. Application Signals and X-Ray

Problem Statement

FlashCart’s store is now a set of services: cart, checkout, payments, and inventory, written in Java and Python and running on Amazon ECS and Amazon EKS (lesson 273.5). During a sale, the AWS X-Ray service map (lesson 274.6) shows that payments is slow, but the business wants more than a map. The product owner wants a promise that checkout stays available 99.9 percent of the time, and that 99 percent of payment calls finish in under one second.

The developers do not want to add monitoring code to every service. They also want the canaries and the real-user data to appear in the same picture as the services, so that one view shows a slow page, the service behind it, and its dependencies.

An engineer asks whether this replaces AWS X-Ray, and whether the exam covers it.

Your challenge:

  • Choose the feature that collects call volume, latency, faults, and errors automatically, and name the languages and platforms it supports.
  • Explain how to express the product owner’s promises, using the terms service level indicator and service level objective.
  • Describe how this feature relates to X-Ray, CloudWatch RUM, and Synthetics.
  • Say how much of the exam this feature is likely to cover, and why.

5.1 What Application Signals Does

CloudWatch Application Signals helps you monitor and improve application performance. It automatically instruments your applications and collects metrics and traces, and it shows key signals such as call volume, availability, latency, faults, and errors, without you building the dashboards.

  • Services list and application map: a summary of all services, with the highest fault rate or latency first, and a map of the relationships between clients, canaries, services, and dependencies.
  • Service level objectives (SLOs): you create and track objectives for CloudWatch metrics, including the standard application metrics that Application Signals collects, and you can alarm on them.
  • Languages: Java, Python, Node.js, and .NET.
  • Platforms: supported and tested on Amazon EKS, Amazon ECS, and Amazon EC2, with support for Lambda as well. On architectures other than Amazon EKS, you supply the names of services and environments.
  • How it collects: auto-instrumentation based on OpenTelemetry, with the CloudWatch agent (lesson 274.1, tab 4) and the AWS Distro for OpenTelemetry receiving the data.
  • Cost: Application Signals is charged. Check the pricing page.

5.2 Service Level Indicators and Objectives

TermMeaningFlashCart example
Service level indicator (SLI)A measurement of how a service behaves.The share of checkout calls that succeed.
Service level objective (SLO)A target for an indicator over a period.99.9 percent of checkout calls succeed, and 99 percent of payment calls finish in under one second.

The gap between 100 percent and the objective is the error budget: the amount of failure that the team can accept before it breaks its promise.

5.3 Relationship to X-Ray, RUM, and Synthetics

  • AWS X-Ray traces requests across services and shows the service map (lesson 274.6). Application Signals adds standard application metrics and SLOs on top, and its traces are stored in X-Ray. The older CloudWatch ServiceLens console also links traces, metrics, and logs.
  • CloudWatch RUM and Synthetics work without Application Signals. When you use them together, client pages and canaries appear in the Application Signals maps and dashboards.
Exam scope

Application Signals is not named in the SAA-C03 exam guide’s service list. Know what it is, but expect the exam to ask about X-Ray, CloudWatch metrics and alarms, and the other services in this module.

Exam trap

Application Signals does not replace X-Ray. It builds on traces and adds metrics and objectives. Also, it does not need code changes in the services, but you do have to enable it, and it supports only certain languages and platforms.

Memory hook

The indicator is the measurement. The objective is the promise.

6. Managed Prometheus and Managed Grafana

Problem Statement

FlashCart’s platform team runs 60 microservices on Amazon EKS (lesson 273.5). The services already expose Prometheus metrics, the team’s dashboards use the Prometheus query language, and the developers like Grafana. Running the Prometheus servers is a burden: storage fills up, a server restarts during a sale, and nobody wants to be on call for it.

The team wants to stop running its own Prometheus servers and Grafana, but keep the queries and dashboards that it has. It also wants one Grafana view that combines the Prometheus metrics with CloudWatch metrics, X-Ray traces, and the OpenSearch data from lesson 272.14. The security team wants people to sign in with the company’s single sign-on, not with separate accounts.

A product manager asks why the team does not simply use CloudWatch for everything.

Your challenge:

  • Choose the two managed services that replace the Prometheus servers and the Grafana installation.
  • Describe how the metrics get into the Prometheus service, with and without installing software in the cluster.
  • Explain how people sign in to the dashboards, and which data sources the dashboards can combine.
  • Answer the product manager: when is CloudWatch enough, and when are the managed open-source services the better choice?

6.1 Amazon Managed Service for Prometheus

Amazon Managed Service for Prometheus is a fully managed, Prometheus-compatible monitoring service for container metrics. You keep the Prometheus ecosystem, but AWS runs the storage, the scaling, and the availability.

  • Workspace: you create a workspace, which is a Prometheus instance that stores and serves your metrics.
  • Ingestion: it has a remote write-compatible API that ingests metrics from OpenTelemetry collectors, Prometheus libraries, and existing Prometheus servers. It does not scrape your applications by itself.
  • No agent on Amazon EKS: the Managed Service for Prometheus collector is an agentless scraper that collects Prometheus metrics from Amazon EKS applications and infrastructure, so you do not build or run a collector.
  • Queries: you query with the Prometheus Query Language (PromQL), so existing queries and recording rules keep working.
  • Security: access for ingesting and querying uses AWS Identity and Access Management (IAM).

6.2 Amazon Managed Grafana

Amazon Managed Grafana is a fully managed data visualization service for open-source Grafana. You create dashboards from several data sources in one place.

  • Data sources: Amazon CloudWatch, Amazon OpenSearch Service (lesson 272.14), AWS X-Ray, Amazon Timestream (lesson 272.9), AWS IoT SiteWise, and Amazon Managed Service for Prometheus.
  • Sign-in: people use Security Assertion Markup Language (SAML) or AWS IAM Identity Center, and you make at least one user an administrator of the workspace.
  • With Prometheus: Managed Grafana connects to the Prometheus workspace with IAM authentication, using a plugin that is included.

6.3 CloudWatch or Managed Open-Source Monitoring

ChooseWhen
CloudWatch with Container Insights (tab 3)You want AWS-native alarms, dashboards, and logs in one place, and you are not tied to Prometheus.
Managed Service for PrometheusYou have a mature Prometheus deployment, or developers who use PromQL, and you want AWS to run it.
Managed GrafanaYou want Grafana dashboards that combine data from CloudWatch, X-Ray, OpenSearch Service, and Prometheus.

If you do not plan to use CloudWatch for metrics, run your own Prometheus server with remote write to the managed workspace, and use Grafana for dashboards.

Exam trap

Managed Service for Prometheus stores and queries metrics only. It does not store logs or traces, and it does not scrape by itself unless you use the managed collector for Amazon EKS or your own collector. Managed Grafana shows data but does not store your metrics.

Memory hook

Prometheus stores the metrics. Grafana shows them. AWS runs both.

7. Network Monitoring

Problem Statement

FlashCart’s new warehouse connects to AWS through the Site-to-Site virtual private network (VPN) from lesson 269.6, with a Direct Connect link planned. For three weeks, label printing at the warehouse is slow for a few minutes at a time, then fine again. The tunnels never go down, so the TunnelState alarm from lesson 274.1 stays green. The team cannot tell whether the problem is in the AWS part of the network, in the internet provider’s part, or in the warehouse router, and it does not want to install software on the warehouse server.

Separately, customers in Brazil reach the store through the internet, and some of them see slow pages. The team wants to know whether the internet path to those customers is unhealthy, and whether a different Region or Amazon CloudFront (lesson 269.7) would help. An engineer also wants to see which of the instances in the cluster have the most troubled Transmission Control Protocol (TCP) connections.

Your challenge:

  • Choose the feature that measures delay and packet loss on the hybrid link, and describe how it measures them.
  • Explain how the team can tell whether a problem is on the AWS side of a Direct Connect path.
  • Choose the feature for the internet path to customers, and say what it can suggest.
  • Choose the feature that shows troubled TCP connections between instances, and compare it with Amazon Virtual Private Cloud (Amazon VPC) flow logs from lesson 269.4.

7.1 CloudWatch Network Monitoring

CloudWatch has three network and internet monitoring capabilities: Network Synthetic Monitor, Internet Monitor, and Network Flow Monitor.

FeatureWhat it measuresHow it worksRelated lesson
Network Synthetic MonitorRound-trip time and packet loss between AWS and on-premises destinations.Probes that you define from Amazon Virtual Private Cloud (Amazon VPC) subnets to on-premises IP addresses, over Direct Connect or Site-to-Site VPN. It is agentless and fully managed.Lesson 269.6
Internet MonitorThe health of the internet path between your application and its clients.It shows a global view of traffic patterns and health events, alerts you to internet problems that affect your clients, and suggests improvements such as using CloudFront or other Regions.Lesson 269.7

7.2 How Network Synthetic Monitor Works

  • A probe is a combination of a source subnet, a destination IP address, a packet size, and a protocol and port.
  • Probes use the Internet Control Message Protocol (ICMP) or the Transmission Control Protocol (TCP). An ICMP probe sends an echo request and expects an echo reply. A TCP probe sends a SYN packet to a port and expects a SYN and ACK packet back.
  • The monitor calculates round-trip time and packet loss and publishes them to CloudWatch metrics, so you can build dashboards and alarms, and set a latency and packet loss threshold for each monitor.
  • For paths through Direct Connect, it also publishes a network health indicator (NHI) that shows whether an issue is on the AWS-controlled part of the path.

The VPN tunnel metric from lesson 274.1 shows whether a tunnel is up. A monitor shows how well it carries traffic.

Exam scope

None of the three network monitoring features is named in the SAA-C03 exam guide’s service list. Know what each one measures, and use it as the answer when a question describes a “grey failure,” internet health for clients, or TCP flow statistics.

Exam trap

A VPN tunnel that is “up” can still lose packets. The tunnel metric will not show that, but a Network Synthetic Monitor probe will. Do not confuse Network Flow Monitor, which uses agents and reads TCP statistics, with VPC flow logs, which record accepted and rejected traffic.

Memory hook

Up is not the same as healthy. Probes measure the health of the path.

10. Knowledge Check

Answer each question in your own words before you open the model answer.

  1. Compare a Synthetics canary and CloudWatch RUM. Which one detects an outage at 3 a.m. with no customers, and why?

    Show the model answer

    A canary is a script that runs on a schedule and tests a flow from outside, so it works with no traffic. RUM collects data from real user sessions through a web client in your pages, so it sees nothing when nobody is on the site.

    The canary detects the 3 a.m. outage. RUM shows what real customers experience during the day, such as slow pages by browser and device.

  2. Name four canary blueprints, and say what each one tests.

    Show the model answer

    The heartbeat monitor loads a URL and confirms that it is up. The API canary calls web APIs, including private APIs, in one or more steps. The broken link checker tests the links on a page and finds 404 errors, invalid host names, and bad URLs. Visual monitoring compares screenshots with a baseline run and fails when the difference is above a threshold.

    The canary recorder and the GUI workflow blueprint cover recorded browser actions and multi-step browser flows.

  3. Describe how a RUM app monitor collects data from a browser, who authorizes the browser, and where the data is stored.

    Show the model answer

    You create an app monitor and add its JavaScript snippet, or module, to your pages. The web client collects the performance, JavaScript error, and HTTP error data that you choose, from the share of sessions that you set.

    An Amazon Cognito identity pool authorizes the browser to send data. The data goes to a CloudWatch Logs log group that keeps it for 30 days by default, and you pay for each RUM event.

  4. Why are standard metrics not enough for containers and functions? Name the feature that fills the gap for each.

    Show the model answer

    Standard metrics for Amazon ECS show service-level CPU and memory, and standard Lambda metrics show invocations, errors, and duration. They do not show which task or container is the problem, or how much memory and processor time a function really uses.

    Container Insights adds task-level and container-level metrics, and links to logs. Lambda Insights adds memory use, processor time, and initialization time, and it is added to a function as an extension layer.

  5. A team still uses the name Performance Insights. What do you tell them?

    Show the model answer

    AWS ended Performance Insights on July 31, 2026, and its console redirects to CloudWatch Database Insights.

    Database Insights has a Standard mode, which keeps the earlier retention and pricing, and an Advanced mode, which adds fleet-level monitoring, lock diagnostics, execution plans, and on-demand analysis.

  6. Explain service level indicators and objectives, and say which CloudWatch feature manages them.

    Show the model answer

    A service level indicator measures how a service behaves, such as the share of successful calls. A service level objective is a target for that indicator, such as 99.9 percent availability. The gap between the target and 100 percent is the error budget.

    CloudWatch Application Signals collects standard application metrics automatically and lets you create and track objectives and alarm on them.

  7. Compare CloudWatch with Amazon Managed Service for Prometheus and Amazon Managed Grafana. When would you choose the managed open-source services?

    Show the model answer

    CloudWatch gives AWS-native metrics, logs, alarms, and dashboards in one place. Managed Service for Prometheus is a Prometheus-compatible store with PromQL that accepts remote write, and Managed Grafana builds dashboards over several data sources.

    Choose the managed open-source services when you already run Prometheus and Grafana and want AWS to operate them while you keep your queries and dashboards.

  8. A VPN tunnel shows as up, but warehouse users see slow printing. Which feature do you use, and how does it measure the problem?

    Show the model answer

    Use CloudWatch Network Synthetic Monitor. You define probes from Amazon VPC subnets to the on-premises IP address, using ICMP or TCP, with no agents to install.

    The monitor publishes round-trip time and packet loss to CloudWatch, where you can alarm on thresholds. For Direct Connect paths, its network health indicator shows whether the problem is on the AWS side.

  9. Design monitoring for every layer of the FlashCart store, from the user to the database, and name the alarm for each tool.

    Show the model answer

    For users, use a canary every minute for the checkout flow, with an alarm on SuccessPercent, and RUM with a sample of sessions for real experience. For the application, use Application Signals with service level objectives, and X-Ray for traces.

    For compute, use Container Insights for the containers and Lambda Insights for critical functions, and alarm on memory and CPU. For data, use Database Insights. For the hybrid link, use Network Synthetic Monitor with packet loss and latency thresholds. Send every alarm to Amazon SNS or EventBridge.

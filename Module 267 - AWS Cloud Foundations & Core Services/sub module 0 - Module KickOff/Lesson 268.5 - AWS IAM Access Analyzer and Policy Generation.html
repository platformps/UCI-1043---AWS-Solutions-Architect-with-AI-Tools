AWS IAM Access Analyzer and Policy Generation

Find unintended and unused access, audit IAM credentials, and generate least-privilege policies.

1. AWS IAM Access Analyzer Overview

Problem Statement

AnyCorp, a growing fintech firm, runs workloads in several AWS accounts. During a routine audit, the chief information security officer (CISO) asks the cloud security engineer three questions. Can anyone outside the organization reach the Amazon Simple Storage Service (Amazon S3) buckets that hold financial records or customer personally identifiable information (PII)? Which IAM roles and credentials have gone unused for more than 90 days? How can the team replace broad wildcard permissions with policies that match what services actually use?

The engineer needs one AWS capability that helps with all three questions. This tab introduces it.

1.1 What IAM Access Analyzer Is

IAM Access Analyzer is a security capability within IAM. It helps organizations identify, verify, and refine access to AWS resources and IAM permissions.

The six capabilities of IAM Access Analyzer.
CapabilityWhat it doesTab
External access analyzersIdentify resources in your organization and accounts that are shared with an external entity.2
Internal access analyzersIdentify which principals inside your organization or account can access selected resources.3
Unused access analyzersIdentify unused access in your organization and accounts.3
Policy validationValidates IAM policies against policy grammar and AWS best practices.5
Custom policy checksValidate IAM policies against security standards that you specify.5
Policy generationGenerates IAM policies from access activity in your CloudTrail logs.5

1.2 Questions It Helps Answer

IAM Access Analyzer helps security administrators answer questions such as:

  • Who can access my AWS resources?
  • Are any resources accessible from outside my AWS account or organization?
  • Which internal identities can access critical resources?
  • Are users or roles keeping permissions that they no longer use?
  • Do my IAM policies follow AWS policy grammar and security best practices?

1.3 How It Works

IAM Access Analyzer uses logic-based automated reasoning to analyze policies and determine possible access paths.

1.3.1 Findings Show Possible Access

For external access, IAM Access Analyzer analyzes resource-based policies and generates a finding when a policy grants access to a principal outside the zone of trust. A finding means that access is possible based on the policy configuration. It does not mean that the external principal has actually accessed the resource.

After the first analysis, the analyzer analyzes policies periodically. When you add or change a policy, it analyzes the new or updated policy within about 30 minutes.

1.3.2 Example Questions It Can Answer

For external access, IAM Access Analyzer can help determine:

  • Whether an S3 bucket is accessible publicly or from another AWS account.
  • Whether a principal outside the trusted account or organization can assume an IAM role.
  • Whether an external principal can access an AWS Key Management Service (AWS KMS) key.
  • Whether an AWS Lambda resource-based policy permits external access.
  • Whether an Amazon Simple Queue Service (Amazon SQS) queue is accessible outside the trusted environment.
  • Whether an AWS Secrets Manager secret is shared with an external principal.

Memory Hook

IAM Access Analyzer reads policies to find possible access. AWS CloudTrail records what actually happened.

Exam Trap

A finding is not proof of use. If a question asks which resources can be accessed from outside the organization, the answer is IAM Access Analyzer. If it asks who actually accessed a resource, the answer is CloudTrail.

Trigger 1: “Which resources are shared with an external AWS account or with the public?”→ IAM Access Analyzer (external access analyzer)

Trigger 2: “Identify unintended access to resources by analyzing resource-based policies”→ IAM Access Analyzer

2. Zone of Trust and External Access Analyzers

Problem Statement

AnyCorp keeps financial records and customer data in S3 buckets across many accounts. The CISO wants to know whether any bucket can be reached from outside the organization or from the public internet. The team cannot review every bucket policy by hand.

2.1 The Zone of Trust

When you enable IAM Access Analyzer for external access, you create an analyzer for your entire AWS Organization or for one account. The organization or account that you choose is the zone of trust for that analyzer. Access by principals inside the zone of trust is trusted. Access by principals outside it can produce a finding.

Account-level and organization-level zones of trust.
Zone of trustTrustedA finding appears when
Account levelPrincipals in that one AWS accountAccess comes from outside that account ID
Organization levelPrincipals in every account of the AWS OrganizationAccess is granted to a principal outside the organization

Important to Know

The zone of trust does not grant or deny access. It sets the boundary that IAM Access Analyzer uses when it reports external access.

2.2 External Access Analysis

“Who outside my trusted environment can access this resource?”

External access analysis evaluates supported resource-based policies and access controls. IAM Access Analyzer can generate a finding when a policy grants access to:

  • Another AWS account outside your zone of trust.
  • The public, for example through a wildcard principal ("*").
  • A principal outside your AWS Organization.
  • Principals that belong to an external organization or organizational unit, depending on the policy and your zone of trust.

AWS describes an external entity as another AWS account, a root user, an IAM user or role, a federated user, an anonymous user, or another entity that you can use to create a filter.

2.2.1 Example: A Public Bucket Policy

This example bucket policy is written in JavaScript Object Notation (JSON).

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Principal": "*",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::mybucket/*"
    }
  ]
}

The wildcard principal ("*") gives every principal read access to the objects in mybucket. IAM Access Analyzer reports this policy as a finding for public access.

2.3 Supported Resources

For external access, IAM Access Analyzer analyzes these resource types. This list was checked against AWS documentation on November 13, 2026; AWS adds resource types over time.

  • Amazon S3 buckets and directory buckets.
  • IAM roles.
  • AWS KMS keys.
  • AWS Lambda functions and layers.
  • Amazon SQS queues.
  • AWS Secrets Manager secrets.
  • Amazon Simple Notification Service (Amazon SNS) topics.
  • Amazon Elastic Block Store (Amazon EBS) volume snapshots.
  • Amazon Relational Database Service (Amazon RDS) DB snapshots and DB cluster snapshots.
  • Amazon Elastic Container Registry (Amazon ECR) repositories.
  • Amazon Elastic File System (Amazon EFS) file systems.
  • Amazon DynamoDB tables and streams.

2.4 Working With Findings

You can view findings in the IAM console. For each finding, decide whether the access is intended.

How to respond to an external access finding.
ActionWhen to use itWhat happens
RemediateThe access is unintended.Modify or remove the policy statement that grants the access. For S3 buckets, change the bucket permissions in the Amazon S3 console. For IAM roles, change the trust policy.
ArchiveThe access is intended and approved.The finding is marked as intentional. Archived findings remain available for later review and can be unarchived.
ResolvedYou changed the policy.IAM Access Analyzer scans the resource again. If the access is gone, the finding status changes to Resolved. This can take up to 30 minutes for external access analyzers.

2.5 Regional Scope

For external access, IAM Access Analyzer analyzes only policies applied to resources in the Region where the analyzer is enabled. To monitor all supported resources, create an external access analyzer in each Region where you use them.

Exam-Style Question 1 (written for this course)

AnyCorp has 30 accounts in one AWS Organization. The security team must find S3 buckets and IAM roles that principals outside the organization can access, without reviewing policies by hand and with the least operational effort. Which solution meets these requirements?

  1. Generate the IAM credentials report in every account and search it for external account IDs.
  2. Review AWS CloudTrail logs for GetObject requests that come from unknown accounts.
  3. Create an external access analyzer that uses the organization as the zone of trust in each Region where AnyCorp uses supported resources.
  4. Create an unused access analyzer with a 90-day tracking period.
Show the answer

Correct answer: C. An external access analyzer analyzes resource-based policies and reports access to principals outside the zone of trust. Using the organization as the zone of trust keeps sharing between AnyCorp’s own accounts from producing findings.

  • Sharing between two accounts in the same organization does not produce an external access finding when the organization is the zone of trust. Sharing with an account outside the organization can.

3. Internal and Unused Access Analyzers

Problem Statement

AnyCorp’s CISO has two follow-up concerns. Some IAM roles and credentials were created for projects that have ended, and nobody is sure which ones are still needed. The CISO also wants to confirm that only the intended internal identities can reach the bucket that holds financial records.

3.1 Internal Access Analyzer

“Who inside my organization can access this resource?”

For selected business-critical resources, an internal access analyzer helps you identify which principals within your organization or account have access to them. This analysis supports least privilege by checking that your specified resources can be accessed only by the intended principals.

Internal access analysis helps you:

  • Determine which IAM users or roles within your account or organization can access your specified resources.
  • Understand the access paths between principals and resources.
  • Verify that your access controls work as intended.
  • Identify and remediate unintended access within your organization.

An internal access analyzer analyzes these resource types: Amazon S3 buckets and directory buckets, Amazon RDS DB snapshots and DB cluster snapshots, and Amazon DynamoDB tables and streams.

3.2 Unused Access Analyzer

“What access are we granting that is no longer being used?”

An unused access analyzer continuously monitors all IAM roles and users in your organization or accounts and generates findings for unused access. The findings cover:

  • Unused IAM roles.
  • Unused access keys for IAM users.
  • Unused passwords for IAM users.
  • Unused services and actions for roles and users that are otherwise active.

3.2.1 Tracking Period

When you create an unused access analyzer, you set a tracking period from 1 to 365 days. With a tracking period of 90 days, the analyzer generates findings for access that shows no use in that period. It evaluates only permissions that existed for the entire period.

3.2.2 Resolving Unused Access Findings

How IAM Access Analyzer recommends resolving unused access findings.
Finding typeRecommended step
Unused roleDelete the unused IAM role.
Unused access keyDeactivate or delete the unused access key.
Unused passwordDelete the unused password for the IAM user.
Unused permissionsReplace the existing permissions policy with the recommended policy, then remove the existing policy.

3.2.3 Scope and Cost Notes

  • Service-linked roles are not analyzed for unused access.
  • Unused access findings do not change by Region, so you do not need an unused access analyzer in each Region.
  • AWS charges for unused access analysis by the number of IAM roles and users analyzed per analyzer per month. Analyzers in several Regions are billed separately. Check the pricing page for current prices.

3.3 Comparing the Three Analyzers

The three IAM Access Analyzer analyzers compared.
AnalyzerQuestion it answersWhat it reports
External accessWho outside my zone of trust can access this resource?Resources shared with an external entity
Internal accessWhich principals inside my organization can access selected resources?Internal access to the resources that you select
Unused accessWhat access are we granting that is no longer used?Unused roles, access keys, passwords, and permissions

Exam Trap

  • Do not confuse internal and unused access. Internal access shows who inside can reach a resource. Unused access shows permissions and credentials that nobody has used.
  • Only external access analyzers need to exist in every Region.

Memory Hook

Internal asks who inside can reach it. Unused asks what nobody is using.

SAA-C03 Keyword Triggers

Trigger 2: “Find unused permissions so that you can move toward least privilege”→ Unused access analyzer (unused permissions findings with recommended policies)

Trigger 3: “Verify which principals inside the organization can access a sensitive S3 bucket”→ Internal access analyzer

4. IAM Credentials Report

Problem Statement

AnyCorp’s external auditor asks for a single file that lists every IAM user in an account and shows the state of each user’s password, access keys, and multi-factor authentication (MFA) device.

4.1 What the IAM Credentials Report Is

The IAM credentials report is an account-level inventory of the IAM users in an AWS account and the status of their credentials. You download it as a comma-separated values (CSV) file.

  • Scope: the IAM users in one account, plus the account root user.
  • Contents: passwords, the first two access keys per user, MFA devices, and X.509 signing certificates.
  • Generation: on demand. You can generate a report as often as once every four hours. If a report from the last four hours exists, IAM returns it.
  • Permissions: iam:GenerateCredentialReport to create the report and iam:GetCredentialReport to download it.

4.2 Reading the Report

password_last_changedWhen the password was last set.

4.3 Users the Report Helps You Identify

The report is especially helpful for finding users who:

  • Still have active credentials but have not signed in recently.
  • Are not using MFA.
  • Have stale access keys.

4.4 IAM Access Analyzer Versus the IAM Credentials Report

Both tools help with auditing access, but they do different jobs.

The IAM credentials report compared with IAM Access Analyzer.
AspectIAM credentials reportIAM Access Analyzer
Primary scopeAccount-level inventory of IAM users and their credentialsPolicy analysis: external, internal, and unused access, plus policy checks
OutputA downloadable CSV fileFindings in the console dashboard and through the findings API
Key informationPassword age, last sign-in, access key rotation, and MFA statusPublicly shared resources, internal access, and unused permissions
GenerationOn demand, at most once every four hoursAnalyzes policies when they change and periodically; unused access is monitored continuously

Exam Trap

The credentials report lists IAM users and their credentials. It does not analyze resource policies, and it does not show what a role can access. It is a snapshot that you request, not a continuous analysis.

Memory Hook

The credentials report is the fastest way to audit all IAM users in one view.

5. Policy Validation and Policy Generation

Problem Statement

Developers at AnyCorp attached broad policies with wildcard actions to speed up delivery. The security team wants every policy checked against AWS best practices before it ships, and wants to replace broad policies with permissions that match what each role actually uses.

5.1 Policy Validation

“Is this IAM policy correctly written and aligned with AWS recommendations?”

IAM Access Analyzer validates IAM policies against IAM policy grammar and AWS best practices before you deploy permission changes. You can create or edit a policy with the AWS Command Line Interface (AWS CLI), the AWS API, or the JSON policy editor in the IAM console. Policy validation can report:

  • Security warnings.
  • Errors.
  • General warnings.
  • Suggestions for improving the policy.

5.1.1 Custom Policy Checks

Custom policy checks validate a policy against security standards that you specify. In the console, you can check whether an updated policy grants new access compared with the existing version. With the AWS CLI and the AWS API, you can also check that specific actions you consider critical are not allowed by a policy.

5.2 Policy Generation From CloudTrail Activity

IAM Access Analyzer reviews your AWS CloudTrail events and generates a policy template that contains the permissions an IAM user or role used during a date range that you choose.

5.2.1 The Four Stages

  1. Set up. Choose the user or role, a time period of up to 90 days, a service role that lets IAM Access Analyzer read your CloudTrail trail and service last accessed information, and the CloudTrail trail that logs events for the account.
  2. Generate. IAM Access Analyzer builds a policy from the activity in your CloudTrail events.
  3. Review and customize. Review the services and actions that the entity used. Add or remove permissions, specify resource Amazon Resource Names (ARNs), and add conditions.
  4. Create and attach. Save the generated policy as a managed policy and attach it to the user or role. Then remove the overly broad policy.

In the IAM console, choose Roles, choose the role, and on the Permissions tab choose Generate policy in the Generate policy based on CloudTrail events section.

5.2.2 Things to Know

  • A CloudTrail trail must be enabled for the account.
  • IAM Access Analyzer does not identify action-level activity for data events, such as Amazon S3 data events.
  • CloudTrail does not track iam:PassRole, so generated policies do not include it.
  • The IAM console keeps a generated policy for up to seven days.
  • Do not use policy generation for auditing. Use CloudTrail instead.
  • Policy generation does not support the trail that AWS Control Tower creates.
  • Review and test a generated policy before you apply it.

5.3 AWS Policy Generator

AWS Policy Generator is a separate graphical tool for building policy documents. You choose the policy type, the service, the actions, and the resources, and the tool produces the JSON policy. It creates IAM policies, S3 bucket policies, SNS topic policies, and SQS queue policies.

Two ways to create policies.
AspectPolicy generation in IAM Access AnalyzerAWS Policy Generator
InputCloudTrail activity of an IAM user or roleYour choices of policy type, service, actions, and resources
PurposeRefine broad permissions to match actual useWrite a new policy
OutputA policy template to review, customize, and attach as a managed policyA JSON policy document to copy

7. Knowledge Check

Answer each question in your own words, and then open the model answer to compare.

Question 1: Zone of Trust Boundaries. Explain the difference in behavior between an account-level zone of trust and an organization-level zone of trust when resources are shared across member accounts.

Show the model answer

With an account-level zone of trust, any access that comes from outside that single AWS account produces an external access finding. With an organization-level zone of trust, sharing between member accounts in the same organization is trusted and produces no finding. A finding appears only when access is granted to a principal outside the organization.

Question 2: Access Analyzer Versus the IAM Credentials Report. Compare IAM Access Analyzer and the IAM credentials report in terms of how they run, what they deliver, and how often they evaluate.

Show the model answer

IAM Access Analyzer analyzes policies when they change and periodically, and it monitors unused access continuously. It delivers findings in the console dashboard and through the findings API. The IAM credentials report is generated on demand, at most once every four hours, and downloads as a CSV file. It is an account-level inventory of IAM users that shows password age, last sign-in, access key rotation, and MFA status.

Question 3: Policy Generation Workflow. How does policy generation use AWS CloudTrail logs to move toward least privilege, and what must an administrator do before applying the generated policy?

Show the model answer

Policy generation analyzes the CloudTrail events of a selected user or role for a date range of up to 90 days. It identifies the services and actions that the entity used and builds a policy template from them. A CloudTrail trail must be enabled. Before attaching the policy, the administrator must review and customize it, for example by specifying resource ARNs and adding conditions, and must test it.

Question 4: Interpreting External Access Findings. What does an external access finding show about a resource, and what common misconception should security engineers avoid?

Show the model answer

An external access finding shows that a resource policy configuration allows access for a principal outside the zone of trust. The misconception to avoid is that the access has already happened. The finding is based on policy permissions, not on usage history.

Question 5: Unused Access and Internal Access. Which analyzer in IAM Access Analyzer detects inactive IAM roles, passwords, and access keys, how does it help reduce permissions, and how does it differ from the internal access analyzer?

Show the model answer

The unused access analyzer finds unused roles, access keys, passwords, and unused permissions during the tracking period that you set, from 1 to 365 days. It recommends steps such as deleting an unused role or replacing a broad policy with a recommended one. The internal access analyzer is different. It shows which principals inside your organization or account can access resources that you select.

Question 6: Regional Requirements. Why is IAM Access Analyzer described as Regional for external access, and what must security teams do to cover their whole environment?

Show the model answer

An external access analyzer analyzes only policies applied to resources in the Region where it is enabled. To monitor all supported resources, security teams create an external access analyzer in each Region where they use those resources. Unused access findings do not change by Region, so an unused access analyzer is not required in each Region.

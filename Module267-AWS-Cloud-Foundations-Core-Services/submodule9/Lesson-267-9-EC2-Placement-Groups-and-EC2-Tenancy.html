1. EC2 Placement Groups

Problem Statement

You work as a junior AWS solutions architect at RetailCloud, a fast-growing e-commerce platform, under the guidance of a lead architect. As traffic to the site grows, the infrastructure team faces pressure on availability, cost, and compliance.

Your lead architect asks you to review where RetailCloud’s EC2 instances run on AWS hardware. Before you recommend changes, you need answers to the questions below. This lesson explains how placement groups and EC2 tenancy options answer them.

Your challenge:

  • How can a group of instances that exchange large amounts of data get the lowest network latency?
  • How can a small number of critical instances avoid failing at the same time?
  • How can a large replicated system limit the impact of a single hardware failure?

1.1 Introduction to Amazon EC2 Placement Groups

Amazon EC2 placement groups determine how your instances are placed on the underlying AWS hardware, so that you can meet the performance, availability, or workload isolation requirements of your application. When you create a placement group, you specify one of the following strategies:

  1. Cluster placement group.
  2. Partition placement group.
  3. Spread placement group.

AWS also lists a fourth strategy, precision time, which places instances on supported hardware with direct access to high-precision time sources in AWS infrastructure. This lesson focuses on the first three.

1.2 Cluster Placement Groups

A cluster placement group places EC2 instances close together within a single Availability Zone. This provides low-latency, high-speed network throughput between the instances, and fast communication between them. However, placing instances close together can increase the risk that one hardware failure affects several instances.

1.2.1 Best For

  • High-performance computing.
  • Scientific simulations.
  • Big data jobs that need to be completed fast.
  • Machine learning training.
  • Applications with frequent server-to-server communication.

1.2.2 Example: Financial Risk Analysis

A financial company runs a risk-analysis application across 20 EC2 instances. The instances must exchange large amounts of data quickly during each calculation. The architect places the instances in a cluster placement group, so that they are located close together and receive low-latency, high-throughput network communication.

A financial institution that runs a high-frequency trading application, or a big data analytics cluster, can likewise place its worker nodes in a cluster placement group for maximum network bandwidth and minimal latency between nodes.

Exam tip: cluster means close together for performance.

1.3 Spread Placement Groups

A spread placement group places a small number of critical instances on distinct underlying hardware racks. Each instance runs on independent hardware with its own power and network sources. A rack-level spread placement group can span multiple Availability Zones, but it supports a maximum of seven running instances per Availability Zone.

Pros: reduced risk of simultaneous failure, because the EC2 instances are on different physical hardware.

1.3.1 Best For

  • Small numbers of critical servers.
  • Applications where instances must be isolated from one another.
  • Domain controllers.
  • Critical applications where each instance must be isolated from the failure of the others.

1.3.2 Examples

Critical authentication servers: a company runs three critical authentication servers. A simultaneous failure of two servers could prevent employees from signing in. The company places the servers in a spread placement group, which reduces the chance that a single physical rack failure affects several authentication servers.

A company that runs a mission-critical primary and secondary database setup can use a spread placement group so that the primary database and its backups never share the same physical hardware rack. This minimizes the risk of simultaneous downtime from a single hardware failure.

Exam tip: spread means separate individual instances for resilience.

1.4 Partition Placement Groups

A partition placement group divides EC2 instances into logical groups called partitions. A partition placement group can have partitions in multiple Availability Zones in the same Region, with a maximum of seven partitions per Availability Zone. Each partition uses a separate set of racks with independent power and networking. A hardware failure in one partition does not directly affect the instances in other partitions, and a partition placement group can scale to hundreds of EC2 instances (for example, Hadoop, Cassandra, and Kafka). Unlike a spread placement group, each partition can contain multiple instances.

1.4.1 Best For

  • Hadoop and HDFS.
  • Apache Kafka.
  • Apache Cassandra.
  • Large distributed databases.
  • Replicated workloads.

1.4.2 Examples

Distributed database: a company operates a Cassandra database across 12 EC2 instances. It creates three partitions and distributes the replicas across them. If the hardware that supports one partition fails, the replicas in the other partitions remain available. This reduces the possibility that one rack-level failure removes all copies of the same data.

A large distributed NoSQL database or a Kafka messaging cluster can likewise use partition placement groups to spread its nodes across distinct hardware partitions, which isolates failures and keeps the application available if an entire rack goes down.

Exam tip: partition means groups of instances separated by a failure boundary.

1.5 Placement Groups: Rules and Limitations

Before you use placement groups, keep the following rules in mind:

  • An instance belongs to one placement group at a time, and it cannot be in several groups.
  • You cannot merge two placement groups into one.
  • On-Demand Capacity Reservations and zonal Reserved Instances reserve capacity in an Availability Zone. An instance that matches a reservation uses the reserved capacity automatically, including when it is launched into a placement group.
  • Dedicated Hosts cannot be launched into placement groups.
  • A Spot Instance that is set to stop or hibernate when it is interrupted cannot be launched into a placement group.
  • A partition placement group that uses Dedicated Instances can have a maximum of two partitions.
  • Network traffic from a cluster placement group to the internet, and over AWS Direct Connect to on-premises resources, is limited to 5 Gbps.

1.6 Step-by-Step Guide: Configure Placement Groups

1.6.1 Navigate to Placement Groups

  1. On the AWS Management Console, open the EC2 Dashboard.
  2. On the left side, scroll down to Network & Security and choose Placement Groups.

1.6.2 Create a Placement Group

  1. Choose Create placement group.
  2. For Name, specify a name for the group.
  3. For Placement strategy, choose the strategy for the group: Cluster, Spread, Partition, or Precision time. The screenshot shows the three classic strategies.
  4. If you chose Spread, for the Spread level, choose Rack or Host. The Host level is available only with AWS Outposts.
  5. If you chose Partition, for Number of partitions, enter the number of partitions for the group.
  6. If you chose Cluster, you can optionally specify a parent precision time placement group, to make sure that the instances in the cluster placement group launch on precision time-capable hardware.
  7. (Optional) To add a tag, under Tags, choose Add new tag, and then enter a key and a value.
  8. Choose Create group.

1.6.3 Launch EC2 Instances in the Placement Group

  1. Create a simple EC2 instance. You can choose the Free Tier.
  2. Configure the instance details, and scroll down to Advanced details.
  3. In the Placement group name list, select the appropriate placement group.
  4. Configure any other necessary settings, and complete the instance launch.

1.7 Important Points for Placement Groups

  • Placement groups are optional.
  • There is no additional charge to create one.
  • An EC2 instance can belong to only one placement group at a time.
  • Supported instance types and capacity must be available.
  • Placement groups influence physical placement. They do not replace backups, replication, Auto Scaling, or a Multi-AZ architecture.
  • A cluster placement group cannot span multiple Availability Zones.
  • Spread and partition strategies focus on reducing correlated hardware failures.
  • Launching all required cluster instances together improves the chance that enough capacity is available.

2. EC2 Tenancy

Problem Statement

RetailCloud’s compliance team reviews a new rule, and the licensing team reviews the software licenses that the company owns. Some workloads may need hardware that is not shared with other AWS customers.

The architect asks you to explain the tenancy options, and then to compare Dedicated Instances with Dedicated Hosts.

Your challenge:

  • What can RetailCloud do when a compliance rule or a software license requires dedicated hardware?
  • How do Dedicated Instances and Dedicated Hosts differ in control and cost?

2.1 Overview of EC2 Tenancy

EC2 tenancy defines how your virtual machine (EC2 instance) is physically placed on the underlying AWS hardware. It determines whether your instance shares a physical server with other AWS customers or runs on hardware that is isolated for your account. AWS provides three primary tenancy options:

  1. Default (shared) tenancy.
  2. Dedicated Instances.
  3. Dedicated Hosts.

2.2 Default (Shared) Tenancy

Shared tenancy is the default tenancy for the VPC and for EC2. With default tenancy, your EC2 instances run on physical hardware that may also host instances that belong to other AWS customers. Multiple AWS accounts run instances on the same physical server, and hypervisors isolate the instances logically. AWS securely isolates each customer’s virtual machines through its virtualization platform.

Key characteristicsTypical use cases
Default option for most EC2 instances. Lowest-cost tenancy option. AWS controls instance placement. Appropriate for most applications.General web apps, APIs, dev and test, and standard workloads.

2.2.1 Scenario

A company hosts a public website on EC2. It has no regulatory or licensing requirement for dedicated physical hardware, so it selects default tenancy to minimize cost.

2.3 Dedicated Instances

Dedicated Instances run on physical hardware that is isolated exclusively for your AWS account, and AWS places the instances automatically. The hardware isolation means no “noisy neighbors” and no cross-tenant risk. However, you do not get detailed visibility or control over the underlying physical server.

  • A Dedicated Instance is isolated from the instances of other AWS accounts, but it can share a physical server with other instances in your own account that are not Dedicated Instances. See Amazon EC2 Dedicated Instances.
  • You can pay for Dedicated Instances On-Demand, save up to 70 percent with Reserved Instances, or save up to 90 percent with Spot Instances. These are the maximum savings that AWS states, and the actual savings vary.
Key characteristicsTypical use cases
Single-tenant physical hardware. Billed per instance. No control over instance placement, so an instance can move to other hardware after a stop and start. No visibility into physical sockets or cores. Limited support for server-bound licenses. More expensive than default tenancy.Regulatory compliance mandates that require single-tenant physical hardware.

2.3.1 Scenario

A healthcare company has an internal policy that requires its EC2 workloads to run on hardware that is not shared with other customers. It uses Dedicated Instances, because it does not need control over specific physical servers.

2.4 Dedicated Hosts

A Dedicated Host is an entire physical EC2 server that is allocated for one customer’s use. Dedicated Hosts give you greater visibility and control over the underlying server, including the physical sockets, the cores, and the instance placement.

  • They allow the use of existing per-socket, per-core, or other software licenses that are tied to the physical host.
  • They allow you to use your eligible software licenses from vendors such as Microsoft and Oracle on Amazon EC2. This is known as BYOL (Bring Your Own License).
  • You can purchase them On-Demand at an hourly rate, or as reservations with up to 70 percent off the On-Demand price.
Key characteristicsTypical use cases
Entire physical server dedicated to the customer. Supports host affinity. Useful for compliance and server-bound licensing requirements.Use your own licenses with the flexibility and cost-effectiveness that you want, together with the simplicity, resilience, and elasticity of AWS. Strict software licensing (per-socket or per-core licenses), or specialized compliance needs.

2.4.1 Scenario

A company owns software licenses that are tied to physical processor sockets. It uses a Dedicated Host, so that it can view the sockets and cores of the server and place its licensed EC2 instances on that specific host.

2.6 Important Clarification

Dedicated tenancy refers to the physical compute server. It does not mean that every connected AWS service uses dedicated physical hardware. For example, an EBS volume that is attached to a Dedicated Instance does not run on the dedicated hardware of the EC2 instance.

2.7 SAA-C03 Exam Tips

  • Do not confuse tenancy with a pricing model such as On-Demand, Spot, or Savings Plans.
  • Dedicated Instances and Dedicated Hosts provide isolation from other customers, but Dedicated Hosts provide greater visibility and placement control.
  • Dedicated Instances: AWS manages instance placement automatically. If you stop and start the instance, it might move to a different physical server, which is still isolated to your account. A reboot keeps the instance on the same host. You pay a per-instance fee plus a dedicated per region fee.
  • Dedicated Hosts: you rent the physical server directly. You control which instances run on which server, and with host affinity set to Host, a stopped instance restarts on the same host. You pay per physical host rather than per instance.

2.9 Lesson Summary

In this lesson, you learned the following:

  • Placement groups influence how EC2 instances are placed on the underlying hardware, and there is no additional charge to create one.
  • A cluster placement group places instances close together in a single Availability Zone for low latency and high network throughput, but one hardware failure can affect several instances.
  • A spread placement group places a small number of critical instances on distinct racks. A rack-level spread placement group can span multiple Availability Zones, and it supports a maximum of seven running instances per Availability Zone.
  • A partition placement group divides instances into partitions that use separate racks. It can have partitions in multiple Availability Zones in the same Region, with a maximum of seven partitions per Availability Zone, and it suits large distributed workloads such as Hadoop, Cassandra, and Kafka.
  • An instance can belong to one placement group at a time, and placement groups do not replace backups, replication, Auto Scaling, or a Multi-AZ architecture.
  • Tenancy defines whether an instance shares a physical server with other AWS customers, and it is separate from a pricing model such as On-Demand, Spot, or Savings Plans. Default tenancy is shared and has the lowest cost.
  • Dedicated Instances run on hardware that is isolated for your AWS account, are billed per instance, and give no visibility or control over instance placement.
  • Dedicated Hosts give you an entire physical server, with visibility into sockets and cores, host affinity, and support for server-bound licenses (Bring Your Own License, BYOL). They are billed per host.

3. Knowledge Check

Answer each question in your own words before you open the model answer. The questions were written for this course.

Question 1: What is an Amazon EC2 placement group, and what are the strategies for it?

Maps to: Objective 1 (Knowledge).

A placement group determines how your instances are placed on the underlying AWS hardware, so that you can meet performance, availability, or isolation needs. You choose a strategy when you create the group: cluster, partition, or spread. AWS also offers a precision time strategy, for instances that need direct access to high-precision time sources. Placement groups are optional, and there is no extra charge to create one.

Question 2: Compare cluster, spread, and partition placement groups for network latency, performance, and fault isolation.

Maps to: Objective 3 (Comprehension and Analysis).

A cluster group places instances close together in one Availability Zone, which gives the lowest latency and high throughput but raises the risk that one failure affects several instances. A spread group places each of a small number of critical instances on a separate rack, with up to seven running instances per Availability Zone, so failures stay isolated. A partition group divides instances into partitions that use separate racks, so a failure stays inside one partition, and it scales to large numbers of instances.

Question 3: Three critical authentication servers must not fail together. Which strategy fits, and what limit applies?

Maps to: Objective 3 (Application).

A spread placement group fits, because it places each instance on distinct hardware with its own power and network. A rack-level spread group supports a maximum of seven running instances per Availability Zone, which is enough for three servers.

Question 4: Why does a partition placement group suit Cassandra, Kafka, and Hadoop?

Maps to: Objective 3 (Analysis).

These systems replicate data across many nodes. A partition group puts groups of nodes on separate racks, so a hardware failure affects only the nodes in one partition, and the replicas in other partitions stay available. Each partition can hold many instances, and a group can scale to hundreds of instances.

Question 5: List the main rules and limitations of placement groups.

Maps to: Objective 2 (Comprehension).

An instance belongs to one placement group at a time, and you cannot merge groups. Dedicated Hosts cannot be launched into placement groups, and a Spot Instance that is set to stop or hibernate when interrupted cannot be launched into one. A cluster group cannot span Availability Zones. Placement groups do not replace backups, replication, Auto Scaling, or a Multi-AZ architecture.

Question 6: What is EC2 tenancy, and how is it different from a pricing model?

Maps to: Objective 4 (Knowledge and Comprehension).

Tenancy defines how an instance is physically placed, meaning whether it shares a physical server with other AWS customers or runs on hardware that is isolated for your account. The options are default (shared) tenancy, Dedicated Instances, and Dedicated Hosts. A pricing model, such as On-Demand, Spot, or Savings Plans, defines how you pay for an instance, and it is a separate choice.

Question 7: Compare default tenancy, Dedicated Instances, and Dedicated Hosts for isolation, control, billing, host affinity, and BYOL support.

Maps to: Objective 5 (Analysis).

Default tenancy shares hardware, gives no placement control, bills per instance, has no host affinity, has limited BYOL support, and costs the least. Dedicated Instances isolate the hardware for your account, let AWS place instances automatically, bill per instance, have no host affinity, and have limited BYOL support. Dedicated Hosts give you an entire server, with visibility into sockets and cores, placement control, host affinity, per-host billing, and the strongest BYOL support, at the highest cost.

Question 8: RetailCloud runs a risk-analysis cluster that needs the lowest latency, and a database whose software license is tied to physical sockets. Which placement group and tenancy would you recommend, and why?

Maps to: Objective 6 (Evaluation).

For the risk-analysis cluster, use a cluster placement group in one Availability Zone, for the lowest latency and highest throughput, and accept the risk that one failure can affect several instances. For the database with a socket-bound license, use a Dedicated Host, so that the company can see the sockets and cores and place the licensed instances on that specific server. Dedicated Hosts cannot be launched into placement groups, so the two choices apply to different workloads.

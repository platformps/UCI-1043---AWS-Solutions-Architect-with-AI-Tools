1. AWS and Global Infrastructure

Problem Statement

A company is moving its online store from a rented server room to the cloud. The company must keep customer data in the country where the customers live, and it must keep the store available if one data center fails.

The team must decide where to place its workloads and which AWS infrastructure options fit each requirement.

Your challenge:

  • Explain what AWS is and what advantages it offers.
  • Use the AWS Management Console to find a service and select a Region.
  • Choose between a Region, an Availability Zone, a Local Zone, an edge location, and AWS Outposts for a stated requirement.
  • Design for high availability and for disaster recovery.

1.1 What Is Amazon Web Services?

AWS is a cloud service provider that offers infrastructure and managed technology services through a global network of data centers. Customers use AWS through the AWS Management Console, command-line tools, software development kits (SDKs), and application programming interfaces (APIs). AWS provides services in categories such as:

  • Compute.
  • Storage.
  • Databases.
  • Networking.
  • Security.
  • Application integration.
  • Analytics and machine learning.
  • Management and governance.

You can combine AWS services to create applications that range from simple websites to globally distributed enterprise systems.

1.2 Key Advantages of AWS

  • Trade capital expense for variable expense: instead of investing heavily in data centers and servers before you know how you will use them, you pay only when you consume resources, and only for the amount that you consume.
  • Benefit from massive economies of scale: because AWS serves a very large number of customers around the world, it can achieve higher economies of scale, which lowers pay-as-you-go prices.
  • Stop guessing capacity: you can launch as few or as many instances as you need, and scale up or down automatically in response to demand.
  • Increase speed and agility: cloud resources are a click away, which reduces the time to make resources available to developers from weeks to minutes.
  • Go global in minutes: you can deploy an application in multiple AWS Regions around the world with a few clicks.

1.3 The AWS Management Console

The AWS Management Console is a web-based graphical user interface (GUI) that you use to manage, provision, and monitor AWS resources. Important features include the following:

  • Navigate to service consoles: use Unified Navigation to open recently visited service consoles, view and add services to your Favorites list, open console settings, and open AWS User Notifications.
  • Search for services and information: use Unified Search to find AWS services, features, and AWS Marketplace products.
  • Customize the console: use Unified settings to change the language, the default Region, and other options.
  • Run commands: open AWS CloudShell from the console to run AWS Command Line Interface (AWS CLI) commands against your services.
  • Access event notifications: view notifications from AWS User Notifications and AWS Health.
  • Customize AWS Console Home: add and arrange widgets on your Console Home page.
  • Create and manage applications: use myApplications in Console Home to monitor the cost, health, security posture, and performance of your applications.
  • Chat with Amazon Q: get answers to AWS service questions from a generative artificial intelligence (AI) assistant in the console, or connect with a live agent for more support.
  • Control account access in your network: use AWS Management Console Private Access to limit console access to a specified set of known AWS accounts when traffic originates from within your network.

To open the console, go to aws.amazon.com/console.

  • AWS Availability Zones.
  • AWS data centers.

1.6 Overview of AWS Regions

An AWS Region is a geographic area that contains multiple isolated Availability Zones. Most AWS resources are deployed within one Region that you select. Building and running your own data centers in many parts of the world would be difficult and expensive for most organizations. As of November 2026, AWS lists 39 launched Regions and 124 Availability Zones on its Global Infrastructure page, and the numbers grow as AWS opens new Regions. Check the page for current counts.

1.6.1 Account Types and Available Regions

Your account type determines the Regions that are available to you. An AWS account provides multiple Regions so that you can create resources in locations that meet your requirements. For example, you can create resources in Europe to be closer to European customers or to meet legal requirements.

  • An AWS GovCloud (US) account provides access to the AWS GovCloud (US-West) Region and the AWS GovCloud (US-East) Region. For more information, see AWS GovCloud (US).
  • An AWS account in China provides access to the Beijing and Ningxia Regions only. For more information, see Amazon Web Services in China.
  • Opt-in Regions: to use a Region that AWS introduced after March 20, 2019, you must enable it first. Regions introduced earlier are enabled by default.

For the services available in each Region, see AWS Services by Region, which lists which services, such as Amazon API Gateway and Amazon Athena, are available in each Region.

Exam tip: You cannot describe or access the Regions of one account type from another. For example, you cannot access the AWS GovCloud (US) Regions or the China Regions from a standard AWS account.

1.7 How to Choose an AWS Region

Consider the following factors when you decide which Region hosts your applications and workloads:

  • Compliance and data residency: enterprise companies often must store customer data in a specific geographic territory to meet regulations. Data does not leave a Region without your explicit permission, so choose a Region that meets your legal and governance requirements.
  • Latency: if your application is sensitive to latency, choose a Region close to your users. Synchronous applications such as gaming, telephony, WebSockets, and Internet of Things (IoT) workloads are strongly affected by higher latency. Asynchronous workloads, such as ecommerce, can also suffer.
  • Price: prices vary from one Region to another because of the local economy and the cost of operating data centers there, including connectivity, imported equipment, customs, and real estate. AWS charges based on these local factors instead of a flat worldwide rate.
  • Service availability: new services and features are not available in every Region. The AWS documentation lists the services available in each Region.
  • Disaster recovery: select a second Region where you can recover your workload if the first Region becomes unavailable.

1.8 AWS Availability Zones

An Availability Zone (AZ) is a distinct infrastructure location within an AWS Region. Each Region consists of multiple AZs. An AZ is a group of one or more data centers with independent power, cooling, and networking, housed in separate facilities. The AZs in a Region connect through high-bandwidth, low-latency networking over dedicated metro fiber, and AWS encrypts the traffic between them. Each AZ is far enough from the others to reduce shared risks, such as a fire, tornado, or flood, but all AZs in a Region are within 100 kilometers (about 60 miles) of each other.

Each Region has at least three AZs, which helps you design highly available applications. The code for an AZ is its Region code followed by a letter. For example, us-east-2a, us-east-2b, and us-east-2c are the AZs in the us-east-2 Region. For more information, see Availability Zones.

1.8.1 Key Characteristics of Availability Zones

  • High availability: architects distribute application components across multiple AZs to reduce the risk of a single-zone failure.
  • Scope: an AZ is not limited to one building. One AZ can contain multiple data centers.
  • Resource management: subnets belong to one AZ, and resources can be zonal or regional.
  • Connectivity: data transfer between zones supports high availability but can add cost.
  • Edge locations: edge locations are separate from AZs. They deliver content closer to users to reduce latency.

1.8.2 Availability Zone Names and IDs

AWS maps AZ names to physical locations separately for each account. For example, us-east-1a in one account is not guaranteed to be the same physical location as us-east-1a in another account. To identify the same physical zone across accounts, use the AZ ID, such as use1-az1. For more information, see Availability Zone IDs for your AWS resources.

1.9 Why Multiple Availability Zones Matter

AWS provides multiple AZs to support high availability and fault tolerance. If an application runs entirely in one AZ, an outage in that AZ can make the application unavailable. A better design distributes critical resources across two or more AZs. For example, a highly available web application can use:

  • An Application Load Balancer across multiple AZs.
  • Amazon Elastic Compute Cloud (Amazon EC2) instances in at least two AZs.
  • An Amazon EC2 Auto Scaling group that spans those AZs.
  • An Amazon Relational Database Service (Amazon RDS) Multi-AZ deployment.
  • Replicated or regional storage services.

If resources in one AZ become unavailable, the application can continue to serve users through resources in another AZ.

1.9.1 Example Scenario

An online retailer runs its application on one EC2 instance in one AZ. If that AZ has a power or networking failure, customers may be unable to reach the website. The solutions architect places EC2 instances in two AZs and sends traffic through an Application Load Balancer. If one instance or AZ becomes unavailable, the load balancer sends traffic to healthy instances in the other AZ. This design removes the single AZ as a single point of failure.

1.9.2 Region Failure Versus AZ Failure

A Multi-AZ architecture protects an application from many failures within a Region, but it does not fully protect against a Region-wide disruption. Use this distinction:

  • Multi-AZ architecture: protects against the failure of an AZ.
  • Multi-Region architecture: supports disaster recovery when an entire Region becomes unavailable.

Multi-Region solutions are generally more complex and expensive, because organizations must replicate data, configure cross-Region traffic routing, and plan how applications fail over.

1.10 AWS Local Zones

AWS Local Zones place compute, storage, database, and other selected services closer to end users. They support applications that need single-digit millisecond latency, such as media production, real-time gaming, complex simulations, and machine learning. A Local Zone is an extension of a parent AWS Region. You can deploy latency-sensitive workloads with familiar tools, such as Amazon EC2, Amazon VPC, Amazon Elastic Block Store (Amazon EBS), and Elastic Load Balancing (ELB), while keeping secure, high-capacity connections to the rest of AWS. For more information, see AWS Local Zones concepts.

The code for a Local Zone is its Region code followed by an identifier that indicates its physical location. For example, us-west-2-lax-1 is in Los Angeles. In the diagram, the VPC spans the two AZs and one of the Local Zones. Each zone in the VPC has one subnet, and each subnet has an instance.

For the available Local Zones, see Available Local Zones in the AWS Local Zones User Guide. For announced Local Zones, see AWS Local Zones locations. AWS also offers Dedicated Local Zones, which are cloud infrastructure built for a specific customer to help meet regulatory and digital sovereignty needs.

1.10.1 Why Use AWS Local Zones?

  • Run low-latency applications at the edge: build and deploy applications close to end users for real-time gaming, live streaming, augmented reality and virtual reality (AR/VR), virtual workstations, and more.
  • Simplify hybrid cloud migrations: migrate applications to a nearby Local Zone while you still meet the low-latency requirements of a hybrid deployment.
  • Meet strict data residency requirements: comply with state and local data residency requirements in sectors such as healthcare, financial services, iGaming, and government.

1.10.2 Managing Local Zones

You can manage resources in a Local Zone with the following options:

  • AWS Management Console: a web interface to manage Local Zones and create resources in them.
  • AWS CLI: commands for a broad set of services, including Amazon VPC, on Windows, macOS, and Linux. The services that you use in Local Zones keep their own namespaces. For example, Amazon EC2 uses the ec2 namespace. For more information, see AWS Command Line Interface.
  • AWS SDKs: language-specific APIs that handle connection details such as signature calculation, request retries, and error handling. For more information, see AWS developer tools.

1.11 AWS Wavelength Zones

AWS Wavelength Zones embed AWS compute and storage services within the 5G networks of communications service providers. They serve applications that need very low latency to mobile devices. Wavelength Zones sit inside telecommunications provider networks, while Local Zones sit in metropolitan areas. For more information, see AWS Wavelength.

1.12 AWS Points of Presence and Edge Locations

In addition to Regions and AZs, AWS operates a globally distributed network of points of presence (PoPs). A PoP is a site designed to deliver AWS services with low latency. PoPs are closer to users than Regions or AZs and are often in major cities. AWS lists more than 750 Amazon CloudFront points of presence and 15 Regional Edge Caches on its Global Infrastructure page. Check the page for current numbers. The following services use edge locations:

  • Amazon CloudFront caches copies of content in edge locations so that content is closer to users and loads faster (lesson 269.7).
  • Amazon Route 53 serves Domain Name System (DNS) responses from edge locations so that nearby queries resolve faster (lesson 269.9).
  • AWS WAF and AWS Shield filter traffic in edge locations to stop unwanted traffic as early as possible (lesson 268.9).

1.12.1 What Is an Edge Location?

An edge location is a site where AWS services receive requests closer to the user, so that not every request travels to an AWS Region. For example:

  1. An application runs in the US East (N. Virginia) Region.
  2. A user accesses the application from California.
  3. Amazon CloudFront directs the user to a nearby edge location.
  4. If the requested content is cached there, CloudFront returns it immediately.
  5. If the content is not cached, CloudFront retrieves it from the origin and may cache it for later requests.

1.12.2 Regional Edge Caches

A Regional Edge Cache is a larger cache between CloudFront edge locations and the application’s origin. If content is missing from an edge location, CloudFront can check a Regional Edge Cache before it contacts the origin. Regional Edge Caches keep less frequently requested content longer than individual edge locations, so they can further reduce requests to the origin.

Exam tip: When a question asks how to reduce latency for users around the world by caching content close to them, think Amazon CloudFront. When a question asks for compute close to users in one metropolitan area, think AWS Local Zones. For another exam tip, see the SAA-C03 exam tip document.

1.13 Overview of AWS Outposts

AWS Outposts brings AWS-managed infrastructure and services into a customer’s on-premises data center or facility. AWS manages the Outposts infrastructure, and the customer hosts it at their location. Outposts is available as racks and as servers. Outposts is useful when an organization needs:

  • Low-latency access to local systems.
  • Local data processing, such as heavy data ingestion on an Internet of Things factory floor, where moving large datasets to the cloud is expensive or limited by bandwidth.
  • On-premises data residency.
  • A consistent hybrid cloud environment.

1.14.1 Scenario A: High Availability Versus Disaster Recovery

  • Multi-AZ deployment supports high availability and fault tolerance. Deploying across two or more AZs in one Region protects against a data center outage, a fire, or a local power loss. Exam pattern: when a question asks for high availability with automatic failover inside a Region, the answer is Multi-AZ.
  • Multi-Region deployment supports disaster recovery and global reach. Deploying across Regions protects against a Region-wide failure or natural disaster. Exam pattern: when a question asks for disaster recovery from a Region-wide outage, or for lower latency for users around the world, choose a Multi-Region solution, for example Amazon Aurora Global Database, Amazon DynamoDB global tables, or Amazon S3 Cross-Region Replication.

1.14.2 Scenario B: Data Sovereignty and Compliance

AWS does not replicate data across Regions unless you configure it, for example with Amazon S3 Cross-Region Replication. Exam pattern: if a legal or regulatory requirement says that data must stay within a country or jurisdiction, keep the resources in an AWS Region located in that country.

1.14.3 Important Points for the Exam

  • A Region is a geographic area.
  • A Region contains multiple AZs.
  • An AZ consists of one or more discrete data centers.
  • AZs have independent infrastructure and are physically separated.
  • AZs within a Region use high-bandwidth, low-latency connections.
  • Deploying resources across multiple AZs improves high availability.
  • Deploying across multiple Regions supports stronger disaster recovery strategies.
  • Selecting the closest Region can reduce latency, but compliance, cost, and service availability also matter.

2.3 Amazon VPC and Subnets

2.3.1 Amazon Virtual Private Cloud

Amazon Virtual Private Cloud (Amazon VPC) lets you create a logically isolated virtual network in AWS where you can securely launch and manage resources. Like a traditional network, a VPC lets you define IP address ranges, create public and private subnets, configure routes, and apply security controls. Important VPC components include:

  • Public and private subnets.
  • Route tables.
  • Internet gateways.
  • Network address translation (NAT) gateways.
  • Security groups.
  • Network access control lists.
  • VPC endpoints.

A VPC spans all AZs in a single AWS Region, and each subnet exists in only one AZ. For more information, see What is Amazon VPC? The diagram shows an example VPC with one subnet in each of the AZs in the Region, EC2 instances in each subnet, and an internet gateway that allows communication between the resources in the VPC and the internet. Lesson 269.1 covers VPCs in depth.

2.3.2 Subnets

A subnet is a range of IP addresses in your VPC. Subnets divide the VPC’s Classless Inter-Domain Routing (CIDR) block, which gives you more control over where resources reside. Each subnet is associated with one AZ. When you launch an EC2 instance or another resource, it is deployed into a specific subnet and receives an IP address from that subnet’s range. For example, a VPC with the CIDR block 172.16.0.0/16 can have four subnets across two AZs:

SubnetAvailability ZoneTypeIP range
Public subnet AAPublic172.16.0.0/24
Private subnet AAPrivate172.16.1.0/24
Public subnet BBPublic172.16.2.0/24
Private subnet BBPrivate172.16.3.0/24

The diagram shows the same VPC. Each AZ has a public subnet and a private subnet, and an internet gateway connects to the public subnets. You explore subnets in more detail later in this course.

2.5 The AWS Shared Responsibility Model

Security and compliance are a shared responsibility between AWS and the customer. AWS is responsible for the security of the cloud. The customer is responsible for security in the cloud. For more information, see the AWS Shared Responsibility Model.

ResponsibilityOwnerExamples
Security of the cloudAWSPhysical data centers, hardware, networking, and the software that runs AWS services, including Regions, AZs, and edge locations.
Security in the cloudCustomerData, identity and access management, operating system and application settings on services such as Amazon EC2, network configuration such as security groups, and encryption choices.

The customer’s share depends on the service. For Amazon EC2, the customer manages the guest operating system, including updates and security patches, the installed software, and the security group configuration. For a managed service such as Amazon RDS, AWS patches the database software and the underlying operating system, while the customer manages the data, the database users, and the network access rules. For a service such as Amazon S3, AWS operates the infrastructure and the platform, and the customer manages the data, the access permissions, and the encryption settings.

TaskAmazon EC2Amazon RDSAmazon S3
Physical security of the data centerAWSAWSAWS
Guest operating system patchingCustomerAWSAWS
Database engine patchingCustomer, for a database installed on EC2AWSNot applicable
Network access rules, such as security groups and bucket policiesCustomerCustomerCustomer
IAM users and permissionsCustomerCustomerCustomer
Data classification and encryption choicesCustomerCustomerCustomer

2.5.1 Shared Controls

Some controls apply to both AWS and the customer, each in its own scope:

  • Patch management: AWS patches the infrastructure, and the customer patches the guest operating system and applications.
  • Configuration management: AWS configures its infrastructure devices, and the customer configures the guest operating system, databases, and applications.
  • Awareness and training: AWS trains its employees, and the customer trains its own employees.

Exam tip: When a question asks who patches the guest operating system of an EC2 instance, the answer is the customer. When a question asks who maintains the physical hardware or the virtualization layer, the answer is AWS.

This tab covers cloud economics, total cost of ownership estimation, cost optimization, and the AWS tools that support them.

3.1 Capital Expense and Variable Expense

Traditional data centers require capital expense (CapEx). Organizations buy hardware, buildings, networking equipment, and software before they know how much capacity they need. With AWS, customers pay for the resources they use. This is a variable expense, or operating expense (OpEx), model.

Traditional CapExAWS variable expense
Large up-front investmentPay for consumed resources
Capacity purchased in advanceCapacity provisioned when needed
Hardware ownershipProvider-managed infrastructure
Long procurement cyclesRapid resource deployment
Risk of overprovisioningAbility to scale dynamically

Some AWS commitments, such as Reserved Instances and Savings Plans, trade flexibility for lower costs. Lesson 267.3 covers these pricing models.

3.2 Estimating Costs and Total Cost of Ownership

To create a useful cost estimate, first identify your basic workload requirements. For an Amazon EC2 deployment, consider:

  • The required operating system.
  • The central processing unit (CPU), memory, and input/output (I/O) requirements.
  • The required storage capacity and type.
  • Database requirements.
  • The expected usage duration.
  • The appropriate purchasing option.

You do not need to finalize every decision before you create an estimate. The AWS Pricing Calculator lets you adjust service configurations and compare options to find the best fit for your technical requirements and budget. For current prices, see AWS Pricing.

3.2.1 Total Cost of Ownership

Total cost of ownership (TCO) considers the complete cost of operating technology, not only the purchase price. TCO can include:

  • Servers, storage, and networking equipment.
  • Software licenses.
  • Data center facilities, power, and cooling.
  • IT administration and maintenance.
  • Hardware replacement and support.
  • AWS services and data transfer charges.

In AWS terms, TCO is more than hourly pricing. Pricing and TCO tools help organizations estimate cloud costs, compare AWS with on-premises infrastructure, plan migrations, and monitor spending.

3.4 AWS Cost Optimization

AWS cost optimization is the process of delivering the required business results at the lowest practical cost. It does not mean choosing the cheapest service. An architecture must still meet its security, availability, performance, and operational requirements. A low-cost solution that cannot meet business requirements is not cost-optimized. Cost optimization involves:

  • Selecting the most appropriate AWS services.
  • Matching resource capacity to workload demand.
  • Removing unused or unnecessary resources.
  • Selecting appropriate pricing and purchasing options.
  • Moving data to suitable storage classes.
  • Monitoring spending and responding to cost changes.
  • Automating scaling and resource schedules.

3.5 Cost Optimization Hub

Cost Optimization Hub is a feature of AWS Billing and Cost Management. It helps you identify, filter, aggregate, and quantify savings for cost optimization recommendations. The hub gathers recommended actions from AWS Cloud Financial Management (CFM) services, including AWS Cost Explorer and AWS Compute Optimizer, in one place. Its dashboard can group estimated savings by resource type and other dimensions. For more information, see Cost Optimization Hub, AWS Cloud Financial Management services, and the Cost Optimization Hub announcement on the AWS News Blog, which has screenshots of the dashboard.

3.5.1 Recommendation Strategies

Cost Optimization Hub groups recommendations into the following strategies:

StrategyWhat it means
Purchase Savings PlansPurchase Compute, EC2 instance, and SageMaker Savings Plans.
Purchase reservationsPurchase reservations for EC2, Amazon RDS, OpenSearch, Amazon Redshift, ElastiCache, MemoryDB, and DynamoDB.

AWS can add strategies over time. For the current list, see Understanding cost optimization strategies.

3.5.2 Reading the Recommendations

The Savings opportunities page shows the resource type, the top recommended action, and the estimated monthly savings. You can filter the list by AWS account, AWS Region, implementation effort, and tag key. You can also filter by Is resource restart needed and Is rollback possible. If you set Is resource restart needed to No, you see only recommendations that do not require a restart, such as Amazon EBS volume recommendations. If you set Is rollback possible to Yes, you see only recommendations that you can roll back.

If you select a specific recommendation, for example rightsizing an EC2 instance, you can view details and open the Amazon EC2 and AWS Compute Optimizer consoles. Estimated monthly savings is an approximation of future savings. Actual savings depend on your future AWS usage.

3.8 Lesson Summary

AWS and global infrastructure.

  • AWS organizes its global infrastructure into Regions, Availability Zones, Local Zones, Wavelength Zones, edge locations, and Outposts.
  • A Region is a geographic area that contains multiple isolated AZs, and each AZ contains one or more data centers with independent power, cooling, and networking.
  • Deploying across multiple AZs improves high availability and fault tolerance, and Multi-Region architectures support disaster recovery.
  • Region selection depends on latency, service availability, price, compliance, and disaster recovery needs.
  • Local Zones place selected services close to users who need very low latency, and edge locations deliver content and process requests closer to users.
  • AWS Outposts extends AWS infrastructure and services into an organization’s on-premises facility.

Core services and security.

  • AWS services fall into categories such as compute, storage, database, networking, security, application integration, and management and governance.
  • Amazon S3, Amazon EBS, and Amazon EFS support object, block, and file storage.
  • Amazon VPC provides an isolated virtual network that contains subnets, routes, gateways, and security controls.
  • Elastic Load Balancing and Amazon EC2 Auto Scaling improve application availability and scalability.
  • Under the Shared Responsibility Model, AWS secures the cloud, and the customer secures what it puts in the cloud.

Pricing and cost tools.

  • AWS replaces capital expense with variable expense, so customers pay for the resources they use.
  • The AWS Pricing Calculator estimates the cost of a planned architecture, and Migration Evaluator supports migration planning.
  • AWS Cost Explorer, AWS Budgets, Cost Optimization Hub, and AWS Compute Optimizer help you review spending and find savings.
  • Cost optimization includes rightsizing resources, removing waste, selecting appropriate purchasing options, and monitoring spending.
  • Data transfer between AZs and between Regions adds cost, so design with both availability and cost in mind.

4. Knowledge Check

Answer each question in your own words before you open the model answer. The questions were written for this course.

Question 1: Explain the purpose and benefits of AWS, and describe how it changes the way a company pays for IT.

Maps to: Objective 1 (Comprehension).

AWS provides infrastructure and managed services on demand, through a global network of data centers. Its advantages include trading capital expense for variable expense, benefiting from economies of scale, stopping guessing capacity, increasing speed and agility, and going global in minutes. Instead of buying hardware before it knows its needs, a company pays only for the resources that it consumes.

Question 2: What is the relationship between a Region and an Availability Zone?

Maps to: Objective 2 (Comprehension).

A Region is a geographic area. It contains multiple isolated Availability Zones, at least three, and each zone has one or more data centers with independent power, cooling, and networking. The zones in a Region connect through high-bandwidth, low-latency networking.

Question 3: What factors should a solutions architect evaluate when selecting an AWS Region?

Maps to: Objective 2 (Application).

Compliance and data residency, latency to users, price, the availability of the needed services in that Region, and the disaster recovery plan, which needs a second Region. Compliance often comes first, because data must stay in the required country or jurisdiction.

Question 4: Why should a production application use more than one AZ?

Maps to: Objective 3 (Analysis).

If the application runs in one AZ, an outage in that AZ makes it unavailable. Spreading critical resources across two or more AZs removes the single AZ as a single point of failure, so the application keeps serving users through the healthy zones.

Question 5: Would a Multi-AZ architecture protect an application from an entire Regional failure? What would you add?

Maps to: Objective 3 (Evaluation).

No. A Multi-AZ design protects against the failure of an AZ, but a Region-wide disruption affects every zone in the Region. A Multi-Region architecture supports disaster recovery, with replicated data, cross-Region traffic routing, and a failover plan. It is more complex and costs more.

Question 6: Which AWS services could distribute an application across multiple AZs?

Maps to: Objective 3 (Application).

An Application Load Balancer, which spreads traffic across AZs, an Amazon EC2 Auto Scaling group that spans the AZs, an Amazon RDS Multi-AZ deployment for the database, and replicated or regional storage services.

Question 7: A team needs shared file storage that several EC2 instances use at the same time, and a managed relational database. Which services fit, and in which categories are they?

Maps to: Objective 4 (Application).

Amazon EFS, a storage service, provides a shared file system that many resources access at once. Amazon RDS, a database service, provides a managed relational database. Amazon EBS would not fit the first need, because an EBS volume is block storage for EC2 instances.

Question 8: A company runs one application on Amazon EC2 and another on Amazon RDS. For each, who patches the operating system?

Maps to: Objective 5 (Application).

For Amazon EC2, the customer patches the guest operating system, because EC2 is a customer-managed compute service. For Amazon RDS, AWS patches the database software and the underlying operating system, and the customer manages the data, the database users, and the network access rules.

Question 9: List three things that you can do in the AWS Management Console, and describe how you would change the Region.

Maps to: Objective 6 (Application).

You can open a service console, search for services with Unified Search, and run commands in AWS CloudShell. To change the Region, select the Region in the console, or change the default Region in the unified settings, before you create resources, because most resources belong to one Region.

Question 10: A team wants to estimate the cost of a new architecture, and later wants to find savings on the running workload. Which tools would you recommend at each stage, and what data transfer cost should the team watch?

Maps to: Objective 7 (Evaluation).

Before deployment, use the AWS Pricing Calculator, and use Migration Evaluator when moving an existing environment. After deployment, use AWS Cost Explorer to analyze spending, AWS Budgets for alerts, and Cost Optimization Hub and AWS Compute Optimizer for recommendations such as rightsizing. Watch data transfer between AZs and between Regions, which is charged per gigabyte, and keep chatty components in the same AZ.

1. IAM Overview, Users, and Groups

Problem Statement

You work as a junior AWS solutions architect at RetailCloud, a fast-growing e-commerce platform, under the guidance of a lead architect. As traffic to the site grows, the infrastructure team faces a compliance risk: unrestricted, broad access policies are granted, and junior developers have full administrator access. The security team wants fine-grained policies instead.

Your lead architect assigns you an access management audit. Before you change anything, you need answers to the questions below. This lesson explains the IAM identities, permissions, and policies that you need to answer them.

Your challenge:

  • Which kind of identity does each person, team, and application need: an IAM user, an IAM group, or an IAM role?
  • How can job-based groups, such as DevTeam, OpsTeam, and Auditors, receive only the permissions that their jobs require?
  • How can developers work in production without holding direct permissions?
  • How does AWS decide whether to allow or deny a request when several policies apply?

1.1 Core AWS Security Services

The diagram gives a categorized breakdown of the core AWS security services that are essential for building secure architectures on AWS and for preparing for the SAA-C03 exam. IAM is the first service in the identity and access category.

1.2 Overview of IAM: AWS Identity and Access Management

AWS Identity and Access Management (IAM) is an AWS service that controls who can access AWS resources and what actions they can perform.

IAM is a global AWS service, so you do not select a Region. It lets you centrally manage fine-grained access to AWS services and resources. It uses an implicit deny default: if a permission is not explicitly allowed, it is blocked.

IAM addresses two important security questions:

  • Authentication: who are you?
  • Authorization: what are you allowed to do?

IAM can control access to services such as Amazon EC2, Amazon S3, Amazon RDS, AWS Lambda, and Amazon DynamoDB. Administrators grant permissions through JSON policy documents. The important characteristics of IAM are:

  • IAM is available globally and is not limited to one AWS Region.
  • IAM can control access to the AWS Management Console, the AWS CLI, SDKs, and APIs.
  • IAM supports fine-grained permissions.
  • IAM supports users, groups, roles, policies, federation, and multi-factor authentication (MFA).
  • IAM is provided at no additional charge.

1.2.1 Real-World Scenario

A company has developers, database administrators, security analysts, and billing specialists in the same AWS environment. IAM lets the company grant each team only the permissions that its job requires. For example:

  • Developers can manage EC2 development instances.
  • Database administrators can manage RDS databases.
  • Security analysts can review security logs.
  • Billing specialists can view cost reports but cannot modify resources.

This follows the principle of least privilege.

Exam tip: IAM is a global service, so its changes apply to all Regions. IAM is also eventually consistent, so a change can take a short time to become visible everywhere. Do not rely on an IAM change taking effect instantly.

For further details, see What is IAM? and How IAM works.

1.3 AWS Account: User Types

AWS provides two primary user types: the AWS account root user and IAM users. The root user is the top-level identity that AWS creates automatically when you set up an AWS account, and it has unrestricted access to the account. An IAM user is a managed IAM identity. For more information, see AWS account root user.

AWS recommends that you do not use the root user for everyday tasks, and that you protect it with MFA.

1.4 Introduction to IAM Identities

IAM identities are the identities that you create inside IAM: IAM users, IAM groups, and IAM roles. IAM policies, shown below the identities in the first image, define their permissions.

1.5 IAM Users

An IAM user represents a person or an application that needs access to resources in one AWS account. An IAM user can have:

  • A username and password for console access.
  • Access keys for programmatic access.
  • MFA devices.
  • Permissions that you assign directly or through an IAM group.
  • A quota of 5,000 IAM users in one AWS account.

IAM users normally have long-term credentials. For this reason, AWS recommends that you use temporary credentials and federation for human workforce access whenever possible.

1.5.1 Use Cases and Types of Credentials

  • Use cases: an employee who needs to manage AWS resources, and an application that needs to access AWS APIs.
  • Console password: lets a user sign in to the AWS Management Console.
  • Programmatic access: an access key ID and a secret access key, used through the AWS CLI or SDKs.
  • SSH keys: used to connect to AWS CodeCommit repositories.
  • Example: create an IAM user named john.doe who needs access to manage EC2 instances.

1.5.2 Real-World Scenario

A small business has one AWS account and creates an IAM user named emergency-admin. This account is reserved for emergency administrative access and is protected with MFA. For everyday employee access, the company uses IAM Identity Center instead of creating individual IAM users.

Important exam point: an IAM user is an identity with long-term credentials. A role is assumed temporarily and provides temporary credentials.

1.6 IAM Groups

An IAM group is a collection of IAM users. Groups make it easier to assign the same permissions to many users, because a policy that is attached to a group applies to every user in the group. For example, an administrator could create the groups Developers, Operations Team, DatabaseAdmins, SecurityAuditors, and BillingTeam. The purpose is to simplify access management by applying permissions to a group instead of managing individual users.

The important characteristics are:

  • A group can contain IAM users.
  • A user can belong to multiple groups, up to 10 by default.
  • Groups cannot contain other groups.
  • Groups cannot be assumed.
  • An IAM group is not used as a principal in a resource-based policy.

1.6.1 Real-World Scenario

A company hires five developers. Instead of attaching the same policies to five IAM users, the administrator adds the users to the Developers group. The group allows developers to start and stop development EC2 instances, read application files from a development S3 bucket, and view CloudWatch logs. When a developer leaves the company, the administrator removes that user from the group.

1.6.2 Critical Exam Rules

  • Groups cannot be nested: a group cannot contain another group.
  • Groups are not identities: they cannot be listed as a Principal in resource-based policies.
  • A user can belong to multiple groups.

2. IAM Roles

Problem Statement

RetailCloud’s developers need to work in production, but the security team does not want them to hold direct permissions there. RetailCloud’s applications on EC2 also need to read files from S3, and the team must not store access keys on the servers.

The architect explains how IAM roles solve both problems.

Your challenge:

  • Explain what an IAM role is and why roles are better than access keys.
  • Describe the trust policy and the permissions policy of a role.
  • Set up a role so that an EC2 application can read S3 without stored keys.

2.1 IAM Roles

An IAM role is an AWS identity with permissions, but it is not permanently associated with one person. A trusted user, application, AWS service, or external identity can assume the role.

IAM roles have several advantages over access keys:

  • Temporary identities: roles have no passwords or access keys. AWS services, such as an EC2 server or a Lambda function, assume them for a short time.
  • No long-term storage: you do not embed or save passwords or secret access keys in your application code.
  • Least privilege access: you can assign fine-grained permissions to a role, which grants only the access that a task or service needs. This minimizes the damage if credentials are compromised.
  • Flexibility: you can associate a role with many entities, which supports central access management and reduces administrative work.
  • Trust relationships: a role can trust other AWS accounts or services, which enables cross-account or cross-service access.

2.1.1 Roles Are Commonly Used For

  • AWS services that need access to other services.
  • Cross-account access.
  • Federated users.
  • Applications that run on EC2.
  • Lambda functions.
  • Temporary administrative access.
  • Temporary security credentials that AWS Security Token Service (AWS STS) provides, which expire and rotate automatically.

2.1.2 The Two Policy Components of a Role

A role typically contains two important policy components. The trust policy defines who, or which service or account, can assume the role:

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Principal": {
      "Service": "ec2.amazonaws.com"
    },
    "Action": "sts:AssumeRole"
  }]
}

The permissions policy defines what the role can do after it is assumed:

{
  "Version": "2012-10-17",
  "Statement": [{
    "Effect": "Allow",
    "Action": ["s3:GetObject", "s3:PutObject"],
    "Resource": "arn:aws:s3:::my-bucket/*"
  }]
}

2.1.3 Real-World Scenario: EC2 Access to S3

An application that runs on an EC2 instance must read files from an S3 bucket. The secure solution is to:

  1. Create an IAM role.
  2. Allow EC2 to assume the role through its trust policy.
  3. Attach a policy that allows the required S3 actions.
  4. Associate the role with the EC2 instance through an instance profile.

The application receives temporary credentials automatically. Developers do not need to store access keys on the instance.

Important exam point: if an AWS service needs permission to access another AWS service, use an IAM role instead of embedding access keys.

For further details, see IAM role creation and Create a role to delegate permissions to an AWS service.

3. IAM Permissions and Policies

Problem Statement

RetailCloud’s security team wants to know exactly how AWS decides whether to allow a request when several policies apply. The team also needs to share an S3 bucket with a customer’s account, and it wants developers to create roles without being able to give themselves administrator rights.

The architect explains permissions, policies, the two policy types, cross-account access, and permissions boundaries.

Your challenge:

  • Explain how IAM evaluates permissions, and apply least privilege.
  • Read and write the main parts of a policy.
  • Distinguish identity-based from resource-based policies, and describe cross-account access.
  • Explain what a permissions boundary does.

3.1 IAM Permissions

3.1.1 What Are IAM Permissions?

IAM permissions determine what actions an identity is allowed or denied to perform on AWS resources. You commonly assign permissions to IAM users, IAM roles, AWS services, and federated identities. You define permissions with IAM policies, which are JSON documents that specify allowed or denied actions.

For example, a user might be allowed to view objects in an S3 bucket, start or stop EC2 instances, and read records from DynamoDB. The same user might be denied permission to delete the S3 bucket, terminate EC2 instances, and modify IAM policies.

Key takeaway: IAM permissions control who can do what on which AWS resources.

3.1.2 IAM Permission Evaluation

When AWS receives a request, it evaluates all the applicable policies. AWS considers permissions from sources such as identity-based policies, resource-based policies, permissions boundaries, service control policies (SCPs), and session policies. The simplified flow is: request, authentication, policy evaluation, allow or deny. AWS checks:

  1. Who is making the request?
  2. What action are they requesting?
  3. Which resource are they accessing?
  4. Which policies apply?
  5. Is there an explicit Deny?
  6. Is the action explicitly allowed?

3.1.3 Least Privilege

The principle of least privilege means granting only the permissions that a job requires. Instead of allowing all actions on all resources, allow only the required actions on the required resources. Avoid:

"Action": "*",
"Resource": "*"

When possible, use a list of specific actions, for a specific S3 bucket:

"Action": [
  "s3:GetObject",
  "s3:PutObject"
]

Least privilege reduces accidental changes, unauthorized access, security exposure, and the damage from compromised credentials.

3.2 IAM Policies

A policy is an object in AWS that defines permissions when you associate it with an identity or a resource. AWS evaluates the policies when an IAM principal, a user or a role, makes a request. The permissions in the policies determine whether the request is allowed or denied. AWS stores most policies as JSON documents that are attached to an IAM identity (a user, a group of users, or a role).

  • A policy states whether specific actions are allowed or denied on specified AWS resources.
  • Policies can be reused with different services in AWS. You can assign the same policy to different people and teams.

3.2.1 IAM Policy Structure

A policy normally contains the following elements:

  • Effect: Allow or Deny.
  • Action: the operations that can be performed.
  • Resource: the resources that the policy affects.
  • Condition: optional requirements that must be satisfied.
  • Principal: the identity that receives access. It is normally used in resource-based and trust policies.

Example 1: start or stop instances based on tags

3.2.2 Example 2: An S3 Read Policy

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::training-materials/*"
    }
  ]
}

This policy allows an identity to read objects from the training-materials bucket. It does not allow the identity to upload, modify, or delete objects.

3.2.3 IAM Policy Components

An IAM policy statement combines the following components:

  • Principal: who the policy applies to, such as an IAM user. Resource-based policies and trust policies include this element.
  • Effect: whether the statement allows or denies the permission.
  • Action: the service and operation that the statement covers, such as running or terminating an Amazon EC2 instance.
  • Resource: the specific resources that the statement covers, such as one Amazon EC2 instance identified by its instance ID. Add this element when permissions must be managed at the resource level.
  • Condition: dynamic information that limits when the statement applies, such as allowing access to an Amazon EC2 instance only if it has the tag environment equal to development.

When a user tries to access a service or perform an action, AWS evaluates all of these components and then grants or denies the access.

3.2.4 Policy Evaluation Rules

Remember these fundamental rules:

  1. Access is denied by default.
  2. An applicable Allow can grant access.
  3. An applicable explicit Deny overrides an Allow.
  4. Principal names the account, user, role, or service that is targeted. It is required in resource-based policies.

3.3 IAM Policy Types

3.3.1 Identity-Based Policies

An identity-based policy is attached to an IAM identity (a user, a group of users, or a role). It defines what that identity can do. For example, a policy that is attached to the Developers role lets developers retrieve objects from a specific S3 bucket. The policy answers the question, “What is this identity allowed to do?”

Identity-based policies include AWS managed policies, customer managed policies, and inline policies.

Policy typeDescription
AWS managed policyA policy that AWS provides by default. AWS creates and maintains it for common job functions or use cases.
Customer managed policyA policy that the customer creates and maintains. It is reusable across identities, and it normally gives more control than a broad AWS managed policy.
Inline policyA policy that is embedded directly in a single IAM user, group, or role, in a one-to-one relationship. It gives granular control, but you cannot reuse it for other users or roles, so it is less flexible than a managed policy.

An identity-based policy defines the permissions of the IAM user, group, or role that it is attached to. It has no Principal element, because the identity that the policy is attached to becomes the principal.

  • Managed policies are reusable policies that you can attach to many identities. For example, one custom policy can be attached to every developer. They are either AWS managed policies, which AWS creates in advance, or customer managed policies, which you create and reuse.
  • Inline policies apply to one user, group, or role only, and you cannot reuse them. For example, an inline policy suits a user who temporarily needs extra permissions for a special activity, because it avoids creating another reusable policy. Deleting the user also deletes the inline policy.

To learn how to create an IAM policy by using JSON policy documents like these, see Creating policies using the JSON editor.

3.3.2 Resource-Based Policies

A resource-based policy is attached directly to a resource. It defines which principals can access that resource, what they can do, and under what conditions. It includes a Principal element, which identity-based policies do not.

Services that support resource-based policies include:

  • Amazon S3 bucket policies.
  • AWS KMS key policies.
  • Amazon SQS queue policies.
  • Amazon SNS topic policies.
  • Lambda resource-based policies.
  • Secrets Manager resource policies.

The policy answers the question, “Who is allowed to access this resource?”

3.3.3 Examples of Resource-Based Policies

Example 1: make an S3 bucket publicly accessible, for example to host a static website:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "PublicReadGetObject",
      "Effect": "Allow",
      "Principal": "*",
      "Action": "s3:GetObject",
      "Resource": "arn:aws:s3:::my-publicbucket/*"
    }
  ]
}
  • my-publicbucket is a placeholder. Replace it with your exact, globally unique S3 bucket name, for example arn:aws:s3:::my-company-public-website-2026/*.
  • Keep the /* at the end, so that the permission applies to the objects inside the bucket.

Example 2: allow an external AWS account, Account A, to send messages to a queue in Account B:

{
  "Version": "2012-10-17",
  "Id": "CrossAccountSQSAccess",
  "Statement": [
    {
      "Sid": "AllowAccountAtoSend",
      "Effect": "Allow",
      "Principal": {
        "AWS": "arn:aws:iam::111122223333:root"
      },
      "Action": "sqs:SendMessage",
      "Resource": "arn:aws:sqs:ap-south-1:444455556666:MyQueue"
    }
  ]
}

3.3.4 Identity-Based Compared With Resource-Based Policies

Identity-based policyResource-based policy
Attached to a user, group, or roleAttached to a resource
Specifies permitted actions and resourcesSpecifies principals, actions, and the resource
Travels with the identityStays with the resource
Does not normally include a PrincipalUsually includes a Principal
Useful for managing a person’s or role’s permissionsUseful for sharing a resource or granting service access

3.3.5 Real-World Scenario

A company wants an external auditing company to read a specific S3 bucket. It can create an S3 bucket policy that identifies the auditor’s AWS role as the principal, allows s3:GetObject, limits access to the audit bucket, and denies unencrypted network connections. This resource-based policy grants access to the bucket without making its contents public. See the official IAM policies and permissions documentation and Identity-based policies and resource-based policies.

Exam tip: when a question asks how to serve a static website or public images directly from S3, the solution needs both of these: an S3 bucket policy that grants s3:GetObject to Principal "*", and S3 Block Public Access turned off for the bucket. As an alternative, use CloudFront Origin Access Control to keep the bucket private.

3.4 Cross-Account Access

Cross-account access lets a principal in one AWS account access resources in another AWS account. A common approach uses an IAM role:

  1. The destination account creates a role.
  2. The role’s trust policy trusts a principal from the source account.
  3. The role receives permissions to access the destination resources.
  4. The source principal receives permission to call sts:AssumeRole.
  5. AWS STS issues temporary credentials when the role is assumed.

3.4.1 Real-World Scenario

A company needs to read objects from an Amazon S3 bucket that belongs to a customer in another AWS account. Account A is the company, the requester, and Account B is the customer, the bucket owner. Both accounts must grant access:

  • In Account B, the customer attaches a resource-based policy to the S3 bucket. The principal in the policy is the Account A account ID and the IAM user from Account A.
  • In Account A, an identity-based policy allows that IAM user to access the S3 bucket.

A resource-based policy can also make a bucket public. For a static website, a policy with the principal set to * and the action set to s3:GetObject lets any user on the internet read any object in the bucket, as in Example 1 in section 3.3.3. Hosting a static website is covered in the Amazon S3 lesson.

3.4.2 Create IAM Policies in the Console

You can create a customer managed policy in the AWS Management Console by using one of these methods:

  • JSON: paste and customize a published example identity-based policy.
  • Visual editor: construct a new policy from scratch in the visual editor. If you use the visual editor, you do not have to understand JSON syntax.
  • Import: import and customize a managed policy from within your account. You can import an AWS managed policy or a customer managed policy that you created earlier.

3.5 IAM Permissions Boundaries

An IAM permissions boundary is an advanced IAM feature that sets the maximum permissions that identity-based policies can grant to an IAM user or role. The most important concept is: a permissions boundary limits permissions, and it does not grant permissions. Permissions boundaries are supported for users and roles, not for groups.

AWS evaluates the permissions that both the identity-based policy and the permissions boundary allow. The effective identity-based permissions are the intersection of the two. See the AWS documentation on permissions boundaries.

3.5.1 How Permissions Boundaries Work

Suppose a developer has an identity-based policy with full access to EC2, S3, DynamoDB, and IAM. The administrator applies a permissions boundary that allows EC2, S3, and DynamoDB. The resulting permissions are:

ServiceIn the identity policyIn the boundaryEffective permission
EC2YesYesAllowed
S3YesYesAllowed
DynamoDBYesYesAllowed
IAMYesNoNot allowed

Even though the identity-based policy grants IAM access, the user cannot use that permission, because it falls outside the boundary.

Think of the permissions boundary as a ceiling. The identity policy grants permissions, and the permissions boundary sets the maximum that the policy can grant. If the boundary permits s3:* but the user’s identity policy grants only s3:GetObject, the user gets only s3:GetObject. The boundary’s s3:* does not give the user the additional S3 permissions.

3.5.2 Why Use Permissions Boundaries?

A common use case is delegated administration. For example, your security administrator wants developers to create IAM roles for their applications, but does not want developers to create roles with unrestricted administrative privileges. The administrator establishes a permissions boundary, and every role that a developer creates must stay within that boundary. AWS specifically recommends permissions boundaries when you delegate permissions management within an account. See IAM best practices.

SAA-C03 key takeaway: IAM permissions boundaries define the maximum permissions that identity-based policies can grant to an IAM user or role. They do not grant permissions themselves. A keyword to associate: “Delegate IAM administration but prevent users from exceeding specified permissions” points to a permissions boundary.

3.6 Lesson Summary

Key points

  • Definition: IAM is a global service, with no Region selection, that controls authentication (“Who are you?”) and authorization (“What are you allowed to do?”).
  • Security principle: IAM denies by default. If an action is not explicitly allowed, it is blocked.
  • Policy evaluation: an explicit Deny always overrides an Allow.
  • Root user: the top-level identity that AWS creates with the account. It has unrestricted access.
  • IAM users represent people or applications and use long-term credentials. AWS recommends that you minimize their use.
  • IAM groups are collections of users. You attach policies to the group instead of to individual users. Groups cannot be nested or assumed.
  • IAM roles provide temporary credentials. They are ideal for AWS services, such as EC2 and Lambda, and for cross-account access, because they remove the need to store long-term keys.
  • Policies are JSON documents that define permissions, and AWS evaluates them whenever a principal makes a request. They include Effect, Action, Resource, Condition, and Principal, which is used in resource-based and trust policies.
  • Identity-based policies are attached to users, groups, or roles. Resource-based policies are attached directly to a resource, such as an S3 bucket.

Important exam points

  • IAM policies define permissions by using JSON, and access is denied by default unless it is explicitly allowed.
  • Permissions boundaries and SCPs can restrict the maximum available permissions.
  • Least privilege reduces unnecessary access.
  • IAM permissions are important for understanding how Amazon Cognito identity pools give application users controlled access to AWS resources.
  • For role-based cross-account access, both sides must be configured: the role’s trust policy identifies who may assume it, and the source identity must have permission to call sts:AssumeRole.
  • Resource-based policies can also provide cross-account access for supported services, such as S3 and SQS.

3.6.1 Common Exam Traps and Tips

  • Storing access keys on an EC2 instance. The incorrect approach is to store an IAM user’s access keys in a configuration file. The best approach is to attach an IAM role to the EC2 instance.
  • Creating IAM users in every AWS account. The incorrect approach is to duplicate workforce identities across all accounts. The best approach is to use IAM Identity Center with AWS Organizations.
  • Assuming a group can access a resource directly. Groups organize IAM users. They are not assumed, and they are not used as principals in resource-based policies.
  • Ignoring an explicit Deny. An Allow does not override an applicable explicit Deny.
  • Confusing authentication with authorization. Passwords, MFA, and identity providers establish identity. Policies determine the permitted actions.
  • Confusing IAM Identity Center with Amazon Cognito. IAM Identity Center serves employees and workforce users. Amazon Cognito serves customers who use web or mobile applications.

Final memory aid: users identify individuals, groups organize users, roles provide temporary access, and policies define permissions.

3.7.1 Exam-Style Question

Written for this course.

Scenario: An IAM user belongs to a group whose policy allows s3:DeleteObject on a bucket. A second policy on the same user explicitly denies s3:DeleteObject on that bucket. The user tries to delete an object. What happens? Which solution meets the requirements?

  • A. The request is allowed, because the group policy allows it.
  • B. The request is denied, because an applicable explicit Deny overrides an Allow.
  • C. The request is allowed, because the most recently attached policy wins.
  • D. The request depends on the Region where the bucket is located.
Show Answer and Explanation

Correct answer: B. An applicable explicit Deny overrides any Allow.

OptionResultReason
AIncorrectAn Allow does not override an explicit Deny.
BCorrectAn explicit Deny always overrides an Allow.
CIncorrectPolicy evaluation does not depend on which policy was attached last.
DIncorrectIAM is global, and this evaluation rule does not depend on the Region.

3.7.2 Exam-Style Question

Written for this course.

Scenario: A company wants to host a static website from an S3 bucket that visitors on the internet can read. Which combination is required? Which solution meets the requirements?

  • A. An identity-based policy for every visitor.
  • B. A bucket policy that grants s3:GetObject to Principal "*", and S3 Block Public Access turned off for the bucket.
  • C. An IAM group that contains all visitors.
  • D. A permissions boundary on the bucket.
Show Answer and Explanation

Correct answer: B. Public reads need a resource-based bucket policy with a public principal, and Block Public Access must not block it.

OptionResultReason
AIncorrectVisitors are anonymous, so no identity-based policy applies to them.
BCorrectThe bucket policy grants public read access, and Block Public Access is turned off for the bucket.
CIncorrectGroups contain IAM users, and visitors are not IAM users.
DIncorrectPermissions boundaries apply to IAM users and roles, not to buckets.

3.7.3 Exam-Style Question

Written for this course.

Scenario: A developer’s identity-based policy grants s3:GetObject. The developer’s permissions boundary allows s3:*. Which S3 permissions does the developer have? Which solution meets the requirements?

  • A. All S3 actions, because the boundary allows s3:*.
  • B. Only s3:GetObject.
  • C. No S3 actions, because the boundary does not grant permissions.
  • D. All S3 actions except s3:DeleteObject.
Show Answer and Explanation

Correct answer: B. The effective permissions are the intersection of the identity-based policy and the boundary, which is s3:GetObject only.

OptionResultReason
AIncorrectA boundary does not grant permissions, so s3:* does not give extra access.
BCorrectThe identity policy grants only s3:GetObject, and the boundary allows it, so s3:GetObject is the only effective permission.
CIncorrectThe boundary does not remove permissions that both policies allow.
DIncorrectNothing in either policy removes s3:DeleteObject while it grants all actions.

3.7.4 Exam-Style Question

Written for this course.

Scenario: A company in Account A must read objects from an S3 bucket in Account B. Which configuration allows this by using a bucket policy? Which solution meets the requirements?

  • A. Only an identity-based policy in Account A.
  • B. Only a bucket policy in Account B.
  • C. A bucket policy in Account B that names the Account A principal, and an identity-based policy in Account A that allows the access.
  • D. A permissions boundary in Account B.
Show Answer and Explanation

Correct answer: C. For an IAM user in another account, both sides must grant access: a resource-based policy in the bucket owner’s account, and an identity-based policy in the requester’s account.

OptionResultReason
AIncorrectThe bucket owner must also grant access to the Account A principal.
BIncorrectThe Account A identity also needs permission to use the bucket.
CCorrectBoth accounts must grant access: the bucket policy in Account B, and the identity-based policy in Account A.

4. Knowledge Check

Answer each question in your own words before you open the model answer. The questions were written for this course.

Question 1: What is the difference between authentication and authorization, and what does it mean that IAM denies by default?

Maps to: Objective 1 (Comprehension).

Authentication answers “Who are you?” and authorization answers “What are you allowed to do?” IAM works with an implicit deny default, so an action that no policy explicitly allows is blocked.

Question 2: Why is IAM called a global service, and what does eventual consistency mean for the changes that you make?

Maps to: Objective 1 (Comprehension).

You do not select a Region for IAM, and its identities and policies apply to all Regions. IAM is eventually consistent, so a change can take a short time to become visible everywhere, and applications should not depend on an IAM change taking effect instantly.

Question 3: Compare the root user, an IAM user, an IAM group, and an IAM role.

Maps to: Objective 2 (Analysis).

The root user is created with the account and has unrestricted access, so it should not be used for everyday tasks. An IAM user represents a person or an application and has long-term credentials. An IAM group is a collection of users to which you attach policies, and it cannot be nested or assumed. An IAM role has no permanent owner. A trusted entity assumes it and receives temporary credentials.

Question 4: An application on an EC2 instance must write to an S3 bucket. Describe the secure setup, and say why it is better than access keys.

Maps to: Objective 2 (Application).

Create a role whose trust policy lets EC2 assume it, attach a permissions policy that allows the needed S3 actions on the bucket, and associate the role with the instance through an instance profile. The application receives temporary credentials automatically, so no access keys are stored on the instance, and the credentials expire and rotate.

Question 5: Rewrite a policy that allows "Action": "*" on "Resource": "*" so that it follows least privilege for an application that reads one S3 bucket.

Maps to: Objective 3 (Application).

Replace the wildcards with the specific action and resource, for example "Action": "s3:GetObject" and "Resource": "arn:aws:s3:::bucket-name/*". Grant only what the job needs, which reduces accidental changes, unauthorized access, and the damage from compromised credentials.

Question 6: A user has one policy that allows an action and another that explicitly denies it. What is the result, and what are the basic evaluation rules?

Maps to: Objective 3 (Application).

The request is denied. Access is denied by default, an applicable Allow can grant access, and an applicable explicit Deny overrides an Allow.

Question 7: Distinguish an identity-based policy from a resource-based policy, and say what each account must configure when a customer’s IAM user reads your S3 bucket.

Maps to: Objective 4 (Analysis).

An identity-based policy is attached to a user, group, or role and has no Principal element. A resource-based policy is attached to a resource, such as an S3 bucket, and names the principals in a Principal element. For a cross-account IAM user, the bucket owner attaches a resource-based policy that names the other account’s principal, and the other account attaches an identity-based policy that allows the access. Both sides must allow it.

Question 8: Explain what a permissions boundary does, using an example, and name a case where you would use one.

Maps to: Objective 3 (Comprehension).

A permissions boundary sets the maximum permissions that identity-based policies can grant to a user or role. It limits permissions and never grants them. The effective permissions are the intersection of the two. If a policy grants EC2, S3, DynamoDB, and IAM, and the boundary allows only EC2, S3, and DynamoDB, the identity cannot use IAM. A common use is delegated administration, where developers create roles that cannot exceed the boundary.

Question 9: RetailCloud wants developers to work in production without holding direct permissions, and job-based teams to get only the permissions that they need. Describe your design.

Maps to: Objectives 2 and 3 (Synthesis).

Create groups for the job functions, such as DevTeam, OpsTeam, and Auditors, and attach least-privilege policies to the groups. Do not give developers direct production permissions. Create a production role with a trust policy that allows the developers to assume it and a permissions policy that grants only the needed access, so that they receive temporary credentials when they work in production. Avoid broad administrator access and long-term access keys.

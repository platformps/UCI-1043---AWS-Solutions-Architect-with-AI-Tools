1. AWS Organizations Overview and Core Components

Problem Statement

FinTech Global, a fast-growing financial services enterprise, scaled from one AWS account to more than 30 accounts. Development, Staging, Security, and Production teams manage their accounts independently. Administrators in non-production accounts disabled Amazon CloudTrail and AWS Config to avoid log clutter, which caused serious compliance audit findings. Teams also manage separate payment methods and logins, which adds administrative overhead.

Leadership wants one central way to govern all of these accounts. What does AWS offer?

1.1 Why Multiple Accounts Create Challenges

Organizations often run several AWS accounts. Different departments, teams, or applications might each use their own account. This creates challenges such as:

  • Billing: Separate billing for each account increases administrative complexity.
  • Management overhead: Separate logins, user management, and maintenance for each account are cumbersome.
  • Security inconsistencies: Configuring IAM policies and security settings account by account can lead to vulnerabilities.
  • Limited resource sharing: Without central control, resources can be underused, and redundancy raises costs.

AWS Organizations addresses these issues with a centralized management model for all your AWS accounts.

Think of AWS Organizations as a multinational company. The management account works like a corporate headquarters. It sets high-level policies and oversees the subsidiary accounts, so every account follows central guidelines while keeping some autonomy.

1.2 What AWS Organizations Is

AWS Organizations is an account management service for central management and governance across multiple AWS accounts. As enterprises grow, managing accounts one by one creates administrative overhead, fragmented security boundaries, and complex billing. AWS Organizations consolidates accounts into one manageable hierarchy. Each organization has a unique organization ID.

1.3 Core Components

  • Organization root: The parent node of the hierarchy. All organizational units and accounts belong to it. The organization root is the top-level container. It is not an AWS account. Policies that you apply to the root cascade down to all OUs and member accounts. An organization always starts with one root.
  • Management account: The account that administers the organization. AWS formerly called it the master account. It is also the payer account: it pays the bill for the entire organization, including all member accounts. It creates and invites accounts, applies policies, and integrates other AWS services.
  • Member accounts: The other AWS accounts in the organization. They host workload resources, for example development, testing, and production.
  • Service control policies (SCPs): Organization-level policies that define the maximum permissions for permitted or denied operations in your accounts. You can apply them to the whole organization, to specific OUs, or to individual accounts.
  • Organizational units (OUs): Groups of accounts that serve specific applications, based on common requirements, environments, or business functions. You can group all development accounts together, for example, and apply consistent policies to that group. OUs support up to five levels of nesting.

Do Not Confuse These Terms

  • The organization root is the top of the hierarchy. It is not an account.
  • The management account is an AWS account that administers the organization and pays its bill.
  • The root user is different. Each AWS account has its own root user, which signs in with the account’s email address. Do not confuse the organization root with an account’s root user.

Exam Trap

  • SCPs do not apply to the management account, so do not place workloads in it.
  • The management account pays the bill for all member accounts. It is not a separate “payer” you create.

Memory Hook

The root is the top of the tree, the management account runs the organization, and OUs group the member accounts.

2. Key Features and Policy Types

Problem Statement

FinTech Global receives a separate bill for each of its 30 accounts, and the security team wants to apply policies in one place instead of account by account. Leadership also wants to know which kinds of policy AWS Organizations can enforce across accounts.

2.1 Key Features

AWS Organizations provides central operational controls that simplify governance, compliance, and billing across an enterprise:

  • Central account management: Administer several AWS accounts from a single interface.
  • Groups with common policies: Organize accounts into OUs to simplify policy enforcement.
  • Security and auditing integration: Integrates with AWS security tools such as AWS IAM Identity Center, AWS CloudTrail, AWS Config, Amazon GuardDuty, and AWS Security Hub to enforce unified audit logging and identity management across accounts.
  • SCPs: Apply policies that define the permitted actions across accounts.
  • AWS service integrations: Works with services such as AWS Resource Access Manager (AWS RAM), which can share Amazon Virtual Private Cloud (Amazon VPC) subnets, and with IAM Identity Center for central single sign-on.
  • Policy-based governance: Enforces organization-wide guardrails across accounts and OUs.
  • Consolidated billing: Merges the charges of all member accounts into one bill that the management account pays. This enables volume discounts across the whole organization.

2.2 Enabling All Features

AWS Organizations has two feature sets: all features, which is the default and preferred way to work, and consolidated billing features only. When you enable all features, AWS Organizations can:

  • Apply SCPs.
  • Enforce tag policies.
  • Manage backup policies.
  • Use AI services opt-out policies.
  • Control access and governance across accounts.
  • Enforce guardrails at the root, OU, and account levels.

Moving from consolidated billing only to all features is one-way. You cannot switch an organization with all features enabled back to consolidated billing only. Invited accounts must approve the change.

2.3 Organization Policy Types

AWS Organizations offers policy types in two broad categories. You can use organization policies when all features are enabled.

2.3.1 Authorization Policies

Authorization policies help you centrally manage the security of accounts across an organization.

  • Service control policies (SCPs) offer central control over the maximum available permissions for IAM users and IAM roles in an organization.
  • Resource control policies (RCPs) offer central control over the maximum available permissions for resources in an organization.

2.3.2 Management Policies

Management policies help you centrally configure and manage AWS services and their features across an organization.

  • Declarative policies centrally declare and enforce desired configurations for an AWS service at scale. Once attached, the configuration is maintained when the service adds new features or APIs.
  • Backup policies manage and apply backup plans to resources across an organization’s accounts.
  • Tag policies standardize the tags on resources in an organization’s accounts.
  • Chat applications policies control access to an organization’s accounts from chat applications such as Slack and Microsoft Teams.
  • AI services opt-out policies control data collection for AWS AI services for all accounts.
  • Security Hub policies address security coverage gaps and apply security requirements centrally.
  • Amazon Inspector policies enable and manage Amazon Inspector across accounts.
  • Amazon Bedrock policies enforce Amazon Bedrock Guardrails safeguards across the organization for all model inference calls.
  • Upgrade rollout policies manage and stagger automatic upgrades across resources and accounts.
  • Amazon S3 policies manage configurations for Amazon S3 resources at scale across accounts.

To enable a policy type, you need permission to run organizations:EnablePolicyType. In the Organizations console you also need organizations:DescribeOrganization and organizations:ListRoots. For more information, see Enabling a policy type in AWS Organizations.

Exam Trap

  • Enabling all features cannot be rolled back.
  • SCPs and RCPs are authorization policies that set maximum permissions. They do not grant permissions.

Memory Hook

All features is the default. Authorization policies set ceilings. Management policies configure services.

3. Service Control Policies Deep Dive

Problem Statement

Engineering teams at FinTech Global launched test environments in AWS Regions outside North America, which violates strict data residency laws and the General Data Protection Regulation (GDPR). Developers also uploaded unencrypted customer records to Amazon S3 buckets, and sandbox accounts ran expensive GPU and high-specification EC2 instances. Account administrators cannot be trusted to enforce the rules account by account.

3.1 What SCPs Are

Service control policies (SCPs) are organization-level governance policies. They specify the maximum permissions for accounts, OUs, or the entire organization, which is why they are often called guardrails. SCPs are Organizations policies, not IAM policies. They limit the permissions that IAM users and roles can be granted. You can apply them to the whole organization, to a specific OU, or to a specific account.

SCPs restrict the effective maximum permissions. This is why they are ideal for security invariants, which are the things that you set once and rarely change. Think about everything that you never want to happen in your accounts, and enforce it through SCPs.

3.2 Common Use Cases

  • Restrict access to services that your organization has banned, for example AI services.
  • Restrict access to AWS Regions where you have no workloads.
  • Restrict instance types and sizes in lower environments.

To create SCPs, you need permission to run organizations:CreatePolicy. For more information, see Creating a policy in AWS Organizations and Service control policy examples.

3.3 The Scope of SCPs

  • Guardrails, not permission grants: SCPs do not grant permissions. They define the maximum permissions available to identities in member accounts. Users and roles still need permissions through IAM policies or IAM Identity Center permission sets.
  • Maximum permission boundary: An IAM policy or permission set cannot authorize an action that an applicable SCP explicitly denies or does not allow. Even the AdministratorAccess policy cannot override an SCP restriction.
  • Member accounts only: SCPs apply only to member accounts. They do not restrict users or roles in the management account.
  • Affected identities: SCPs restrict IAM users, IAM roles, and the root user in affected member accounts. They also apply to member accounts that are delegated administrators.
  • Policy evaluation: An action can be performed only when an applicable SCP permits it and an IAM policy, permission set, or other authorization policy grants it.
  • Explicit deny takes precedence: If an IAM policy allows an action but an applicable SCP explicitly denies it, AWS denies the request.
  • Resource-based policies: SCPs do not attach to or directly restrict resource-based policies. They restrict principals in affected member accounts. For example, an SCP on account A does not stop an external principal in account B from using a bucket in account A that grants that principal access.
  • Service-linked roles: SCPs do not restrict service-linked roles, which allow AWS services to act on behalf of an account.

Consider a development account where an SCP restricts users from launching EC2 instances above a certain size. This prevents over-allocation of resources in non-production environments. You can apply such policies everywhere or only to specific accounts and groups.

3.4 Main Components of an SCP

SCPs use JSON syntax that is similar to IAM policies.

The main components of an SCP.
ComponentDescription
VersionThe policy language version, normally 2012-10-17.
StatementOne or more policy rules.
SidAn optional name for a statement.
EffectAllow or Deny.
ActionThe AWS service actions that are affected.
NotActionThe actions that the statement excludes.
ResourceThe resources that are affected. Often "*" in broad guardrails.
ConditionApplies the rule only when the specified conditions are met.

For more detail about SCP syntax, see SCP syntax in AWS Organizations.

Exam Trap

  • SCPs never apply to the management account. A Deny SCP on the root restricts every member account, but the management account is always exempt.
  • SCPs also do not apply to service-linked roles or to principals outside the organization.
  • SCPs restrict the root user of a member account.

Memory Hook

An SCP is a ceiling. It never hands out permissions.

4. How SCPs Work With IAM

Problem Statement

A developer at FinTech Global has an IAM policy that allows launching EC2 instances, yet the request to launch an instance fails in the production account. The developer even holds the AdministratorAccess policy. The cloud team needs to explain why, and to show developers what the guardrails look like in JSON.

4.1 Example 1: SCP and IAM Together

Assume an IAM policy allows a developer to launch EC2 instances:

{
  "Effect": "Allow",
  "Action": "ec2:RunInstances",
  "Resource": "*"
}
  • If the applicable SCP also permits EC2, the developer can launch an instance.
  • If an SCP explicitly denies ec2:RunInstances, the request is denied, even if the developer has the IAM AdministratorAccess policy.
How IAM permissions and SCPs combine.
IAM permissionSCP permits the actionResult
AllowYesAllowed
AllowNoDenied
AllowExplicit denyDenied
No permissionYesDenied

An SCP can restrict an IAM permission, but it cannot create one. The effective permissions are the intersection of the permissions that IAM grants and the permissions that the applicable SCPs permit.

4.2 Example 2: Restrict EC2 to One Instance Type

This SCP restricts all users to launching only the t2.micro instance type.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "RequireMicroInstanceType",
      "Effect": "Deny",
      "Action": "ec2:RunInstances",
      "Resource": [
        "arn:aws:ec2:*:*:instance/*"
      ],
      "Condition": {
        "StringNotEquals": {
          "ec2:InstanceType": "t2.micro"
        }
      }
    }
  ]
}

4.3 Example 3: Deny Unencrypted Uploads to Amazon S3

This SCP denies uploads to S3 buckets when the request does not include server-side encryption. The Null condition is true when the s3:x-amz-server-side-encryption key is missing from the request.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Deny",
      "Action": "s3:PutObject",
      "Resource": "*",
      "Condition": {
        "Null": {
          "s3:x-amz-server-side-encryption": "true"
        }
      }
    }
  ]
}

5. Comparing Access Control Mechanisms

Problem Statement

FinTech Global’s new engineers ask why the company needs identity-based policies, permissions boundaries, SCPs, and IAM Identity Center permission sets. They all seem to control access. The cloud team needs a clear way to tell them apart.

5.1 SCPs Versus IAM Policies

At first glance, SCPs and IAM policies look alike. Both control access, and both support least privilege. Their scope and application differ:

  • IAM policies apply at the user or role level. For example, the role DevManager cannot provision any EC2 instance in the us-east-1 Region. SCPs apply at the organization root, an OU, or an account. For example, no EC2 instance can be provisioned in the us-east-1 Region in any account under that OU.
  • SCPs make more sense when an organization has many accounts and OUs, because an SCP applies at the account level. IAM applies to the users and roles inside one account.

IAM and SCPs complement each other. SCPs control permissions at the account level, and users in each account define IAM policies within the limits of the SCPs that apply to that account.

5.2 Permissions Boundary Versus Identity Policy Versus SCP

A permissions boundary can be used together with AWS Organizations SCPs.

Four access control mechanisms compared.
Control mechanismTarget or scopePrimary purposeCan grant permissions?
Identity-based IAM policyIAM user, group, or roleDefines the specific AWS actions and resources that an identity is allowed or deniedYes
Permissions boundaryIAM user or roleSets the maximum permissions that identity-based policies can grant to the user or roleNo
IAM Identity Center permission setUsers and groups that access AWS accounts through IAM Identity CenterDefines a reusable collection of permissions for central workforce access to one or more accountsYes — through the IAM roles that IAM Identity Center creates in the target accounts
Service control policy (SCP)AWS Organizations root, OU, or accountDefines organization-level permission guardrails and limits the maximum available permissionsNo

Permissions boundaries and SCPs can both restrict permissions, but they work at different levels. A permissions boundary applies to one IAM user or role. An SCP sets guardrails for principals in member accounts.

5.3 A Simple Mental Model

  • IAM policy: grants permissions.
  • Permissions boundary: limits one IAM user or role.
  • Permission set: defines workforce permissions across AWS accounts.
  • SCP: limits permissions across an AWS Organization.

Exam Trap

Only identity-based policies and permission sets grant permissions. Permissions boundaries and SCPs only limit them. A permissions boundary does not grant anything on its own.

Memory Hook

Grants: identity policy and permission set. Limits: boundary and SCP.

6. Allow-List and Deny-List Strategies

Problem Statement

FinTech Global must decide how to govern its accounts. One option is to leave services available and block only the actions that must never happen. The other is to allow only an approved list of services and block everything else.

6.1 Deny-List Strategy

The organization keeps the AWS-managed FullAWSAccess SCP and adds explicit deny statements for prohibited activities. For example:

  • Permit AWS services generally.
  • Deny leaving the organization.
  • Deny disabling security monitoring.
  • Deny using unapproved Regions.

This is usually easier to introduce, because services stay available unless they are denied.

6.2 Allow-List Strategy

The organization permits only explicitly approved services and actions. For example:

  • Allow Amazon EC2.
  • Allow Amazon S3.
  • Allow Amazon RDS.
  • Do not allow other services.

With this strategy, an appropriate allow must exist at every level from the organization root through the OU hierarchy to the account. If an action is not allowed at one of those levels, it is unavailable.

6.3 The FullAWSAccess SCP

AWS Organizations attaches an AWS-managed SCP named FullAWSAccess by default. It contains:

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Effect": "Allow",
      "Action": "*",
      "Resource": "*"
    }
  ]
}

This does not give users administrator permissions. It only means that the SCP does not restrict the permissions that IAM policies can grant. Removing FullAWSAccess without creating replacement allow policies can unintentionally block access to AWS services.

6.4 A Real-World Example

A company organizes its accounts into an organization root, a Production OU, and a Development OU, with several accounts in each OU. It applies these controls:

  • Organization root: An SCP prevents every member account from leaving the organization.
  • Production OU: An SCP prevents administrators from stopping CloudTrail logging, deleting CloudTrail trails, disabling AWS Config, and deploying resources in unapproved Regions.
  • Development OU: Developers have more flexibility, but an SCP still restricts resource creation to approved Regions.

A developer in a production account has an IAM policy that permits EC2 administration. The developer can manage EC2 resources in approved Regions but cannot launch instances in a Region that the production SCP denies. Even granting AdministratorAccess would not override the SCP.

6.4.1 Example SCP: Restrict Regions

This policy denies all actions outside us-east-1 and eu-west-1, except for global services such as IAM and Amazon Route 53. Replace the Region list with your approved Regions. AWS’s own example exempts more global services, so check Service control policy examples before you use a policy like this.

{
  "Version": "2012-10-17",
  "Statement": [
    {
      "Sid": "DenyAllOutsideApprovedRegions",
      "Effect": "Deny",
      "NotAction": [
        "iam:*",
        "organizations:*",
        "route53:*",
        "cloudfront:*",
        "support:*"
      ],
      "Resource": "*",
      "Condition": {
        "StringNotEquals": {
          "aws:RequestedRegion": [
            "us-east-1",
            "eu-west-1"
          ]
        }
      }
    }
  ]
}

Exam-Style Question 2 (written for this course)

FinTech Global wants developers to use any AWS service except a few banned ones, without maintaining a long list of approved services. Which SCP strategy fits best?

  1. Attach a permissions boundary to every IAM user and role.
  2. Use an IAM Identity Center permission set for each service.
  3. Keep FullAWSAccess and add explicit Deny statements for the banned services.
  4. Remove FullAWSAccess and allow every approved service at the root, OU, and account levels.
Show the answer

Correct answer: C. A deny-list strategy keeps FullAWSAccess and denies specific actions. It is easier to introduce because services stay available unless they are denied.

Each option checked against the requirement.
OptionFits “everything except a few”?Verdict
ANo — boundaries apply to individual identities, not to accounts or OUsIncorrect
BNo — permission sets grant permissions and do not set guardrailsIncorrect
CYes — deny-list strategyCorrect
DNo — that is an allow-list strategy, which requires a list of approved servicesIncorrect

Exam Trap

  • With an allow-list, an allow must exist at every level from the root to the account. Removing FullAWSAccess without replacements can block access to all services.
  • FullAWSAccess does not make anyone an administrator. IAM must still grant the permissions.

Memory Hook

Deny-list: everything is allowed unless denied. Allow-list: everything is blocked unless allowed at every level.

7. Comparison & Scenarios

7.1 Real-World Architectural Examples

7.1.1 Scenario 1: Multi-Account Retail Environment

An enterprise retailer structures its cloud infrastructure in an AWS Organization with dedicated OUs for Security, Development, and Production.

  • Governance strategy: The security team assigns full administrative access in the Development account to support rapid prototyping, and read-only access for engineers in the Production account.
  • SCP application: An SCP attached to the Production OU stops all users from changing network configurations or security group settings unless they sign in under a dedicated automated deployment role.

7.1.2 Scenario 2: Enforcing Regional and Service Limits

To satisfy data residency laws, an enterprise requires workloads to run only in approved geographic Regions.

  • SCP implementation: An SCP at the organization root denies all API calls outside the approved Regions, for example us-east-1 and us-west-2. This blocks any attempt to create resources elsewhere.

7.1.3 Scenario 3: Protecting Core Security Controls

Organizations must stop local account administrators from tampering with central security and logging infrastructure.

  • SCP implementation: An SCP across all member accounts stops users, including root users, from stopping or deleting CloudTrail logs, disabling Amazon GuardDuty, or changing central AWS Config rules.

Integrations such as single sign-on through AWS IAM Identity Center simplify access by removing the need for multiple logins. Enabling CloudTrail across the organization adds comprehensive API activity insight for security and operational oversight.

7.2 Exam-Style Question

Exam-Style Question 3 (written for this course)

A large financial services company manages 45 AWS accounts under AWS Organizations. A security audit found that account administrators disabled CloudTrail logging in three member accounts. The security team needs a solution that (1) ensures CloudTrail is enabled and logging in all current and future member accounts, (2) prevents any account administrator from disabling or modifying CloudTrail, and (3) centralizes all CloudTrail logs in a single S3 bucket in a dedicated Security account. Which combination of actions meets all three requirements? (Select TWO.)

  1. Create a CloudTrail trail in each of the 45 member accounts and use AWS Config rules to detect and re-enable CloudTrail if it is disabled.
  2. From the management account, create an organization trail with the Log Archive S3 bucket in the Security account.
  3. Create an SCP that denies cloudtrail:StopLogging, cloudtrail:DeleteTrail, and cloudtrail:UpdateTrail for all principals, and attach it to the organization root.
  4. Create an IAM policy in each member account that denies CloudTrail modification actions, and attach it to all IAM users and roles.
  5. Enable AWS Security Hub in the management account with the CloudTrail compliance standard to monitor and alert when CloudTrail is disabled.
Show the answer

Correct answer: B and C. The organization trail covers existing and new accounts and delivers logs to one bucket, which meets requirements 1 and 3. The SCP stops administrators, including root users of member accounts, from stopping, deleting, or changing CloudTrail, which meets requirement 2.

8. Knowledge Check

Answer each question in your own words, and then open the model answer to compare.

Question 1: Organization Components. Describe the organization root, the management account, member accounts, and organizational units, and explain how the organization root differs from the root user of an account.

Show the model answer

The organization root is the top-level container of the hierarchy. All OUs and accounts belong to it, and it is not an AWS account. The management account administers the organization, applies policies, and pays the bill for all member accounts. Member accounts host workloads. OUs group accounts so that you can apply consistent policies, and they nest up to five levels. The root user is a different thing: each AWS account has its own root user, which signs in with the account’s email address.

Question 2: Guardrails, Not Grants. Explain why an SCP does not grant permissions, and describe what happens when an IAM policy allows an action that an SCP does not allow.

Show the model answer

An SCP sets the maximum permissions available to principals in member accounts. It does not give any identity a permission. Users and roles still need an IAM policy or permission set that grants the action. Effective permissions are the intersection of what IAM grants and what the SCPs allow. If the SCP does not allow the action, or denies it explicitly, the request is denied even when an IAM policy allows it.

Question 3: What SCPs Do Not Restrict. Name what SCPs do not restrict and what they do restrict in a member account. Why does this matter for where you run workloads?

Show the model answer

SCPs do not restrict the management account, service-linked roles, or principals outside the organization. They do restrict IAM users, IAM roles, and the root user in member accounts. Because the management account is exempt from SCPs, you should not run workloads there.

Question 4: Reading an SCP. Read the SCP that denies ec2:RunInstances with the condition StringNotEquals ec2:InstanceType t2.micro. What does it enforce, and which statement element sets the condition?

Show the model answer

It denies launching any EC2 instance whose type is not t2.micro, so accounts under the policy can launch only t2.micro instances. The Condition element sets when the Deny applies. The Effect is Deny, the Action is ec2:RunInstances, and the Resource limits it to instance resources.

Question 5: Allow-List or Deny-List. A company wants developers to use any AWS service except a few banned ones. Which SCP strategy fits, and what must you keep in place?

Show the model answer

A deny-list strategy fits. Keep the AWS-managed FullAWSAccess SCP attached, and add explicit Deny statements for the banned services. An allow-list strategy would require an allow at every level from the organization root to the account, and removing FullAWSAccess without replacements could block access to services.

Question 6: Designing a Hierarchy. Design a simple hierarchy for a company with Security, Development, and Production accounts. Name the OUs and one SCP that you would attach at each level.

Show the model answer

A hierarchy has an organization root with the management account, a Security OU, a Development OU, and a Production OU, with member accounts in each OU. At the root, attach an SCP that prevents accounts from leaving the organization and restricts usage to approved Regions. At the Production OU, attach an SCP that prevents stopping CloudTrail and disabling AWS Config. At the Development OU, attach an SCP that restricts instance types or sizes. Keep FullAWSAccess in a deny-list design.

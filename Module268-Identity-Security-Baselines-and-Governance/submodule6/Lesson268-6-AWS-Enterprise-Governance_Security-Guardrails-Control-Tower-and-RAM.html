Lesson 268.6 - AWS Enterprise Governance: Security Guardrails, Control Tower, and RAM

Enforce guardrails, automate a multi-account landing zone, and share resources across accounts without duplication.

Overview and Objectives

Lesson Overview

This lesson covers foundational AWS enterprise governance services and concepts that manage, secure, and streamline multi-account environments at scale.

  • Security guardrails: Automated policy boundaries enforced through preventive controls, such as service control policies (SCPs), and detective monitoring, such as AWS Config and AWS Security Hub, to maintain compliance without slowing development.
  • AWS Control Tower: An orchestration service that automates the setup of a secure multi-account landing zone, preconfigures guardrails, and simplifies compliant account provisioning with Account Factory.
  • AWS Resource Access Manager (AWS RAM): A service that shares AWS resources, such as subnets and transit gateways, securely and centrally across accounts and organizational units (OUs), so teams avoid duplicate infrastructure and extra cost.

1. Security Guardrails

Problem Statement

Imagine your company starts small, with one AWS account and a handful of engineers. Then it grows to 15 teams that each want their own account for isolation, billing, blast radius, and permissions. Suddenly you have more than 50 AWS accounts.

How do you make sure that every account disables public Amazon S3 buckets by default? How do you stop someone in the Marketing account from launching resources in a Region you do not operate in? How do you prevent a developer from disabling AWS CloudTrail logging to hide their tracks? And how do you enforce these rules consistently, without configuring each account by hand?

You need a way to define rules once, centrally, and have them apply automatically across your organization. In some cases the rules should be impossible to violate. That is what guardrails solve.

1.1 Overview of Security Guardrails

Guardrails are high-level rules that enforce policy across the AWS accounts in an organization. They act as automated policy boundaries and keep accounts compliant with enterprise security standards regardless of individual developer permissions. They set boundaries without making the central security team approve every action.

For example, an organization can set guardrails that:

  • Prevent users from disabling AWS CloudTrail.
  • Restrict resource deployment to approved AWS Regions.
  • Detect publicly accessible Amazon S3 buckets.
  • Require encryption for storage resources.
  • Prevent the use of a member account’s root user.
  • Verify that security groups do not allow unrestricted administrative access.

Security guardrails are a governance concept, not a single AWS service. AWS implements guardrails through services and policy mechanisms such as:

  • AWS Organizations.
  • Service control policies (SCPs).
  • Resource control policies (RCPs).
  • AWS Config.
  • AWS CloudFormation hooks.
  • AWS Control Tower.
  • Amazon EventBridge and remediation services.

1.2 Why Guardrails Are Needed

Without centrally managed guardrails, each AWS account can be configured differently. For example:

  • One account records activity with CloudTrail, while another does not.
  • One team encrypts its Amazon EBS volumes, while another creates unencrypted volumes.
  • A developer accidentally creates a public S3 bucket.
  • An account administrator deploys resources in an unapproved Region.
  • A security service is turned off, on purpose or by accident.

Guardrails reduce these risks by applying common expectations across OUs and member accounts.

1.3 Types of Guardrails

Guardrails fall into two functional categories.

1.3.1 Preventive Guardrails

Preventive guardrails enforce policy compliance by blocking non-compliant API calls or actions before they occur. They stop unauthorized activity regardless of the caller’s identity or IAM role.

  • Implementation: SCPs attached to AWS Organizations OUs.
  • Example 1: Restrict the Regions where workloads can be deployed, prevent root user actions, or block changes to S3 public access settings.
  • Example 2: An SCP that denies s3:PutAccountPublicAccessBlock and s3:PutBucketPublicAccessBlock so that nobody can turn off S3 Block Public Access. No one, even an administrator, can override it unless the SCP is changed at the root.

1.3.2 Detective Guardrails

Detective guardrails continuously monitor existing resources. They identify and alert on non-compliant configurations or security anomalies after they occur.

  • Implementation: AWS Config rules, Amazon GuardDuty, and AWS Security Hub.
  • Example 1: Detect unencrypted EBS volumes, flag SSH ports open to 0.0.0.0/0, or audit missing IAM multi-factor authentication (MFA) settings.
  • Example 2: An AWS Config rule that continuously checks whether CloudTrail is enabled in every account. If someone turns it off, Config flags the account as non-compliant and can trigger a remediation Lambda function.

Exam-Style Question 1

A company must ensure that nobody can make S3 buckets publicly accessible, and that every unencrypted EBS volume is flagged for audit. Which combination of guardrails meets these requirements?

  1. A detective guardrail for S3 public access and a preventive guardrail for EBS encryption.
  2. Detective guardrails for both requirements, implemented with AWS Config rules.
  3. A preventive guardrail for S3 public access, implemented with an SCP, and a detective guardrail for unencrypted EBS volumes, implemented with an AWS Config rule.
  4. Preventive guardrails for both requirements, implemented with SCPs only.
Show the answer

Correct answer: C. “Nobody can” points to a preventive guardrail, which an SCP provides. “Flagged for audit” points to a detective guardrail, which an AWS Config rule provides.

  • Guardrails are a concept, not a service. The services that implement them are SCPs, AWS Config, and related tools.
  • Preventive guardrails stop an action. Detective guardrails report on it after it happens.

2. AWS Control Tower Overview and Core Components

Problem Statement

AWS Organizations provides the structure for multiple accounts, OUs, policies, and consolidated billing. Even so, an organization still has to design and configure recommended OUs, centralized logging, security accounts, account provisioning, governance controls, compliance monitoring, and identity integrations.

Doing all of this by hand means writing your own SCPs, setting up AWS Config, building a CloudTrail aggregation pipeline, and creating an account factory. That is undifferentiated heavy lifting that AWS has already built. Which service automates it?

2.1 Overview of AWS Control Tower

  • AWS Control Tower automates the setup of a secure, multi-account AWS environment based on best practices. It is the easy way to start multi-account governance.
  • It brings together AWS management and security services, such as AWS Organizations, AWS Service Catalog, and AWS Config, under a unified governance console.
  • It creates a governed environment that is called a landing zone.

AWS Organizations provides the multi-account foundation. AWS Control Tower establishes and governs the landing zone that is built on that foundation.

2.2 Core Components

2.2.1 What Is a Landing Zone

A landing zone is a standardized, multi-account AWS environment that is designed to support secure and scalable workloads. It provides a foundation for:

  • Account organization.
  • Centralized logging.
  • Security auditing.
  • Identity integration.
  • Account provisioning.
  • Governance controls.
  • Compliance visibility.

Control Tower uses AWS Organizations and integrates other AWS services to establish the landing zone. When you first set it up in your management account, it provisions an account factory, creates two shared accounts (a log archive account and an audit account), and applies controls.

2.2.2 Controls (Guardrails)

AWS Control Tower calls its guardrails controls. A control is a high-level rule that provides ongoing governance for your environment, and it is expressed in plain language.

How AWS Control Tower classifies controls.
ClassificationValuesMeaning
BehaviorPreventive, detective, or proactivePreventive controls are implemented as SCPs and stop actions. Detective controls are implemented as AWS Config rules and detect non-compliance. Proactive controls are implemented with AWS CloudFormation hooks and check resources before they are provisioned.
GuidanceMandatory, strongly recommended, or electiveGuidance is the recommended practice for applying a control to your OUs. It is independent of the behavior.

You can apply a control to an OU with a single action, which enforces the policy continuously. Mandatory controls protect the resources that AWS Control Tower deploys. Strongly recommended and elective controls cover common practices, for example disallowing public access to S3 buckets, disallowing SSH and RDP from the internet, enforcing tagging, and disallowing public sharing of Amazon RDS snapshots. Check the controls reference for the current catalog.

2.2.3 Account Factory

Account Factory is a self-service way to provision new, preconfigured, compliant AWS accounts in minutes. It uses AWS Service Catalog and a central template to standardize provisioning. Distributed teams can request accounts that arrive with the required networks, security controls, and guardrails already in place.

2.2.4 Centralized Compliance Dashboard

The dashboard gives a centralized view of the landing zone, the compliance status of policies across all accounts, and non-compliant resources organized by account and OU. It shows account health, active controls, and compliance status across the enterprise.

Key Points

  • AWS Control Tower does not replace AWS Organizations.
  • AWS Control Tower automates and governs the setup.
  • Under the hood, everything is still AWS Organizations, SCPs, and AWS Config.

3. AWS Control Tower Limitations and Comparison With AWS Organizations

Problem Statement

A cloud operations team is deciding how to build a multi-account environment for several business units. Some teams want the fastest path to a secure baseline. Others already run a mature organization with a custom OU design. The team must know what Control Tower does well and where it has limits.

3.1 Limitations and Considerations

  • Control Tower is intended for multi-account governance, not for application deployment.
  • Enabling controls can affect existing workloads.
  • Not every control or governed resource is available in every Region.
  • Proactive controls apply to supported AWS CloudFormation deployments.
  • Control Tower itself has no additional charge, but the AWS services and resources that it configures can generate charges.
  • You can enroll existing accounts, but they must meet the applicable prerequisites.
  • Administrators should not change Control Tower-managed resources by hand without understanding the effect on governance.

3.2 AWS Control Tower Versus AWS Organizations

When to choose AWS Organizations and when to choose AWS Control Tower.
Choose AWS Organizations when...Choose AWS Control Tower when...
You need a multi-account structure.You want a pre-built, best-practice setup.
You need a specific OU design that differs from AWS best practices.You want automated account provisioning and guardrails out of the box.
You already have a mature Organizations setup and do not want to rebuild it.You are starting a new multi-account environment and want the fastest path to a secure baseline.
You need only basic grouping and billing consolidation.You want a compliance dashboard that shows the health of all accounts.
You need advanced use and have deep expertise.You want faster setup and enforced best practices.

Important to Know

Control Tower builds on AWS Organizations. When you set it up, it configures the organizational structure of the landing zone for you, and you manage governance through Control Tower instead of working directly with each underlying service.

4. AWS Resource Access Manager

Problem Statement

After separating workloads into multiple AWS accounts, several teams need the same infrastructure. Without resource sharing, each account might create its own transit gateway, network subnet, Route 53 Resolver rule, IP address pool, license configuration, or Dedicated Host. This duplication raises cost, administrative effort, configuration inconsistency, network complexity, and security risk. How can the accounts use one shared copy?

4.1 What AWS RAM Is

AWS Resource Access Manager (AWS RAM) shares supported AWS resources securely:

  • Across AWS accounts.
  • With an entire AWS Organization.
  • With selected OUs.
  • With selected IAM roles or IAM users, for supported resource types.
  • In some cases, with accounts outside the organization.

AWS RAM can share only resource types that explicitly support it, and you can share a resource only if you own it. AWS RAM is a Regional service.

4.2 Shareable Resources

These common resource types are shareable. The list changes as AWS services add RAM support, so check the current list in the AWS documentation before you design.

  • Amazon VPC subnets, which let multiple accounts launch resources into the same subnet. Subnets can be shared only within an organization.
  • Transit gateways, prefix lists, and other Amazon VPC resources.
  • Amazon Route 53 Resolver forwarding rules.
  • Amazon Aurora DB clusters.
  • Amazon EC2 capacity reservations and Dedicated Hosts.
  • AWS License Manager license configurations.
  • AWS Outposts local gateway route tables, Outposts, and sites.
  • Other resources that the lesson document lists: AWS Systems Manager documents, AWS Glue Data Catalog resources, and Amazon SageMaker AI resources.

4.3 Benefits

  • Reduces duplicate resources.
  • Centralizes infrastructure ownership.
  • Supports separation of duties.
  • Simplifies multi-account networking.
  • Provides scalable, OU-based sharing.
  • Improves configuration consistency.
  • Lets consumers use resources without taking over ownership.
  • Reduces operational complexity and cost by consolidating shared services.

4.4 Limitations

  • Only supported resource types can be shared.
  • Sharing does not transfer resource ownership.
  • AWS RAM does not automatically grant consumer IAM permissions.
  • Some resource types cannot be shared outside an organization.
  • Regional resources must be shared and accessed according to their Regional requirements.
  • Removing a share can disrupt workloads that depend on the resource.

4.5 Key Concepts to Remember

Key concepts for AWS RAM.
ConceptDetail
No duplicationThe resource stays in the owner’s account. It is shared, not copied.
BillingIn most cases the owner account keeps the cost and management responsibility. This depends on the resource type.
Within AWS OrganizationsSharing can happen without a manual accept step when sharing with AWS Organizations is enabled.
Granular sharingShare with specific accounts, OUs, or the entire organization.
Lower operational overheadYou do not recreate the same subnet or transit gateway in every account.

5. Comparison & Scenarios

5.1 How the Services Tie Together

The exam often tests these concepts as one combined scenario.

  • AWS Organizations: The foundational multi-account structure, with OUs, consolidated billing, and SCPs.
  • AWS Control Tower: Automates the setup of that structure, applies guardrails out of the box (preventive through SCPs and detective through AWS Config), and provides Account Factory for provisioning.
  • Security guardrails: The actual preventive and detective rules that are enforced across all accounts, whether you set them up manually through AWS Organizations or automatically through AWS Control Tower.
  • AWS RAM: Once you have multiple accounts, lets them share specific resources, such as subnets and transit gateways, instead of duplicating infrastructure.

5.2 A Typical Combined Scenario

A company is expanding into a multi-account strategy. It wants to quickly establish a secure baseline with governance rules applied automatically, and it wants its application teams to share a common VPC subnet without duplicating network infrastructure.

The answer is AWS Control Tower for the secure multi-account setup and guardrails, plus AWS RAM to share the subnet across accounts.

6. Knowledge Check

Answer each question in your own words, and then open the model answer to compare.

Question 1: Preventive Versus Detective Guardrails. Your organization needs to ensure that S3 buckets are never made publicly accessible and that any unencrypted EBS volume is flagged immediately for audit. Explain how you would implement these requirements with AWS guardrail mechanisms, distinguish the preventive and detective approaches, and identify the AWS services you would use.

Show the model answer

Use a preventive guardrail for S3: attach an SCP to the OUs, or to the organization root, that denies actions that turn off S3 Block Public Access, so no one can make buckets public, even an administrator. Use a detective guardrail for EBS: an AWS Config rule that checks whether EBS volumes are encrypted marks unencrypted volumes as non-compliant, and AWS Security Hub or the AWS Control Tower dashboard shows the finding for audit. A remediation function can respond when a volume is flagged.

Question 2: AWS Control Tower, Landing Zones, and AWS Organizations. A central cloud operations team must set up a multi-account environment for several business units. Compare setting up AWS Organizations manually with deploying AWS Control Tower, and explain how Control Tower automates landing zones and new account provisioning through Account Factory.

Show the model answer

AWS Organizations provides the core multi-account structure of OUs, SCPs, and consolidated billing. Configuring baseline logging, audit trails, account factory workflows, and security baselines by hand takes significant operational effort. AWS Control Tower automates this by establishing an orchestrated landing zone that is built on AWS Organizations. It integrates AWS Config, AWS CloudTrail, and IAM Identity Center. Its Account Factory is a self-service way, built on AWS Service Catalog, to provision standardized, preconfigured accounts with baseline security controls, networks, and guardrails applied automatically.

Question 3: AWS RAM and the Ownership Model. An enterprise network team maintains a central VPC with multiple subnets and transit gateways. Several development teams in separate AWS accounts need access to these network resources. Describe how AWS RAM addresses this, what happens to resource ownership, and name three other resource types that you can share with AWS RAM.

Show the model answer

AWS RAM removes the need for duplicate infrastructure, extra cost, and complex connections between networks by sharing supported resources centrally across accounts or OUs. Ownership stays with the owning account: resources are shared, not duplicated or transferred. Other shareable resource types include Route 53 Resolver forwarding rules, Aurora DB clusters, AWS Outposts resources, License Manager configurations, and EC2 Dedicated Hosts.

Question 4: Combining the Services. An enterprise is starting a cloud transformation that needs rapid onboarding of developer teams, strict security oversight, and efficient use of resources. Explain how AWS Control Tower, security guardrails and SCPs, and AWS RAM work together to deliver a complete multi-account architecture.

Show the model answer

AWS Control Tower provides the automated multi-account foundation, the landing zone, and the account creation portal, Account Factory. Security guardrails, which are preventive SCPs and detective AWS Config rules, enforce organizational policy and continuous compliance across all accounts that Control Tower governs. Once accounts are provisioned and governed, AWS RAM lets central teams share core infrastructure, such as subnets and transit gateways, across member accounts without duplicating resources or giving up ownership. Together they provide secure automation, central control, and cost-effective use of resources at scale.

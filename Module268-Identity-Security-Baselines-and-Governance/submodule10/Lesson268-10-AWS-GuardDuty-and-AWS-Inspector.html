Lesson 268.10 - AWS GuardDuty and AWS Inspector

Detect threats with Amazon GuardDuty and find vulnerabilities with Amazon Inspector: what each service analyzes, how its findings work, and how to respond to them automatically.

Introduction

A secure AWS environment needs more than good access rules. Someone can still steal a password, an instance can still run software with a known flaw, and an attacker can still send traffic from inside the network. GuardDuty and Inspector help in different ways. GuardDuty watches the activity in an account and reports behavior that looks like an attack. Inspector looks at the workloads themselves and reports software flaws before an attacker uses them. An architect who passes SAA-C03 questions on security needs to know which service answers which question.

This lesson assumes that you know the basics of AWS accounts, IAM, Amazon EC2, and AWS CloudTrail. It follows Northwind, the company from the module 268 kick-off, through the Problem Statement of each tab.

Use the tab list on the left, or the Previous and Next buttons, to move through the lesson. Each topic tab opens with a Problem Statement and ends with exam traps, keyword triggers, and resource links. The Knowledge Check is the last tab.

Three terms appear often in this lesson:

  • Threat: activity that looks like an attack or misuse, for example a call from a known malicious address.
  • Vulnerability: a flaw in software that an attacker could use. A CVE is a public record of a known vulnerability.
  • Finding: a report that a security service creates when it detects a threat or a vulnerability.

1. Threat Detection and Vulnerability Management

Problem Statement

Northwind runs its web application on Amazon EC2 instances in several AWS accounts. A security review asks two questions. First, would Northwind notice if someone used a stolen access key, or if an instance began to talk to a known malicious server? Second, do any of the instances, container images, or Lambda functions contain software with a known flaw? Northwind has a small security team, and it cannot read logs or scan servers by hand. The team needs to know which AWS services answer each question.

1.1 Two Different Questions

  • Threat detection asks whether someone is attacking or misusing the environment right now. Amazon GuardDuty answers this question by analyzing the activity in your account.
  • Vulnerability management asks whether the workloads contain flaws that an attacker could use. Amazon Inspector answers this question by scanning your workloads.
  • GuardDuty looks at behavior, such as API calls, network traffic, and DNS queries. Inspector looks at software, such as installed packages, container images, and function code.
  • Neither service blocks traffic or fixes a problem. Each one creates findings, and you or an automatic workflow respond to them.

1.2 Where the Services Fit

  • Amazon GuardDuty: detects threats and suspicious activity.
  • Amazon Inspector: finds software vulnerabilities and unintended network exposure.
  • Amazon Macie: finds sensitive data in Amazon S3 (Lesson 271.2, tab 12).
  • AWS Security Hub: collects findings from several security services in one place.
  • Amazon EventBridge: routes findings to targets such as AWS Lambda functions and Amazon SNS topics, so that a response can run automatically.

1.3 What the Services Have in Common

  • Both services are managed. You turn them on, and you do not run servers or write scanning code.
  • Both publish findings to Amazon EventBridge and to AWS Security Hub.
  • Both work with AWS Organizations. You can name a delegated administrator account that manages the service for the member accounts.
  • Both work Region by Region, so you turn them on in each Region that you use.

Exam Trap

Remember these two points:

  • GuardDuty detects threats from activity. Inspector finds vulnerabilities in workloads. A question about an attack in progress points to GuardDuty, and a question about unpatched software points to Inspector.
  • Neither service blocks an attack or fixes a flaw. They report, and another service or a person responds.

Memory Hook

GuardDuty = behavior and threats. Inspector = software and vulnerabilities. Macie = sensitive data.

2. Amazon GuardDuty

Problem Statement

A Northwind developer pushes an access key to a public code repository by mistake. Two days later an attacker uses the key from another country to list S3 buckets and to start instances. At the same time, one EC2 instance in a private subnet starts to contact an address that is on a list of malicious servers. Northwind did not turn on any extra logging. The team needs a service that watches the account for this kind of activity without agents or log pipelines.

2.1 What Amazon GuardDuty Is

  • Amazon GuardDuty is a threat detection service. It continuously monitors, analyzes, and processes specific AWS data sources and logs in your environment.
  • It uses machine learning, anomaly detection, and threat intelligence to find activity that looks like an attack or misuse.
  • When GuardDuty finds a potential threat, it creates a finding.
  • GuardDuty is a managed service. You turn it on, and you do not install agents for its foundational monitoring.
  • When you turn GuardDuty on for the first time, you get a 30-day free trial.

2.2 Foundational Data Sources

When you turn GuardDuty on in an account, it automatically starts to ingest these foundational data sources:

  • AWS CloudTrail management events: the API calls and user activity in the account.
  • VPC flow logs: the network traffic of your Amazon EC2 instances.
  • DNS logs: the DNS queries that resources in your VPCs make.
  • You do not have to turn on VPC flow logs or the other sources yourself. GuardDuty starts to ingest them when you enable the service.

2.3 Protection Plans

Protection plans let GuardDuty monitor logs and events from other AWS services:

  • S3 Protection: monitors Amazon S3 data events in AWS CloudTrail, which are object-level activity.
  • EKS Protection: EKS Audit Log Monitoring analyzes Kubernetes audit logs from your Amazon EKS clusters.
  • Runtime Monitoring: monitors operating system-level events on Amazon EKS, Amazon EC2, and Amazon ECS, including AWS Fargate.
  • Malware Protection: detects malware on Amazon EBS volumes of EC2 instances and container workloads, and in newly uploaded objects in Amazon S3 buckets.
  • RDS Protection: analyzes the login activity of supported Amazon Aurora and Amazon RDS databases.
  • Lambda Protection: monitors the network activity logs of Lambda functions, starting with VPC flow logs, to detect threats such as cryptomining or contact with malicious servers.
  • When you enable GuardDuty for the first time, it turns on all protection plans except Runtime Monitoring, and it includes them in the 30-day free trial.
  • You can use Malware Protection for S3 on its own, without turning on the rest of GuardDuty. All other protection plans need the GuardDuty service.

2.4 Extended Threat Detection

  • Extended Threat Detection detects multi-stage attacks that span foundational data sources, several types of AWS resources, and time, within an AWS account.
  • It correlates separate signals into one attack sequence, instead of leaving you with many unrelated findings.

3. GuardDuty Findings and Management

Problem Statement

GuardDuty now reports many findings for Northwind. Some are real threats, and some come from the security scanner that Northwind runs on purpose. The security team wants to be paged for serious findings, to stop seeing the harmless ones, to see the findings of all 12 accounts in one place, and to know what GuardDuty will cost before it goes to every Region.

3.1 GuardDuty Findings

  • A finding is a detailed security alert. It describes the affected resource, the threat actor, and the severity of the activity.
  • Each finding has a severity. Use it to decide which findings need an immediate response.
  • GuardDuty stores findings for 90 days.
  • You can view findings in the GuardDuty console, and you can send them to other services.

3.2 Responding to Findings Automatically

  • GuardDuty creates an event in Amazon EventBridge when findings change: for a newly generated finding and for a newly aggregated finding.
  • An EventBridge rule can match findings, for example by severity, and send them to a target such as an AWS Lambda function or an Amazon SNS topic.
  • GuardDuty also sends findings to AWS Security Hub, to Amazon Detective, and to an Amazon S3 bucket that you choose.
  • Example: a rule matches high-severity findings and sends a notification to the security team through SNS.

3.3 Suppression Rules

  • A suppression rule hides findings that you do not need, to reduce noise. You can suppress a whole finding type or only findings that match a filter.
  • GuardDuty still creates a suppressed finding, but it marks the finding as archived. You can view an archived finding for 90 days.
  • Archived findings are not sent to Security Hub, Amazon S3, Amazon Detective, or EventBridge.
  • In a multi-account setup, only the GuardDuty administrator account can create suppression rules.

3.4 Trusted IP Lists and Threat Lists

  • A trusted IP list names addresses that you trust, such as the exit address of your VPN. GuardDuty does not create findings for activity from these addresses.
  • A threat list names addresses that you know are malicious. GuardDuty creates a finding when it sees activity that involves them.
  • These lists apply to VPC flow log and CloudTrail findings. They do not apply to DNS findings.
  • A trusted IP list stops a finding from being created at all. A suppression rule creates the finding and archives it.

3.5 Using GuardDuty Across Accounts and Regions

  • GuardDuty works with AWS Organizations. Only the organization management account can designate a GuardDuty delegated administrator.
  • The administrator account manages GuardDuty for the member accounts in the organization, and it sees their findings in one place.
  • GuardDuty is a Regional service. Turn it on, and set up the administrator, in every Region that you use.

3.6 Amazon GuardDuty Pricing

Prices change often and differ by Region. Always check the current rates on the Amazon GuardDuty pricing page, and estimate your own cost with the AWS Pricing Calculator.

  • You get a 30-day free trial when you turn GuardDuty on for the first time.
  • Foundational protection is billed by the volume of CloudTrail events, VPC flow logs, and DNS logs that GuardDuty analyzes.
  • Each optional protection plan has its own billing unit, for example the volume of data scanned for Malware Protection, and the number of login events analyzed for RDS Protection.
  • More activity and more protection plans cost more, so turn on the plans that match the services that you use.

4. Amazon Inspector

Problem Statement

Northwind’s security review also found that the team does not know which EC2 instances run old packages, which container images in Amazon ECR contain known flaws, or which Lambda functions use vulnerable libraries. New instances and images appear every day, so a yearly scan is not enough. The team needs a service that finds these workloads on its own and keeps scanning them.

4.1 What Amazon Inspector Is

  • Amazon Inspector is an automated vulnerability management service. It discovers and scans Amazon EC2 instances, container images in Amazon ECR, and AWS Lambda functions.
  • It looks for known software vulnerabilities and for unintended network exposure.
  • Inspector automatically discovers your eligible resources and begins scanning them. It scans continuously, so a new instance or image is scanned as it appears.
  • Unlike traditional scanning software, Inspector has minimal impact on the performance of your fleet.
  • A vulnerability is usually a CVE, a public record of a known software flaw.

What Has Changed

AWS has added scan targets since the three above. Amazon Inspector now also scans code repositories. Its code security feature, generally available since June 17, 2025, integrates with GitHub and GitLab and covers application source code, third-party dependencies, and infrastructure as code. Inspector can also scan Amazon Machine Images (AMIs) directly, without launching an instance or installing an agent, and it can run Center for Internet Security (CIS) benchmark assessments on EC2 instances. SAA-C03 questions still focus on EC2 instances, ECR images, and Lambda functions. For details, see Amazon Inspector launches code security.

4.2 How Inspector Scans Each Resource

4.2.1 Amazon EC2 Instances

  • Agent-based scanning: Inspector uses the AWS Systems Manager Agent (SSM Agent) to collect the software inventory of an instance, and then checks that inventory for vulnerabilities.
  • Agentless scanning: Inspector can scan an instance without an agent. It takes a snapshot of the EBS volume and analyzes it.
  • Inspector chooses the best scan mode that is available for each instance.
  • Inspector also checks EC2 instances for network reachability, which shows unintended exposure to the network.
  • Deep inspection finds package vulnerabilities for application programming language packages on Linux instances.

4.2.2 Container Images in Amazon ECR

  • Inspector scans container images when they are pushed to Amazon ECR.
  • Inspector can also rescan images that stay in the registry, so a flaw that becomes known later is still found.

4.2.3 AWS Lambda Functions

  • Standard scanning checks the application dependencies of a function and of its layers, for example Python and Node.js packages.
  • Code scanning checks your own function code for security problems, such as injection flaws, data leaks, and hardcoded secrets.

4.3 The Inspector Risk Score

  • Inspector assigns a risk score to each finding. The score starts from the CVE information and adjusts for factors such as network access and exploitability.
  • The score helps you decide which findings to fix first.
  • The Inspector dashboard has a risk-based remediation panel. It shows the findings that affect the largest number of instances and images.

5. Amazon Inspector in Practice

Problem Statement

Northwind decides to turn on Amazon Inspector. The team has to answer practical questions: how to turn it on for all 12 accounts, what an EC2 instance needs so that it can be scanned, where the findings go, how to fix what Inspector finds, and what the service costs.

5.1 Turning On Amazon Inspector

  • You activate Inspector for the resource types that you want to scan: EC2 instances, ECR container images, and Lambda functions.
  • With AWS Organizations, you designate an account as the Inspector delegated administrator. That account can manage findings data and certain settings for the member accounts.
  • Inspector works Region by Region, so activate it in each Region that you use.

5.2 What an EC2 Instance Needs

  • For agent-based scanning, the instance must run the SSM Agent and be managed by AWS Systems Manager. Many Amazon Machine Images (AMIs) include the SSM Agent.
  • Instances without the agent can still be scanned with agentless scanning.

5.3 Findings and Integrations

  • You manage findings in the Inspector console or with the API. You can view them by instance, by container image, and by Lambda function.
  • Inspector publishes findings to Amazon EventBridge as events, so that you can process them in near real time, for example to open a ticket.
  • If AWS Security Hub is active, Inspector also publishes findings to Security Hub.
  • Container image findings are also sent to Amazon ECR.
  • You can export findings to an Amazon S3 bucket as a report.
  • Inspector can also export a software bill of materials (SBOM), which lists the software that your resources contain.

5.4 Fixing What Inspector Finds

  • For EC2 instances, patch the vulnerable packages. AWS Systems Manager Patch Manager can do this at scale (Lesson 268.8).
  • For container images, update the base image or the dependency, rebuild the image, and push it again. Inspector then scans the new image.
  • For Lambda functions, update the vulnerable dependency or fix the code, and deploy the function again.
  • Fix the findings with the highest risk score first.

5.5 Amazon Inspector Pricing

Prices change often and differ by Region. Always check the current rates on the Amazon Inspector pricing page, and estimate your own cost with the AWS Pricing Calculator.

  • The cost depends on the number of resources that Inspector scans: EC2 instances, container images, and Lambda functions.
  • For container images, the cost depends on how often you build and push images, because each new image is scanned.
  • Each scan type has its own rate. Lambda code scanning is a separate option from standard scanning.
  • Activate only the scan types for the resources that you use.

6.4 Lesson Summary

This lesson covered the following points:

  • GuardDuty detects threats from activity. It ingests CloudTrail management events, VPC flow logs, and DNS logs automatically, and optional protection plans add S3, EKS, RDS, Lambda, runtime, and malware monitoring.
  • GuardDuty findings carry a severity, go to EventBridge, Security Hub, Detective, and S3, and can be managed with suppression rules, trusted IP lists, and threat lists. A delegated administrator manages an organization, and the service is Regional.
  • Inspector finds vulnerabilities. It scans EC2 instances with the SSM Agent or agentless, ECR images on push and by rescan, and Lambda functions for dependencies and code.
  • The Inspector risk score helps you decide what to fix first. Findings go to EventBridge, Security Hub, and an S3 report.
  • Neither service blocks an attack or fixes a flaw. An EventBridge rule can start an automatic response, and patching tools or a rebuild fix the flaw.
  • Both services are billed by usage, so check the pricing pages and turn on only what you need.

Memory Hook

GuardDuty watches the activity. Inspector scans the software. Macie finds the data. Security Hub collects. EventBridge reacts.

Question 1: Explain the difference between threat detection and vulnerability management, and name the AWS service for each.

Maps to: Objectives 1 and 7 (Comprehension).

Vulnerability management asks whether workloads contain flaws an attacker could use, and Amazon Inspector answers it by scanning EC2 instances, ECR images, and Lambda functions. Neither service blocks an attack or fixes a flaw.

Question 2: Name the foundational data sources of GuardDuty and three optional protection plans.

Maps to: Objective 2 (Knowledge).

The foundational sources are AWS CloudTrail management events, VPC flow logs, and DNS logs, and GuardDuty ingests them automatically without agents. Optional protection plans include S3 Protection, EKS Protection, Malware Protection, RDS Protection, Lambda Protection, and Runtime Monitoring.

Question 3: Compare a trusted IP list, a threat list, and a suppression rule.

Maps to: Objectives 4 and 6 (Analysis).

A trusted IP list names addresses that you trust, and GuardDuty does not create findings for them. A threat list names known malicious addresses, and GuardDuty creates a finding when activity involves them. A suppression rule creates the finding but archives it, and archived findings are not sent to Security Hub, S3, Detective, or EventBridge.

Question 4: Design an automatic response to a high-severity GuardDuty finding in a multi-account organization.

Maps to: Objective 8 (Synthesis).

Designate a GuardDuty delegated administrator account in AWS Organizations so that it sees the findings of all member accounts in each Region. In that account, create an Amazon EventBridge rule that matches high-severity GuardDuty findings and sends them to an Amazon SNS topic for the security team, or to a Lambda function that starts a response. Use suppression rules to remove known harmless findings.

Question 5: Describe how Amazon Inspector scans EC2 instances, ECR images, and Lambda functions.

Maps to: Objective 3 (Comprehension).

For EC2 instances Inspector uses the SSM Agent to collect the software inventory, or scans an EBS snapshot without an agent, and it also checks network reachability. For ECR images it scans when an image is pushed and rescans images that stay in the registry. For Lambda functions standard scanning checks the dependencies and code scanning checks the function code for problems such as injection flaws and hardcoded secrets.

Question 6: Explain the Inspector risk score and where Inspector sends its findings.

Maps to: Objective 5 (Comprehension).

The risk score starts from the CVE information and adjusts for factors such as network access and exploitability, so that you can fix the most serious findings first. Inspector shows findings in its console, publishes them to Amazon EventBridge, sends them to AWS Security Hub if it is active, sends image findings to Amazon ECR, and can export a findings report to Amazon S3.

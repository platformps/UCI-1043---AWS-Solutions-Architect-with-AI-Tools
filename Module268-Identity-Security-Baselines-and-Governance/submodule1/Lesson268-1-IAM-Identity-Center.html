Lesson 268.1 - IAM Identity Center

Give workforce users single sign-on and temporary access to many AWS accounts with permission sets, account assignments, and federation.

Overview and Objectives

Lesson Overview

In previous modules, you explored the fundamentals of AWS Identity and Access Management (IAM). In this lesson, you explore AWS IAM Identity Center (formerly AWS Single Sign-On), the central service for managing workforce access across multiple AWS accounts and cloud applications.

  • Tab 1 places IAM Identity Center among the AWS security services and explains why organizations use it instead of IAM users in every account.
  • Tab 2 shows how IAM Identity Center works and covers identity sources, users, and groups.
  • Tab 3 covers permission sets, account assignments, and the integration with AWS Organizations.
  • Tab 4 covers the AWS access portal, temporary credentials, and multi-factor authentication (MFA).
  • Tab 5 covers federation, including outbound identity federation for AWS workloads.
  • Tab 6 applies the concepts to a multi-account retail scenario and lists decision rules for the AWS Certified Solutions Architect – Associate (SAA-C03) exam.
  • Tab 7 checks your understanding with open-ended questions.

Learning Objectives

By the end of this lesson, you will be able to:

  1. Define AWS IAM Identity Center and the AWS security service categories that it belongs to.
  2. Explain the architectural role and core capabilities of IAM Identity Center.
  3. Describe identity sources, users, groups, permission sets, account assignments, and the AWS access portal.
  4. Differentiate IAM roles and users from IAM Identity Center permission sets.

  6. Evaluate federation, IAM users, and IAM Identity Center for a workforce access requirement.
  7. Design a multi-account access architecture that integrates an external identity provider and assigns workforce access across AWS accounts.

1. AWS Security Services and IAM Identity Center

Problem Statement

A retail company runs separate AWS accounts for development, testing, production, security, and billing. Today, administrators create IAM users in each account. Each new hire needs several separate sign-ins, former employees can keep access until every account is cleaned up, and some developers store long-term access keys on their laptops.

The company wants employees to sign in once with the corporate identity provider, receive only the access their job requires in each account, and use temporary credentials. Which AWS service meets these needs?

1.2 Overview of IAM Identity Center

AWS IAM Identity Center is the central AWS tool for managing workforce user access across multiple AWS accounts and cloud applications. It was previously called AWS Single Sign-On. It lets employees, administrators, contractors, and other workforce users sign in once and reach the AWS accounts and applications that they are authorized to use.

1.3 Why Use IAM Identity Center

Without IAM Identity Center, an organization might create separate IAM users in every AWS account. This becomes hard to manage as the number of users and accounts grows.

AWS describes IAM Identity Center as the AWS solution for connecting your workforce users to AWS managed applications, such as Kiro and Amazon Quick, and to other AWS resources. You can connect your existing identity provider and synchronize users and groups from your directory, or create and manage users directly in IAM Identity Center. You can then use it for user access to applications, user access to AWS accounts, or both. IAM Identity Center provides:

  • Centralized user access: Create users and groups in IAM Identity Center.
  • Single sign-on: Users log in once through a personalized portal to reach assigned AWS accounts and third-party applications such as Microsoft 365 or Salesforce.
  • Group-based assignments: Assign access to groups instead of individual users.
  • Temporary credentials: Provide temporary credentials for AWS Command Line Interface (AWS CLI) and software development kit (SDK) access.
  • Centralized permission management: Define permissions once and apply them across accounts.
  • MFA: Add another verification factor during sign-in.
  • Identity source integration: Connect external providers such as Microsoft Entra ID, Okta, or Google Workspace, connect Active Directory, or manage users directly in the built-in Identity Center directory.
  • Multi-account access: Assign access across multiple AWS accounts with reusable permission sets.
  • One portal: Give users access to accounts and applications through the AWS access portal.

AWS recommends an organization instance of IAM Identity Center for centrally managing workforce access across AWS accounts. Account instances are meant only for isolated deployments of select AWS managed applications.

1.4 IAM Versus IAM Identity Center

  • IAM Identity Center is designed for human workforce users who need access to multiple accounts and applications.
  • Traditional IAM is built for machine workloads, granular service roles, and fine-grained permissions inside a single account.
  • IAM Identity Center does not replace IAM. It uses IAM roles and policies in the target AWS accounts.
AWS IAM compared with IAM Identity Center.
AWS IAMIAM Identity Center

1.4.1 Example: 500 Employees and 20 Accounts

A company has 500 employees and 20 AWS accounts, and Microsoft Entra ID already manages the employees. Instead of creating 500 IAM users in each account, the company connects Entra ID to IAM Identity Center. It then assigns:

  • Developers to development accounts.
  • Security analysts to every account with read-only security permissions.
  • Finance employees to billing accounts.
  • Administrators to production accounts under tightly controlled permissions.

Employees sign in through one portal and select an authorized account and role.

1.4.2 Important Distinction

  • IAM: Fine-grained permissions and roles inside AWS accounts.
  • IAM Identity Center: Centralized workforce access across accounts and applications.
  • Amazon Cognito: Customer identity for web and mobile applications (lesson 268.4).

2. How IAM Identity Center Works

Problem Statement

A new hire at the retail company needs access to the development account on the first day. The administrator does not want to create an IAM user, and the new hire does not want yet another password. What happens between the moment the new hire signs in and the moment the AWS console opens?

2.1 The Workflow

  1. A user signs in with the configured identity source.
  2. IAM Identity Center verifies the user’s identity.
  3. The access portal displays the assigned accounts and applications.
  4. The user selects an AWS account and a permission set.
  5. IAM Identity Center provides temporary credentials.
  6. The user assumes an IAM role in the selected AWS account.
  7. IAM policies, permissions boundaries, service control policies (SCPs), and resource policies determine the final permissions.

2.2 Identity Source

The identity source determines where users and groups are created and managed. IAM Identity Center supports these identity sources:

The identity sources that IAM Identity Center supports.
Identity sourceDescription
Identity Center directoryUsers and groups are created directly in IAM Identity Center.
Active DirectoryConnects to an AWS Managed Microsoft AD or to a supported on-premises Active Directory environment (lesson 268.3).
External identity providerUses an external provider such as Microsoft Entra ID, Okta, or another supported identity provider.

Only one identity source can be configured for an AWS organization. External providers commonly use Security Assertion Markup Language (SAML) 2.0 for user authentication and System for Cross-domain Identity Management (SCIM) for automatic user and group provisioning.

2.3 Users

A user represents a person who needs access to AWS accounts or applications. Examples include:

  • Cloud administrators.
  • Developers.
  • Database administrators.
  • Security analysts.
  • Contractors.

Users can be created directly in the Identity Center directory or synchronized from an external identity provider.

2.4 Groups

A group is a collection of users who require similar access. Examples include Cloud-Administrators, Developers, Database-Administrators, Security-Auditors, and Read-Only-Users. Instead of assigning access to every user separately, administrators should normally assign access to a group:

User → Group → AWS account assignment

When a user joins or leaves a team, the administrator changes the user’s group membership instead of editing many individual permissions.

Exam Trap

  • IAM Identity Center supports one identity source for an AWS organization.
  • Assign access to groups, not to individual users, so that joiners and leavers need only a group change.

Memory Hook

Identity source, then users, then groups, then assignments.

SAA-C03 Keyword Triggers

Trigger 1: “Employees are already managed in Microsoft Entra ID or Okta”→ Connect the external identity provider to IAM Identity Center

Trigger 2: “Automatically provision users and groups from the corporate directory”→ SCIM with IAM Identity Center

Trigger 3: “Create workforce users without an external provider”→ Identity Center directory

3. Permission Sets and Account Assignments

Problem Statement

At the retail company, developers need broad access in the development account and read-only access in production. The security team wants to define these access levels once and reuse them across accounts, instead of creating policies in each account.

3.1 Permission Sets

A permission set is a reusable template that defines what a user or group can do in an AWS account. A permission set can contain AWS managed policies, customer managed policies, inline policies, permissions boundaries, and session-duration settings. Examples include:

Examples of permission sets.
Permission setExample access
AdministratorFull administrative access
DeveloperManage application resources but not IAM
Database AdministratorManage Amazon RDS, Amazon Aurora, and Amazon DynamoDB
Security AuditorReview security configurations and logs
Read OnlyView resources without changing them

When you assign a permission set to an AWS account, IAM Identity Center creates and manages a corresponding IAM role in that account. Authorized users receive temporary credentials that let them assume that role.

3.2 Account Assignments

An account assignment connects three elements: a user or group, an AWS account, and a permission set. For example, the Developers group plus the development AWS account plus the PowerUser permission set lets members of the Developers group use the PowerUser role in the development account. The same group can receive a more restrictive permission set in production. A user can have different permissions in different AWS accounts.

3.3 AWS Organizations Integration

IAM Identity Center commonly integrates with AWS Organizations to manage access across multiple AWS accounts. An organization might contain a management account, a development account, a testing account, a production account, and a security account. Administrators can centrally assign users and groups to these accounts without creating separate IAM users in each account (lesson 268.2).

Permission sets determine what users can do inside an account. Service control policies, managed through AWS Organizations, set the maximum available permissions for accounts or organizational units. A permission set cannot grant an action that an SCP prohibits.

4. Access Portal, Temporary Credentials, and MFA

Problem Statement

Some developers at the retail company keep long-term access keys on their laptops. If a laptop is lost or a key is committed to a repository, the key stays valid until someone revokes it. The company also wants extra protection for administrators and for people who can change IAM permissions.

4.1 AWS Access Portal

The AWS access portal is a personalized webpage where workforce users sign in to reach their assigned AWS accounts and applications. A portal address might look like https://company-name.awsapps.com/start. After signing in, users see only the accounts, roles, and applications that are assigned to them. From the portal, a user can:

  • Open the AWS Management Console.
  • Select an authorized AWS account.
  • Select an assigned permission set.
  • Open assigned business applications.
  • Obtain temporary AWS CLI credentials.

4.2 Temporary Credentials

IAM Identity Center provides temporary credentials instead of requiring users to maintain long-term IAM access keys. Temporary credentials:

  • Expire automatically.
  • Reduce the risk of exposed access keys.
  • Connect to the user’s assigned permission set.
  • Work with the AWS Management Console.
  • Work with the AWS CLI and SDKs.

4.2.1 AWS CLI Access

For AWS CLI access, users configure an IAM Identity Center profile, sign in, and confirm their identity:

aws configure sso
aws sso login --profile development
aws sts get-caller-identity --profile development

This is safer than storing permanent access keys on a workstation.

4.3 Multi-Factor Authentication

IAM Identity Center supports MFA, which adds another verification factor during sign-in. Authentication factors can include:

  • A password.
  • An authenticator application.
  • A security key.
  • A built-in device authenticator.

MFA is especially important for:

  • Administrators.
  • Users who can change IAM permissions.
  • Users who access sensitive production resources.
  • The AWS account root user, which you protect with MFA in the account itself, not in IAM Identity Center.

MFA reduces the risk that an attacker can reach AWS resources with only a stolen password.

Exam Trap

  • MFA improves authentication security but does not grant permissions.
  • Temporary credentials from IAM Identity Center expire automatically. Long-term access keys do not.

Memory Hook

Portal, then assigned role, then temporary credentials. No permanent keys on the laptop.

SAA-C03 Keyword Triggers

Trigger 1: “Developers must use the AWS CLI without long-term access keys”→ IAM Identity Center with aws configure sso and aws sso login

Trigger 2: “Add a second verification factor to workforce sign-in”→ Multi-factor authentication (MFA)

Trigger 3: “Users see only the accounts and applications assigned to them”→ AWS access portal

5. Federation

Problem Statement

The retail company wants employees to use their existing corporate credentials instead of separate IAM passwords. A separate Lambda function must also send metrics to an external monitoring service, and the team does not want to store an API key for that service.

5.1 Workforce Federation

Federation lets users reach AWS by authenticating through an existing identity provider instead of using a separate IAM user name and password. The organization’s identity provider verifies the user. AWS then authorizes the user to assume a role and provides temporary credentials.

Federation technologies include:

  • SAML 2.0: Frequently used for enterprise workforce access.
  • OpenID Connect (OIDC): Commonly used by web applications, mobile applications, and automated workloads.
  • IAM Identity Center: The recommended centralized solution for workforce access to multiple AWS accounts.

5.1.1 Example: A Healthcare Organization

A healthcare organization stores employee accounts in Active Directory, and employees already use those accounts for email and company applications. The organization connects its directory to IAM Identity Center. Employees sign in with their existing corporate credentials and receive AWS access based on their department. The company does not need to create or manage separate IAM passwords for every employee.

5.1.2 Example: A Consulting Company

A consulting company gives its employees access to multiple customer environments. Consultants sign in through the company’s identity provider and select an approved customer role. Each session uses temporary credentials. When a consultant leaves, disabling the central corporate identity removes the person’s ability to authenticate, so nobody has to clean up users in every AWS account.

5.2 Outbound Identity Federation

Outbound identity federation works in the other direction. It lets your AWS workloads securely reach external services without storing long-term credentials. Your workloads can:

  • Integrate with external software-as-a-service (SaaS) providers for analytics, data processing, and monitoring. For example, a Lambda function can send metrics to an observability platform.
  • Authenticate with your own applications that run on AWS, on other cloud providers, or in on-premises data centers. For example, an AWS workload can interact with containerized applications in an on-premises Kubernetes cluster.
  • Avoid storing long-term credentials for external services. For example, a Lambda function can present a short-lived JSON Web Token (JWT) from AWS Security Token Service (AWS STS) to a third-party API instead of using a stored API key.

5.2.1 How the Process Works

  1. The Lambda function calls the GetWebIdentityToken API to request a JWT from AWS STS.
  2. AWS STS validates the request and returns a signed JWT to the Lambda function.
  3. The Lambda function sends the JWT to the external service.
  4. The external service extracts the issuer URL from the token, checks that it matches a known trusted issuer, and fetches the verification keys and metadata from the OIDC discovery endpoint.
  5. The external service uses the verification keys to verify the token’s signature and validates claims such as expiration time, subject, and audience.
  6. After successful validation, the external service grants access to the Lambda function.

You must enable outbound identity federation for the AWS account before workloads can call GetWebIdentityToken, and the calling IAM principal needs the sts:GetWebIdentityToken permission.

5.3 Federation Versus IAM Users

IAM users compared with federated identities.
IAM usersFederated identities
Created in one AWS accountManaged by an external or centralized identity source
May use long-term credentialsNormally receive temporary credentials
Appropriate for limited special casesPreferred for workforce access
Must be managed separatelySupports centralized user lifecycle management
Does not inherently provide centralized multi-account SSOCan provide SSO across accounts and applications

6. Comparison & Scenarios

6.1 Workplace Scenario: Securing a Multi-Account Retail Organization

A retail company operates separate AWS accounts for development, testing, production, security, and billing.

6.1.1 Business Requirements

  • Developers need broad access in development.
  • Developers need read-only access in production.
  • Security analysts need audit access to every account.
  • An EC2 application must read product images from Amazon S3.
  • A Lambda function must write order records to Amazon DynamoDB.
  • An external auditor needs temporary access to compliance reports.
  • Employees must use the company’s existing identity provider.
  • Privileged access must require MFA.

6.1.2 IAM Solution

  • IAM Identity Center connects the company’s existing identity provider to AWS.
  • Groups in the identity provider organize developers, security analysts, and finance employees.
  • Permission sets assign different access levels across AWS accounts.
  • IAM roles provide temporary permissions inside each account.
  • An EC2 role allows the application to read from the product-image bucket.
  • A Lambda execution role allows the function to write to the DynamoDB orders table.
  • An S3 bucket policy permits the external auditor’s role to read only the compliance reports.
  • A cross-account role allows the central security team to review account configurations.
  • MFA protects privileged workforce sessions.
  • IAM Access Analyzer checks for unintended external access (lesson 268.5).

This architecture avoids embedded access keys and provides centrally managed, temporary, least-privilege access.

6.2 SAA-C03 Exam Cheat Sheet and Decision Rules

6.2.1 Important IAM Exam Distinctions

Decision rules for SAA-C03 questions about IAM and IAM Identity Center.
#If the question says...Answer
1Permissions for an individual identityIAM policy
2The same permissions for multiple IAM usersIAM group
3An EC2 application accessing S3IAM role attached to the EC2 instance
4A Lambda function accessing DynamoDBLambda execution role
5Temporary accessIAM role and AWS STS
6Access from one AWS account to anotherCross-account role or a supported resource-based policy
7Central workforce access to multiple accountsIAM Identity Center
8Existing corporate credentialsFederation
9Customer sign-in for an applicationAmazon Cognito
10Additional sign-in protectionMFA
11Detecting external or unused accessIAM Access Analyzer

13Sharing an S3 bucket with another accountS3 bucket policy or cross-account role

6.2.2 Rules to Remember

  • IAM users have long-term credentials. Roles provide temporary credentials.
  • Applications that run on AWS should use roles, not embedded access keys.
  • IAM groups contain users, not roles or other groups.
  • Identity-based policies attach to identities.
  • Resource-based policies attach to resources.
  • A role’s trust policy controls who can assume it.
  • A role’s permissions policy controls what it can do.
  • Explicit Deny overrides Allow.
  • IAM Identity Center is preferred for workforce access across multiple accounts.
  • Federation uses an existing identity provider and temporary AWS credentials.
  • MFA improves authentication security but does not grant permissions.
  • Service control policies limit permissions but do not grant them.
  • IAM is global, although many resources that IAM controls are Regional.

7. Knowledge Check

Answer each question in your own words, and then open the model answer to compare.

Question 1: The Problem IAM Identity Center Solves. What problem does IAM Identity Center solve for a company that has many AWS accounts?

Show the model answer

Without it, administrators create separate IAM users in every account, which is hard to manage as users and accounts grow. IAM Identity Center gives one place to manage workforce access and assignments across accounts and applications.

Question 2: Permission Sets and IAM Roles. How do permission sets relate to the IAM roles in each AWS account?

Show the model answer

A permission set is a reusable template. When it is assigned to an account, IAM Identity Center creates and manages a corresponding IAM role in that account, and users assume the role with temporary credentials.

Question 3: From Sign-In to AWS Access. Describe what a workforce user does, from sign-in to AWS access, when the company uses IAM Identity Center.

Show the model answer

The user signs in with the configured identity source. IAM Identity Center verifies the user, and the access portal shows the assigned accounts and applications. The user selects an account and permission set, receives temporary credentials, and assumes the IAM role. IAM policies, permissions boundaries, service control policies, and resource policies determine the final permissions.

Question 4: Account Assignments. Which three elements does an account assignment connect? Give an example in which one group has different access in two accounts.

Show the model answer

An account assignment connects a user or group, an AWS account, and a permission set. For example, the Developers group with the development account and the PowerUser permission set gets broad access in development, and the same group with the production account and the ReadOnly permission set gets view-only access in production.

Question 5: Federation and IAM Users. Compare federated identities with IAM users for workforce access. Which do you prefer for a company with many accounts, and why?

Show the model answer

IAM users are created in one account, can use long-term credentials, and must be managed separately. Federated identities are managed by an external or centralized identity source, normally receive temporary credentials, and support centralized lifecycle management and single sign-on across accounts. Federation, preferably through IAM Identity Center, is preferred for workforce access because access ends centrally when an identity is disabled.

Lesson 268.8 - AWS Systems Manager

Manage, patch, and automate fleets of servers on AWS and on premises with Systems Manager.

Overview and Objectives

Lesson Overview

This lesson covers what AWS Systems Manager is, how it works, and what it can do: its core concepts and capabilities, running commands across fleets with Run Command, automating maintenance with Automation runbooks, and patching with Patch Manager.

  • Tab 1 gives an overview of the service, its technical concepts (managed nodes, the SSM Agent, documents, and targets), its capabilities in four categories, and its practical applications.
  • Tab 2 covers Run Command: running the same command or script on many instances at once, without SSH, with output to Amazon S3 or Amazon CloudWatch Logs.
  • Tab 3 covers Automation: automating maintenance tasks such as restarts, AMIs, and snapshots with runbooks, triggered manually, by Amazon EventBridge, on a schedule, or by AWS Config.
  • Tab 4 covers Patch Manager: automating operating system and application patching across the fleet with patch baselines, patch groups, and Maintenance Windows, and reporting patch compliance.
  • Tab 5 compares Session Manager, Run Command, and Automation, and lists decision rules for the AWS Certified Solutions Architect – Associate (SAA-C03) exam.
  • Tab 6 checks your understanding with open-ended questions.

Session Manager, the Systems Manager capability that replaces bastion hosts, is covered in lesson 269.5, Remote Session: Bastion Host, Session Manager.

1. What Is AWS Systems Manager?

Problem Statement

Your company runs 400 servers: Amazon EC2 instances in several accounts and Regions, plus servers in its own data center. Every month the operations team logs in to each server to install patches, keeps a spreadsheet of which software runs where, stores database passwords in configuration files, and fixes broken settings by hand. Every task uses a different script or tool, and nobody can say for sure that all servers are patched and configured the same way.

You need one place to see, access, patch, configure, and automate all your servers, wherever they run, without logging in to each one.

1.1 Overview of AWS Systems Manager

  • Automates common and repetitive IT operations and management tasks, and gives you control of your AWS infrastructure.
  • AWS Systems Manager is a management service that lets you view, manage, and operate your nodes at scale: EC2 instances, on-premises servers, and virtual machines in other clouds.
  • It gives a centralized view of your nodes across AWS accounts and Regions.
  • It provides safe, secure remote management without logging in to servers, replacing the need for bastion hosts, SSH, or remote PowerShell.
  • It works through the SSM Agent, which runs on AWS, on premises, and in other clouds, so the same tools work everywhere.
  • It bundles many tools, for example to patch nodes with security updates, connect to them securely, run commands at scale, and automate operational tasks.

For the exam, think of Systems Manager as the answer whenever a question asks you to manage a fleet of servers, especially without SSH, at scale, or across hybrid (AWS plus on-premises) environments.

1.1.1 Who Can Use Systems Manager

Systems Manager is designed to enable multiple roles to perform various operations on managed resources, such as Amazon Elastic Compute Cloud (Amazon EC2) instances. System administrators, software developers, security architects, cloud architects, and IT professionals can all use it to manage AWS resources.

1.2 Systems Manager Technical Concepts

AWS Systems Manager operates across several IT domains, including infrastructure management, application management, and security operations. Understanding these domains helps you implement Systems Manager effectively in your environment.

Each managed node runs the SSM Agent, which connects outbound to Systems Manager. An IAM role (on EC2) or a hybrid activation (on premises and in other clouds) gives it permission. SSM documents define the actions, and the tools act on the nodes. The following seven concepts make this work.

Concept 1 of 7

Managed node

Any machine configured for use with Systems Manager: an EC2 instance, an on-premises server, an edge device, or a VM in another cloud.

Concept 2 of 7

SSM Agent

AWS Systems Manager Agent (SSM Agent) is software installed on your instances (on each node) that communicates with Systems Manager. It runs the tasks requested by Systems Manager and sends status and execution information back to the service. It connects outbound over HTTPS (443), so no inbound ports are needed. It is preinstalled on Amazon Linux and many other AWS-provided AMIs.

Concept 3 of 7

IAM role (instance profile)

Systems Manager requires specific IAM roles and policies to function properly. Instances need an instance profile (an attached IAM role) that grants permission to communicate with the Systems Manager service, and users need appropriate permissions to perform management tasks.

For instances, the usual choice is the AmazonSSMManagedInstanceCore managed policy.

Concept 4 of 7

Hybrid activation

Registers on-premises servers and VMs in other clouds as managed nodes. Their node IDs start with mi- instead of i-.

Concept 5 of 7

SSM document

A JSON or YAML file that defines the actions Systems Manager performs, for example a command document for Run Command or an Automation runbook. AWS provides hundreds, and you can write your own.

Concept 6 of 7

Targets

How you choose which nodes an action applies to: specific node IDs, tags (for example Environment=Production), or resource groups.

Concept 7 of 7

Parameter Store

Parameter Store, a capability of AWS Systems Manager, provides secure storage for configuration data, secrets, and other operational parameters. It helps you centralize configuration management and reduce the risk of exposing sensitive information.

Parameters can be stored as plaintext or encrypted values, with encryption handled by AWS Key Management Service (AWS KMS). With this flexibility, you can store both sensitive and nonsensitive data in a single location.

2. Systems Manager Run Command

Problem Statement

A critical security fix must be applied to 200 EC2 instances across several environments today. Logging in to each one, even through Session Manager, would take hours and invite mistakes. You need to run the same command on all of them at once, without SSH, see which ones succeeded or failed, and keep the output for the audit team.

2.1 What Is Run Command

Run Command is the Systems Manager capability for running the same command or script on many managed nodes at once, without logging in to any of them. It works through the SSM Agent on each node (section 1.2), so each node needs the same setup as any Systems Manager tool: the SSM Agent, an attached IAM role, and outbound HTTPS to the Systems Manager endpoints.

  • Execute a document (a script) or just run a command.
  • Run commands across multiple instances, using resource groups or tags.
  • No need for SSH.
  • Command output can be shown in the AWS Management Console, sent to an Amazon S3 bucket, or sent to CloudWatch Logs.
  • Send notifications to Amazon Simple Notification Service (Amazon SNS) about command status (In progress, Success, Failed, and so on).
  • Integrated with IAM and AWS CloudTrail.
  • Can be invoked using EventBridge.

2.2 How It Works

  • Choose a document: an AWS-provided document, such as AWS-RunShellScript (Linux) or AWS-RunPowerShellScript (Windows), or your own custom document.
  • Choose the targets: specific instances, instances with a tag (for example Environment=Production), or a resource group.
  • Control the rollout: set rate control (how many instances run at the same time) and an error threshold (stop if too many fail).
  • Choose where results go: the console, an Amazon S3 bucket, or CloudWatch Logs, plus optional Amazon SNS status notifications.
  • Run it: manually, from the AWS CLI or SDK, or automatically through an EventBridge rule or schedule.

Exam-Style Question 1

A critical security fix must be applied to 200 EC2 instances today. The team wants to run the same command on all of them without SSH, stop the rollout if too many instances fail, and keep the command output for the audit team. Which solution meets these requirements?

  1. Open a Session Manager session on each instance and run the command by hand.
  2. Create an Automation runbook that restarts each instance.
  3. Use Run Command with tag-based targets, rate control, an error threshold, and logged output.
  4. Create a hybrid activation for each instance.
Show the answer

Correct answer: C. Run Command runs the same command on many instances at once. Rate control and an error threshold make the rollout safe, and the output options keep an audit trail.

Each option checked against the requirements.
OptionMeets all requirements?Verdict
ANo — Session Manager opens an interactive shell on one instance at a timeIncorrect

Exam Trap

  • Run Command acts inside the operating system of many instances. Session Manager gives an interactive shell on one instance.
  • Rate control sets how many instances run at the same time. The error threshold sets when to stop.

3. Systems Manager Automation

Problem Statement

Every Sunday night, your team stops a fleet of instances, takes EBS snapshots, creates fresh AMIs, and restarts everything, by hand, following a checklist. Sometimes a step is missed. And when AWS Config flags a non-compliant resource, such as an unencrypted volume or an open security group, someone has to notice and fix it manually. You need these multi-step maintenance tasks to run automatically and the same way every time.

3.1 What Is Systems Manager Automation

  • Simplifies common maintenance and deployment tasks of EC2 instances and other AWS resources.
  • Examples: restart instances, create an AMI, take an Amazon EBS snapshot.
  • An Automation runbook is an SSM document that defines the actions performed on your EC2 instances or AWS resources. Runbooks can be predefined (provided by AWS) or custom (written by you).

AWS provides hundreds of ready-made runbooks, for example AWS-RestartEC2Instance, AWS-StopEC2Instance, AWS-CreateImage, and AWS-CreateSnapshot. A runbook can chain several steps, such as stop the instance, take a snapshot, create an AMI, and then start it again.

3.2 How Automation Is Triggered

The four ways to trigger an Automation runbook.
TriggerTypical use
Manually, using the AWS Management Console, AWS CLI, or SDKOne-off tasks, such as creating an AMI before a risky change
Amazon EventBridgeReact to events, such as an instance state change or a CloudWatch alarm
On a schedule, using Maintenance WindowsRecurring tasks at a set time, such as weekly snapshots and restarts
AWS Config, for rule remediationAutomatically fix non-compliant resources, such as closing an open security group port

3.3 Run Command Versus Automation

  3. Use Patch Manager with a patch baseline.
  4. Use Automation runbooks, scheduled with a Maintenance Window.

Correct answer: D. Automation runs multi-step workflows against AWS resources, and a Maintenance Window schedules them. Snapshots and AMIs are actions on AWS resources, not commands inside the operating system.

4. Systems Manager Patch Manager

Problem Statement

A critical security vulnerability is announced, and the auditors want proof within a week that every server is patched: 300 Linux and Windows instances in several accounts, plus servers in the data center. Today, each team patches its own servers by hand, at different times, with different rules, and nobody can produce a single report that shows which servers are still missing patches.

You need to patch the whole fleet automatically, on a schedule, using consistent rules, and see at any time which servers are compliant.

4.1 Introduction to Patch Manager

  • Patch Manager is a Systems Manager node tool that automates the process of patching managed nodes with security-related updates and other types of updates.
  • It patches both operating systems and, on some operating systems, applications.
  • It supports Linux, Windows Server, and macOS, on EC2 instances, on-premises servers, and VMs in other clouds (hybrid activations, section 1.2).
  • You can scan nodes to report only which patches are missing, or scan and install the missing patches.
  • It reports patch compliance: which nodes are compliant and which are missing approved patches.
  • It works through the same SSM Agent as every Systems Manager tool. Under the hood, it runs the AWS-RunPatchBaseline document through Run Command (tab 2).

4.2 Key Concepts

The key concepts of Patch Manager.
ConceptWhat it means
Patch baselineThe rules that decide which patches are approved for installation. It can auto-approve patches by classification and severity, for example critical security updates 7 days after release, and list specific patches to always approve or reject.
Predefined versus custom baselinesAWS provides a predefined default baseline for each operating system. You can create custom baselines with your own approval rules, for example a stricter one for production.
Patch groupA set of nodes that share a baseline, selected with a tag such as Patch Group = Production. Different groups, for example development and production, can use different baselines.
Patch policyThe recommended way to set up patching, created with Quick Setup. One policy defines the baselines, schedule, and targets, and can apply across multiple accounts and Regions in an AWS Organization.
Scan versus InstallThe two operations of AWS-RunPatchBaseline. Scan only reports missing patches. Install scans and installs them, rebooting the node if needed.
Maintenance WindowThe schedule for patching, so updates and reboots happen outside business hours (tab 3).
Patch nowAn on-demand option to patch nodes immediately from the console, for example for an urgent fix.

4.3 How Patch Manager Works

  • Choose a patch baseline: use the predefined default for each operating system, or create a custom one.
  • Choose the targets: tag nodes into patch groups, or use a patch policy.
  • Schedule it: create a Maintenance Window, or let the patch policy define the schedule.
  • Patching runs: Run Command executes AWS-RunPatchBaseline with Scan or Install on each node.
  • Review compliance: the Patch Manager dashboard shows which nodes are compliant and which are missing patches.

Nodes need to reach their patch sources, such as the operating system vendor’s repositories or Windows Update. For nodes in private subnets, that usually means a NAT gateway or a local patch repository.

Exam-Style Question 3

A company must patch 300 Linux and Windows instances and its data center servers. It wants to approve only critical security patches 7 days after release and patch outside business hours, and it needs a report of which servers are missing patches. Which design meets these requirements?

  2. Run Command with a shell script that installs all available updates every night.
  3. Automation runbooks that restart each instance every week.
  4. State Manager with the default patch baseline and no schedule.
Show the answer

Correct answer: A. A custom patch baseline sets the approval rules, a Maintenance Window sets the time, and Patch Manager reports patch compliance. Hybrid activations bring the data center servers in.

Each option checked against the requirements.

Patch Manager means keeping every server up to date, by the same rules, on a schedule.

6. Knowledge Check

Answer each question in your own words, and then open the model answer to compare.

Question 1: Run Command and Session Manager. How is Run Command different from Session Manager, and how would you safely run a patch script on 200 production instances with it?

Show the model answer

Session Manager opens an interactive shell on one instance. Run Command runs the same document or command on many instances at once. Both use the SSM Agent and need no SSH. For 200 instances, target them by tag (for example Environment=Production) or a resource group, use rate control to run on a limited number at a time and an error threshold to stop if too many fail, send output to Amazon S3 or CloudWatch Logs for the audit trail, and send status notifications to Amazon SNS.

Question 2: Automation Runbooks. What is a Systems Manager Automation runbook, and what are the four ways to trigger one?

Show the model answer

A runbook is an SSM document that defines a series of actions on EC2 instances or other AWS resources, such as restarting instances, creating an AMI, or taking an EBS snapshot. It can be provided by AWS or written by you. It can be triggered manually (console, CLI, or SDK), by Amazon EventBridge, on a schedule through Maintenance Windows, or by AWS Config to remediate non-compliant resources.

Question 3: Choosing the Right Capability. Your team must install a monitoring package on 300 instances, and separately create a weekly AMI of 20 critical servers. Which Systems Manager capability fits each task, and why?

Show the model answer

Installing the package runs a command inside each instance’s operating system, so it fits Run Command: target the instances by tag, use rate control and an error threshold, and send the output to Amazon S3 or CloudWatch Logs. Creating weekly AMIs is a recurring workflow against AWS resources, so it fits Automation: use a runbook such as AWS-CreateImage, scheduled with a Maintenance Window.

Question 4: The Four Categories of Tools. What are the four categories of Systems Manager tools? Give one tool and one practical use for each.

Show the model answer

Node tools, for example Patch Manager to patch every server monthly. Change management tools, for example Automation to create AMIs on a schedule. Application tools, for example Parameter Store to keep database passwords out of code. Operations tools, for example OpsCenter to collect and resolve operational issues.

Question 5: What a Server Needs. What does a server need before Systems Manager can manage it, and how is this different for an on-premises server?

Show the model answer

It needs the SSM Agent installed and running, permission to talk to Systems Manager, and outbound HTTPS (443) access to the Systems Manager endpoints. An EC2 instance gets permission from an attached IAM role (for example with AmazonSSMManagedInstanceCore). An on-premises server or a VM in another cloud is registered through a hybrid activation instead, and its node ID starts with mi- rather than i-.

Question 6: Patch Baselines. What is a patch baseline, and how would you patch development and production servers with different rules and at different times?

Show the model answer

A patch baseline is the set of rules that decides which patches are approved, for example auto-approving critical security updates 7 days after release, plus lists of patches to always approve or reject. Tag the servers into two patch groups (for example Patch Group = Development and Patch Group = Production), give each group its own custom baseline, and patch each group in its own Maintenance Window. Or define both in a patch policy with Quick Setup. Then check patch compliance to confirm every node is up to date.

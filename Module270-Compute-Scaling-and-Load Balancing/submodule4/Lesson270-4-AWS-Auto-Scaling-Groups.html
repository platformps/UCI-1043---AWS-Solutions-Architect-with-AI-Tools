Introduction

Applications that run on a fixed number of servers fail when a server fails and waste money when demand is low. An Auto Scaling group solves both problems by replacing failed instances and by matching the number of instances to demand. Architects who pass SAA-C03 questions on resilience and cost need to know which Auto Scaling group setting solves which problem.

This lesson assumes basic AWS knowledge, such as launching an Amazon Elastic Compute Cloud (Amazon EC2) instance and recognizing subnets and Availability Zones. It covers the Auto Scaling group of Amazon EC2 Auto Scaling only. Scaling of other AWS services is outside this lesson. Elastic Load Balancing is covered in lessons 270.1 to 270.3.

1. What Is an Auto Scaling Group?

Problem Statement

An online ticketing company runs its website on a single Amazon EC2 instance. When tickets for a popular concert go on sale, traffic jumps from a few hundred visitors to tens of thousands within minutes, and the instance fails. At night the same instance sits near 5 percent CPU utilization while the company still pays for it. The team needs the site to recover from a failed instance without human action, add servers during a rush, and remove them afterward.

1.1 Overview of Auto Scaling Groups

An Auto Scaling group (ASG) is a logical group of EC2 instances that AWS launches, replaces, and removes automatically to keep an application available and sized to its load.

An Auto Scaling group works as follows:

  • You specify the minimum, maximum, and desired number of instances.
  • The group uses Amazon CloudWatch alarms (lesson 274.1) to trigger scaling actions based on metrics.
  • A group performs two core jobs: it keeps the number of running instances at the level you set, and it changes that number automatically when demand changes.
  • The group launches and terminates instances automatically, following rules that you define.
  • Instances inside a group are interchangeable. A group works best when each instance can be replaced without losing data, so keep state in services such as Amazon Relational Database Service (Amazon RDS), Amazon Simple Storage Service (Amazon S3), or Amazon ElastiCache rather than on the instance.

The goal of an Auto Scaling group is to:

  • Scale out (add EC2 instances) to match an increased load.
  • Scale in (remove EC2 instances) to match a decreased load.
  • Ensure that a minimum and a maximum number of EC2 instances are running.
  • Register new instances with a load balancer automatically.
  • Re-create an EC2 instance when a previous one is terminated, for example because it is unhealthy.

An Auto Scaling group has no additional charge. You pay only for the underlying EC2 instances and the other resources that the group uses. Check the pricing page for current details.

TermMeaningExample

Minimum capacity works as follows:

  • It is the lowest number of EC2 instances in the group.
  • Even if demand drops to zero, the instance count does not go below this number.
  • It ensures that there is always enough baseline capacity for the application.

Desired capacity works as follows:

  • It is the number of EC2 instances that the group aims to maintain to handle the steady-state load.
  • You can set it manually, or scaling policies can change it automatically.

1.3 The Launch Template

1.3.1 The Need for a Launch Template

A company operates several web servers in an Auto Scaling group. Each server must use the same operating system, security groups, storage configuration, permissions, and startup script.

Manually configuring every new instance would be slow and inconsistent. The company needs a reusable configuration that Auto Scaling can apply whenever it launches an instance.

Solution: Create an EC2 launch template and associate it with the Auto Scaling group.

A launch template is a reusable blueprint that stores the settings of an EC2 instance, so that every instance the group launches is configured the same way.

Amazon EC2 Auto Scaling uses the launch template to create consistent EC2 instances when it:

  • Creates an Auto Scaling group.
  • Increases capacity.
  • Replaces an unhealthy instance.
  • Performs an instance refresh.
  • Restores the desired capacity of the group.

The launch template works as follows:

  • The group launches every instance from a launch template. The template holds the AMI, instance type, key pair, security groups, storage, AWS Identity and Access Management (IAM) instance profile, and user data.
  • A launch template can hold many versions. To change a setting, create a new version instead of editing an existing one.
  • The group points to a version as $Default, $Latest, or a specific number such as 2.
  • Changing the template does not touch instances that are already running. Replacing them is a separate step, covered in section 7.5.
  • Use a launch template for every new group. Since October 1, 2024, Amazon EC2 Auto Scaling no longer supports launch configurations for new accounts.

For more detail, visit Auto Scaling launch templates.

Important Distinction

The launch template does not determine how many instances run.

The Auto Scaling group determines:

  • How many instances to maintain.
  • Where to launch them.
  • When to add or remove capacity.
  • Which health checks to use.
  • Which load balancer target groups receive the instances.

1.3.2 Launch Template Workflow

The launch template is used in this sequence:

  1. An administrator creates a launch template.
  2. The administrator associates the template with an Auto Scaling group.
  3. A scaling event changes the desired capacity.
  4. Auto Scaling reads the selected template version.
  5. Auto Scaling launches identically configured EC2 instances.
  6. The new instances initialize and enter service.

1.3.3 Real-World Example

Scenario: An online retailer runs a web application behind an Application Load Balancer.

The launch template contains:

  • An Amazon Linux AMI.
  • The t3.small instance type.
  • A web server security group.
  • An IAM role for CloudWatch and Amazon S3.
  • A 20 GB encrypted EBS volume.
  • A user data script that installs the application.
  • Required resource tags.

The Auto Scaling group specifies:

  • Minimum capacity: 2.
  • Desired capacity: 4.
  • Maximum capacity: 10.
  • Subnets in two or more Availability Zones.
  • An Application Load Balancer target group.
  • A target tracking policy based on request count.

When traffic increases, the Auto Scaling group launches instances using the launch template and registers them with the target group.

1.4 Where the Group Places Instances

The group places instances using these rules:

  • A group runs in an Amazon Virtual Private Cloud (VPC). You choose one or more subnets, and each subnet belongs to one Availability Zone.
  • The group balances capacity evenly across the Availability Zones you enable. A group with four instances and two zones aims for two per zone.
  • Choose subnets in at least two Availability Zones for any production web tier.
  • A common layout places the Application Load Balancer (ALB) in public subnets and the group in private subnets, so users reach the load balancer and never the instances directly.

1.5 How the Pieces Fit Together

Each part has one job:

  • The launch template says what to launch.
  • The group says how many to keep and where to place them.
  • The scaling policy says when to change that number, usually in response to an Amazon CloudWatch alarm.
  • An ALB spreads user traffic across the instances in the group.

1.6 Work With Auto Scaling Groups

You can create, access, and manage your Auto Scaling groups using any of the following interfaces:

  • AWS Management Console — Provides a web interface that you can use to access your Auto Scaling groups. If you have signed up for an AWS account, sign in to the AWS Management Console, use the search box on the navigation bar to search for Auto Scaling groups, and then choose Auto Scaling groups.
  • AWS Command Line Interface (AWS CLI) — Provides commands for a broad set of AWS services, and is supported on Windows, macOS, and Linux. To get started, see Prepare to use the AWS CLI. For more information, see autoscaling in the AWS CLI Command Reference.
  • AWS Tools for Windows PowerShell — Provides commands for a broad set of AWS products for those who script in the PowerShell environment. To get started, see the AWS Tools for PowerShell User Guide. For more information, see the AWS Tools for PowerShell Cmdlet Reference.
  • AWS Software Development Kits (AWS SDKs) — Provide language-specific API operations and take care of many of the connection details, such as calculating signatures, handling request retries, and handling errors. For more information, see AWS SDKs.
  • Query API — Provides low-level API actions that you call using HTTPS requests. Using the Query API is the most direct way to access AWS services. However, it requires your application to handle low-level details such as generating the hash to sign the request, and handling errors. For more information, see the Amazon EC2 Auto Scaling API Reference.
  • AWS CloudFormation (lesson 296.1) — Supports creating Auto Scaling groups using CloudFormation templates. For more information, see Create Auto Scaling groups with AWS CloudFormation.

2. Auto Scaling Groups With On-Demand and Spot Instances

Problem Statement

A company runs a web tier that needs at least four servers at all times, but traffic doubles for several hours every day. The finance team wants a lower compute bill. The web servers are stateless, and replacing one takes a few minutes. The team needs a group that always keeps its steady capacity safe and fills the extra capacity with cheaper servers that AWS might reclaim.

2.1 Mixed Instances in One Group

A mixed instances group has these characteristics:

  • A group that uses a launch template can combine several instance types and two purchase options: On-Demand Instances and Spot Instances.
  • You describe the mix in a mixed instances policy on the group.
  • On-Demand Instances are available when you need them. You pay the On-Demand price, and AWS does not reclaim them.
  • Spot Instances use spare EC2 capacity at a lower price, but Amazon EC2 can reclaim them with a two-minute interruption notice.
  • Use Spot Instances only for work that tolerates interruption, such as stateless web servers behind a load balancer or batch workers.

2.2 Instances Distribution Settings

SettingWhat it controlsExample
On-Demand base capacityThe minimum amount of the group’s capacity that must be fulfilled by On-Demand Instances.A base of 4 keeps the first four instances On-Demand.
On-Demand percentage above baseThe share of On-Demand Instances in the capacity above the base. The rest is Spot.50 means half of the extra instances are On-Demand and half are Spot. 0 means all Spot above the base.
Spot allocation strategyHow the group picks Spot capacity pools. The console selects price-capacity-optimized by default.Price-capacity-optimized, capacity-optimized, capacity-optimized-prioritized, or lowest-price.
On-Demand allocation strategyWhich instance type the group tries first for On-Demand capacity.Prioritized follows the order of your instance types.
Maximum Spot priceThe highest price you will pay for a Spot Instance. If you leave it blank, the On-Demand price is the limit.Leave the default blank for most workloads.

The Spot allocation strategies work as follows:

StrategyHow it picks Spot pools
Price-capacity-optimizedChooses from the pools with the most available capacity and then takes the lowest price among them.
Capacity-optimizedLaunches from the pools with the most available capacity, which lowers the chance of interruption.
Capacity-optimized-prioritizedHonors your instance type priorities on a best-effort basis, but optimizes for capacity first.
Lowest-priceLaunches from the lowest-priced pools and spreads instances evenly across the number of pools you set.

2.4 Reducing Spot Interruptions

These practices lower the chance and the cost of an interruption:

  • Diversify instance types. List several instance types and sizes so the group can draw from many Spot capacity pools.
  • Use several Availability Zones. Each zone has its own Spot pools.
  • Choose a capacity-focused allocation strategy. Price-capacity-optimized and capacity-optimized favor pools that are less likely to be interrupted.
  • Turn on Capacity Rebalancing. The group proactively replaces a Spot Instance that is at elevated risk of interruption. It launches a replacement before it terminates the old instance.
  • Keep instances stateless. Store data in services such as Amazon S3 or Amazon RDS so that a reclaimed instance loses nothing.

2.4.1 Exam-Style Question

The company wants the lowest cost without risking the steady capacity. Which configuration meets these requirements?

  • A. Run every instance as a Spot Instance with the lowest-price allocation strategy.
  • B. Use a mixed instances group with an On-Demand base capacity of 4 and Spot Instances for the capacity above the base.
  • C. Use a mixed instances group with no On-Demand base and 100 percent On-Demand above the base.
  • D. Run four On-Demand Instances outside the group and launch the peak capacity by hand.

3. Auto Scaling Groups With a Load Balancer

Problem Statement

A company runs its web tier in an Auto Scaling group. Last week the group launched four new instances during a traffic spike, but customers still received errors because nobody added the new servers to the load balancer. Later, when the group removed two instances, customers lost requests that were still in progress. The team needs the group and the load balancer to stay in step without manual work.

3.1 Why Attach a Load Balancer

  • Instances in a group come and go, so users need one stable entry point. A load balancer gives them one DNS name.
  • The load balancer spreads requests across the healthy instances in the group.
  • When you use Elastic Load Balancing (ELB) with a group, you do not register individual instances yourself.

3.2 How the Attachment Works

Load balancer integration follows these rules:

  • You attach a target group to the group when you use an Application Load Balancer, a Network Load Balancer (NLB), or a Gateway Load Balancer. You attach the load balancer itself only for a Classic Load Balancer.
  • The group registers new instances with the target group automatically and deregisters terminated instances.
  • The load balancer and its target group must be in the same AWS account, VPC, and Region as the group.
  • A group cannot use a target group with a target type of ip. It registers instances.
  • By default, the group uses EC2 health checks only. Turn on the ELB health check so that the group also replaces a target that fails the load balancer check (section 6.2).
  • By default, ELB waits 300 seconds for in-flight requests to finish when it deregisters an instance. This is also called connection draining.

3.3 Traffic Flow and Subnets

  • Place the ALB in public subnets and the group in private subnets. Users reach the load balancer, and the instances accept traffic only from the load balancer.
  • Enable at least two Availability Zones for both the load balancer and the group.
  • Allow the instance security group to accept traffic only from the load balancer security group.

3.4 Scaling on Load Balancer Metrics

  • After you attach a target group, a scaling policy can use a load balancer metric. The common choice is ALBRequestCountPerTarget, the average number of requests per instance.
  • Target tracking on this metric keeps the request load per instance near a value you choose (section 5.3).

3.5 Elastic Load Balancing and Auto Scaling Group With Simple Scaling

A load balancer with simple scaling works as follows:

  • A simple scaling policy (section 4.4.3) runs when an Amazon CloudWatch alarm fires. The alarm watches a metric, such as the average CPU utilization of the group.
  • Scale out: when average CPU is above 80 percent, the alarm triggers an action, and the group launches EC2 instances.
  • Scale in: when average CPU is below 30 percent, a second alarm triggers an action, and the group terminates EC2 instances.
  • You create both alarms and both policies yourself.
  • After each action, the group waits for the cooldown to end before it responds to another alarm (tab 8).
  • The load balancer sends traffic to the new instances after the group registers them, and it stops sending traffic to terminated instances.

3.6 Elastic Load Balancing and Auto Scaling Group With Target Tracking

A load balancer with target tracking works as follows:

  • You choose a metric and a target value (section 4.4.1). In the example, the first group targets about 40 percent average CPU, and the second group targets about 50 percent.
  • The group launches EC2 instances when the metric rises above the target and terminates them when it falls below the target, so that it stays near the target value.
  • You do not create alarms or step values. Amazon EC2 Auto Scaling creates and manages the CloudWatch alarms for you (tab 5).
  • Each group sits behind a load balancer. The load balancer spreads requests across the instances, so adding instances lowers the average CPU of each instance.

3.7 Application Load Balancer as a Target of a Network Load Balancer

This design works as follows:

  • A Network Load Balancer (NLB) can use an Application Load Balancer (ALB) as its target.
  • Use case: a client needs static IP addresses to add to the allow-list of the corporate network firewall for a web application hosted in AWS.
  • The NLB provides the static IP addresses, and an ALB does not. The firewall allows traffic only to those addresses.
  • The NLB forwards the traffic to the ALB, which sends the HTTPS requests to the EC2 instances behind it.

3.8 Blue/Green Deployment With Weighted Target Groups

This design works as follows:

  • Use case: a blue/green deployment where traffic is gradually shifted to the green deployment.
  • Use weighted target groups to shift the traffic gradually.
  • Use separate Auto Scaling groups for both target groups, and manage the capacity manually as the traffic shifts.

4. Scaling Policies

Problem Statement

A retail site averages 30 percent CPU utilization during the day. Every weekday at 12:00 a flash sale pushes CPU to 95 percent within minutes, and new instances need about five minutes to boot. Marketing has also announced a one-time event on a specific date at 09:00. The team must decide which scaling methods to combine so that capacity is ready before each rush and the site does not run large idle capacity the rest of the time.

4.1 Overview of Scaling Policies

  • A scaling policy tells the group how to change its desired capacity when demand changes.
  • The group then launches or terminates instances to match the new desired capacity, and it always stays between the minimum and the maximum capacity.
  • A policy can scale out (add instances) and scale in (remove instances).
  • The scaling methods are manual, scheduled, dynamic (target tracking, step, and simple), and predictive.
  • You can combine several policies on one group, for example target tracking for general demand and a scheduled action for a known event.

4.2 Scaling Methods at a Glance

MethodWhat triggers itBest for
ManualYou change the desired capacity yourself.Testing and one-off changes.
ScheduledA date and time that you set.Known events and fixed daily patterns.
Dynamic: target trackingA metric moving away from a target value.Most workloads. It is the simplest to manage.
Dynamic: stepA CloudWatch alarm, with different actions for different breach sizes.Fine control over how much to add.
Dynamic: simpleA CloudWatch alarm, with one action and then a wait.Older designs.
PredictiveA forecast built from recent history.Repeating patterns that need capacity ready ahead of time.

4.3 Manual Scaling

  • With manual scaling, you set the required number of EC2 instances in the Auto Scaling group configuration.
  • The number must stay between the minimum and the maximum capacity.

4.4 Dynamic Scaling

4.4.1 Target Tracking Scaling

Target tracking works as follows:

  • You choose a metric and a target value, for example average CPU utilization of 50 percent. The group adds or removes instances to stay near that value, much as a thermostat holds a room temperature.
  • Amazon EC2 Auto Scaling creates and manages the CloudWatch alarms for you (tab 5).
  • Predefined metrics include average CPU utilization (ASGAverageCPUUtilization), average network in and out (ASGAverageNetworkIn and ASGAverageNetworkOut), and Application Load Balancer request count per target (ALBRequestCountPerTarget). You can also use a custom metric.
  • Target tracking scales out quickly and scales in more cautiously, to avoid removing capacity that traffic may still need.
  • Example: keep the average CPU utilization of the group at around 40 percent.

4.4.2 Step Scaling

Step scaling works as follows:

  • You create the CloudWatch alarm and define step adjustments. A larger breach triggers a larger adjustment.
  • Example: alarm threshold at 60 percent CPU. From 60 to 70 percent add one instance, from 70 to 85 percent add two, and above 85 percent add four.
  • Adjustment types are a change in capacity (add or remove a number), a percentage change, or an exact capacity.
  • A minimum adjustment magnitude can force a larger change. For example, a 25 percent increase on a small group might be less than two instances, and a minimum of two makes the group add two.

4.4.3 Simple Scaling

Simple scaling works as follows:

  • One CloudWatch alarm triggers one adjustment, and then the group waits for the cooldown to end before it responds to another alarm (tab 8).
  • AWS recommends target tracking or step scaling instead of simple scaling, because they give better scaling performance.
  • Example, scale out: when a CloudWatch alarm is triggered (for example, CPU above 70 percent), add two instances.
  • Example, scale in: when a CloudWatch alarm is triggered (for example, CPU below 30 percent), remove two instances.

4.5 Scheduled Scaling

Scheduled actions work as follows:

  • A scheduled action sets the minimum, maximum, or desired capacity at a time you choose. It can run once or repeat on a recurring schedule.
  • Example, recurring: raise minimum capacity to 6 at 11:45 on weekdays so instances are running before the 12:00 sale.
  • Example, one time: raise minimum capacity to 12 before 09:00 on the announced event date, then lower it afterward.
  • Example: increase the minimum capacity to 10 at 5 p.m. on Fridays.
  • Scheduled scaling is best when the date and time are known in advance. Dynamic policies still handle demand that exceeds the plan.

4.6 Predictive Scaling

Predictive scaling works as follows:

  • Predictive scaling uses machine learning on recent CloudWatch history to forecast load. It produces an hourly forecast for the next 48 hours and refreshes that forecast every six hours.
  • It needs at least 24 hours of data before it can forecast.
  • A new policy starts in forecast only mode so you can compare the forecast with real traffic. You then switch to forecast and scale mode.
  • By default, the group scales at the start of each hour based on the forecast for that hour. A pre-launch buffer can start instances earlier so they are ready when load arrives.
  • It assumes the group is homogeneous, meaning instances have equal capacity. A group that mixes instance types with different virtual CPU (vCPU) counts can produce poor CPU-based forecasts.
  • If you replace a group with a new one, the new group needs 24 hours of data before predictive scaling forecasts again.
  • Predictive scaling works well with dynamic scaling. The forecast handles the repeating pattern and the dynamic policy handles unexpected demand.
  • Example: a site has a traffic peak every weekday at 09:00. After the group has run for several days, predictive scaling forecasts the peak and launches instances before 09:00, so capacity is ready when users arrive.

4.7 Choosing a Policy

SituationChoose
Keep CPU or request count near a value with little setupTarget tracking
Add 1, 2, or 4 instances depending on how far a metric has movedStep scaling
Event on a known date or fixed daily rushScheduled scaling
Weekly or daily pattern, slow instance boot, need capacity ready earlyPredictive scaling

For the retail site in the Problem Statement, a good design combines target tracking for general demand, a scheduled action for the one-time event, and predictive scaling for the weekday 12:00 rush once at least 24 hours of data exist.

5.2 How a CloudWatch Alarm Triggers a Policy

The chain from a metric to a new instance works as follows:

  1. A CloudWatch alarm watches one metric. It uses a statistic, a period, a threshold, and a number of evaluation periods.
  2. When the metric crosses the threshold for the number of periods you set, the alarm enters the ALARM state.
  3. The alarm runs the scaling policy that you linked to it.
  4. The policy changes the desired capacity of the group.
  5. The group launches or terminates instances to reach the new desired capacity.
  • Step and simple scaling need two alarms: one to scale out and one to scale in. You create both.
  • Target tracking creates and manages its alarms for you.

6. Capacity, Health Checks, and Load Balancing

Problem Statement

A company runs a web tier of four instances behind an Application Load Balancer. Last month one Availability Zone had an outage and the site slowed down for 20 minutes. This month an instance stayed in the running state while its web service froze, and users received errors for an hour because nothing replaced it. The team needs the group to recover from both failures without anyone contacting an engineer.

6.1 Capacity Settings

SettingMeaningExample
Minimum capacityThe lowest number of instances the group may run.2, so each of two Availability Zones keeps one instance.
Desired capacityThe number the group tries to run right now.4 during normal traffic.
Maximum capacityThe highest number the group may run.8, which also caps cost.

Capacity settings follow these rules:

  • Desired capacity always stays between the minimum and the maximum.
  • Scaling policies, scheduled actions, and manual changes all work by changing desired capacity.
  • A group with minimum 1, desired 1, and maximum 1 is a simple recovery pattern: if the single instance fails, the group launches a replacement.
  • A minimum of 1 does not give high availability, because the application is down while a replacement boots. Use a minimum of at least 2 across two Availability Zones.

6.2 Health Checks

Health check typeWhat it testsDefault
EC2 status checksWhether the instance and its host are running and reachable at the infrastructure level.Yes — on by default.
Elastic Load Balancing (ELB)Whether the instance passes the load balancer target group health check, which can test the application itself, for example an HTTP path.No — turn it on for the group.
CustomAny result your own monitoring reports to the group through the Amazon EC2 Auto Scaling Application Programming Interface (API).No — optional.

Health check replacement follows these rules:

  • When an instance is marked unhealthy, the group terminates it and launches a replacement.
  • Replacing an unhealthy instance does not wait for a scaling cooldown to end.
  • The EC2 check alone cannot see an application failure. An instance can pass the EC2 check while the web service returns errors, so groups behind a load balancer should also use the ELB check.

6.2.1 Health Check Grace Period

The grace period works as follows:

  • The grace period is the time after an instance enters service during which the group ignores health check failures, so the instance has time to boot and start the application.
  • In the console, the default is 300 seconds. A value of 0 turns the grace period off.
  • During the grace period, an instance that is no longer in the EC2 running state is still marked unhealthy and replaced immediately.
  • Set the value to at least the time your application needs to start. If startup takes four minutes and the grace period is 60 seconds, the load balancer check fails, the group terminates the instance, and the cycle repeats.

6.3 Load Balancing and Health

  • With the ELB health check on, the group treats an instance as unhealthy if it fails either the EC2 check or the load balancer check.
  • The target group health check settings decide when the load balancer reports a target as unhealthy.
  • The load balancer stops sending requests to an unhealthy target, and the group replaces it. Section 3.2 explains how the group registers and deregisters instances.

6.4 Availability Zone Rebalancing

Availability Zone rebalancing follows these rules:

  • The group tries to keep capacity evenly split across the enabled Availability Zones.
  • If one zone fails, the group launches replacements in the healthy zone.
  • After the failed zone recovers, the group can be unbalanced, and it gradually rebalances. Rebalancing can terminate instances in the other zones.
  • When rebalancing, the group launches new instances before it terminates old ones, so availability is not reduced.

  • C. Increase the health check grace period to 3,600 seconds.
  • D. Change the termination policy to OldestInstance.
Show Answer and Explanation

Correct answer: A. The default EC2 status check only sees infrastructure problems. The load balancer check tests the application, so a failing target is marked unhealthy and replaced.

7. Lifecycle, Termination, and Maintenance

Problem Statement

A team runs an application in an Auto Scaling group with 20 instances. They need to install and verify a security agent before a new instance receives traffic. They need to upload log files to Amazon S3 before an instance is terminated. They also need to roll out a patched AMI to all 20 instances without taking the site down, and they want to reduce a seven-minute application startup time that slows every scale-out.

7.1 Instance Lifecycle States

Instances move through these states:

  • An instance starts in Pending and moves to InService when it is ready.
  • During scale in or a failed health check it moves to Terminating and then Terminated.
  • With a lifecycle hook, the instance pauses in a wait state, Pending:Wait or Terminating:Wait, until the hook finishes or times out.
  • An instance can also be placed in Standby to troubleshoot it. It stays in the group but stops receiving traffic and is not replaced as unhealthy.

7.2 Lifecycle Hooks

Lifecycle hooks work as follows:

  • A lifecycle hook pauses an instance at launch or at termination so that your own actions can run first.
  • Launch and terminate transitions need two separate hooks.
  • Example, launch: install and verify a security agent before the instance receives traffic.
  • Example, terminate: copy log files to Amazon S3 before the instance is removed.
  • Notifications can go to Amazon EventBridge (the console default), Amazon Simple Notification Service (Amazon SNS), or Amazon Simple Queue Service (Amazon SQS). These services are covered in lesson 273.3. Your automation then completes the action with CompleteLifecycleAction.
  • The heartbeat timeout is 3,600 seconds (one hour) by default when you use put-lifecycle-hook. You can extend a wait by recording a heartbeat. The total wait cannot exceed 48 hours or 100 times the heartbeat timeout, whichever is smaller.
  • The default result decides what happens when the timeout ends: CONTINUE proceeds with the launch or termination, and ABANDON stops it.

7.3 Termination Policies

Termination policies follow these rules:

  • A termination policy decides which instance a group removes during scale in. The group always balances Availability Zones first, whatever policy is set.
  • The default policy works in this order: pick the Availability Zone that has the most instances; within it, prefer instances launched from an outdated launch configuration, a different launch template, or an older template version; then choose the instance closest to its next billing hour.
  • In a mixed instances group, the default policy also balances On-Demand and Spot Instances across the zones. Within a zone, it first prefers a termination that aligns the remaining instances with the allocation strategy, and then applies the outdated-configuration and billing-hour rules above.
PolicyWhat it terminates first
DefaultFollows the order above.
OldestLaunchTemplateInstances on the oldest launch template or template version.
OldestInstanceThe instance that has run the longest.
NewestInstanceThe most recently launched instance.
ClosestToNextInstanceHourThe instance nearest to its next billing hour.
AllocationStrategyInstances that align the remaining capacity with the group's allocation strategy.
Custom Lambda functionThe instance that your own AWS Lambda function (lesson 273.1) selects.

7.4 Scale-In Protection and Standby

Scale-in protection and Standby work as follows:

  • Scale-in protection stops the group from choosing a protected instance during scale in. Use it for an instance doing long-running work.
  • Scale-in protection does not stop a health check replacement.
  • Standby removes an instance from service for troubleshooting or patching while keeping it in the group.

7.5 Instance Refresh

An instance refresh works as follows:

  • An instance refresh replaces the running instances of a group in batches so that they pick up a new launch template version, such as a patched AMI.
  • The minimum healthy percentage is the share of desired capacity that must stay in service during the rollout. Without an instance maintenance policy it defaults to 90 percent.
  • With 20 instances and 90 percent, at least 18 stay in service, so the refresh replaces about two at a time.
  • The checkpoint delay defaults to one hour. Checkpoints let you pause to verify a first batch before continuing.
  • You can turn on automatic rollback so the group returns to its previous configuration if the refresh fails.
  • Instance warmup tells the refresh how long to wait before it treats a new instance as ready and moves on.
  • A bake time, which is zero by default, adds a wait at the end of the refresh before the refresh counts as complete.

7.6 Warm Pools

Warm pools work as follows:

  • A warm pool is a pool of pre-initialized instances that sits next to the group. During scale out, the group draws from the pool instead of booting a new instance from the beginning.
  • Pool instances can be kept Stopped, Running, or Hibernated. The default state is Stopped.
  • A Stopped instance costs storage but no instance charges, and a Running instance is billed as a normal instance. Check the pricing page for current rates.
  • Use warm pools for applications with long initialization, such as the seven-minute startup in the Problem Statement.
  • Add a lifecycle hook so an instance finishes initializing before it is stopped or put in service.
  • Warm pools are not supported with weighted mixed instance groups.
  • While instances are in the warm pool, scaling policies scale out only when the metric from InService instances is above the policy threshold.

Exam Trap

Remember these three points:

  • A lifecycle hook delays a state change. It does not stop billing: an instance in a wait state is still running.
  • A new launch template version affects only new instances. Use an instance refresh to replace instances that already run.
  • Scale-in protection blocks scale in. It does not block replacement of an unhealthy instance.

Memory Hook

Hooks pause. Refresh replaces. Warm pools pre-boot.

8. Scaling Cooldown

Problem Statement

A retail site uses a simple scaling policy: when CPU is above 70 percent, add two instances. A traffic spike starts, and the group adds two instances. The new instances are still booting, and the alarm stays in the ALARM state. Sometimes the group adds instances again and again, and at other times it stops adding instances when more are needed. The team does not know which timer controls this behavior.

8.1 What a Cooldown Is

A cooldown works as follows:

  • A cooldown is a pause after a scaling activity. During the pause, the group does not respond to another alarm, so it has time to stabilize.
  • A cooldown applies to simple scaling policies.
  • The default cooldown is 300 seconds (five minutes).
  • Example: a simple scaling policy launches two instances, and the group then pauses scaling activities until the cooldown ends.
  • AWS recommends target tracking or step scaling instead of simple scaling and cooldowns, because they give better scaling performance.

8.2 Default Cooldown and Scaling-Specific Cooldown

  • Every group has a default cooldown. If you do not define it, the value is 300 seconds.
  • You cannot set the default cooldown on the creation page of the console. You can change it afterward in the group settings or with the AWS Command Line Interface (AWS CLI).
  • By default, every simple scaling policy uses the default cooldown of the group.
  • You can set a scaling-specific cooldown on one simple scaling policy to override the default.
  • A common use is a shorter cooldown on a scale in policy. Terminating instances takes less time than launching them, so a cooldown of 300 seconds is too long for scale in.

8.3 Instance Warmup for Target Tracking and Step Scaling

Target tracking and step scaling do not use a cooldown:

  • They can start a scale out activity immediately, without waiting for a cooldown to end.
  • Each new instance has an instance warmup: the time before the instance sends metrics to CloudWatch and counts toward the capacity of the group.
  • AWS recommends that you set the default instance warmup for the group.
  • If you do not set it, target tracking and step scaling use the default cooldown value as the warmup time. Instance refresh uses the health check grace period, and predictive scaling has no default warmup.
  • If you are not sure which value to use, start with 300 seconds.

8.4 Cooldown, Warmup, and Grace Period Compared

8.5 What a Cooldown Does Not Delay

  • A cooldown does not delay the replacement of an unhealthy instance.
  • When you scale the group manually, the default is not to wait for a cooldown.

Exam Trap

Remember these three points:

  • A cooldown applies to simple scaling policies only. For target tracking and step scaling, the matching setting is instance warmup.
  • The health check grace period is a different timer. It delays health checks, not scaling.
  • A question that asks for a faster scale in points to a shorter scaling-specific cooldown on the scale in policy.

10.6 Lesson Summary

This lesson covered the following points:

  • A launch template defines each instance, and an Auto Scaling group keeps between its minimum and maximum number of instances running across Availability Zones.
  • A mixed instances group keeps an On-Demand base for steady capacity and fills the capacity above the base with Spot Instances to lower cost.
  • A group registers its instances with an attached target group automatically. The default EC2 health check finds failed instances, and the ELB health check also finds failed applications.
  • Target tracking, step, and simple policies react to CloudWatch metrics and alarms. Scheduled scaling follows the clock. Predictive scaling follows a forecast built from at least 24 hours of data.
  • Lifecycle hooks pause launch or termination, termination policies choose which instance leaves, instance refresh replaces running instances, and warm pools shorten slow startups.
  • A cooldown pauses simple scaling, instance warmup delays the metrics of a new instance, and the grace period delays health checks.

Question 1: Describe the role of the launch template, the Auto Scaling group, and the scaling policy.

Question 2: Explain how a mixed instances group lowers cost, and what the On-Demand base capacity protects.

A mixed instances group combines On-Demand Instances and Spot Instances. The On-Demand base capacity is the minimum amount of capacity that must be On-Demand, so the steady load keeps running even if AWS reclaims Spot capacity. The capacity above the base follows the On-Demand percentage, and the Spot share costs less than On-Demand. Using several instance types and Availability Zones lowers the chance of interruption.

Question 3: A group has minimum 1, desired 2, and maximum 4 in two Availability Zones. Explain what happens when one zone fails, and whether you would change the settings.

Question 4: Instances pass their EC2 status checks but the application returns errors, and the group never replaces them. Identify the cause and the fix.

The group uses the default EC2 health check, which tests only the instance and host, not the application. Also confirm that the health check grace period is long enough for the application to start.

Question 5: Trace what happens from a rising CPU metric to a new instance, and compare target tracking with step scaling.

Maps to: Objective 5 (Analysis).

A CloudWatch alarm watches the metric. When the metric crosses the threshold for the evaluation periods, the alarm enters the ALARM state and runs the scaling policy. The policy changes the desired capacity, and the group launches instances to match. Target tracking keeps a metric near a target value and manages its own alarms. Step scaling needs alarms that you create and applies a larger adjustment for a larger breach.

Question 6: Differentiate cooldown, instance warmup, and the health check grace period.

Maps to: Objective 6 (Analysis).

A cooldown pauses further scaling after a scaling activity and applies to simple scaling policies, with a default of 300 seconds. Instance warmup is the time a new instance needs before its metrics count in scaling decisions, and it applies to target tracking and step scaling. The health check grace period is the time after an instance enters service during which health check failures are ignored, with a console default of 300 seconds. They solve three different problems: preventing repeated scaling, avoiding premature metrics, and avoiding premature replacement.

Question 7: A team updated the launch template to use a patched AMI, but the existing instances still run the old AMI. Recommend a safe way to update them and justify the settings.

Maps to: Objective 7 (Evaluation).

Start an instance refresh. It replaces instances in batches, controlled by the minimum healthy percentage, which defaults to 90 percent without an instance maintenance policy. With 20 instances that keeps at least 18 in service, so about two are replaced at a time. Use a checkpoint to verify the first batch, turn on automatic rollback in case the new instances fail, and set instance warmup so the refresh waits until each new instance is ready.

Question 8: A team needs to (1) install and verify a security agent before an instance receives traffic, (2) upload log files before an instance is terminated, (3) keep one instance that runs a long job from being removed during scale in, (4) shorten a seven-minute startup, and (5) remove instances that use an old launch template version first during scale in. Recommend a feature for each need and justify it.

Maps to: Objective 7 (Evaluation).

(1) Use a lifecycle hook on launch. It pauses the instance in Pending:Wait until the agent is verified or the timeout ends. (2) Use a lifecycle hook on termination. It pauses the instance in Terminating:Wait until the logs are copied to Amazon S3. (3) Turn on scale-in protection for that instance. It stops the group from choosing the instance during scale in, but it does not stop the replacement of an unhealthy instance. (4) Add a warm pool of pre-initialized instances, with a lifecycle hook so each instance finishes its setup before it is stopped or put in service. (5) Use the OldestLaunchTemplate termination policy. The group still balances the Availability Zones first.

Question 9: Workers read jobs from a queue, and the backlog changes during the day. Choose a scaling metric and policy, and state what you must turn on.

Maps to: Objective 5 (Application).

Scale on the backlog per instance, which is the number of visible messages in the queue divided by the number of in-service instances in the group. Use that custom metric with a target tracking policy and a target value, such as 100 messages per instance. The calculation uses the group metric GroupInServiceInstances, so turn on group metrics collection. Target tracking creates and manages the CloudWatch alarms.

Question 10: Design a web tier for a site with a daily noon rush, a one-time launch event, a seven-minute application startup, and a request to lower cost. Justify each component.

Maps to: Objective 8 (Synthesis).

Use a launch template with a preconfigured AMI that already contains the application to shorten startup, and an Auto Scaling group across subnets in at least two Availability Zones with a minimum of 2. Put an Application Load Balancer in front, attach its target group, and enable the ELB health check with a grace period longer than the startup time. Add target tracking on CPU or ALBRequestCountPerTarget for general demand, a predictive scaling policy for the daily noon rush once 24 hours of data exist, and a scheduled action for the one-time event. Use a mixed instances policy with an On-Demand base for the steady capacity and Spot Instances above it. Add a warm pool with a lifecycle hook to reduce the effect of the seven-minute startup, and use an instance refresh to roll out new AMIs.

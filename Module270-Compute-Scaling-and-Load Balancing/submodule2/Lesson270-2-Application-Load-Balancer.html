1. Application Load Balancer

Problem Statement

Northwind's shop is now many small services: a users service and a posts service on EC2, image containers on Amazon Elastic Container Service (Amazon ECS) (lesson 273.5), and a Lambda function for orders (lesson 273.1). Today each one has its own load balancer, and nobody can check the health of the whole shop in one place.

You need one entry point that routes each request by its content, sends traffic only to healthy targets, scales by itself, and can use WAF and user authentication.

1.1 What Is an Application Load Balancer?

  • Works at layer 7: it reads the HTTP request. Supports HTTP, HTTPS, and WebSocket.
  • Routing to different target groups:
    • Routing based on the path in the URL (example.com/users and example.com/posts).
    • Routing based on the hostname in the URL (one.example.com and other.example.com).
    • Routing based on the query string and headers (example.com/users?id=123&order=false).
    • It can also route by HTTP method or source IP address.
  • ALBs are a great fit for microservices and container-based applications (for example Docker and Amazon ECS), because one load balancer can serve several applications. Amazon ECS can register several ports on one instance.
  • Targets: EC2 instances, ECS tasks, Lambda functions, and IP addresses (including on-premises servers).
  • Can redirect HTTP to HTTPS, return fixed responses, and authenticate users (for example with Amazon Cognito).
  • Gives a fixed hostname, not a fixed IP address.
  • The application does not see the client's IP address directly. It reads it from the X-Forwarded-For header (and the port and protocol from X-Forwarded-Port and X-Forwarded-Proto).

1.2 Application Load Balancer Core Functionality

  • The Application Load Balancer serves as the entry point for client traffic, intelligently distributing requests across registered targets to maintain application availability and scalability.
  • It continuously monitors the health of registered targets and routes traffic only to healthy targets.
  • It automatically scales capacity in response to incoming application traffic.

1.3 Application Load Balancer Technical Concepts

The Application Load Balancer operates within networking, security, and application architecture domains. Understanding these domains helps you implement an Application Load Balancer effectively in your infrastructure.

  • Key networking concepts include virtual private cloud (VPC) configuration, subnets, and security groups.
  • Application architecture involves understanding how your applications handle requests and responses.

1.3.1 Listeners

  • A listener checks for connection requests from clients, using the protocol and port that you configure.
  • An Application Load Balancer needs at least one listener to accept traffic.
  • You define rules for your listener that determine how the load balancer routes requests to the registered targets.
  • Listeners support the HTTP and HTTPS protocols, and can be configured with security policies that decide which ciphers and protocols are supported.
  • For an HTTPS listener, you must deploy at least one Secure Sockets Layer and Transport Layer Security (SSL/TLS) server certificate on the load balancer (lesson 270.3, tab 5).
  • Example: an HTTPS listener on port 443 with an AWS Certificate Manager (ACM) certificate, and an HTTP listener on port 80 whose only rule redirects to HTTPS.

1.3.2 Target Groups

  • Target groups are logical groupings of targets that receive traffic from the load balancer.
  • Targets can be EC2 instances, IP addresses, Lambda functions, or containers.
  • Each target group routes requests to one or more registered targets, using the protocol and port that you specify.
  • Target groups also define the health check settings that the load balancer uses to evaluate the health of the targets.
  • You can register a target with multiple target groups, and you can configure different health check settings for each target group to meet the needs of each application.
  • Example: an api-servers target group on port 8080 with a health check on /health, and an image-servers target group on port 80 with a health check on /.

1.3.3 Rules

  • Rules determine how the load balancer routes requests to targets.
  • Each rule consists of a priority, one or more actions, and one or more conditions. When the conditions for a rule are met, the actions are performed.
  • Rules can match on path patterns, host headers, HTTP headers, methods, query parameters, and source IP addresses.
  • This flexibility lets you create complex routing logic that directs traffic based on the content of the request, which makes the Application Load Balancer ideal for microservices architectures.

1.3.4 Sticky Sessions

  • Sticky sessions, or session affinity, maintain a consistent user experience by routing a user's requests to the same target that handled their previous requests.
  • The Application Load Balancer supports sticky sessions using cookies.
  • When sticky sessions are enabled, the load balancer generates a cookie and uses it to route subsequent requests that contain the cookie to the same place, maintaining the session state for applications that require it.
  • You turn it on in the target group settings. Tab 2 explains the cookie types and the trade-offs.

1.3.5 Content-Based Routing

  • Rules can route requests to different target groups based on the content of the request. The conditions you can use are:
    • Host-based routing (api.example.com).
    • Path-based routing (/images/*).
    • HTTP header-based routing (for example X-Version: B).
    • HTTP method-based routing (GET, POST).
    • Query string parameter-based routing (/app?version=v2).
    • Source IP Classless Inter-Domain Routing (CIDR)-based routing.
  • You can combine conditions in one rule. Example: the host is api.example.com and the method is POST.
  • Rules are checked by priority, and the first rule whose conditions match decides the target group.

1.3.5.1 Host-Based Routing

  • Host-based routing forwards requests to different target groups based on the host name in the request's host header.
  • It supports hosting multiple websites or applications on the same set of servers.
  • Example: direct traffic for api.example.com to one target group and traffic for www.example.com to another.
  • It enables domain-based multi-tenancy without separate load balancers for each domain.
  • Use case: hosting multiple subdomains or application modules with the same load balancer.
  • Regular users go to the user module: user.example.com.
  • Admin users go to the admin module: admin.example.com.

1.3.5.2 Path-Based Routing

  • Path-based routing directs requests to different target groups based on the URL path in the request.
  • It is particularly useful for microservices architectures, where different services handle different parts of an application.
  • Example: route requests for /api to a target group of API servers, requests for /images to a target group of image servers, and all other requests to a default target group.
  • This lets you optimize resource allocation based on the type of request.
  • Use case: a microservices architecture where each service handles a different URL.
  • Static images go to the image services: example.com/image/*.
  • Dynamic content goes to the API services: example.com/api/*.

1.3.5.3 HTTP Header-Based Routing

  • HTTP header-based routing routes requests based on the values of HTTP headers. It gives extra flexibility beyond path-based and host-based routing.
  • Use it to implement A/B testing: route users with specific header values to different versions of your application.
  • It also supports routing based on user-agent strings, to give different experiences to different device types.
  • Beta testers: requests with the header X-Environment: Beta go to the beta features target group.
  • Mobile users: requests with the header User-Agent: Mobile go to the mobile optimized backend.
  • Everyone else: regular production traffic goes to the production application.

1.3.5.4 HTTP Method-Based Routing

  • HTTP method-based routing sends requests to different target groups based on the HTTP method of the request, such as GET or POST.
  • Example: send GET requests (reads) to a read-optimized target group, and POST, PUT, and DELETE requests (writes) to a write target group.
  • This lets you scale reads and writes separately, and keep write traffic on more protected servers.

1.3.5.5 Query Strings/Parameters Routing

  • Query string routing sends requests to different target groups based on the query string, the parameters in the URL after the ?.
  • A rule condition matches a key and value pair. Example: ?Platform=Mobile goes to Target Group 1, and ?Platform=Desktop goes to Target Group 2.
  • Target Group 1 can be EC2-based, in AWS. Target Group 2 can be on premises, using private IP routing: the servers are registered by IP address, and the traffic reaches them over a virtual private network (VPN) or Direct Connect link (lesson 269.6).
  • Use it for: device-specific backends, feature flags, A/B testing, and moving part of an application from on premises to AWS step by step.
Query string conditionTarget groupWhere the targets run
?Platform=MobileTarget Group 1EC2 instances in AWS
?Platform=DesktopTarget Group 2On-premises servers (private IP routing)
  • Use case: ideal for e-commerce platforms or APIs.
  • Product search goes to example.com/product?service=search.
  • Checkout goes to example.com/product?service=checkout.

1.3.5.6 Source IP CIDR-Based Routing

  • Source IP routing sends requests to different target groups based on the client's IP address, matched against a Classless Inter-Domain Routing (CIDR) block such as 203.0.113.0/24.
  • Example: requests from the company's office network go to an internal tools target group, and everyone else goes to the public site.
  • The load balancer matches the address it sees. If a proxy or a service such as CloudFront is in front, the load balancer sees that service's address, not the end user's.
Exam Tips

Content-based routing is only part of Layer 7 (application layer) capability, and it is supported by the Application Load Balancer only. The Classic Load Balancer and the Network Load Balancer do not support these routing options.

1.3.6 Deregistration Delay

  • Deregistration delay gives in-flight requests time to complete when a target is deregistered.
  • During this time, the load balancer stops sending new requests to the target, but lets existing connections complete.
  • You can specify a time period of 0 to 3600 seconds. The default is 300 seconds. Setting an appropriate value helps maintain a good user experience during deployments or when instances need to be removed from service.

1.3.7 Fixed Response

  • With a fixed response action, the Application Load Balancer (ALB) responds immediately with a fixed HTTP status code, message, and content type. The request never reaches a target.
  • Use case: return a custom message when a route is under maintenance.
  • Use case: respond with 403 Forbidden if a path is restricted.
  • Use case: show an API deprecation notice.
  • A fixed response can use a 2XX, 4XX, or 5XX status code, and content types such as text/plain, text/html, and application/json. For a 3XX answer, use a redirect action instead.
Rule conditionFixed responseWhy

1.4 Container and Serverless Integration

  • The Application Load Balancer integrates with containerized and serverless workloads.
  • It works natively with Amazon ECS, supporting dynamic port mapping for multiple containers on a single instance.
  • For serverless architectures, it can directly invoke Lambda functions in response to requests.
  • This flexibility lets you build applications using the compute resources that best match your needs.

1.5 Security and Authentication

1.5.1 Security Groups

  • Security groups act as virtual firewalls that control inbound and outbound traffic to your Application Load Balancer and targets.
  • You must configure them to allow traffic on the listener ports and the health check ports.
  • For the load balancer: allow inbound traffic from clients on the listener ports (for example 443).
  • For the targets: allow inbound traffic from the load balancer on both the application port and the health check port.
  • Tab 5 of lesson 270.3 shows the full security group chain.

1.5.2 AWS WAF and Amazon Cognito

  • The Application Load Balancer integrates with AWS WAF to protect your applications against common web exploits and malicious attacks (lesson 268.9).
  • It also works with Amazon Cognito to provide user authentication at the load balancer level.
  • These built-in security features help you protect your applications and manage user access without additional infrastructure.

1.7.1 E-Commerce Platforms

  • E-commerce businesses use an Application Load Balancer to handle varying traffic loads, particularly during sales events or holiday seasons.
  • An Application Load Balancer automatically scales its capacity as traffic grows, which helps customers keep browsing and buying during sales.
  • Path-based routing directs product catalog requests, shopping cart operations, and payment processing to different backend services.
  • This architecture improves resource utilization and lets teams scale and update individual components independently. That results in more reliable shopping experiences and increased conversion rates.
PathBackend serviceWhy it is separate
/catalog/*Product catalog serviceMany reads, scales out for browsing traffic
/cart/*Shopping cart serviceNeeds the session or cart data to stay available
/payment/*Payment serviceHandled separately, updated with extra care

1.7.2 SaaS and Multi-Tenant Applications

  • A software-as-a-service company serves many customers from the same application, each with its own address, such as customer1.example.com and customer2.example.com.
  • Host-based routing sends each hostname to the right target group, so the company does not need a separate load balancer for each customer.
  • Several certificates on one load balancer, with Server Name Indication (SNI), give each customer's domain its own HTTPS (lesson 270.3, tab 5).
  • Business result: lower cost, and simpler operations as the number of customers grows.

1.7.3 Microservices and Containerized Applications

  • A company splits a large application into small services that run as containers on Amazon ECS.
  • Path-based routing sends each part of the application to its own target group, and dynamic port mapping lets several containers share one instance.
  • Each service has its own health checks and its own scaling.
  • Business result: teams release and scale their own service independently, which speeds up delivery.

1.7.4 Internal Enterprise Applications

  • Employees use internal portals, such as HR, finance, or reporting tools, that must not be reachable from the internet.
  • An internal Application Load Balancer in private subnets is reached over the company's VPN or Direct Connect link (lesson 269.6).
  • The load balancer can authenticate users with Amazon Cognito or an OpenID Connect (OIDC) identity provider before a request reaches the application.
  • Business result: sign-in is handled in one place, so each application does not need its own authentication code.

1.7.5 Safe Releases: A/B Testing and Gradual Rollouts

  • A team wants to try a new version with a few users before everyone gets it.
  • Header-based routing sends users with a chosen header value to the new version for A/B testing.
  • Weighted target groups send a small share, for example 10 percent, of the traffic to the new version, and the share is raised as the release looks healthy.
  • The deregistration delay lets in-flight requests finish when old instances are removed.
  • Business result: lower risk, and releases without downtime.

2. ELB Stickiness

Problem Statement

A customer adds items to the shopping cart on Instance A. On the next click, the load balancer sends the request to Instance B, which has never seen this customer, and the cart is empty.

You need a way to send the same customer to the same instance, and you need to know the trade-offs.

2.1 What Is Stickiness?

  • Stickiness, also called session affinity, redirects the same client to the same target behind the load balancer.
  • It works with the Application Load Balancer, the Network Load Balancer, and the Classic Load Balancer. On ALB and NLB, you turn it on for the target group.
  • On the ALB and the Classic Load Balancer, it uses a cookie with an expiration date that you control, and the client must support cookies. The NLB uses the client's source IP address instead (section 2.2).
  • Use case: keep users from losing their session data, such as a shopping cart or a login.
  • Drawback: stickiness can make the load uneven across the instances.

2.2 Cookie Types

TypeWho creates the cookieCookie nameDuration
Duration-basedThe load balancerAWSALB (ALB), AWSELB (Classic Load Balancer, CLB)You set it, for example one hour
Application-based: custom cookieThe target (your application), with any attributes it needsA name you choose for each target group. Do not use AWSALB, AWSALBAPP, or AWSALBTG, which the load balancer reservesThe application sets it
Application-based: application cookieThe load balancer, based on your application's cookieAWSALBAPPFollows your application's cookie
  • If your application has its own session cookie, use application-based stickiness.
  • If it does not, use duration-based stickiness.
  • The NLB uses the client's source IP address, not a cookie.

2.3 Requirements and Limits

  • Sticky sessions with an ALB need cross-zone load balancing to be on, and at least one healthy target in each Availability Zone.
  • The duration of a load balancer cookie can be from 1 second to 7 days.
  • Application-based stickiness does not work with weighted target groups.
  • WebSocket connections are inherently sticky.
  • If the sticky target becomes unhealthy, is deregistered, or is removed when the group scales in, the load balancer sends the client to another target and the session data is lost.
  • Cookies add imbalance: a busy client can overload one instance.
  • You can turn stickiness off in the target group settings.

Exam trap: stickiness is not the best answer for availability

Stickiness solves lost sessions quickly, but it causes uneven load and loses the session if the instance fails. For a highly available design, store the session in ElastiCache or DynamoDB. ALB uses cookies (duration-based AWSALB or application-based). NLB uses the source IP.

Sticky = same client, same instance, with a cookie. Better = keep the session outside the instance.

5. Knowledge Check

Answer each question in your own words first, then expand the model answer to compare.

  1. How does an Application Load Balancer decide where to send a request?

    Show model answer

    A listener checks for connections on a protocol and a port. The listener's rules are checked by priority. Each rule has conditions, such as the path, the host header, an HTTP header, the method, the query string, or the source IP address, and an action, such as forward, redirect, or fixed response. The first rule whose conditions match decides the action, and the default rule handles everything else. A forward action sends the request to a target group, and the health checks of the target group keep traffic away from unhealthy targets.

  2. A shop sends /api/* to an API service, /images/* to an image service, and requests from its mobile app, which add a custom header, to a mobile service. Describe the ALB rules.

    Show model answer

    Create one target group for each service, each with its own health check. On the listener, add rules in priority order. One rule has a path condition for /api/*, one has a path condition for /images/*, and one has an HTTP header condition for the mobile app. Each rule forwards to its target group. The rules are checked by priority, the first match decides the action, and the default rule handles everything else.

  3. How do the cookie types for stickiness differ?

    Show model answer

    Duration-based stickiness uses a cookie generated by the load balancer (AWSALB on an ALB) with a duration you set. Application-based stickiness uses your application's own cookie, either a custom cookie with a name you choose, or an application cookie that the load balancer builds from it (AWSALBAPP). The NLB uses the client's source IP address instead.

  4. Why is a stateless design better than stickiness for high availability?

    Show model answer

    With stickiness the session lives on one instance, so the load can be uneven, and the session is lost if the instance fails or the group scales in. If the session is kept in ElastiCache or DynamoDB, any instance can serve any request, so the application scales and recovers more easily.

  5. Design the ALB layer for a shop made of an API service, an image service, and a checkout service, with a gradual release of a new checkout version.

    Show model answer

    Place one ALB in public subnets across two or more Availability Zones, with an HTTPS listener and an ACM certificate. Create a target group for each service with its own health check, and use path-based rules to send each URL path to its group. For the gradual release, create a second checkout target group and use weighted target groups, for example 90 percent and 10 percent, each with its own Auto Scaling group. Set a deregistration delay so in-flight requests finish when instances are removed, and keep the services stateless instead of relying on stickiness.

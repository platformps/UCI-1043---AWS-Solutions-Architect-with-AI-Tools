Lesson 270.1 - Scalability, High Availability and Load Balancing Basics

Scalability, elasticity, and high availability, vertical and horizontal scaling, and the basics of Elastic Load Balancing: its components, the four load balancer types, external and internal load balancers, and cross-zone load balancing.

Lesson Overview

This lesson covers the following topics:

  • Scalability, Elasticity, and High Availability — three ideas that are often confused, plus agility, a fourth word to tell apart, and vertical and horizontal scaling.
  • Load Balancing and Elastic Load Balancing — what a load balancer does, what makes Elastic Load Balancing (ELB) a managed service, and its components.
  • Load Balancer Types — the four types, where they work in the Open Systems Interconnection (OSI) model, and how to choose one.
  • External and Internal Load Balancer — public and private load balancers, the subnets they use, and who can reach them.
  • Cross-Zone Load Balancing — how a load balancer shares traffic across Availability Zones, and the default setting for each load balancer type.
  • Comparison and Scenarios — scenarios, a cheat sheet, and a memory hook for scaling, load balancer schemes, and cross-zone load balancing.

Learning Objectives

By the end of this lesson, you will be able to:

  1. Define scalability, elasticity, and high availability.
  2. Distinguish vertical scaling from horizontal scaling.
  3. Describe load balancing and the components of an Elastic Load Balancer.
  4. Identify the four load balancer types, the layer that each one works at, and the main use of each.
  5. Differentiate an external (internet-facing) load balancer from an internal load balancer.
  6. Explain how cross-zone load balancing changes the share of traffic each target receives.
  7. Design a load balancing layout that keeps a public web tier highly available across Availability Zones.

1. Scalability, Elasticity, and High Availability

Problem Statement

Northwind Shop runs on one Amazon Elastic Compute Cloud (Amazon EC2) instance. During a sale, traffic jumps from 1,000 to 50,000 visitors, the instance slows down, and then crashes. A week later, a power problem in the data center takes the shop offline for an hour.

You need to understand three ideas, scalability, elasticity, and high availability, tell them apart from a fourth word, agility, and know the two ways to scale: bigger servers or more servers.

1.1 What Is Scalability?

  • Scalability is the ability of a system to handle a larger load by making the system bigger.
  • There are two kinds: vertical scaling (a bigger server) and horizontal scaling (more servers). Section 1.6 explains both.
  • Example: an application that serves 100 users today is scalable if you can adjust it to serve 100,000 users without redesigning it.
  • Scalable does not mean automatic. You can scale by hand, for example by launching two more instances before a sale.

1.2 What Is Elasticity?

  • Elasticity means that a scalable system adds and removes resources automatically to match the current load.
  • It is cloud-friendly: you pay only for what you use, you match supply to demand, and you optimize costs.
  • Example: an Auto Scaling group adds instances when average CPU goes above 70 percent and removes them when it drops below 30 percent.
  • Elasticity needs scalability first. A system that cannot scale cannot scale automatically.

1.3 What Is Agility?

  • Agility means that new IT resources are only a click away, so the time to get a server drops from weeks to minutes.
  • Agility is about speed of change for your team. It is not the same as scalability or elasticity, which are about the load on a system.

1.4 What Is High Availability?

  • High availability (HA) means your application runs despite failure in some of the components and during increased traffic.
  • In the AWS world, high availability generally refers to using multiple Availability Zones, with at least two. An Availability Zone is one or more data centers with independent power and networking, so the application keeps running if a data center is lost.
  • Passive HA: a standby takes over after a failure. Example: Amazon Relational Database Service (Amazon RDS) Multi-AZ, where a standby database in another Availability Zone takes over.
  • Active HA: all copies serve traffic at the same time. Example: several web servers in different Availability Zones behind a load balancer.
  • High availability is not the same as scalability. A system can be highly available with two small servers and still be unable to handle a big load.

1.6 Vertical and Horizontal Scaling

1.6.1 Vertical Scaling (Scale Up and Down)

  • You change the size of the server: more CPU, memory, and network capacity.
  • Scale up means a bigger server. Scale down means a smaller one.
  • On EC2: you change the instance type, for example from a small general-purpose instance to a much larger one. The instance must be stopped first, so there is downtime.
  • Common for non-distributed systems, such as a database, because they are hard to spread across servers.
  • There is a hardware limit: you cannot go above the largest instance type, and it is still one point of failure.
  • Everyday example: a one-person help desk where you replace the worker with a faster and more experienced one.

1.6.2 Horizontal Scaling (Scale Out and In)

  • You change the number of servers.
  • Scale out means adding servers. Scale in means removing servers.
  • It implies a distributed system: the work must be spread across servers, usually with a load balancer.
  • Very common for web and modern applications, and it is easy on the cloud.
  • On EC2: an Auto Scaling group adds and removes instances. There is no downtime, and the limit is far higher (account quotas still apply).
  • Combined with several Availability Zones, it also gives high availability.
  • Everyday example: the same help desk, where you hire more workers and put a queue in front of them.

1.7 Putting It Together on AWS

  • Place several instances in an Auto Scaling group that spans two or more Availability Zones.
  • Put an Elastic Load Balancing load balancer in front of the group to spread the traffic.
  • This gives you scalability (more instances), elasticity (scaling policies add and remove them), and high availability (the loss of one Availability Zone does not stop the application).
  • The next tab explains the load balancer.
Exam trap: four different words

Scalability = bigger or more. Elasticity = automatic scaling to match demand. Agility = how fast the team gets new resources. High availability = survive a data center loss, usually two or more Availability Zones. RDS Multi-AZ gives high availability, not scalability. Read replicas give read scalability.

Memory hook

Up = bigger (vertical). Out = more (horizontal). Elastic = automatic. HA = two or more Availability Zones.

2. Load Balancing and Elastic Load Balancing

Problem Statement

Northwind now runs four web servers, each with its own IP address. Customers would have to pick a server by hand, and when one server fails, some of them get errors.

You need one address for the shop, a way to spread the requests, and a way to stop sending requests to a broken server.

2.1 What Is Load Balancing?

  • A load balancer distributes incoming traffic to multiple downstream servers called targets:
    • EC2 instances.
    • Containers (lesson 273.5).
    • IP addresses.
    • Lambda functions (lesson 273.1).
  • Users connect to the load balancer only. They never need to know the targets' addresses.
  • Everyday example: the host at a restaurant door who seats each new guest at a table with free seats, and does not send guests to a closed table.

2.2 Why Use a Load Balancer?

  • Spread the load across several servers.
  • Expose a single point of access, one DNS name, to your application.
  • Handle the failure of a backend server smoothly, using health checks.
  • Do regular health checks on the instances.
  • Provide Secure Sockets Layer (SSL) termination (HTTPS) for your websites.
  • Enable stickiness with cookies.
  • Give high availability across Availability Zones.
  • Separate public traffic from private traffic: a public load balancer in front, and internal load balancers between tiers.

2.3 What Is Elastic Load Balancing?

  • Elastic Load Balancing (ELB) is a managed load balancer.
  • AWS takes care of upgrades, maintenance, and high availability, and gives you a few configuration settings.
  • It scales automatically with the incoming traffic.
  • It can look cheaper to set up your own load balancer on EC2, but it takes much more effort to run it, scale it, and keep it available.
  • It is integrated with many AWS offerings and services:
    • EC2, EC2 Auto Scaling groups (lesson 270.4), Amazon Elastic Container Service (Amazon ECS) (lesson 273.5).
    • AWS Certificate Manager (ACM), Amazon CloudWatch (lesson 274.1).
    • Route 53, AWS WAF, AWS Global Accelerator.
  • ELB is a regional service: a load balancer works in one Region and spreads traffic across the Availability Zones that you enable.

2.4 Health Checks

  • The load balancer checks each target regularly and sends requests only to healthy targets.
  • You configure the protocol, port, and path of the check. Example: HTTP on port 80 and path /health.
  • A target is healthy when it answers as expected, for example with HTTP 200.
  • If a target fails the check several times in a row, it becomes unhealthy and gets no traffic. When it passes again, it gets traffic again.
  • If every target in an Application Load Balancer (ALB) target group is unhealthy, the ALB sends requests to all of them anyway, regardless of their health.
  • Health checks are set on the target group (next section).

3. Load Balancer Types

Problem Statement

Northwind has four very different needs. The shop website must route /api/* and /images/* to different services. A live auction uses User Datagram Protocol (UDP) and needs millions of connections. A partner will allow-list only a fixed IP address. The security team wants all traffic to pass through a fleet of third-party firewalls.

Elastic Load Balancing has four types. You must choose the right one for each need.

4. External and Internal Load Balancer

Problem Statement

Northwind Shop now runs two groups of servers. The web servers serve customers on the internet. The application servers process orders and must be reachable only by the web servers. The team wants a load balancer in front of each group and must decide which one is open to the internet.

You need to know which load balancer faces the internet, which one stays inside the VPC, and which subnets each one uses.

4.1 External Load Balancer (Public)

  • An external load balancer is also called a public or internet-facing load balancer.
  • It is launched in a public subnet.
  • It receives traffic from the internet.
  • Its nodes have public IP addresses, and its DNS name resolves to those addresses, so clients on the internet can reach it.
  • Internet-facing is the default setting when you create a load balancer.

4.2 Internal Load Balancer (Private)

  • An internal load balancer is also called a private load balancer.
  • It is launched inside the private subnets.
  • It receives traffic from within the VPC.
  • Its nodes have only private IP addresses, and its DNS name resolves to those private addresses, so only clients with access to the VPC can reach it.

4.4 Using Both in a Multi-Tier Design

  1. A client on the internet sends a request, which enters the VPC through the internet gateway and reaches the external load balancer in the public subnets.
  2. The external load balancer sends the request to an instance of the web tier, in a private subnet.
  3. The web tier sends its request to the internal load balancer.
  4. The internal load balancer sends the request to an instance of the application tier, in a private subnet.
  • Each load balancer spreads traffic across instances in two Availability Zones.
  • Only the external load balancer faces the internet. The web and application instances stay in private subnets.
Exam trap: private instances can still sit behind a public load balancer

Instances in private subnets do not need an internal load balancer. To receive traffic from the internet, use an external (internet-facing) load balancer in the public subnets and keep the instances in private subnets. Use an internal load balancer only when the clients are inside the VPC.

Memory hook

External = public subnet, traffic from the internet. Internal = private subnet, traffic from within the VPC.

SAA-C03 Keyword Triggers
  • Trigger 1: "Users on the internet must reach the web tier..."
    → External (internet-facing) load balancer in the public subnets
  • Trigger 2: "The application tier must not be reachable from the internet..."
    → Internal load balancer in the private subnets
  • Trigger 3: "Keep the instances private but accept traffic from the internet..."
    → External load balancer in public subnets, with the instances in private subnets
  • Trigger 4: "Traffic between tiers must stay inside the VPC..."
    → Internal load balancer

5. Cross-Zone Load Balancing

Problem Statement

Northwind Shop runs two web servers in Availability Zone A and eight web servers in Availability Zone B behind one load balancer. The two servers in zone A are overloaded, while the eight servers in zone B are mostly idle.

You need to know why the traffic is uneven, which setting spreads it evenly, and which load balancers have that setting turned on by default.

5.1 What Is Cross-Zone Load Balancing?

  • Each load balancer node normally receives an equal share of the traffic, one for each Availability Zone.
  • With cross-zone load balancing on, each node distributes its traffic across the targets in all enabled Availability Zones.
  • Application Load Balancer: on by default (it can be turned off for a target group), with no charge for the data between Availability Zones.
  • Network Load Balancer and Gateway Load Balancer: off by default. If you turn it on, you pay for the data between Availability Zones.

5.2 Example: Two Targets and Eight Targets

Setup: two targets in AZ A, eight targets in AZ BShare for each target in AZ AShare for each target in AZ B
Cross-zone off (each node gets 50% of the traffic)25%6.25%
Cross-zone on10%10%
Exam trap: cross-zone defaults

Cross-zone is on for the ALB by default and off for the Network Load Balancer (NLB) and Gateway Load Balancer (GWLB), where turning it on is charged. Uneven traffic with a different number of targets in each zone is the symptom that cross-zone load balancing fixes.

Memory hook

Cross-zone off = each node serves only its own zone. Cross-zone on = every node serves all zones, so every target gets an equal share.

SAA-C03 Keyword Triggers
  • Trigger 1: "Uneven traffic because there are more targets in one Availability Zone..."
    → Cross-zone load balancing
  • Trigger 2: "Each target must receive an equal share of the traffic across all Availability Zones..."
    → Turn on cross-zone load balancing

7. Knowledge Check

Answer each question in your own words first, then expand the model answer to compare.

  1. Explain scalability, elasticity, and high availability, and how they differ.

    Show model answer

    Scalability is the ability to handle a larger load by making the system bigger. Elasticity means a scalable system adds and removes resources automatically to match demand, so you pay for what you use. High availability means the application keeps running if a data center is lost, usually by running in two or more Availability Zones. A system can have one without the others.

  2. Compare vertical and horizontal scaling.

    Show model answer

    Vertical scaling changes the size of one server (scale up or down). On EC2 it needs a stop and start, so there is downtime, it has an upper limit, and it remains a single point of failure. It suits databases. Horizontal scaling changes the number of servers (scale out or in), needs a load balancer, has no downtime and a far higher limit (account quotas still apply), and with several Availability Zones also gives high availability.

  3. What does a load balancer do, and why use Elastic Load Balancing instead of your own?

    Show model answer

    A load balancer forwards traffic to several targets behind one DNS name, runs health checks, can terminate TLS, supports stickiness, and works across Availability Zones. Elastic Load Balancing is managed: AWS runs, patches, scales, and keeps it available, and it integrates with services such as Auto Scaling, ACM, CloudWatch, Route 53, and WAF, so there is far less effort.

  4. Describe the components of an Elastic Load Balancer.

    Show model answer

    A load balancer has a DNS name, a scheme, subnets, and security groups, with a node in each enabled Availability Zone. A listener checks for connections on a protocol and port. Rules, on an ALB, decide the action, such as forwarding to a target group. A target group has targets, such as instances, IP addresses, or Lambda functions, plus health checks.

  5. What is cross-zone load balancing, and what are the defaults?

    Show model answer

    With cross-zone load balancing, each load balancer node spreads its traffic across targets in all enabled Availability Zones, which evens out the load when the zones have different numbers of targets. It is on by default for the ALB with no inter-zone data charge, and off by default for the NLB and GWLB, where turning it on is charged.

  6. What is the difference between an external and an internal load balancer?

    Show model answer

    An external (internet-facing) load balancer is launched in public subnets and receives traffic from the internet, and its nodes have public IP addresses. An internal load balancer is launched in private subnets and receives traffic only from within the VPC, and its nodes have only private IP addresses. In a multi-tier design, the external load balancer fronts the web tier, and an internal load balancer sits between the web tier and the application tier, so the application instances are not reachable from the internet.

  7. Design the load balancing layout for a public website with private application servers in two Availability Zones.

    Show model answer

    Use an internet-facing (external) load balancer in public subnets in at least two Availability Zones, so users on the internet reach it. Put the application servers in private subnets. If the web tier calls an application tier, put an internal load balancer in front of that tier, in private subnets. Spread the targets across both zones. Cross-zone load balancing is on by default for the ALB and off for the NLB and GWLB, so turn it on when the targets are uneven, and remember that data between zones can be charged for the NLB.

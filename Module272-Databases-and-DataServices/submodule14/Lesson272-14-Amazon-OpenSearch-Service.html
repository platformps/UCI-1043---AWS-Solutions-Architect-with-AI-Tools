AWS Analytics Services

1. Introduction to OpenSearch Service

Problem Statement

FlashCart stores its products in a DynamoDB table. DynamoDB finds an item fast when the query uses the primary key or an index. Shoppers, however, type partial words, and they expect matches in the name, the brand, and the description.

The engineering team must not move the catalog out of DynamoDB. It needs a way to search the same data by any field.

Your challenge:

  • Choose a service for full-text search.
  • Explain how the search service relates to the DynamoDB table.
  • Name the other kinds of work that the same service can do.

1.1 Introduction to Amazon OpenSearch Service

  • OpenSearch is an open-source search and analytics engine, derived from Elasticsearch. It is used for log analytics, real-time application monitoring, and clickstream analysis.
  • Amazon OpenSearch Service is a managed service that deploys, operates, and scales OpenSearch clusters in the AWS Cloud. It is the successor to Amazon Elasticsearch Service.
  • A domain is the unit that you create. A domain is the same thing as an OpenSearch cluster, and each Amazon EC2 instance in it is one node.
  • OpenSearch Service provisions the resources, launches the cluster, and automatically detects and replaces failed nodes. You can scale the cluster with one API call or a few clicks.
  • It supports OpenSearch and the legacy open-source versions of Elasticsearch, up to 7.10.
  • You create and manage domains with the AWS Management Console, the AWS CLI, the AWS SDKs, or Terraform.

1.2 Search Concepts

  • A document is one record, written as JSON, such as one product.
  • An index is a collection of documents that belong together, such as all the products.
  • A shard is a piece of an index. OpenSearch splits an index into shards and spreads them across the nodes, so the work runs in parallel.
  • A replica is a copy of a shard on a different node. It protects the data, and it can serve search requests.
  • A search can look at any field, including partial matches. A database that queries only by key or index cannot do that.
  • You query with the OpenSearch query language, which uses JSON. OpenSearch Service also supports SQL, for integration with business intelligence applications.

1.3 Use Cases

  • Full-text search: website and application search, such as a product search box.
  • Log analytics and monitoring: searching and analyzing the logs and metrics of applications and infrastructure in near real time.
  • Clickstream analysis: studying what shoppers view and click.
  • Security analytics: managing security and event information.
  • Vector search: semantic search on vector embeddings, which supports generative AI applications such as chatbots.

1.4 OpenSearch Dashboards

  • OpenSearch Dashboards is the visualization tool that comes with OpenSearch Service. You build charts and dashboards from the data in an index.
  • You can also visualize data from OpenSearch Service with AWS Quick (lesson 272.15).

1.5 OpenSearch and DynamoDB Together

  • DynamoDB queries only by primary key or index. OpenSearch searches any field, including partial matches.
  • OpenSearch is commonly used as a complement to another database. It is not the system of record.
  • A common pattern copies the changes of a DynamoDB table to OpenSearch Service. The application calls DynamoDB to retrieve items, and it calls OpenSearch to search for them.
NeedDynamoDBOpenSearch Service
Read or write one item by keyYes. This is its purpose.Not the best choice.
Search any field, with partial matchesNo. Queries use the key or an index.Yes. This is its purpose.
Act as the system of recordYes.No. Keep a database as the source.
Analyze logs and build dashboardsNo.Yes, with OpenSearch Dashboards.

Exam Trap

Remember these points:

  • OpenSearch is not a system of record. Keep the data in DynamoDB or another database, and copy it to OpenSearch for search.
  • When DynamoDB queries must use any field or partial matches, add OpenSearch Service.
  • A question that says Elasticsearch on AWS points to Amazon OpenSearch Service, its successor.
  • A domain is a cluster. A collection is the unit of OpenSearch Serverless (Tab 3).

2. Loading Data and Integrations

Problem Statement

FlashCart’s logs arrive in several places. The application functions and the API write their logs to a central log service, the orders live in DynamoDB, and a clickstream flows through a stream. The operations team wants all of it searchable within seconds or minutes.

The team also wants to add the loading without changing the applications that write the data.

Your challenge:

  • Choose a loading path for each source.
  • Decide when a delivery service is enough and when code is needed.
  • Explain how an application in a VPC reaches the domain.

2.1 Ways to Load Data

SourceLoading path
Amazon DynamoDBTurn on DynamoDB Streams, and use an AWS Lambda function (lesson 273.1) to write each change to OpenSearch Service.
Amazon CloudWatch Logs (lesson 274.2)Create a subscription filter. Send the logs to a Lambda function for real-time loading, or to Amazon Data Firehose (lesson 273.6) for near-real-time loading.
Amazon Kinesis Data StreamsUse a Lambda function that reads the stream and writes to OpenSearch Service.
Amazon Data FirehoseFirehose delivers streaming data directly to OpenSearch Service as a destination.
Amazon S3Use a Lambda function that runs when an object arrives, and writes its contents to OpenSearch Service.
Many sourcesUse OpenSearch Ingestion, a managed pipeline service (2.3).

2.2 Amazon Data Firehose to OpenSearch Service

  • Amazon Data Firehose delivers streaming data to destinations such as Amazon S3, Amazon Redshift, Amazon OpenSearch Service, and HTTP endpoints.
  • It buffers the records by size and by time, so the delivery is near real time and not instant.
  • It can run a Lambda function to transform the records before delivery.
  • It can back up the failed deliveries, the failed transformations, and all the source records to an Amazon S3 bucket.
  • A common use case sends operational logs to OpenSearch Service for search and visualization.

2.3 OpenSearch Ingestion

  • Amazon OpenSearch Ingestion is a managed service for pipelines that ingest, transform, and route data. Use it when you do not want to write and run your own loading code.
  • The compute capacity of a pipeline is measured in OpenSearch Compute Units (OCUs). You pay for the OCUs that the pipeline uses, billed by the hour with per-minute granularity.
  • You can set a minimum and a maximum number of OCUs for a pipeline, and you can pause a pipeline that you do not use.

2.4 Querying and Visualizing

  • Applications send search requests to the domain endpoint, with the OpenSearch API.
  • OpenSearch Dashboards turns the data into charts and dashboards for the operations team.
  • AWS Quick can read data from OpenSearch Service for business dashboards.
  • SQL support lets business intelligence tools query OpenSearch Service.

2.5 Reaching a Domain in a VPC

  • A Lambda function runs outside your VPC by default, so it cannot reach a private resource in a VPC.
  • To let the function reach a domain in a VPC, configure the function to run in the VPC. Lambda creates a network interface in the subnet, and the VPC controls apply to it: security groups and route tables.
  • If the function must also reach the internet, add a NAT gateway and a route for the subnet.

Exam Trap

Remember these points:

  • Firehose is near real time, because it buffers. A Lambda function on a stream or a subscription filter loads in real time.
  • For DynamoDB, the loading path is DynamoDB Streams and Lambda.
  • A Lambda function that writes to a domain in a VPC must be configured to run in the VPC.
  • Firehose can send failed deliveries to Amazon S3, so no records are lost.

3. Domains, Serverless, and Availability

Problem Statement

FlashCart’s search must stay up when an Availability Zone fails. The log indexes are large, and the team rarely searches logs older than a few weeks, but it must keep a year of them and still be able to search them.

The team also has no OpenSearch specialists, so it wants as little cluster work as possible.

Your challenge:

  • Choose between a domain and a serverless collection.
  • Make the search survive the loss of a zone.
  • Keep old logs searchable at a lower cost.

3.1 Domains

  • A domain is a cluster with the settings, instance types, instance counts, and storage that you specify.
  • You choose the instance types, including cost-effective Graviton instances. A domain can have up to 1002 data nodes and up to 25 PB of attached storage. Check the quotas page for the current limits.
  • Data nodes hold the shards and run the indexing and search.
  • Dedicated master nodes manage the cluster, so the data nodes can focus on the data. Three is the recommended number, because it gives a quorum of two. Never choose an even number.
  • You pay for the instance hours and the storage, so you must choose sizes and watch the capacity.

3.2 Amazon OpenSearch Serverless

  • Amazon OpenSearch Serverless is an on-demand option that removes the work of provisioning, configuring, and tuning clusters.
  • The unit is a collection, a group of indexes that support one workload.
  • It separates indexing from search, with Amazon S3 as the primary storage. Compute is measured in OCUs, provisioned separately for indexing and for search. It adds OCUs when needed and scales back down.
  • You choose one of three collection types when you create the collection, and you cannot change it afterward: time series for log analytics, search for full-text search, and vector search for semantic search.
  • It is compatible with open-source OpenSearch, and it supports OpenSearch Dashboards. All communication with its endpoints uses TLS 1.2.
FeatureDomainOpenSearch Serverless
UnitA cluster of nodes.A collection of indexes.
CapacityYou choose the instance types and the node count.Automatic. Measured in OCUs.
StorageEBS volumes on data nodes, plus UltraWarm and cold storage.Amazon S3 as the primary storage.

  • There is no automatic migration from a domain to a collection. You must reindex the data.

3.3 High Availability

  • Multi-AZ spreads the nodes of a domain across two or three Availability Zones in the same Region.
  • Without standby, a Multi-AZ domain offers 99.9% availability. Create at least one replica for each index, because replicas are how the data reaches another zone.
  • Multi-AZ with Standby offers 99.99% availability. It uses three zones, with two active and one on standby. It requires three dedicated master nodes and a multiple of three data nodes.
  • Each zone holds a full copy of the data, and the standby nodes do not serve search requests. If a zone fails, OpenSearch Service promotes the standby nodes to active.
  • OpenSearch Service replaces failed nodes automatically.

3.4 Storage Tiers

TierWhere the data livesUse it for
HotOn the data nodes.Data that you index, update, and search often. This is the fastest access.
UltraWarmIn Amazon S3, read through UltraWarm nodes that cache and pre-fetch the data.Older data that you search less often. The data is read-only.
Cold storageIn Amazon S3, detached from the UltraWarm nodes.Rarely used data that you keep and can attach again when needed.
  • Moving older indexes to UltraWarm and cold storage lowers the cost of keeping a long history.
  • OpenSearch Service does not bill for the data transfer between UltraWarm or cold nodes and Amazon S3.

3.5 Snapshots and Versions

  • Automated snapshots back up a domain to Amazon S3 at no additional charge. They run hourly and are kept for 14 days. You can also take manual snapshots of a domain.
  • OpenSearch Service supports many versions of OpenSearch and legacy Elasticsearch. Older versions leave standard support on set dates.
  • A domain on a version that is no longer in standard support pays extended support charges automatically. Upgrade to the latest OpenSearch version to avoid them, and check the dates on the documentation page.

Exam Trap

Remember these points:

  • 99.99% availability means Multi-AZ with Standby: three zones, two active and one standby, three dedicated master nodes.
  • A Multi-AZ domain without standby needs replicas to have copies in other zones.
  • UltraWarm data is read-only and lives in Amazon S3. Use it with cold storage to keep a long history cheaply.
  • OpenSearch Serverless is for no cluster work. A domain is for control. Serverless does not allow manual snapshots or cross-account access.

4. Security, Monitoring, and Pricing

Problem Statement

FlashCart’s support agents must search orders, but they must not see the customer email field. The operations team signs in to dashboards with the company login. The domain must not be reachable from the internet.

The finance team also asks which costs it should expect.

Your challenge:

  • Keep the domain private.
  • Control who can see which data, down to the field.
  • Name the cost dimensions of each deployment.

4.1 Networking

  • You can place a domain in a VPC. Domains in a VPC are logically isolated and are not reachable through a public endpoint.
  • VPC security groups control which clients can connect.
  • A Lambda function or an application that connects to the domain must run in the VPC, or have a network path to it (2.5).

4.2 Access Control

  • IAM and domain access policies control who can call the domain and its APIs.
  • Fine-grained access control provides security at the cluster, index, document, and field levels. AWS strongly recommends turning it on.
  • You must turn on node-to-node encryption and encryption at rest to use fine-grained access control.
  • Without fine-grained access control, you can still limit access by placing the domain in a VPC, applying a restrictive access policy, or both.

4.3 Signing In to Dashboards

  • OpenSearch Dashboards supports Amazon Cognito (lesson 273.2), HTTP basic, and SAML authentication.
  • Use SAML or Amazon Cognito to connect the dashboards to the company login. Dashboards multi-tenancy keeps the saved work of teams apart.

4.4 Encryption

  • At rest: OpenSearch Service encrypts the data of a domain with AWS KMS keys. You can choose your own key.
  • Node-to-node: encrypts the traffic between the nodes of the domain.
  • In transit: clients connect over HTTPS. OpenSearch Serverless endpoints require TLS 1.2.

4.5 Monitoring and Auditing

  • OpenSearch Service sends domain metrics to Amazon CloudWatch (lesson 274.1) automatically, so you can watch the health and the performance of a domain and set alarms.
  • AWS CloudTrail (lesson 274.3) records the configuration API calls to OpenSearch Service.
  • Audit logs record the activity of users in the domain.
  • Amazon SNS (lesson 273.3) can send alerts when the data passes a threshold.

4.6 Pricing

Prices change often and differ by Region. Check the current rates on the Amazon OpenSearch Service pricing page.

DeploymentWhat you pay for

UltraWarm and cold storageThe UltraWarm nodes and the managed storage that you use.

  • In a Multi-AZ domain, OpenSearch Service does not bill for the traffic between zones or for the traffic of shard allocation and rebalancing.
  • It does not bill for the data transfer between UltraWarm or cold nodes and Amazon S3.

Exam Trap

Remember these points:

  • Fine-grained access control is the answer for rules at the index, document, or field level.
  • A VPC and security groups keep the domain private. A VPC does not replace access control.
  • Fine-grained access control needs node-to-node encryption and encryption at rest.
  • For dashboards with the company login, use SAML or Amazon Cognito.

5.2 When to Use OpenSearch Service

5.2.1 Use It When

  • Users search text, and they expect partial matches and ranked results.
  • You analyze logs and metrics in near real time and show them on dashboards.
  • You need to complement a database that can query only by key.

5.2.2 Use Another Service When

  • DynamoDB or Amazon RDS: you need a system of record with transactions or key lookups.
  • Amazon Athena: you query large files in Amazon S3 with SQL, and you do not need a search index.
  • OpenSearch Serverless: you want search with no cluster work. This is still OpenSearch Service.

5.4 Lesson Summary

This lesson covered the following points:

  • Amazon OpenSearch Service is a managed search and analytics service. It stores documents in indexes that are split into shards with replicas, and it searches any field, including partial matches.
  • Use it for full-text search, log analytics with OpenSearch Dashboards, and vector search. It complements a database such as DynamoDB, and it is not the system of record.
  • Data reaches it from DynamoDB through DynamoDB Streams and Lambda, from CloudWatch Logs through a subscription filter, from Kinesis and Amazon S3 through Lambda, from Firehose directly, or through OpenSearch Ingestion.
  • A domain gives control of the cluster. OpenSearch Serverless removes cluster work with collections and OCUs.
  • Multi-AZ with Standby gives 99.99% availability. UltraWarm and cold storage lower the cost of a long history, and automated snapshots back up a domain.
  • Security uses a VPC, IAM, fine-grained access control, SAML or Cognito for the dashboards, and encryption with AWS KMS.

6. Knowledge Check

Answer each question in your own words before you open the model answer. The questions were written for this course.

Question 1: Explain what Amazon OpenSearch Service is, and why FlashCart should add it next to its DynamoDB table instead of replacing the table.

Maps to: Objectives 1 and 7 (Comprehension).

Amazon OpenSearch Service is a managed service that runs OpenSearch, an open-source search and analytics engine. It searches any field, including partial matches, and it ranks the results. DynamoDB queries only by primary key or index, so it cannot do that. OpenSearch is not a system of record, so FlashCart keeps the catalog in DynamoDB and copies it to OpenSearch for search. The application retrieves items from DynamoDB and searches them in OpenSearch.

Question 2: Describe the concepts of document, index, shard, and replica, and explain why an index is split into shards.

Maps to: Objective 1 (Comprehension).

A document is one JSON record. An index is a collection of related documents. OpenSearch splits an index into shards and spreads them across the nodes, so indexing and search run in parallel and the index can grow beyond one node. A replica is a copy of a shard on a different node. It protects the data if a node fails, and it can serve search requests.

Question 3: Describe how data gets into OpenSearch Service from DynamoDB, from CloudWatch Logs, and from a Kinesis data stream.

Maps to: Objective 3 (Application).

For DynamoDB, turn on DynamoDB Streams and use a Lambda function that writes each change to the domain. For CloudWatch Logs, create a subscription filter that sends the logs to Lambda for real-time loading, or to Amazon Data Firehose for near-real-time loading, and Firehose delivers them to the domain. For a Kinesis data stream, use a Lambda function that reads the stream and writes to the domain. OpenSearch Ingestion is a managed alternative that needs no custom code.

Question 4: Compare an OpenSearch Service domain with an OpenSearch Serverless collection, and say when you would choose each.

Maps to: Objective 4 (Analysis).

A domain is a cluster. You choose the instance types, the node count, and the storage, and you can use UltraWarm and cold storage and manual snapshots. Choose it when you need control of the cluster. A collection is the unit of OpenSearch Serverless. Capacity is measured in OCUs, scaled automatically for indexing and search, with data in Amazon S3. Choose it when the team does not want cluster work. Serverless supports only automated snapshots, does not allow cross-account access to collections, and is available in a subset of Regions.

Question 5: Explain how to make a domain survive the loss of an Availability Zone, and compare Multi-AZ with Standby with Multi-AZ without standby.

Maps to: Objective 5 (Comprehension).

Spread the domain across Availability Zones with Multi-AZ, and use replicas so that copies of the data are in other zones. Multi-AZ without standby offers 99.9% availability, and each index needs at least one replica. Multi-AZ with Standby offers 99.99% availability. It uses three zones, with two active and one on standby, it requires three dedicated master nodes and a multiple of three data nodes, and it promotes the standby nodes if a zone fails.

Question 6: FlashCart’s support agents must search orders without seeing the email field, and the domain must be private. Describe how you would configure the domain.

Maps to: Objective 6 (Application).

Place the domain in a VPC and use security groups to allow only the client networks. Turn on encryption at rest with AWS KMS and node-to-node encryption, which fine-grained access control requires. Turn on fine-grained access control and create a role for the support agents with field-level security that hides the email field. Use SAML or Amazon Cognito so that people sign in to OpenSearch Dashboards with the company login. Watch the domain metrics in Amazon CloudWatch.

Question 7: Design a solution for FlashCart that provides product search and log analytics, keeps a year of logs at a low cost, and survives a zone failure.

Maps to: Objective 8 (Synthesis).

Keep the catalog in DynamoDB, turn on DynamoDB Streams, and use a Lambda function to index the products in an OpenSearch Service domain for the search box. Send the application logs to CloudWatch Logs, and use a subscription filter and Amazon Data Firehose to deliver them to the domain. Use OpenSearch Dashboards for the operations team. Deploy the domain in a VPC with Multi-AZ with Standby, three dedicated master nodes, and fine-grained access control. Keep recent logs on the hot data nodes, move older indexes to UltraWarm and cold storage, and rely on the automated snapshots for backup. Choose OpenSearch Serverless instead if the team wants no cluster work.

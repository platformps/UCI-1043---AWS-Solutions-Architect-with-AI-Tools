Introduction

Most business applications keep orders, customers, and payments in relational tables that they query with SQL. A team can install a database on an EC2 instance, but then the team patches the operating system, schedules the backups, builds the failover, and watches the disks. Amazon RDS takes that work over. An architect who passes SAA-C03 questions on databases needs to know which RDS feature solves which problem: Multi-AZ for availability, read replicas for read scaling, snapshots and point-in-time restore for recovery, and RDS Proxy for connection management.

This lesson assumes that you know the basics of Amazon EC2, Amazon EBS, Amazon VPC, and AWS KMS. It follows FlashCart Inc., an online store, through the Problem Statement of each tab. Amazon Aurora and Amazon ElastiCache appear only in the comparison, because other lessons cover them.

1.2 What Amazon RDS Is

  • Amazon Relational Database Service (Amazon RDS) is a managed service for databases that use SQL as their query language.
  • AWS handles provisioning, patching, upgrades, backup, recovery, repair, and monitoring.
  • You create a DB instance, choose the engine, the instance class, and the storage, and then connect to it through an endpoint.
  • The storage of a DB instance is backed by Amazon EBS.

The main RDS features are:

  • Multi-AZ deployment: deploy the database across several Availability Zones.
  • Read replicas: scale the read queries.
  • Storage Auto Scaling: increase the storage automatically.
  • RDS Custom: get access to the underlying host.
  • Backups: automated and manual backups.
  • Security: authentication, encryption, and network controls.

Amazon RDS runs a database for you, so that AWS handles the servers, the patches, and the backups. This lesson shows what RDS gives you, where it sits in your VPC, how its storage grows, how Multi-AZ deployments and read replicas protect and scale a database, how backups and restores work, how RDS secures data, and when to add RDS Proxy or RDS Custom. It ends with the monitoring and pricing basics and a comparison of the options. The last two tabs prepare you for the AWS Certified Solutions Architect – Associate (SAA-C03) exam.

1.4 Amazon RDS Shared Responsibility Model

Amazon RDS is responsible for hosting the software components and the infrastructure of DB instances and DB clusters. You are responsible for query tuning, which is the process of adjusting SQL queries to improve performance.

  • Query performance depends heavily on the database design, the data size, the data distribution, the application workload, and the query patterns, which can vary greatly.
  • Monitoring and tuning are highly individualized processes that you own for your RDS databases.
  • You can use CloudWatch (lesson 274.1) Database Insights, which replaced Performance Insights, and other tools to identify problematic queries (tab 9).

1.5 Advantages Over a Database on EC2

  • Automated provisioning and operating system patching.
  • Continuous backups, and restore to a specific point in time.
  • Monitoring dashboards.
  • Read replicas for better read performance.
  • Multi-AZ setup for disaster recovery.
  • Maintenance windows for upgrades.
  • Scaling: vertical, by changing the instance class, and horizontal for reads, with read replicas.
  • The limit: you cannot use SSH to connect to the instance, except with RDS Custom (tab 8).

1.7 Core RDS Components

1.7.1 Amazon RDS DB Instances

A DB instance is an isolated database environment in the AWS Cloud that runs the database engine that you choose. It is the basic building block of Amazon RDS. It includes:

  • Virtual compute resources and memory.
  • Network connectivity.
  • The database engine.
  • Attached database storage.
  • An endpoint and a database port.
  • Backup settings, maintenance settings, and a monitoring configuration.
  • A DB instance can contain one or more user-created databases.
  • You can access a DB instance with the same tools and applications that you use with a standalone database instance.
  • You can create and modify a DB instance with the AWS Command Line Interface (AWS CLI), the Amazon RDS API, or the AWS Management Console.

1.7.2 DB Instance Class

The DB instance class decides the number of virtual CPUs, the memory, the network performance, the storage bandwidth, and the number of database connections that are available.

CategoryExample use
BurstableDevelopment and light workloads.
General purposeBalanced production workloads.
Memory optimizedLarge databases and memory-intensive queries.
Previous generationLegacy compatibility. Avoid it for new deployments.

1.7.3 Endpoint

  • Applications connect to RDS through a DNS endpoint and a port, for example database-name.abc123.us-east-1.rds.amazonaws.com.
  • Use the endpoint, not an IP address. The IP address can change during maintenance or a failover.
  • After a failover, the same endpoint points to the new primary, so the application keeps its connection string.
  • The DB subnet group, the parameter group, and the option group are covered in tab 2.

Each step in this chain depends on the one before it:

  • The engine decides which instance classes, features, and ports are available.
  • The instance class and the storage decide the performance.
  • The DB subnet group and the security group decide where the database lives and who can reach it.
  • The endpoint is the destination that the application uses.

1.11 Setting Up Your Amazon RDS Environment

The basic building block of Amazon RDS is the DB instance. In a DB instance, you create your databases. A DB instance provides a network address called an endpoint, and your applications use this endpoint to connect to the DB instance.

When you create a DB instance, you specify details such as storage, memory, the database engine and version, network configuration, security, and maintenance periods. You control network access to a DB instance through a security group.

Before you create a DB instance and a security group, you must know your DB instance and network needs. Consider these points:

  • Resource requirements: what are the memory and processor requirements of your application or service? These settings help you decide which DB instance class to use.
  • VPC, subnet, and security group: your DB instance will most likely be in a VPC. To connect to it, you set up security group rules. The rules depend on the kind of VPC that you use and how you use it:
    • Default VPC: if your AWS account has a default VPC in the current Region, that VPC is configured to support DB instances. If you specify the default VPC when you create the DB instance, create a VPC security group that authorizes connections from the application or service to the DB instance, and specify the default DB subnet group. If this is the first DB instance in the Region, Amazon RDS creates the default DB subnet group when it creates the DB instance.
    • User-defined VPC: create a VPC security group that authorizes connections from the application or service to the DB instance. The VPC must meet certain requirements to host DB instances, such as having at least two subnets, each in a separate Availability Zone. Also specify a DB subnet group that defines which subnets in that VPC the DB instance can use.
  • High availability: do you need failover support? A Multi-AZ deployment creates a primary DB instance and a standby DB instance in another Availability Zone. AWS recommends Multi-AZ deployments for production workloads. For development and test, you can use a deployment that is not Multi-AZ.
  • IAM policies: if you connect to AWS with IAM credentials, your IAM account must have policies that grant the permissions that Amazon RDS operations need.
  • Open ports: which TCP/IP port does your database listen on? The firewalls at some companies block the default port of a database engine. If yours does, choose another port for the new DB instance. You can change the port later by modifying the DB instance.
  • AWS Region: in which Region do you want the database? A database that is close to your application or web service can reduce network latency.
  • DB disk subsystem: what are your storage requirements? Amazon RDS provides two storage types: General Purpose SSD and Provisioned IOPS. Magnetic storage, which is also known as standard storage, is deprecated and is no longer offered for new DB instances.

When you have this information, you can create the security group and the DB instance. For more detail, see Setting up your Amazon RDS environment.

2. RDS Network and Configuration

Problem Statement

After the move to RDS, the FlashCart engineers must decide where the database lives and who can reach it. A test database was created as publicly accessible, a script that used a hard-coded IP address stopped working after a failover, and nobody can say how to raise the connection limit of the engine or when the next patch will run. The security team wants one clear design for all of it.

2.1 The VPC and the DB Subnet Group

  • Amazon VPC lets you launch AWS resources, such as Amazon RDS DB instances, into a virtual private cloud (VPC). An RDS database lives in your VPC.
  • When you use a VPC, you control your virtual networking environment. You can choose your own IP address range, create subnets, and configure routing and network access control lists.
  • There is no additional cost to run your DB instance in a VPC.
  • Every account has a default VPC. All new DB instances are created in the default VPC unless you specify otherwise.
  • A DB subnet group is a collection of VPC subnets that RDS can use when it places database resources.
  • A production subnet group should contain subnets in at least two Availability Zones. Without them, RDS cannot place a standby in another zone.
  • Use private subnets for the database.

2.4 Parameter Groups

  • A DB parameter group holds the engine configuration values. Examples are the maximum number of connections, logging behavior, memory settings, query settings, character sets, and time zones.
  • A dynamic parameter can take effect without restarting the database. A static parameter needs a reboot first.
  • You cannot edit an AWS default parameter group. Create a custom parameter group when you need to change a value.

2.5 Option Groups

  • An option group turns on additional, engine-specific features for a DB instance.
  • They are mainly used with RDS for Oracle and RDS for SQL Server. Examples are native backup and restore, auditing, and Oracle Enterprise Manager.

  • RDS handles operating system updates, database engine patches, hardware maintenance, and certificate updates.
  • The maintenance window defines when pending maintenance can be applied. A change can be applied immediately or scheduled for the next maintenance window.

2.7 Connecting to an RDS Database: Example

The following high-level steps launch an RDS for MySQL database that has no public access, and connect to it from an EC2 instance in the same VPC:

  1. Launch an EC2 instance in the default VPC, and connect to it over SSH.
  2. Create a MySQL RDS database in the default VPC, with no public access. The database security group allows the database port from the EC2 instance.
  3. Install a MySQL-compatible client on the EC2 instance.
  4. Connect to the RDS database by using the database endpoint.

From the EC2 instance, connect with the client and run a few statements:

mysql -h <database endpoint> -u admin -p

CREATE DATABASE shop;
USE shop;
CREATE TABLE products (product_id INT, name VARCHAR(64), price DECIMAL(8,2));
INSERT INTO products VALUES (1001, 'Widget', 9.99);
  • Replace <database endpoint> with the endpoint that RDS shows for the DB instance. The command asks for the password of the master user.
  • The connection works only because the database security group allows the EC2 instance. A client outside the VPC cannot reach a database with no public access.

3. RDS Storage and Scaling

Problem Statement

The FlashCart orders database grew faster than the team expected, and during the first minutes of a flash sale the disk filled up and the shop stopped taking orders. Someone then enlarged the storage by hand at midnight. The team wants storage that grows on its own, and it needs to choose the right storage type for a busy database.

3.1 RDS Storage Types

Storage typeWhat it isUse it for
General Purpose SSD: gp3 (recommended) and gp2SSD storage with a balance of price and performance. gp2 is the previous generation.Most workloads, including development and test.
Provisioned IOPS SSD: io2 Block Express (recommended) and io1SSD storage where you choose the IOPS rate. io2 Block Express can reach up to 256,000 IOPS and has sub-millisecond latency on Nitro-based instances. io1 is the previous generation.I/O-intensive, latency-sensitive production databases.
MagneticA deprecated legacy type. New DB instances cannot use it, and a snapshot of a Magnetic volume must be restored to another storage type.Not for new databases.
  • Storage is backed by Amazon EBS.
  • You can create MySQL, MariaDB, PostgreSQL, and Db2 DB instances with up to 64 TiB of storage. For Oracle and SQL Server, additional storage volumes raise the limit to 256 TiB.
  • The type of storage for a read replica does not depend on the storage type of the primary DB instance.

3.2 RDS Storage Auto Scaling

  • Storage Auto Scaling increases the storage of a DB instance dynamically when RDS detects that free storage is running out.
  • You must set a Maximum Storage Threshold, which is the upper limit for the storage.
  • RDS increases the storage only when all of these conditions are true: free storage is less than 10 percent of the allocated storage, the low-storage condition lasts at least 5 minutes, and at least 6 hours have passed since the last storage modification.
  • It helps applications with unpredictable workloads, and it supports all RDS database engines.
  • It works with gp2, gp3, and Provisioned IOPS volumes.

3.3 Choosing Storage

  • Start with gp3 for most databases.
  • Choose io2 Block Express when the database needs high, steady IOPS and low latency.
  • Turn on Storage Auto Scaling when the amount of data is hard to predict, and set a maximum so that cost cannot grow without a limit.
  • A stopped DB instance still costs money for its storage.

3.4 Storage Performance Dimensions

  • Allocated storage.
  • Input/output operations per second (IOPS).
  • Storage throughput and storage latency.
  • The bandwidth of the DB instance.
  • The database page size and the behavior of the queries.

3.5 Scaling Up the DB Instance Class

  • Vertical scaling changes the DB instance class, for example from a db.t class to a db.m class or a db.r class.
  • It changes the CPU, the memory, the network bandwidth, the storage bandwidth, and the maximum number of connections.
  • The change can cause downtime or a failover, so schedule it, or apply it in the maintenance window.

3.6 Limits of Storage Scaling

  • You can increase storage by hand or with Storage Auto Scaling.
  • Storage Auto Scaling never reduces the storage, and RDS does not let you reduce the allocated storage of an existing instance. To use less storage, restore or migrate the data into a new, smaller DB instance where that is supported.
  • For Provisioned IOPS storage, the ratio of IOPS to allocated storage must stay inside the allowed range.

4. High Availability With Multi-AZ

Problem Statement

Last year an Availability Zone problem took the FlashCart database offline for 40 minutes, and an engineer had to rebuild it from a backup. The business now asks for a database that fails over on its own when a zone, a network link, an instance, or a disk fails, and without a change to the application.

4.1 What Multi-AZ Is

  • A Multi-AZ deployment keeps a copy of the database in a second Availability Zone, to improve availability and for disaster recovery.
  • RDS copies the data to the standby synchronously, so the standby has every committed change.
  • The application uses one DNS name. After a failure, RDS makes the standby the new primary, and the same name points to it.
  • Failover happens on the loss of an Availability Zone, the loss of the network, and the failure of the instance or of the storage.
  • The application needs no manual change.
  • Multi-AZ is for availability. It is not a way to scale reads.

4.2 Two Multi-AZ Options

  • Multi-AZ deployments can have one standby or two standby DB instances.
  • When the deployment has one standby DB instance, it is called a Multi-AZ DB instance deployment. It has one standby DB instance that provides failover support but does not serve read traffic.
  • When the deployment has two standby DB instances, it is called a Multi-AZ DB cluster deployment. It has standby DB instances that provide failover support and can also serve read traffic.

4.3 From Single-AZ to Multi-AZ

  • Zero downtime operation.
    • A database stop is not required.
  • Choose Modify for the database.
    • You can update the database from the AWS Management Console, with the Modify option.
  • The following happens internally:
    1. RDS takes a snapshot.
    2. RDS restores a new database from the snapshot in another Availability Zone.
    3. RDS establishes synchronization between the two databases.

4.4 Single-AZ Deployments

  • A Single-AZ deployment has one DB instance and no standby in another Availability Zone.
  • Use it for development, testing, noncritical workloads, and workloads that can tolerate database downtime.
  • It has no automatic failover. If the instance or the zone fails, you restore from a backup.

4.6 Automatic Failover

RDS can start a failover after:

  • A failure of the primary DB instance.
  • A disruption of the Availability Zone.
  • A storage failure.
  • A loss of network connectivity.
  • Some operating system maintenance.
  • A manual reboot with failover.
  • A change of the DB instance class, in some configurations.

A failover proceeds in these steps:

  1. The application sends its requests to the endpoint, which points to the primary.
  2. The primary becomes unavailable.
  3. RDS promotes the standby to be the new primary.
  4. The same endpoint points to the new primary, and the application reconnects.

The application should:

  • Use the RDS DNS endpoint.
  • Retry the connection.
  • Refresh its DNS resolution.
  • Avoid hard-coded IP addresses.
  • Use connection pooling, for example RDS Proxy (tab 8).

4.7 Identifying the Multi-AZ Deployment Type

You can use the AWS Management Console to determine whether a Multi-AZ deployment is a Multi-AZ DB instance deployment or a Multi-AZ DB cluster deployment. In the navigation pane, choose Databases, and then choose a DB identifier.

  • A Multi-AZ DB instance deployment has the following characteristics:
    • There is only one row for the DB instance.
    • The value of Role is Instance or Primary.
    • The value of Multi-AZ is Yes.
  • A Multi-AZ DB cluster deployment has the following characteristics:
    • There is a cluster-level row with three DB instance rows under it.
    • For the cluster-level row, the value of Role is Multi-AZ DB cluster.
    • For each instance-level row, the value of Role is Writer instance or Reader instance.
    • For each instance-level row, the value of Multi-AZ is 3 Zones.

5. Read Replicas

Problem Statement

During the FlashCart sale the finance team runs heavy reports on the orders database, and the checkout pages slow down because the reports share the same database. The team needs to move the read-only work somewhere else, and it also wants a copy of the data in another Region that it could use if the main Region fails.

5.1 Overview of Amazon RDS Read Replicas

  • A read replica is a read-only copy of a DB instance. You can reduce the load on your primary DB instance by routing queries from your applications to the read replica.
  • In this way, you can elastically scale out beyond the capacity constraints of a single DB instance for read-heavy database workloads.
  • To create a read replica from a source DB instance, Amazon RDS uses the built-in replication features of the DB engine.
  • You can create up to 15 read replicas for RDS for MySQL, MariaDB, and PostgreSQL.
  • Replicas can be in the same Availability Zone, in another Availability Zone, or in another Region.
  • Replication is asynchronous, so reads from a replica are eventually consistent.
  • Data is written only to the primary. Replicas serve SELECT statements, and not INSERT, UPDATE, or DELETE.
  • Applications must update their connection string to use the replicas, because each replica has its own endpoint.

5.2 Use Cases

Deploying one or more read replicas for a given source DB instance might make sense in a variety of scenarios, including the following:

  • Read scaling: scaling beyond the compute or I/O capacity of a single DB instance for read-heavy database workloads. You can direct this excess read traffic to one or more read replicas.
  • Reads while the source is unavailable: serving read traffic while the source DB instance is unavailable. In some cases, your source DB instance might not be able to take I/O requests, for example due to I/O suspension for backups or scheduled maintenance. In these cases, you can direct read traffic to your read replicas. Keep in mind that the data on the read replica might be stale because the source DB instance is unavailable.
  • Reporting and analytics: business reporting or data warehousing scenarios where you might want business reporting queries to run against a read replica, rather than your production DB instance.
  • Disaster recovery: you can promote a read replica to a standalone instance as a disaster recovery solution if the primary DB instance fails.

5.3 Promoting a Replica

  • A replica can be promoted to its own standalone DB instance. After the promotion, it no longer replicates from the old primary.
  • You can set up a read replica itself as a Multi-AZ deployment for disaster recovery.

5.4 Network Cost

  • In AWS, data that moves from one Availability Zone to another normally has a network cost. For RDS read replicas in the same Region, you do not pay that fee for the replication traffic.
  • For a replica in another Region, you pay for the data transfer.

5.7 Read Replica Behavior

  • Replication can fall behind the primary, which is replica lag. The CloudWatch metric ReplicaLag shows it.
  • The application decides what to read from a replica. A read that needs the newest data must go to the primary.
  • Promoting a replica is a separate operation. It is not the same as an automatic Multi-AZ failover.
  • Support for cross-Region replicas depends on the database engine.
  • A replica can also help with a database migration.
  • Each replica has the normal charges of a DB instance.

6. Backups and Restore

Problem Statement

An engineer at FlashCart ran a DELETE statement without a WHERE clause on a Tuesday afternoon, and about two hours of order changes were lost before anyone noticed. The team needs to bring the database back to the minute before the mistake. It also wants backups that it can keep for audits and copy to another Region.

6.1 Automated Backups

  • RDS takes a daily full backup of the database during the backup window.
  • RDS also saves the transaction logs every 5 minutes.
  • Together they let you restore to any point in time, from the oldest backup to about 5 minutes ago. This is point-in-time restore (PITR).
  • The retention period is 1 to 35 days. A value of 0 turns automated backups off.
  • You can choose the backup window. A backup can have a small effect on I/O, so choose a time with little traffic.
  • When you delete a DB instance, RDS can remove its automated backups, unless you choose to keep them.

6.2 Manual Snapshots

  • A manual snapshot is a backup that you start yourself.
  • It stays for as long as you want, until you delete it.
  • RDS stores snapshots in Amazon S3, and you can copy them to another account or another Region to create a new database there.
  • A snapshot is a good way to keep a database that you stop for a long time. A stopped DB instance still pays for storage, so snapshot it and restore it later.

6.3 Restoring

  • Restoring an automated backup or a snapshot creates a new DB instance with a new endpoint. It does not overwrite the old database.
  • After a restore, the application must use the new endpoint, or you rename the instances.
  • You can restore an on-premises MySQL database to a new RDS for MySQL instance: create a backup of the database, store it in Amazon S3, and restore it from there.

  • AWS Backup can also manage RDS backups with a central policy (Lesson 271.4, tab 6).

6.5 More Backup Details

  • For a DB instance, the retention period can be 0 to 35 days. A Multi-AZ DB cluster needs 1 to 35 days.
  • You can take a final snapshot when you delete a DB instance, and you can choose to keep its automated backups.
  • Manual snapshots stay until you delete them, can be copied to another Region, and can be shared with other accounts when the requirements are met.
  • Use a snapshot to create a development or test environment from production data.

7. RDS Security

Problem Statement

FlashCart’s security review of the orders database lists five findings. The data is not encrypted, applications log in with a shared password, the database accepts connections from too many places, nobody can say who connected last week, and the team asks how to encrypt a database that is already running. The engineers have to fix all five.

7.1 Encryption at Rest

  • RDS encrypts the database, its automated backups, its snapshots, and its read replicas with keys from AWS KMS.
  • You must turn on encryption when you create the database. You cannot turn it on for a running database.
  • If the primary is not encrypted, its read replicas cannot be encrypted.
  • Snapshots of an encrypted database are encrypted too.

7.2 Encrypting an Existing Database

  1. Take a snapshot of the unencrypted database.
  2. Copy the snapshot, and choose a KMS key to encrypt the copy.
  3. Restore the encrypted snapshot as a new DB instance.
  4. Switch the application to the new endpoint, and delete the old database.

7.3 Encryption in Transit

  • RDS supports TLS (SSL) for connections from clients.
  • Clients use the AWS TLS root certificates to verify the server.
  • The application must use an encrypted connection, trust the RDS certificate authority, validate the server certificate, and update certificates when required.

7.4 Authentication and Access

  • All engines support user name and password authentication. Store the credentials in AWS Secrets Manager or in AWS Systems Manager Parameter Store, and not in the application code.
  • IAM database authentication lets applications connect with an IAM role and a short-lived token, instead of a password. It works with RDS for MySQL, MariaDB, and PostgreSQL.
  • You create the database users and their permissions yourself.
  • RDS also supports Kerberos and Active Directory authentication for some engines.
  • AWS Secrets Manager stores and encrypts the credentials, can rotate supported credentials, removes hard-coded passwords from applications, and supplies credentials to RDS Proxy.
  • IAM policies control actions such as creating, modifying, or deleting a DB instance, and creating or restoring a snapshot. Permission to manage an RDS resource does not let a user sign in to the database.

7.5 Network Security

  • Put the database in private subnets of your VPC. It has no public internet access unless you explicitly allow it.
  • Security groups control which sources can connect. For example, open port 3306 for MySQL only to the application’s security group.
  • Network ACLs also apply to the subnets.
  • There is no SSH access to a standard RDS instance. RDS Custom is the exception (tab 8).

7.6 Auditing

  • You can turn on audit logs and send them to Amazon CloudWatch Logs (lesson 274.2), which keeps them for longer.
  • AWS CloudTrail (lesson 274.3) records the RDS API calls, such as who created or deleted a database.

7.7 Security Layers

  1. VPC routing decides whether traffic can reach the database subnets.
  2. The security group decides which sources can connect.
  3. Database authentication proves who the user is.
  4. Database permissions decide what the user can do.
  5. Encryption protects the data at rest and in transit.

8. RDS Proxy and RDS Custom

Problem Statement

The FlashCart order-confirmation service runs as thousands of short-lived application instances during the sale, and each instance opens its own connection to the database. The database runs out of memory and connections, and the failover that follows takes too long. Separately, an acquired business runs an Oracle application that needs an operating-system setting that standard RDS does not allow.

8.1 Amazon RDS Proxy

  • Amazon RDS Proxy is a fully managed database proxy for RDS and Aurora.
  • It sits between the application and the database, and it pools and shares the database connections.
  • Modern and serverless applications often open many short-lived connections, which can use up the memory and the CPU of the database. A proxy reduces that load and the number of open connections.
  • It is serverless, scales automatically, and is highly available across Availability Zones.
  • It reduces the failover time of RDS and Aurora by up to 66 percent.
  • It supports RDS for MySQL, PostgreSQL, MariaDB, and SQL Server, and Aurora for MySQL and PostgreSQL.
  • Most applications need no code changes. They connect to the proxy endpoint.
  • Security: the proxy stores the database credentials in AWS Secrets Manager. Applications can use IAM authentication to connect to the proxy, and you can require it.
  • The proxy is not publicly accessible. It always runs inside a VPC.
  • Use case: serverless applications and applications with unpredictable, high-concurrency workloads.

8.1.1 What RDS Proxy Does Not Do

  • It does not cache query results.
  • It does not replace a read replica.
  • It does not add CPU or memory to the database.
  • It does not optimize SQL automatically.
  • It does not replace database backups.

8.2 Amazon RDS Custom

  • RDS Custom is a managed database service for Oracle and Microsoft SQL Server that gives you access to the operating system and the database.
  • You can configure settings, install patches, enable native features, and reach the underlying EC2 instance with SSH or SSM Session Manager.
  • It suits customized, legacy, and packaged applications that need operating-system changes or special database configurations.
  • RDS still automates tasks such as backups and monitoring.
  • To make customizations, deactivate Automation Mode first, and take a DB snapshot before you change anything.

9. Monitoring and Pricing

Problem Statement

Three months after FlashCart moved to RDS, the finance team asks two questions. How will the engineers know that the database is healthy or about to have a problem, and why does the bill have so many lines? The team has to explain what RDS reports and what it charges for.

9.1 Monitoring

  • Amazon CloudWatch collects RDS infrastructure metrics, such as CPU use, free storage, and the number of connections, and you can set alarms on them.
  • Enhanced Monitoring adds operating-system metrics of the DB instance.
  • CloudWatch Database Insights shows the database load, the queries, and the waits, and helps you find what slows the database. It replaced Performance Insights, which AWS ended on July 31, 2026, so older questions and documents may still use the old name. The Advanced mode adds execution plans and on-demand analysis.
  • CloudWatch Logs receives exported database logs, such as audit logs, for longer retention.
  • AWS CloudTrail records the RDS API calls.
  • Amazon EventBridge (lesson 273.3) and RDS event notifications (through Amazon SNS (lesson 273.3)) respond to events such as a failover or a backup.
  • Database Activity Streams audit database activity for supported engines.

9.2 Maintenance

  • RDS applies operating-system and engine updates in a maintenance window that you can choose.
  • A Multi-AZ deployment reduces the effect of maintenance, because RDS can update the standby first.

9.3 Amazon RDS Pricing

Prices change often and differ by Region. Always check the current rates on the Amazon RDS pricing page, and estimate your own cost with the AWS Pricing Calculator.

  • DB instance hours: you pay for each DB instance-hour, from the time that you launch an instance until you stop or delete it. The price depends on the engine and the instance class.
  • Storage: a price per GB-month for the storage that you allocate, and a price for Provisioned IOPS if you use it.
  • Multi-AZ: you pay for the standby instance or instances too, so a Multi-AZ deployment costs more than a Single-AZ deployment.
  • Read replicas: each replica is a DB instance with its own cost. Replication in the same Region has no cross-AZ fee, and replication to another Region has a data transfer fee.
  • Backups: backup storage and snapshots have a cost beyond the free amount that the database size gives.
  • Data transfer: data that leaves AWS or moves between Regions has a cost.
  • Database engine licensing: some commercial engines include the license in the price, and some let you bring your own license.
  • RDS Proxy, Enhanced Monitoring, and logs: each has its own charge.
  • Extended Support: older engine versions that are past standard support can carry an extra charge.

9.4 Lowering the Cost

  • Reserved Instances give a lower price for a steady database that runs all the time, with a one-year or three-year term and payment options of all upfront, partial upfront, or no upfront.
  • Choose gp3 storage, and use Storage Auto Scaling with a maximum, instead of a large disk that is mostly empty.
  • Use Multi-AZ for production, and Single-AZ for development and test.
  • Snapshot and delete a database that you do not need for weeks.
  • You can stop a DB instance for up to 7 days at a time, and RDS then starts it again automatically. While it is stopped you do not pay for instance hours, but you still pay for storage, snapshots, and backup storage.
  • Remove read replicas that nobody uses.

10.5 Architecture Selection Flow

10.6 Lesson Summary

This lesson covered the following points:

  • Amazon RDS is a managed service for relational databases. AWS patches, backs up, and monitors them, and you manage the access, the encryption, the users, and the manual backups. You cannot use SSH, except with RDS Custom.
  • Storage is backed by EBS. Use gp3 for most workloads and io2 Block Express for heavy I/O, and turn on Storage Auto Scaling with a maximum for unpredictable growth.
  • Multi-AZ improves availability with a synchronous standby and an automatic failover behind one DNS name. A Multi-AZ DB cluster adds readable standbys. Multi-AZ does not scale reads.
  • Read replicas scale reads and support reports and disaster recovery. They are asynchronous, they use their own endpoints, and they can be in another Region.
  • Automated backups with transaction logs give point-in-time restore for 1 to 35 days. Manual snapshots stay until you delete them. Every restore creates a new DB instance.
  • An RDS database sits in private subnets of a DB subnet group, behind a security group chain. Parameter groups set the engine behavior, option groups add engine features, and the maintenance window controls the patching.
  • Multi-AZ, read replicas, and backups solve different problems. Replication alone does not protect against logical errors, so keep backups.
  • Encryption at rest is set at creation. To encrypt an existing database, snapshot it, copy the snapshot with encryption, and restore it. IAM authentication, Secrets Manager, security groups, and private subnets protect access.
  • RDS Proxy pools connections and shortens failover. RDS Custom gives operating-system access for Oracle and SQL Server.
  • The cost has instance hours, storage, the Multi-AZ standby, replicas, backups, and data transfer. Reserved Instances lower the price of a steady database.

Memory Hook

Multi-AZ keeps it up. Replicas scale reads. Snapshots and logs bring it back. KMS locks it. Proxy shares the connections.

11. Knowledge Check

Answer each question in your own words before you open the model answer. The questions were written for this course.

Question 1: Explain what Amazon RDS manages for you, and what you still manage yourself.

Maps to: Objectives 1 and 2 (Comprehension).

AWS provisions and manages the EC2 host that runs the database, patches the operating system and the database software, takes the automated backups, and does the database maintenance. You manage the network access, the security group rules, encryption at rest, the database users and their permissions, and the manual backups. You cannot connect to the instance with SSH, except with RDS Custom.

Question 2: Describe the RDS storage types, and explain when Storage Auto Scaling increases the storage.

Maps to: Objective 4 (Comprehension).

RDS offers General Purpose SSD (gp3 recommended, and gp2) and Provisioned IOPS SSD (io2 Block Express recommended, and io1), and the legacy Magnetic type is being retired. Storage Auto Scaling raises the storage when free space is below 10 percent of the allocated storage, the condition lasts at least 5 minutes, and at least 6 hours have passed since the last change. You must set a Maximum Storage Threshold.

Question 3: Differentiate a Multi-AZ deployment from a read replica, and say which one you use for a database that must fail over automatically.

Maps to: Objective 5 (Analysis).

A Multi-AZ deployment copies the data synchronously to a standby in another Availability Zone and fails over automatically behind one DNS name. It is for availability, and in a DB instance deployment the standby cannot be read. A read replica receives the data asynchronously and serves read-only queries from its own endpoint. It scales reads, and you promote it by hand. For automatic failover, use Multi-AZ.

Question 4: Explain how automated backups, point-in-time restore, and manual snapshots work, and what a restore creates.

Maps to: Objective 6 (Comprehension).

RDS takes a daily full backup in the backup window and saves the transaction logs every 5 minutes. Together they allow a point-in-time restore to any time from the oldest backup to about 5 minutes ago, within a retention period of 1 to 35 days. A manual snapshot is started by you and stays until you delete it. A restore from either one creates a new DB instance with a new endpoint.

Question 5: Describe how to encrypt an RDS database that already runs without encryption.

Maps to: Objective 7 (Application).

You cannot turn encryption on for a running database. Take a snapshot of the database, copy the snapshot and choose a KMS key to encrypt the copy, and restore the encrypted snapshot as a new DB instance. Then switch the application to the new endpoint. If a primary is not encrypted, its read replicas cannot be encrypted either.

Question 6: Explain when to use RDS Proxy and when to use RDS Custom.

Maps to: Objective 8 (Comprehension).

Use RDS Proxy when many short-lived connections, for example from Lambda functions, use up the memory and CPU of the database. It pools and shares the connections, uses Secrets Manager and IAM authentication, runs inside a VPC, and can shorten the failover time. Use RDS Custom when an Oracle or SQL Server application needs access to the operating system or the database host, which standard RDS does not allow.

Question 7: Design an RDS solution for a production order database that needs high availability, read scaling for reports, point-in-time recovery, encryption, and a controlled cost.

Maps to: Objective 10 (Synthesis).

Create an encrypted RDS database with gp3 storage, Storage Auto Scaling with a maximum, and a Multi-AZ deployment in private subnets, with security groups that allow only the application. Add a read replica for the reports and set the backup retention period for point-in-time restore. Store the credentials in Secrets Manager or use IAM authentication, add RDS Proxy if Lambda functions connect, and buy Reserved Instances for the steady production instance.

Question 8: Describe how to place an RDS database in a VPC, and who should be able to reach it.

Maps to: Objective 3 (Application).

Create a DB subnet group with subnets in at least two Availability Zones, and place the database in private subnets, with public accessibility turned off. Give the database security group a rule that allows the database port only from the application security group, and give the application security group a rule that allows traffic from the load balancer security group. Public accessibility alone does not open a database to everyone, because the security groups still decide who can connect.

Question 9: Explain what happens during an automatic failover, and how the application should be written.

Maps to: Objective 5 (Application).

After a failure of the primary, the instance, the storage, the network, or the zone, RDS promotes the standby to be the new primary, and the same endpoint points to it. The application should use the DNS endpoint and not an IP address, retry the connection, refresh its DNS resolution, and use connection pooling, for example RDS Proxy.

Question 10: Explain why replication alone is not a full disaster recovery plan, and which RDS feature meets each requirement.

Maps to: Objective 6 (Analysis).

Replication copies every change, including an accidental delete or a corrupted row, so a replica or a standby does not protect against a logical error. Use Multi-AZ for availability and automatic failover, read replicas for read scaling and a possible disaster recovery copy in another Region, and automated backups with point-in-time recovery, snapshots, or AWS Backup to recover from deletion, corruption, or historical errors.

Introduction

Many applications use MySQL or PostgreSQL but outgrow what a standard RDS instance gives: faster failover, more replicas, storage that grows by itself, and a cross-Region design. Aurora answers these needs without changing the drivers or the SQL. An architect has to know which Aurora feature fits which requirement, and when a different database is the better answer.

This lesson assumes that you know Amazon RDS (Lesson 272.1): DB instances, Multi-AZ, read replicas, backups, and encryption. It follows FlashCart Inc. through the Problem Statement of each tab.

1. What Amazon Aurora Is

Problem Statement

FlashCart runs its orders on Amazon RDS for MySQL. During the sale the reads slow down, a failover takes minutes, and the team has to resize the disk by hand. The engineers want to keep using MySQL drivers and tools, but they want a database that is faster, fails over in seconds, and grows its own storage.

1.1 What Amazon Aurora Is

  • Amazon Aurora is a relational database that AWS built for the cloud. It is compatible with MySQL and PostgreSQL, so the drivers and tools for those engines work with it.
  • Aurora is part of the Amazon RDS family. AWS manages the servers, the patching, the backups, and the failure recovery, as in RDS.
  • AWS states that Aurora offers up to 5 times the throughput of standard MySQL and up to 3 times the throughput of standard PostgreSQL on the same hardware, at a fraction of the cost of commercial databases.
  • Aurora is proprietary technology from AWS. It is not open source.
  • Aurora separates compute from storage. The storage grows by itself, and it is shared by all the instances of the cluster.

1.3 Related Offerings to Know

  • Aurora Serverless v2 sizes the capacity of an Aurora database automatically (tab 4).
  • Amazon Aurora DSQL is a separate serverless, distributed SQL database with PostgreSQL compatibility. It is built for active-active, multi-Region applications with strong consistency, and its PostgreSQL feature set is narrower than Aurora PostgreSQL.
  • Aurora Limitless Database adds horizontal scaling (sharding) to Aurora PostgreSQL for workloads that outgrow a single writer.

1.4 Aurora Features at a Glance

  • Automatic failover, backup and recovery, isolation and security, and industry compliance.
  • Push-button scaling, automated patching with zero downtime, advanced monitoring, and routine maintenance.
  • Backtrack: restore data to any point in time without using backups (Aurora MySQL).
  • Aurora Global Database (tab 3), Aurora Serverless (tab 4), and Aurora cloning (tab 5).
  • Aurora machine learning and RDS Proxy (tab 6), and RDS Reserved Instances (tab 7).

2. Cluster Architecture and Endpoints

Problem Statement

The FlashCart engineers ask how Aurora keeps the data safe when a zone fails, and how the application should connect: where to send the writes, where to send the reports, and what happens to the connection string after a failover.

2.1 The Cluster

  • An Aurora DB cluster has one writer instance (the primary) and up to 15 Aurora Replicas (the readers).
  • All the instances use one shared cluster storage volume that spans three Availability Zones.
  • The writer takes the writes. The replicas serve read-only queries.

2.2 The Storage Layer

  • Aurora keeps 6 copies of your data across 3 Availability Zones, 2 copies in each zone.
  • A write needs 4 of the 6 copies, and a read needs 3 of the 6. So the cluster keeps write availability after the loss of 2 copies, and read availability after the loss of 3 copies.
  • The storage is self-healing: Aurora checks the copies and repairs them in the background. The data is striped across hundreds of volumes.
  • The volume grows automatically in 10 GB steps, up to 128 TiB, or 256 TiB on recent engine versions (Aurora MySQL 3.10 and later, and Aurora PostgreSQL 15.13, 16.9, 17.5, and later), and you pay for what you use.
  • The replicas read the same storage, so the replication to them is faster than MySQL replication. The course slides cite a replica lag of under 10 milliseconds.

2.3 Endpoints

EndpointWhere it pointsUse it for
Cluster (writer) endpointAlways the current writer instance.All writes and the reads that must see the newest data. After a failover it points to the new writer.
Reader endpointLoad balances connections across the Aurora Replicas.Read-only traffic, so that many clients share the replicas.
Custom endpointA group of instances that you choose.A special workload, for example analytics queries on larger replicas.
Instance endpointOne specific instance.Troubleshooting or a case that needs one particular instance.
  • After you define custom endpoints, the reader endpoint is generally not used.

2.4 Failover

  • If the writer fails, Aurora promotes an Aurora Replica to be the new writer. The cluster endpoint then points to it.
  • You can set a failover priority (tier) for each replica, so that Aurora promotes the one that you prefer first.
  • If the cluster has no replica, Aurora tries to create a new writer instance, which takes longer. For production, keep at least one replica in another Availability Zone.
  • The application should connect through the cluster endpoint, retry connections, and avoid hard-coded IP addresses.

3. Scaling and Global Database

Problem Statement

The FlashCart read traffic doubles every Friday. The business also wants customers in Europe to read the catalog with low latency, and it wants a plan if the whole US Region fails. The engineers must scale the reads, serve a second Region, and keep a disaster recovery copy.

3.1 Aurora Replicas and Aurora Auto Scaling

  • An Aurora cluster can have up to 15 Aurora Replicas. They share the same storage as the writer, so there is no data to copy to them.
  • Aurora Auto Scaling adds and removes replicas by itself, based on a target such as the average CPU use of the replicas or the number of connections.
  • The reader endpoint spreads the connections over the replicas, including the new ones.

3.2 Cross-Region Options

Cross-Region read replicaAurora Global Database
What it isA separate cluster in another Region that reads changes from the source.One database that spans several Regions.
ReplicationAurora MySQL uses binary log replication, so you must turn on binary logging.Handled by the Aurora storage layer, not by the database engine.
LagHigher.Typically under 1 second.
LimitUp to 5 cross-Region replica clusters for Aurora MySQL.One primary Region and up to 10 secondary Regions.
RecommendationSimple to set up for disaster recovery.Recommended for global reads and disaster recovery.

3.3 Aurora Global Database

  • Data is written in the primary Region only. The secondary clusters are read-only, and each can have up to 16 Aurora Replicas.
  • Use it to bring read data close to customers in other Regions, and to recover quickly from a Regional disaster by promoting a secondary cluster.
  • It supports a managed switchover for a planned change of the primary Region, and a failover for an outage. Both need the same major and minor engine version in the clusters.
  • Aurora Auto Scaling is not supported for the secondary clusters.
  • Aurora Serverless v2 works with Aurora Global Database. You can use Serverless for the reader instances of a secondary cluster for more flexible scaling.
  • Applications that write connect to the Aurora Global Database writer endpoint. It always points to the primary DB cluster, even after a switchover or a failover to another Region.
  • Aurora replicates the data to the secondary Regions over dedicated infrastructure, by using the cluster storage volume and not the database engine, so the replication has little effect on the primary cluster.
  • Promoting a secondary Region for disaster recovery has a recovery time objective (RTO) of under 1 minute (course slide).

3.4 Advantages of Aurora Global Database

  • Global reads with local latency: keep the main source of information in the primary Region. Offices and users in the other Regions read from their own Region.
  • Scalable secondary clusters: add read-only instances to a secondary Region. A secondary cluster is read-only, so it supports up to 16 read-only DB instances, instead of the usual limit of 15.
  • Fast replication: the replication has little performance impact on the primary cluster, so its instances serve the application reads and writes.
  • Recovery from Region-wide outages: a secondary cluster can become the new primary Region faster (a lower RTO) and with less data loss (a lower RPO) than with traditional replication.

3.5 Switchover and Failover

OperationWhen to use itWhat it does
SwitchoverA planned operation, such as a Regional rotation. It was previously called managed planned failover.Moves the primary cluster of a healthy global database to a secondary Region with no data loss.
FailoverAn outage in the primary Region.Recovers the global database by promoting a cluster in another Region (a cross-Region failover).
  • Managed cross-Region switchovers and failovers work only if the primary and the secondary clusters have the same major and minor engine version. Some engine versions also need identical patch levels. If they do, you perform the failover manually.
  • Create the secondary clusters with the same engine version as the primary.

3.6 Write Forwarding

  • Only the primary cluster performs writes. With write forwarding, you can configure the global database so that a secondary cluster sends the write requests of its clients to the primary cluster.
  • It lets an application in a secondary Region use a local connection for writes, but the writes still run in the primary Region. Aurora Global Database is not an active-active database.

3.7 Limitations of Aurora Global Database

  • It is available only in certain AWS Regions and for specific Aurora MySQL and Aurora PostgreSQL versions. Check the supported Regions and engines before you design.
  • Backtrack is not supported.
  • Aurora Auto Scaling is not supported for the secondary clusters.
  • The AWS Secrets Manager integration is not supported. Turn it off for a DB instance before you add a Region to the global database.
  • You cannot stop or start the clusters of a global database one by one.
  • Automatic minor version upgrade does not apply to clusters that are part of a global database.
  • You cannot rename a Regional cluster while it is a member of a global database.
  • Reader instances in a secondary Region restart when the writer instance of the primary Region restarts or fails over. The secondary cluster is unavailable until its readers are back in sync.
  • For Aurora PostgreSQL, cluster cache management is not supported for the secondary clusters.

4. Aurora Serverless v2

Problem Statement

The FlashCart staging database is used only a few hours a day, and the production database has traffic that no one can predict. The engineers are tired of choosing instance sizes. They want the database to follow the load, and they want the staging database to cost almost nothing when nobody uses it.

4.1 What Aurora Serverless v2 Is

  • Aurora Serverless v2 is an on-demand, auto-scaling configuration of Aurora. Instead of a fixed instance class, you set a minimum and a maximum capacity, and Aurora adjusts the capacity between them.
  • The unit is the Aurora capacity unit (ACU). One ACU is about 2 GiB of memory with matching CPU and networking.
  • Capacity changes in steps of 0.5 ACU, and the range goes from 0 to 256 ACUs. The range that you can use depends on the engine version.
  • You pay per second for the capacity that you use.
  • A cluster can mix Serverless v2 instances and provisioned instances.
  • It supports full Aurora features, including Multi-AZ, Aurora Replicas, and Aurora Global Database, for Aurora MySQL and Aurora PostgreSQL.

4.2 Scaling to Zero

  • Set the minimum capacity to 0 ACUs to turn on auto-pause. The instance pauses after a period without connections, and you do not pay for compute while it is paused. Storage is still billed.
  • The wait before a pause is set in seconds until auto-pause. The default is 5 minutes, and the maximum is 1 day.
  • A new connection resumes the instance, with a short delay. Do not use it where a delay is not acceptable.
  • A proxy that keeps connections open, such as RDS Proxy, prevents the instance from pausing.
  • Auto-pause is available for Serverless v2 with Aurora MySQL and Aurora PostgreSQL, on newer engine versions.

4.3 Choosing the Minimum and the Maximum

  • A very low minimum saves money, but the scale-up from a small size is slower, and the buffer cache can lose data when the capacity falls.
  • For a high number of connections, use a higher minimum. A low minimum also limits the maximum number of connections on Aurora PostgreSQL.
  • A reader that does not scale with the writer can lag, so raise the minimum if replicas fall behind.
  • Set the maximum high enough for the peak, and low enough to cap the cost.

4.4 Serverless v1 Is Retired

  • Aurora Serverless v1 reached end of life on March 31, 2025. Use Serverless v2 for new and existing workloads.
  • Older material may still describe v1 features, such as the proxy fleet, so check which version a question means.

5. Backups, Cloning, and Backtrack

Problem Statement

A FlashCart developer ran a bad UPDATE statement on the orders table. The team needs to go back to the minute before the mistake. The QA team also wants a full copy of production to run load tests within minutes, without a long restore and without touching the live database.

5.1 Backups

  • Aurora takes continuous, automated backups of the cluster volume. The retention period is 1 to 35 days, and you cannot turn automated backups off.
  • You can restore to any point in time inside the retention period.
  • Manual snapshots are started by you and stay until you delete them.
  • A restore from a backup or a snapshot always creates a new DB cluster.
  • You can restore an Aurora MySQL cluster from a backup file that you stored in Amazon S3, which helps with a migration from an on-premises MySQL database. Create the backup of the on-premises database with Percona XtraBackup, store the file in S3, and restore it onto a new Aurora MySQL cluster.

5.2 Aurora Cloning

  • Cloning creates a new Aurora cluster from an existing one in minutes, without copying all the data.
  • It uses a copy-on-write protocol. At first the clone uses the same storage as the source. Aurora copies only the blocks that change in either cluster.
  • It is faster and cheaper than a snapshot and restore, so it is ideal for test and development copies of production.
  • You can create multiple clones, up to 15, from the same source cluster.

5.3 Backtrack

  • Backtrack rewinds an Aurora MySQL cluster to a chosen time in place, without restoring from a backup.
  • The backtrack window is limited to 72 hours, so it does not replace backups.
  • It is available for Aurora MySQL only.

5.4 Choosing a Recovery Method

NeedUse
Return to a point in time and keep a separate copyPoint-in-time restore (a new cluster).
Rewind Aurora MySQL quickly, in placeBacktrack (up to 72 hours).
A copy for tests within minutesAurora cloning.
Keep a backup for yearsA manual snapshot, or AWS Backup.

6. Security and Integrations

Problem Statement

The FlashCart security team asks how Aurora is protected, and the engineers want to add three things: pooling for the many short-lived application connections, a product recommendation feature that calls machine learning from SQL, and a way to move a legacy SQL Server application without rewriting its T-SQL code.

6.1 Security

  • Encryption at rest uses AWS KMS. Set it when you create the cluster. The writer, the replicas, the backups, and the snapshots are all encrypted.
  • If the source is not encrypted, its replicas cannot be encrypted. To encrypt an existing cluster, snapshot it, copy the snapshot with encryption, and restore it.
  • Encryption in transit uses TLS.
  • IAM database authentication and AWS Secrets Manager avoid stored passwords.
  • Place the cluster in private subnets, and control access with security groups.
  • There is no SSH access to the instances of an Aurora cluster.

6.2 Integrations

RDS ProxyPools and shares connections for Aurora, reduces failover time, and uses Secrets Manager and IAM. It is not publicly accessible. It supports Aurora MySQL and Aurora PostgreSQL, and it reduces the failover time by up to 66 percent.

Use cases include fraud detection, ads targeting, sentiment analysis, customer churn prediction, recommendations, summarization, and classification.

  • Aurora uses the same security, monitoring, and maintenance features as RDS, including maintenance windows and CloudWatch (lesson 274.1) metrics.

7. Aurora Pricing

Problem Statement

The FlashCart finance team sees a new line on the Aurora bill every month: instance hours, storage, and I/O requests. The sale made the I/O line the biggest one. The CFO asks which Aurora configuration to choose and how to lower the cost without lowering the availability.

7.1 What You Pay For

Prices change often and differ by Region. Check the current rates on the Amazon Aurora pricing page, and estimate your own cost with the AWS Pricing Calculator.

  • Compute: instance hours for provisioned instances, or ACU-hours for Serverless v2, billed per second.
  • Storage: a price per GB-month for the storage that the cluster uses, not for a size that you allocate. Paused Serverless v2 instances still pay for storage.
  • I/O requests: charged per request in the Standard configuration.
  • Backups: backup storage up to 100 percent of the cluster storage in a Region is included. Extra backup storage and snapshots cost more.
  • Data transfer: replication between Availability Zones is free. Cross-Region replicas and Global Database add transfer charges, and traffic between an EC2 instance and an instance in another Availability Zone has the usual charge.

7.2 Aurora Standard and Aurora I/O-Optimized

Aurora StandardAurora I/O-Optimized
I/O chargesYou pay per million I/O requests.No charge for read and write I/O.
Instance and storage priceLower.Higher.
Best forWorkloads where I/O is a small part of the bill.I/O-intensive workloads with a high, steady, or unpredictable I/O cost.
  • As a guide, consider I/O-Optimized when the I/O charges are more than about 25 percent of the total Aurora spend.
  • You can switch between the two configurations.

7.3 Lowering the Cost

  • Use Reserved Instances for a steady provisioned workload. They can save up to 69 percent over On-Demand for RDS and Aurora (course slide).
  • Reserved Instances have three payment options: All Upfront, Partial Upfront, and No Upfront. All Upfront and Partial Upfront have a one-year or three-year term, and No Upfront has a one-year term only.
  • Reserved Instances give instance size flexibility for Aurora, MySQL, MariaDB, PostgreSQL, and Db2.
  • Use Serverless v2 for variable or idle workloads, and a minimum of 0 ACUs where a resume delay is acceptable.
  • Use cloning instead of a full copy for test data.
  • Pick the right configuration, Standard or I/O-Optimized, from your own I/O numbers.
  • Delete old snapshots that you do not need.

8.4 Lesson Summary

This lesson covered the following points:

  • Aurora is a MySQL- and PostgreSQL-compatible relational database from AWS. It separates compute from storage, keeps 6 copies of the data in 3 Availability Zones, and grows storage up to 128 TiB, or 256 TiB on recent engine versions.
  • A cluster has one writer and up to 15 Aurora Replicas. The cluster endpoint follows the writer, the reader endpoint balances the replicas, and custom endpoints target chosen instances.
  • Aurora Global Database has one writer Region and up to 10 read-only secondary Regions with typically under one second of lag. DynamoDB global tables are the answer for active-active writes.
  • Aurora Serverless v2 follows the load in ACUs, from 0 to 256, and a minimum of 0 ACUs turns on auto-pause. Serverless v1 is retired.
  • Backups last 1 to 35 days and cannot be disabled, Backtrack rewinds Aurora MySQL for up to 72 hours, and cloning makes a test copy in minutes.
  • Babelfish, Aurora machine learning, and RDS Proxy extend Aurora. I/O-Optimized fits workloads with a high I/O share of the bill.

Memory Hook

Six copies keep it safe. Replicas share the volume. Global reaches other Regions. Serverless follows the load. Clones copy in minutes.

9. Knowledge Check

Answer each question in your own words before you open the model answer. The questions were written for this course.

Question 1: Explain how Aurora differs from RDS in its storage and its high availability.

Maps to: Objectives 1 and 2 (Comprehension).

Aurora decouples compute from storage. The cluster has one shared storage volume that keeps 6 copies of the data in 3 Availability Zones, grows in 10 GB steps up to 128 TiB (256 TiB on recent engine versions), and heals itself. Replicas read the same storage, so a failover to a replica typically takes under 30 seconds, while an RDS Multi-AZ DB instance failover typically takes 60 to 120 seconds. RDS has coupled storage that goes up to 64 TiB, or 256 TiB for Oracle and SQL Server.

Question 2: Describe the Aurora endpoints and when you use each one.

Maps to: Objective 3 (Application).

The cluster endpoint always points to the writer and follows it after a failover, so it serves writes. The reader endpoint balances connections across the Aurora Replicas for read-only traffic. A custom endpoint groups chosen instances, for example larger replicas for analytics. An instance endpoint points to one instance for troubleshooting.

Question 3: Compare an Aurora Global Database with a cross-Region read replica, and say when DynamoDB global tables are the better answer.

Maps to: Objective 4 (Analysis).

A global database replicates at the storage layer with typically under one second of lag, has one writer Region and up to 10 read-only secondary Regions, and supports managed switchover and failover. A cross-Region read replica uses engine replication, has more lag, and is simpler. Both keep writes in one Region. For active-active writes in several Regions, DynamoDB global tables are the better answer.

Question 4: Explain how Aurora Serverless v2 scales and how to make it cost almost nothing when idle.

Maps to: Objective 5 (Comprehension).

You set a minimum and a maximum capacity in ACUs, where one ACU is about 2 GiB of memory, and Aurora adjusts the capacity in steps of 0.5 ACU between them, from 0 to 256 depending on the engine version. With a minimum of 0 ACUs, an idle instance pauses after the configured time and compute is not billed. A new connection resumes it. A proxy that keeps connections open blocks the pause.

Question 5: Choose the right recovery option: point-in-time restore, Backtrack, or cloning.

Maps to: Objective 6 (Application).

Point-in-time restore creates a new cluster at the chosen time within 1 to 35 days. Backtrack rewinds an Aurora MySQL cluster in place for up to 72 hours. Cloning makes a writable copy in minutes with copy-on-write, so it suits test and development copies. For long-term retention, use manual snapshots or AWS Backup.

Question 6: Design the Aurora setup for a production orders database that needs fast failover, read scaling, a copy in a second Region, and a predictable cost under heavy I/O.

Maps to: Objective 7 (Synthesis).

Create an encrypted Aurora cluster in private subnets with a writer and replicas in several Availability Zones, and turn on Aurora Auto Scaling for the replicas. Add an Aurora Global Database with a secondary Region for local reads and disaster recovery. Send writes to the cluster endpoint and reads to the reader endpoint. Add RDS Proxy for Lambda connections, and choose Aurora I/O-Optimized if the I/O charges are a large share of the bill, with Reserved Instances for the steady instances.

Question 7: Explain how an Aurora global database handles a planned move of the primary Region, an outage, and writes from a secondary Region, and name three limitations.

Maps to: Objective 4 (Analysis).

A switchover is a planned operation that moves the primary cluster to a secondary Region with no data loss. A failover recovers the global database after an outage in the primary Region by promoting a cluster in another Region. Both managed operations need the same major and minor engine versions. The Aurora Global Database writer endpoint always points to the primary cluster. With write forwarding, a secondary cluster sends the writes of its clients to the primary, so all writes still run in the primary Region. Limitations include no Backtrack, no Aurora Auto Scaling for the secondary clusters, no Secrets Manager integration, and no starting or stopping of the clusters one by one.

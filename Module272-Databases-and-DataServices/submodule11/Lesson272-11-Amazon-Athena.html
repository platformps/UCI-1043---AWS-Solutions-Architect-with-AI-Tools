1. Introduction to Amazon Athena

Problem Statement

FlashCart’s security team stores its AWS account activity logs and VPC flow logs in Amazon S3. After an alert about unusual sign-ins, the team must find out which users signed in to the console during the last two days. Loading the logs into a database first would take days, and the team does not want to run servers for a question that it asks a few times a month.

Your challenge:

  • Choose a service that runs SQL directly on the files in Amazon S3.
  • Describe how the service knows the columns and data types of the files.
  • Name where the results of each query are stored.

1.1 Introduction to Amazon Athena

  • Amazon Athena is a serverless, interactive query service that lets you analyze data directly in Amazon S3 by using standard SQL.
  • Serverless means that there is no infrastructure to set up or manage. You run a query, and Athena scales automatically and runs the query in parallel.
  • The SQL engine is based on the open source Trino and Presto engines, which are built for fast, interactive, ad hoc analysis.
  • The data stays in Amazon S3, and Athena reads it in place. You do not need a loading step or an ETL job before you query.
  • You pay for the queries that you run (2.1).
  • Athena can also run Apache Spark code in a Spark workgroup (1.6).

1.2 How Athena Works

  1. The data files are stored in Amazon S3.
  2. You create a table that describes the files: the columns, the data types, and the Amazon S3 location. The table definition is metadata in the AWS Glue Data Catalog, or you create it with a DDL statement in Athena.
  3. You write a SQL query in the Athena console, or you send it through the API, the CLI, an SDK, or a JDBC or ODBC driver.
  4. Athena applies the table definition when it reads the files. This is called schema-on-read: the files are not changed.
  5. The results appear in the console, and Athena writes them to an Amazon S3 location that you choose.
  • Athena works with AWS Glue. A Glue crawler can discover the schema of your files and fill the Data Catalog with the table and partition definitions (Lesson 272.10).
  • A Glue ETL job can convert the data to a columnar format, which makes Athena queries faster and cheaper (2.2).

1.3 Supported Data Formats

  • Athena also reads other formats, such as Amazon Ion, and the log formats of AWS services, such as AWS CloudTrail (lesson 274.3).

1.4 Use Cases and Querying AWS Logs

  • Ad hoc SQL queries for business intelligence and analytics, such as sales by product.
  • Queries on the logs of AWS services that write to Amazon S3: AWS CloudTrail, Application Load Balancer access logs, Amazon S3 access logs, AWS Network Firewall logs, and VPC flow logs.
  • Interactive exploration of a data lake before you decide on a bigger pipeline.

1.5 Example Query

The security team uses this query on a table that it created over the CloudTrail logs. It lists the console sign-ins between two dates:

SELECT useridentity.username, sourceipaddress,
       eventtime, additionaleventdata
FROM your_athena_tablename
WHERE eventname = 'ConsoleLogin'
  AND eventtime >= '2026-01-15T00:00:00Z'
  AND eventtime < '2026-01-17T00:00:00Z';
  • The query returns the user name, the source IP address, the event time, and the extra event data of every console sign-in in the two-day window.
  • your_athena_tablename stands for the table that you create over the CloudTrail logs.
  • The filter on the event time limits the data that the query needs to read. If the table is partitioned by date, the query scans less data (2.4).

1.6 Athena Engines: SQL and Apache Spark

  • The workgroup that you use decides the engine. A SQL workgroup runs SQL queries. A Spark workgroup runs Apache Spark code.
  • SQL queries are billed by the data that they scan, or by reserved compute capacity. Apache Spark code is billed by the compute that it uses (2.1).
  • This lesson focuses on SQL, which is the main topic of the exam.

1.7 Running Queries and Integrations

  • Run queries from the Athena console, the API, the AWS CLI, an AWS SDK, or BI tools that use the Athena JDBC and ODBC drivers.
  • AWS Quick (lesson 272.15) can use Athena as a data source to build dashboards.
  • Athena integrates with the AWS Glue Data Catalog, and AWS Lake Formation (lesson 272.12) can add fine-grained access control (a later lesson).
  • A SQL query in Athena can call an Amazon SageMaker model for machine learning inference.

2. Performance and Cost

Problem Statement

The FlashCart analytics team now queries three years of CSV sales files with Athena. Every query reads every column of every file, the queries are slow, and the monthly Athena bill keeps growing. Most of the queries ask for one product in one month and use only three of the forty columns.

The finance team also asks for a way to limit how much each team can spend on Athena queries.

Your challenge:

  • Explain what Athena charges for.
  • Reduce the amount of data that each query scans.
  • Control the cost for each team.

2.1 Athena Pricing

Prices change often and differ by Region. Always check the current rates on the Amazon Athena pricing page.

  • SQL queries are billed by the amount of data that they scan. The less data a query scans, the less it costs.
  • SQL queries with Capacity Reservations use reserved compute capacity, measured in DPUs, and they are billed per DPU-hour. Use them for predictable, high-volume workloads.
  • Apache Spark code in a Spark workgroup is billed at an hourly rate for the compute that it uses.
  • Athena queries data directly in Amazon S3. Standard Amazon S3 charges for storage, requests, and data transfer apply separately.

2.2 Columnar Formats

  • Parquet and ORC store data by column. A query that needs three columns reads only those three, so it scans far less data.
  • Columnar files are also compressed, so they are smaller than the same data in CSV.
  • Use an AWS Glue ETL job to convert the data to Parquet or ORC (Lesson 272.10).

2.3 Compression and File Size

  • Compress the data to reduce the amount that Athena retrieves. The supported codecs depend on the file format. They include BZIP2, GZIP, LZ4, Snappy, ZLIB, and ZSTD. The ZIP format is not supported.
  • For CSV, TSV, and JSON files, Athena finds the compression type from the file extension, such as .gz. Use a lowercase extension.
  • Use larger files, for example more than 128 MB, to reduce the overhead of opening many small files. This is guidance from the course slides.

2.4 Partitioning

  • Partitioning divides a table into parts, such as one folder for each month. A query that filters on the partition column reads only the matching folders.
  • Athena uses Hive-style folder names in the form column=value. An example is s3://athena-examples/flight/parquet/year=1991/month=1/day=1/.
  • Partition by the columns that your queries filter on most often, such as the date.
  • Partition projection lets Athena calculate the partitions instead of looking them up in the catalog, which helps with tables that have many partitions.

The next table shows the example from the course slides. Each file or folder holds 1 GB, and the query asks for product X in November 2025:

LayoutWhat Athena readsData scanned
No partitions: one file for each product and month.All six files, because the file names cannot be used to skip files.6 GB

2.5 Workgroups

  • A workgroup separates users, teams, applications, or workloads in Athena.
  • A per-query data usage limit cancels any query in the workgroup that scans more than the limit. A canceled query is still charged for the data that it scanned.
  • A workgroup data usage alert sends an Amazon SNS (lesson 273.3) notification when the queries in the workgroup scan more than a threshold in an hour or a day. It does not cancel the queries.
  • A workgroup can enforce settings such as the query results location and encryption.
  • You can track the cost of each workgroup, with cost allocation tags and workgroup query metrics in Amazon CloudWatch (lesson 274.1), so each team sees its own spending.
  • The workgroup also decides the engine, SQL or Apache Spark (1.6).

2.6 Tables From Query Results

  • A CTAS query, short for CREATE TABLE AS SELECT, writes the results of a query to a new table. You can choose a new format, such as Parquet.
  • Use CTAS to convert a CSV table to Parquet, or to keep a smaller table with only the columns and rows that you need.
  • Avoid SELECT * on large tables. It reads every column.

Exam Trap

Remember these points:

  • Athena on-demand cost depends on the data scanned, not on how long a query runs.
  • To cut cost, use Parquet or ORC, compression, and partitioning. A Glue job can do the conversion.
  • Use a workgroup to set data scan limits and to track the cost of each team.
  • Capacity Reservations suit predictable, high-volume workloads. On-demand pricing suits occasional queries.

Memory Hook

Scan less, pay less. Columns, folders, and small bytes.

3. Federated Query and Security

Problem Statement

FlashCart keeps its orders as files in Amazon S3, its customer profiles in Amazon DynamoDB, and its loyalty data in an Amazon Aurora database. An analyst wants to join the three in one SQL query without copying the data into the data lake.

The security team also wants to control who can query the logs, and it wants the query results to be encrypted.

Your challenge:

  • Join data across data stores without moving it.
  • Decide where the connectors run.
  • Protect the data and the query results.

3.1 Athena Federated Query

  • Federated query lets Athena run SQL on data that is not in Amazon S3, and join it with data that is.
  • Athena uses data source connectors to reach the other data stores. A connector translates between Athena and the data source.
  • The connectors run as AWS Lambda (lesson 273.1) functions.
  • AWS provides connectors for data stores such as Amazon DynamoDB, Amazon Redshift, Amazon CloudWatch, Amazon DocumentDB, and relational databases such as MySQL and PostgreSQL. You can also build a connector for a custom data source, including an on-premises database.
  • The query results are written to Amazon S3.

3.2 Security

  • Control access to the data with IAM policies, access control lists, and Amazon S3 bucket policies.
  • Athena can query encrypted data in Amazon S3, and it can write the results back to Amazon S3 encrypted. Both server-side encryption and client-side encryption are supported.
  • Give each team its own workgroup with its own query results location, and restrict access to each location with IAM and bucket policies.
  • AWS Lake Formation can add fine-grained access control, such as table, column, and row permissions, on top of the Data Catalog (a later lesson).

Exam Trap

Remember these points:

  • Federated query uses connectors that run on AWS Lambda. The data stays in its source, and the results go to Amazon S3.
  • Athena does not copy data for a federated query. It does not replace an ETL job when the data must be moved and transformed for repeated use.
  • Query results are stored in Amazon S3. Encrypt them, and restrict access to the results bucket.

Memory Hook

Connectors on Lambda reach everywhere. Results land in S3.

4.2 When to Use Each Service

4.2.1 Use Amazon Athena When

  • You need ad hoc or occasional SQL queries on data that is already in Amazon S3.
  • You want no servers to manage and no loading step.
  • You query service logs, such as CloudTrail, load balancer, and VPC flow logs.
  • You want to pay only for the data that your queries scan.

4.2.2 Use Another Service When

  • Amazon Redshift: you run complex, repeated queries and joins on a large warehouse, and many users query it at the same time.
  • AWS Glue: you must transform the data, convert formats, or run an ETL job.
  • Amazon EMR: you need Spark, Hive, or other big data frameworks with control of the cluster.

4.4 Lesson Summary

This lesson covered the following points:

  • Amazon Athena is a serverless, interactive query service that runs standard SQL on data in Amazon S3. Its engine is based on Trino and Presto.
  • A table definition in the AWS Glue Data Catalog describes the files, and Athena applies it when it reads them. The results are written to Amazon S3.
  • Athena supports CSV, JSON, Avro, Parquet, and ORC. It is often used to query CloudTrail, load balancer, S3 access, and VPC flow logs.
  • Athena SQL queries are billed by the data that they scan. Parquet or ORC, compression, larger files, and partitioning reduce the data scanned. Workgroups limit and track the cost of each team.
  • Athena Federated Query uses connectors that run on AWS Lambda to query other data stores, and the results go to Amazon S3. Access is controlled with IAM policies and bucket policies, and the data and results can be encrypted.
  • Choose Athena for ad hoc SQL on Amazon S3, Redshift for a data warehouse, Glue for ETL, and EMR for big data frameworks.

5. Knowledge Check

Answer each question in your own words before you open the model answer. The questions were written for this course.

Question 1: Explain what Amazon Athena is, and describe how it runs a SQL query on files in Amazon S3.

Maps to: Objectives 1 and 2 (Comprehension).

Athena is a serverless, interactive query service that runs standard SQL on data in Amazon S3. Its engine is based on Trino and Presto. A table definition, stored in the AWS Glue Data Catalog or created with a DDL statement, describes the columns, data types, and location of the files. When you run a query, Athena applies the table definition as it reads the files in place, and it writes the results to an Amazon S3 location that you choose. There are no servers to manage and no loading step.

Question 2: Name the data formats that Athena supports, and say which formats you recommend and why.

Maps to: Objective 1 (Knowledge).

Athena supports CSV, JSON, Avro, Parquet, and ORC. Parquet and ORC are recommended. They store data by column, so a query reads only the columns that it needs, and they are compressed, so the files are smaller. Both effects reduce the data that Athena scans, which lowers the cost and speeds up the query.

Question 3: The FlashCart analysts query one product in one month, and the bill is too high. Explain how pricing, file format, and partitioning affect the cost, and recommend changes.

Maps to: Objective 3 (Application).

Athena SQL queries are billed by the amount of data that they scan, so the goal is to scan less. Convert the CSV files to Parquet or ORC so that a query reads only the columns that it needs. Compress the files and use larger files to reduce the overhead. Partition the table by the columns that the queries filter on, such as product, year, and month, so that a query reads only the matching folders. Use workgroups to set data scan limits and to track the cost of each team. Check the pricing page for the current rates.

Question 4: Describe how an Athena federated query works and when to use one.

Maps to: Objective 5 (Comprehension).

A federated query lets Athena run SQL on data in other data stores, such as Amazon DynamoDB, Amazon Redshift, Amazon CloudWatch, and relational databases, and join it with data in Amazon S3. Athena uses data source connectors that run as AWS Lambda functions, and the query results are written to Amazon S3. Use a federated query for ad hoc joins across sources without copying the data. If the data must be moved and transformed for repeated use, build an ETL job instead.

Question 5: Differentiate Amazon Athena from Amazon Redshift, AWS Glue, and Amazon EMR, and name one requirement that points to each.

Maps to: Objectives 6 and 7 (Analysis).

Athena runs ad hoc SQL on data in Amazon S3, with no servers and no loading step. Redshift is a data warehouse where the data is loaded, and it suits complex, repeated queries with many users. Glue is a serverless ETL and catalog service that transforms and moves data. EMR runs big data frameworks such as Spark and Hive on clusters or serverless capacity. A requirement for occasional SQL on S3 logs points to Athena. A requirement for a large warehouse with repeated joins points to Redshift. A requirement to convert CSV to Parquet points to Glue. A requirement to migrate Hadoop jobs points to EMR.

Question 6: Design a query solution for FlashCart that lets the security team investigate CloudTrail logs, lets the analysts query sales data, and keeps the cost under control.

Maps to: Objective 8 (Synthesis).

Keep the CloudTrail logs and the sales files in an Amazon S3 data lake. Use a Glue crawler to create the table definitions in the Glue Data Catalog. Use a Glue ETL job to convert the sales files to Parquet, partitioned by date, and compress them. Give the security team and the analytics team separate Athena workgroups, each with its own query results location, a data scan limit, and cost tracking. Control access with IAM policies and bucket policies, and encrypt the data and the results. Use a federated query for the occasional join with a DynamoDB table, and AWS Quick for dashboards. If the query volume becomes high and predictable, consider Capacity Reservations. Check the pricing page for current costs.

1. Introduction to Amazon MSK

Problem Statement

FlashCart’s website sends an event every time a shopper views a product or adds an item to a cart, and the warehouse scanners send a message for every package. The engineering team already runs Apache Kafka on a few Amazon EC2 instances, and several applications read from it.

Patching the brokers, replacing failed instances, and growing the disks use up the team’s weekends. The team wants to keep its Kafka producers, consumers, and tools exactly as they are.

Your challenge:

  • Choose a service that runs Apache Kafka as a managed service.
  • Explain what stays the same for the applications.
  • Name what AWS manages for the team.

1.1 Introduction to Amazon MSK

  • Amazon Managed Streaming for Apache Kafka (Amazon MSK) is a fully managed service that lets you build and run applications that use Apache Kafka to process streaming data.
  • It runs open-source versions of Apache Kafka. Existing applications, tools, and plugins from the Kafka community work without changes to the application code.
  • MSK creates and manages the Kafka infrastructure for you. It creates the brokers and the metadata nodes, detects the common failures, replaces unhealthy brokers, and handles the hardware maintenance.
  • It is an alternative to Amazon Kinesis Data Streams (lesson 273.6) for real-time ingestion of streaming data and for messaging between applications.
  • You use the AWS Management Console, the AWS CLI, or the AWS SDK to create and manage clusters. You use Apache Kafka clients to produce and consume data.

1.2 Apache Kafka Concepts

  • A producer is an application that writes records to a topic.
  • A topic is a named stream of records, such as orders. A topic is split into partitions.
  • A partition is an ordered log of records. Kafka keeps the records of one partition in order. It spreads the partitions of a topic across brokers, and it replicates them on other brokers.
  • A broker is a server in the Kafka cluster. It stores partitions and serves the producers and the consumers.
  • A consumer reads records from a topic. Several consumers can form a consumer group, and each consumer reads at its own rate, much like a message queue.

1.3 How Amazon MSK Works

ComponentWhat it does
Broker nodesYou choose the number of brokers in each Availability Zone, with a minimum of one broker per zone. Each zone has its own VPC subnet.
ZooKeeper nodes or KRaft controllersThey hold the cluster metadata. MSK creates them for you. KRaft controllers are included at no additional cost.
Producers, consumers, and topic creatorsYour code or your tools. They use the Apache Kafka data-plane operations to create topics and to produce and consume data.
Cluster operationsThe control-plane operations: create, update, and delete clusters, view their properties, and change the number and type of brokers.
  • When MSK detects a broker failure, it mitigates the failure or replaces the unhealthy broker with a new one. It reuses the storage of the old broker where possible, and the producers and consumers keep using the same broker IP addresses.

1.4 MSK in the Streaming Pipeline

  • MSK sits in the ingestion stage, next to Amazon Kinesis Data Streams. Sources include website click streams, IoT devices, banking transactions, and metrics and logs.
  • The consumers that process the stream include Amazon Managed Service for Apache Flink, AWS Glue streaming ETL jobs, AWS Lambda (lesson 273.1), and applications on Amazon EC2, Amazon ECS (lesson 273.5), and Amazon EKS.
  • The results go to destinations such as Amazon S3, Amazon Redshift, and Amazon OpenSearch Service (lesson 272.14).

Exam Trap

Remember these points:

  • Amazon MSK is managed Apache Kafka. If the question says that applications must keep their Kafka clients and tools, the answer is MSK.
  • MSK uses topics and partitions. Amazon Kinesis Data Streams uses streams and shards.
  • The producers and consumers are your code or other AWS services. MSK manages the brokers and the metadata nodes.
  • MSK clusters run in your VPC, with one subnet in each Availability Zone.

2. Cluster Types and Availability

Problem Statement

FlashCart’s website traffic is steady, but the marketing campaigns create sudden spikes. The data science team also wants a small Kafka cluster for experiments, and it does not want to size one.

The operations team wants the data to survive the loss of a zone, and it wants to copy topics to a second Region for disaster recovery.

Your challenge:

  • Choose a cluster type for the steady workload and for the spiky workload.
  • Make the cluster survive the loss of a zone.
  • Copy the data to another Region.

2.1 MSK Provisioned: Standard and Express Brokers

  • MSK Provisioned clusters have broker instances that you choose. You pick the broker type, the instance size, and the number of brokers in each Availability Zone.
  • MSK Provisioned offers two broker types, Standard brokers and Express brokers.
  • Standard brokers can also use tiered storage, a low-cost tier for older data. It has its own storage and retrieval charges (3.6).
FeatureStandard brokersExpress brokers
ConfigurationThe most flexible. You can use custom configurations.MSK protects settings that can hurt availability and durability, and it simplifies the configuration.
StorageYou provision the storage, and you can optionally provision storage throughput.You do not provision or manage storage. MSK manages the storage layer.
ReplicationYou can choose a custom replication strategy for each topic.MSK always replicates the data across three Availability Zones.
Designed forWorkloads that need control of the configuration and the storage.Up to 3 times the throughput per broker and up to 20 times faster scaling than Standard brokers, depending on the instance size.
Availability ZonesTwo or three zones. Three is the default and the recommended setup.Three zones only.

2.2 MSK Serverless

  • MSK Serverless is a cluster type that runs Apache Kafka without you managing or scaling the cluster capacity.
  • It automatically provisions and scales capacity and manages the partitions in your topics, so you do not need to right-size the cluster.
  • It is fully compatible with Apache Kafka, so you can use any compatible client to produce and consume data. It also works with AWS PrivateLink, AWS Glue Schema Registry, Amazon Managed Service for Apache Flink, and AWS Lambda.
  • MSK Serverless requires IAM access control for every cluster. Apache Kafka access control lists are not supported (3.2).
  • Use it when your applications need streaming capacity on demand that scales up and down, or for a small cluster that you do not want to size.
  • MSK Serverless is available in selected Regions, and it has service quotas. Check the Amazon MSK documentation to confirm that your workload fits.

2.3 Choosing a Cluster Type

Cluster typeCapacityBest for
Provisioned, Standard brokersYou size the brokers and the storage.Steady workloads that need full control of the configuration.
Provisioned, Express brokersYou size the brokers. MSK manages the storage.High throughput and quick scaling, with less to manage.
ServerlessMSK manages the capacity.Variable or unpredictable workloads, and small clusters.

2.4 High Availability

  • You choose two or three Availability Zones for Standard brokers, and three for Express brokers. Each zone has at least one broker. AWS recommends three zones for high availability, and it is the default.
  • MSK uses Apache Kafka leader-follower replication to copy the data between brokers. A broker in another zone holds a copy of each partition.
  • With Standard brokers, three zones and one broker in each zone give a cluster of three brokers. Express brokers are only available in a three-zone setup.
  • MSK detects the most common failures and recovers from them automatically, so producers and consumers can continue with minimal impact.

2.5 MSK Connect

  • Kafka Connect is an open-source part of Apache Kafka. It connects Kafka with external systems, such as databases, key-value stores, search indexes, and file systems.
  • MSK Connect runs Kafka Connect connectors as a managed feature. Use it to stream data to and from your Kafka cluster without building the integration yourself.

2.6 MSK Replicator and Schema Registry

  • MSK Replicator replicates data reliably across MSK Provisioned clusters, in the same Region or in different Regions. Use it for disaster recovery and for moving data between clusters.
  • Apache Kafka clients can use the AWS Glue Schema Registry, a serverless feature of AWS Glue, at no additional charge. It manages and enforces the schemas of the records.

Exam Trap

Remember these points:

  • MSK Serverless removes capacity management. Express brokers remove storage management and add throughput. Standard brokers give the most control.
  • For a copy of Kafka data in another Region, use MSK Replicator. For a Kafka integration with databases and other systems, use MSK Connect.
  • The broker count is per Availability Zone: at least one broker in each zone.

Memory Hook

Standard to tune, Express to fly, Serverless to forget.

3. Security, Monitoring, and Pricing

Problem Statement

FlashCart’s Kafka clients include applications on Amazon EC2, serverless functions, and a partner system. The security team requires that the data is encrypted, that only approved clients can read each topic, and that the cluster cannot be reached from the internet.

The finance team also asks which costs it should expect from the cluster.

Your challenge:

  • Control who can connect and what each client can do.
  • Encrypt the data in transit and at rest.
  • Name the cost dimensions of each cluster type.

3.1 Networking

  • An MSK cluster runs in your VPC, with a subnet in each Availability Zone.
  • Security groups on the cluster’s network interfaces control who can connect and communicate with the cluster.
  • Public access to the brokers is a setting that you can turn off. Keep it off, and keep the cluster in private subnets.
  • Clients in other VPCs or on premises can connect through VPC peering, AWS Transit Gateway, or the multi-VPC private connectivity of MSK.

3.2 Authentication

MethodHow it works
IAM access controlClients sign in with IAM roles or users, and IAM policies authorize the Kafka actions. It has no additional cost, and it is the simplest option when your clients run on AWS. MSK Serverless requires it.
SASL/SCRAMClients use a user name and a password that are stored as secrets, in AWS Secrets Manager.
Mutual TLSClients present a certificate. You need an AWS Private CA, in the same account as the cluster or in another account. MSK does not support certificate revocation lists, so use Kafka ACLs and security groups to block a compromised certificate.
UnauthenticatedMSK also has an option for unauthenticated access. Use it only when the network controls are enough.

3.3 Authorization

  • With IAM access control, one IAM policy controls both the authentication and the Kafka actions, such as listing topics or writing to a topic. You do not manage Kafka access control lists.
  • With SASL/SCRAM and mutual TLS, you use Apache Kafka access control lists to control what each client can do.
  • IAM access control also records Kafka resource changes, such as creating a topic or adding partitions, in AWS CloudTrail (lesson 274.3).

3.4 Encryption

  • In transit: MSK supports TLS between the clients and the brokers, and between the brokers. The client-broker setting can be TLS only, TLS and plaintext, or plaintext. Choose TLS only for sensitive data.
  • At rest: MSK encrypts the data on the broker volumes with AWS KMS. If you do not specify a key, MSK creates one for you, and you can choose your own key.

3.5 Monitoring

  • MSK publishes cluster and broker metrics to Amazon CloudWatch (lesson 274.1).
  • You can deliver the broker logs to Amazon CloudWatch Logs (lesson 274.2), Amazon S3, or Amazon Data Firehose. By default, the logs are at the INFO level. MSK API calls are logged in AWS CloudTrail.
  • Watch the storage use, the broker CPU use, and the lag of the consumers, which shows how far a consumer is behind the newest records.

3.6 MSK Pricing

Prices change often and differ by Region. Check the current rates on the Amazon MSK pricing page.

Cluster typeWhat you pay for
Provisioned, Standard brokersBroker instance hours, the storage that you provision, optional provisioned storage throughput, the low-cost storage tier and its retrieval if you use it, and data transfer.
Provisioned, Express brokersBroker instance usage, the storage that you use, a per-GB rate for the data that you write, and data transfer.
ServerlessAn hourly rate for the cluster, an hourly rate for each partition, a per-GB rate for the data that producers write and consumers read, and the storage that you use.
  • MSK Connect is billed by connector worker hours. MSK Replicator is billed by the hour for each Replicator and by the GB that it processes, plus cross-Region data transfer. Private connectivity, powered by AWS PrivateLink, has an hourly charge and a per-GB charge.
  • You are not charged for data transfer for replication between brokers, or between the metadata nodes and the brokers. Standard AWS data transfer charges apply to data that goes in and out of the cluster.

Exam Trap

Remember these points:

  • IAM access control is the answer when clients should use IAM roles and policies and nobody wants to manage credentials or Kafka ACLs.
  • SASL/SCRAM uses user names and passwords in Secrets Manager. Mutual TLS uses client certificates.
  • MSK Serverless requires IAM access control. It does not support Kafka ACLs.
  • MSK encrypts data at rest with AWS KMS, and in transit with TLS. Plaintext is an option, so choose TLS only for sensitive data.
  • Keep the cluster private: private subnets, security groups, and public access turned off.

4. Comparison & Scenarios

4.1 MSK and Kinesis Data Streams Compared

4.2 When to Use Each Service

4.2.1 Use Amazon MSK When

  • Applications already use Apache Kafka, and you want to keep the clients, the tools, and the code.
  • You want the open-source Kafka ecosystem, such as Kafka Connect.
  • You want portability: the same Kafka APIs on AWS and elsewhere.

4.2.2 Use Another Service When

  • Amazon Kinesis Data Streams: you are building a new application on AWS and you do not need Kafka compatibility.
  • Amazon SQS or Amazon SNS (lesson 273.3): you need a simple message queue or notifications, not a replayable stream.
  • Amazon Managed Service for Apache Flink or AWS Glue: you need to process the stream. MSK ingests it.

4.4 Lesson Summary

This lesson covered the following points:

  • Amazon MSK is a fully managed service that runs open-source Apache Kafka. Applications keep their Kafka clients and tools, and AWS manages the brokers and the metadata nodes.
  • Kafka stores records in topics. Each topic has partitions that spread across brokers and are replicated. Producers write, and consumer groups read at their own rate.
  • MSK Provisioned has Standard brokers for control and Express brokers for throughput and managed storage. MSK Serverless removes capacity management.
  • MSK spreads a cluster across up to three Availability Zones, recovers from common failures, and offers MSK Connect for integrations and MSK Replicator for copying data between clusters.
  • Security uses a VPC with security groups, IAM access control, SASL/SCRAM, or mutual TLS for authentication, TLS in transit, and AWS KMS at rest.
  • Choose MSK for Kafka workloads, and Kinesis Data Streams for new AWS-native streaming applications.

5. Knowledge Check

Answer each question in your own words before you open the model answer. The questions were written for this course.

Question 1: Explain what Amazon MSK is, and what stays the same for the applications that already use Apache Kafka.

Maps to: Objectives 1 and 2 (Comprehension).

Amazon MSK is a fully managed service that runs open-source Apache Kafka. AWS creates and manages the brokers and the metadata nodes, replaces unhealthy brokers, and deploys hardware patches. Because MSK runs open-source Kafka, the existing producers, consumers, tools, and plugins keep working without changes to the application code. The team manages the topics and the applications, and not the servers.

Question 2: Describe the Apache Kafka concepts of producer, topic, partition, broker, and consumer group, and show how they fit together.

Maps to: Objective 1 (Comprehension).

A producer writes records to a topic. The topic is split into partitions, and each partition is an ordered log of records. Kafka spreads the partitions across brokers, which are the servers of the cluster, and replicates them on other brokers. Consumers read the records, and consumers in a consumer group share the partitions. Each consumer reads at its own rate.

Question 3: Compare MSK Provisioned with Standard brokers, MSK Provisioned with Express brokers, and MSK Serverless, and say when you would choose each one.

Maps to: Objective 3 (Analysis).

With Standard brokers, you choose the broker size, you provision the storage, and you can use custom configurations. Choose them for steady workloads that need control. With Express brokers, you choose the broker size, MSK manages the storage and always replicates across three Availability Zones, and you get higher throughput and faster scaling. Choose them for demanding workloads with less to manage. With MSK Serverless, MSK manages the capacity and scales the compute and the storage. Choose it for variable workloads and small clusters.

Question 4: Explain how an MSK cluster stays available when a zone fails, and name the features for copying data to another Region and for connecting Kafka to databases.

Maps to: Objective 4 (Comprehension).

The cluster has brokers in up to three Availability Zones, and Kafka leader-follower replication keeps copies of each partition on brokers in other zones. MSK detects common failures and replaces an unhealthy broker, and the clients keep using the same broker addresses. MSK Replicator replicates data between MSK Provisioned clusters in the same or different Regions. MSK Connect runs Kafka Connect connectors to stream data to and from databases and other systems.

Question 5: FlashCart clients run on Amazon EC2 and AWS Lambda. Describe how you would secure the MSK cluster.

Maps to: Objective 5 (Application).

Place the cluster in private subnets of a VPC, turn off public access, and use security groups to allow only the client networks. Use IAM access control so that the clients authenticate with IAM roles, and write IAM policies that allow only the topics and actions that each client needs. Set the client-broker encryption to TLS only, and use AWS KMS for encryption at rest. Send the broker logs to Amazon CloudWatch Logs, and watch the metrics in Amazon CloudWatch.

Question 6: Differentiate Amazon MSK from Amazon Kinesis Data Streams, and name one requirement that points to each.

Maps to: Objectives 6 and 7 (Analysis).

MSK is managed Apache Kafka, with Kafka APIs, topics, and partitions. Kinesis Data Streams is an AWS-native service with its own APIs, streams, and shards. MSK supports IAM, SASL/SCRAM, and mutual TLS for authentication, and Kinesis uses IAM. A requirement to keep existing Kafka producers, consumers, and tools points to MSK. A requirement for a new streaming application that is built only on AWS, with no Kafka compatibility needed, points to Kinesis Data Streams.

Question 7: Design a streaming ingestion solution for FlashCart that keeps its Kafka applications, processes the events in real time, and stores them for analytics.

Maps to: Objective 8 (Synthesis).

Create an MSK cluster across three Availability Zones. Use MSK Serverless or Express brokers if the traffic spikes, or Standard brokers if the team needs control. Keep the existing Kafka producers and consumers, and secure them with IAM access control, TLS, and AWS KMS. Process the events with Amazon Managed Service for Apache Flink, an AWS Glue streaming ETL job, or AWS Lambda, and write the results to Amazon S3 for analysis with the services in this module. Use MSK Replicator to copy the topics to a second Region for disaster recovery. Check the pricing page for the current costs.

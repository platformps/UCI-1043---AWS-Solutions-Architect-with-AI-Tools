Introduction

Some applications write enormous volumes of rows, such as telemetry, messages, or user activity, and read them back by a known key. Apache Cassandra is a popular open-source database for that pattern, but a Cassandra cluster is demanding to operate. Amazon Keyspaces keeps the Cassandra interface and removes the operations. An architect has to recognize the Cassandra keywords, design the keys around the queries, and tell Keyspaces apart from DynamoDB and DocumentDB.

This lesson assumes that you know the database groups from Lesson 272.1. It follows FlashCart Inc. through the Problem Statement of each tab.

1. What Amazon Keyspaces Is

Problem Statement

FlashCart tracks its delivery trucks. Each truck sends a reading every ten seconds, and the fleet team needs very fast writes and reads by truck and time, at a large scale. The data team already knows Apache Cassandra and its query language, but nobody wants to run and patch a Cassandra cluster.

1.1 What Apache Cassandra Is

  • Apache Cassandra is an open-source, distributed wide-column NoSQL database. It stores rows in tables, but each row is found by a partition key, and different rows can have different columns.
  • It is built for very high write throughput, linear scaling, and no single point of failure.
  • Applications use the Cassandra Query Language (CQL), which looks like SQL but has no joins.
  • Running it yourself means managing nodes, replication, repairs, and upgrades.

1.2 What Amazon Keyspaces Is

  • Amazon Keyspaces (for Apache Cassandra) is a scalable, highly available, managed, Cassandra-compatible database service.
  • It is serverless: you do not provision, patch, or manage servers, and you do not install or maintain software.
  • It uses the CQL API, so you run your existing Cassandra workloads with the same Cassandra application code, drivers, and developer tools that you use today.
  • You can create keyspaces and tables with a few clicks in the AWS Management Console, or with a few lines of code, without deploying any infrastructure or installing software.
  • Tables scale up and down automatically with the traffic of the application.
  • It gives single-digit millisecond latency at any scale, for thousands of requests per second, with virtually unlimited throughput and storage.
  • It is serverless, so you pay only for the resources that you use.
  • Data is replicated three times across multiple Availability Zones.

1.3 When to Use It

  • An application that already uses Cassandra and CQL, and that should move to a managed service with few code changes.
  • Large volumes of writes and reads by a known key: device and sensor data, telemetry, time-series data, messaging, and user activity.
  • Not a fit: joins, ad hoc analytics, or a workload that does not use Cassandra, where DynamoDB is usually simpler.

1.4 How Keyspaces Compares With Apache Cassandra

1.5 How Keyspaces Appears to the Client

  • You connect through a public AWS service endpoint or through a private interface VPC endpoint, which uses AWS PrivateLink in your VPC.
  • Through a public endpoint, Keyspaces appears to the client as a nine-node Apache Cassandra 3.11.2 cluster. Through an interface VPC endpoint, it appears as a three-node cluster.
  • In both cases Keyspaces provides virtually unlimited throughput and storage. It maps the visible nodes to load balancers that route your queries to one of the many underlying storage partitions.
  • A partition is an allocation of storage for a table, backed by solid state drives (SSDs). Keyspaces replicates the data automatically across several Availability Zones in the Region.

1.7 Functional Differences and Limits

  • Keyspaces uses IAM for authentication and authorization, so it does not support the security configuration commands of Apache Cassandra, such as creating roles in CQL.
  • Lightweight transactions (compare-and-set on INSERT, UPDATE, and DELETE) are fully supported, with no performance penalty.
  • A logged batch supports up to 100 commands.
  • The maximum row size is 1 MB, not counting static column data.
  • The default partitioner is the Cassandra-compatible Murmur3Partitioner.
  • Some Apache Cassandra features work differently or are not supported. Check the AWS page "Functional differences: Amazon Keyspaces vs. Apache Cassandra" before you migrate, especially if the application uses indexes, materialized views, or special data types.

2. Data Model and Consistency

Problem Statement

The FlashCart data team now designs the truck readings table. It must answer one question very fast: "give me the readings of one truck in a time range". The team has to choose the keys, and it has to understand what consistency Keyspaces gives.

2.1 Keyspaces, Tables, and Keys

  • A keyspace is a namespace that groups tables. A table holds the rows.
  • The partition key decides where a row is stored, so queries by the partition key are fast.
  • Clustering columns sort the rows inside a partition, so a time range is a cheap query.
  • Design the table around the queries. There are no joins, so you often copy data into more than one table.
  • Spread the reads and the writes evenly across partitions for the best performance.

2.2 CQL Example

CREATE TABLE truck_fleet.truck_readings (
  truck_id text,
  reading_time timestamp,
  speed int,
  engine_temp int,
  PRIMARY KEY (truck_id, reading_time)
);
  • In PRIMARY KEY (truck_id, reading_time), the first column is the partition key and the next column is the clustering column.
  • A keyspace in one Region uses the SingleRegionStrategy replication setting.

2.3 Consistency

  • All writes use LOCAL_QUORUM consistency, for durability.
  • Reads can use LOCAL_QUORUM, which is strongly consistent inside the Region, or LOCAL_ONE or ONE, which is eventually consistent and costs less.
  • The unit of a read is 4 KB at LOCAL_QUORUM, and the unit of a write is 1 KB per row.

2.4 Partition Key Design and Throttling

  • Keyspaces spreads the data across storage partitions by the partition key, as Cassandra does. A single partition key value can handle only a limited amount of traffic.
  • Choose a partition key with many distinct values that the requests use evenly, such as deviceId or userId, so the load spreads across partitions.
  • Avoid a key with few values, or a key that sends most writes to one value at the same time, such as the current date. That creates a hot partition, and Keyspaces throttles the requests above its limit, even when the table has unused capacity.
  • Use clustering columns to sort the rows inside a partition, for example by time, and keep each partition to a size that your queries can read efficiently.
  • To spread a very busy key, add a bucket to the partition key, for example deviceId plus the day or a shard number from 1 to 10.
  • Watch the CloudWatch (lesson 274.1) throttling metrics (4.5), and retry throttled requests with exponential backoff.
Partition keyGood choice?Why
(device_id)YesMany devices, each with a modest number of readings.
(reading_date)NoEvery device writes to the same key on the same day.
(device_id, reading_date)YesA compound key spreads the load and keeps each partition to one day of data.

3. Capacity, Availability, and TTL

Problem Statement

The FlashCart truck fleet doubles during the holiday season, and the team wants the table to keep up without a capacity project. It also wants the data to stay available if a zone or a whole Region has a problem, and old readings should delete themselves.

3.1 Capacity Modes

On-demand capacity modeProvisioned capacity mode
How it worksScales automatically. You pay per read and write request.You set the read and write capacity units for the table, with optional auto scaling.
Best forUnpredictable or spiky traffic, and new tables.Predictable traffic, with a lower cost.
UnitRead request unit (RRU) and write request unit (WRU).Read capacity unit (RCU) and write capacity unit (WCU).
  • One RRU or RCU reads up to 4 KB of data at LOCAL_QUORUM consistency, or two reads at LOCAL_ONE consistency. One WRU or WCU writes up to 1 KB of data per row.

3.2 Availability and Durability

  • Keyspaces stores the data durably across multiple Availability Zones, with a replication factor of three.
  • Multi-Region replication gives fully managed, active-active replication across the Regions that you choose. It supports local reads and writes in every Region, and availability up to 99.999 percent.
  • There is no charge for data transfer between Regions when you use multi-Region replication.
  • A multi-Region keyspace is made of replica keyspaces, one in each Region, that are treated as a single unit. Every Region has the same table schema.
  • If one Region fails, point your application to one of the healthy Regions of the multi-Region keyspace.
  • A multi-Region table needs its write capacity set to on-demand mode, or to provisioned mode with auto scaling.

3.3 Time to Live (TTL)

  • TTL sets an expiry time on rows and on attributes, and Keyspaces deletes the data automatically after it expires.
  • It is fully managed. It does not use your read and write capacity.
  • Use it for telemetry that loses value after some days.

3.4 Capacity Examples

  • Reading an 8 KB row takes 2 RRUs at LOCAL_QUORUM consistency, and 1 RRU at LOCAL_ONE consistency.
  • Writing a 2 KB row takes 2 WRUs, because one WRU covers up to 1 KB.
  • A larger row uses more units, so keep the rows small.

3.5 Change Data Capture and Client-Side Timestamps

  • Change data capture (CDC) streams record the row-level change events of a table in near real time.
  • Client-side timestamps are Cassandra-compatible timestamps that Keyspaces keeps for each cell. Use them to resolve conflicts and to let the client application decide the order of writes.

4. Backup and Security

Problem Statement

The FlashCart security team asks how the readings are protected and how the table is recovered after a bad deployment that wrote wrong values for an hour.

4.1 Backup and Recovery

  • Point-in-time recovery (PITR) gives continuous backups of the table. You can restore the table to any second in the preceding 35 days.
  • PITR protects against accidental writes and deletes.
  • A restore creates a new table.
  • PITR must be turned on for the table. The earliest restorable backup is up to 35 days back, or the time when PITR was turned on, whichever is more recent. You cannot change the 35-day maximum.
  • You can also restore a deleted table, if PITR was on and the deletion happened within the last 35 days.
  • A restore keeps the encryption settings of the source table, and you can change them when you restore. You can also restore a multi-Region table.
  • Keyspaces publishes metrics to Amazon CloudWatch, so you can monitor a table.

4.2 Security

  • Keyspaces encrypts all customer data at rest by default.
  • Connections use TLS.
  • AWS Identity and Access Management (IAM) manages access to the tables and the data.
  • Keyspaces is a Regional service. Your application reaches it over the network, and a VPC endpoint can keep that traffic inside AWS.

4.3 Authentication and Connections

  • Keyspaces encrypts client connections in transit. The port and the protocol depend on how you access it:
Access methodPortProtocol
cqlsh9142TLS
Cassandra client driver9142TLS
AWS CLI443HTTPS
AWS SDK443HTTPS
  • Port 9142 applies to CQL connections through cqlsh and Cassandra drivers. For these TLS connections, Keyspaces uses certificates issued under Amazon Trust Services (Amazon Root CAs 1 to 4).
  • Requests through the AWS CLI and the AWS SDKs, for example to create a table or to change its settings, use HTTPS on port 443.

Two authentication methods. Keyspaces supports two main ways to give users and applications credentials:

  1. Service-specific credentials
    • They use a Cassandra-style user name and password.
    • They are generated for a specific IAM user.
    • They are long-term credentials.
    • They can access only Amazon Keyspaces.
    • They cannot be used by IAM roles or federated identities.
  2. IAM credentials with the SigV4 authentication plugin
    • They use AWS access credentials instead of a Cassandra user name and password. The SigV4 plugin is added to the Cassandra client driver, and AWS provides it for Java, Node.js, Python, and Go.
    • They support IAM users, IAM roles, and federated identities, for example the role of an EC2 instance, a Lambda function (lesson 273.1), or an ECS (lesson 273.5) task.
    • They can use temporary credentials from AWS Security Token Service (AWS STS).
    • They are the recommended option for stronger security.
  • In both cases, IAM policies decide what each identity can do on which keyspaces and tables.
  • IAM users have long-term credentials, which are a security risk. If you use service-specific credentials, give the IAM user only the permissions it needs, and remove the user when it is no longer needed.

4.4 Encryption

  • All Amazon Keyspaces tables are encrypted at rest, with AES-256. Encryption cannot be disabled, and the whole table is encrypted: you cannot choose columns or rows.
  • Server-side encryption is transparent, so applications do not need any changes.

KMS key options. When you create or update a table, you choose one of the following AWS KMS key options:

AWS owned keyCustomer managed KMS key
Who creates and manages itAWS. It is used by default.You, in your own AWS account.
ControlYou cannot view, manage, or audit it.You control the key policies, IAM policies, and grants, automatic rotation, enabling and disabling, tags and aliases, and deletion.
AuditingNot available.AWS CloudTrail (lesson 274.3) records the requests that Keyspaces sends to AWS KMS for your key.
ChargeNo separate KMS charge.AWS KMS charges apply, and AWS KMS quotas apply.
  • You can select a different customer managed key for each table. The key of a table also encrypts its metadata and its restorable backups.
  • You can change the key of a table at any time, in the console or with the CQL ALTER TABLE statement. AWS designs the key change to cause no application downtime or service degradation.
  • You can switch a table between an AWS owned key and a customer managed key up to four times in 24 hours, and switch back to an AWS owned key at any time.
  • Keep the customer managed key available. If you disable it or schedule it for deletion, Keyspaces cannot read or write the table. You must restore access within seven days, or Keyspaces deletes the table, after it creates a restorable backup that it keeps for 35 days.
  • In transit: all data is encrypted with TLS (4.3).

4.5 Monitoring and Auditing

  • Amazon CloudWatch collects Keyspaces metrics, such as consumed read and write capacity, throttled requests, and latency. Create alarms, for example on throttling.
  • AWS CloudTrail records the API calls and the schema changes (DDL) on Keyspaces, such as creating or deleting a table. You can also log data operations (DML) as CloudTrail data events for chosen tables, to audit who read or changed data.
  • Use CloudWatch for performance and capacity, and CloudTrail for "who did what, and when".

5. Keyspaces Pricing

Problem Statement

The FlashCart finance team asks what Keyspaces costs and what the levers are.

5.1 What You Pay For

Prices change often and differ by Region. Check the current rates on the Amazon Keyspaces pricing page, and estimate your own cost with the AWS Pricing Calculator.

  • Reads and writes: per request in on-demand mode, or per capacity unit in provisioned mode.
  • Storage: a price per GB-month for the stored data.
  • Point-in-time recovery: charged by the size of the table.
  • Multi-Region replication: the writes to every replica Region, with no data transfer charge between the Regions.
  • TTL: TTL deletes do not use read or write capacity. They are billed for each TTL delete, in units of 2.5 KB, so check the pricing page.

5.2 Lowering the Cost

  • Use provisioned mode with auto scaling for steady traffic, and on-demand mode for spikes.
  • Use TTL to keep the stored data small.
  • Use eventually consistent reads (LOCAL_ONE) where strong consistency is not needed.
  • To estimate the cost of a move, use the pricing calculator for Amazon Keyspaces on GitHub. You enter metrics from the nodetool status output of your Cassandra cluster and your intended serverless configuration, and it compares the operational costs. It does not include total cost of ownership (TCO) factors such as infrastructure maintenance, operational overhead, and support.

Remember these points:

  • Keyspaces has no servers to pay for. You pay for requests or capacity, storage, and optional features.

6.2 Running Cassandra Yourself on EC2

If a team runs Apache Cassandra itself on Amazon EC2, it manages the instances, the placement, the storage, and the repairs. The following points apply:

  • Use a partition placement group. It spreads the instances across logical partitions, and instances in one partition do not share racks with instances in the other partitions, so a partition failure does not affect the other partitions. It suits large distributed and replicated workloads such as HDFS, HBase, Cassandra, and Kafka.
  • A placement group can have up to 7 partitions per Availability Zone, can span several zones in a Region, and can hold hundreds of EC2 instances.
  • For the storage of a NoSQL database such as Cassandra, use Provisioned IOPS SSD volumes (io1 or io2 Block Express).
  • With Amazon Keyspaces, none of this work is needed.

6.3 Real-World Scenario: Moving Warehouse Telemetry to Keyspaces

This scenario follows the FlashCart platform team as it moves its warehouse telemetry from a self-managed Cassandra cluster to Amazon Keyspaces. It brings together the migration, data model, capacity, security, and recovery choices of this lesson. The Situation

These figures are invented for this scenario.

  • FlashCart’s warehouse scanners and sensors send about 50,000 readings per minute to a self-managed Apache Cassandra cluster of nine EC2 instances in one Region.
  • A two-person platform team spends several days each month on repairs, upgrades, and replacing failed nodes.
  • Last month, a node failed during an upgrade, and the dashboards were down for three hours.
  • The application code uses CQL and the DataStax Java driver, and the team does not want to rewrite it.
  • The security team now requires encryption with a key that the company controls, an audit trail, and no passwords in application code.

Step 1: Plan an Online Migration

  • Check the functional differences first, such as the 1 MB maximum row size, and estimate the cost with the pricing calculator for Amazon Keyspaces.
  • Create the keyspace and the tables in Keyspaces with the same CQL schema.
  • Deploy the ZDM Dual Write Proxy, so new writes go to both Cassandra and Keyspaces without changing the application.
  • Copy the historical data with AWS Glue.
  • Compare reads from both databases until the results match, then switch the application to Keyspaces and decommission the Cassandra cluster.

Step 2: Keep a Good Data Model

  • The partition key is (device_id, reading_date), so the writes spread across many partitions and each partition holds one device for one day.
  • The clustering column reading_time sorts the readings, newest first.
  • A default TTL of 90 days removes old readings automatically.
CREATE TABLE telemetry.readings (
  device_id text, reading_date date, reading_time timestamp,
  temperature double, battery double,
  PRIMARY KEY ((device_id, reading_date), reading_time)
) WITH CLUSTERING ORDER BY (reading_time DESC)
  AND default_time_to_live = 7776000;

Step 3: Choose Capacity and Consistency

  • Start in on-demand mode, because the real traffic pattern after the move is not known yet.
  • After a few weeks of steady traffic, switch to provisioned capacity with auto scaling to lower the cost.
  • Writes use LOCAL_QUORUM, the only write consistency level.
  • The dashboards read with LOCAL_ONE, which costs half as much per read and is good enough for charts. The device history page reads with LOCAL_QUORUM for the latest data.

6.5 Lesson Summary

This lesson covered the following points:

  • Amazon Keyspaces is a serverless, managed, Cassandra-compatible database that uses CQL and the Cassandra drivers. It replicates data three times across Availability Zones.
  • A table is designed around its queries: the partition key finds the data, and clustering columns sort the rows inside it.
  • On-demand mode fits spiky traffic and provisioned mode fits steady traffic. Multi-Region replication is active-active, and TTL deletes expired rows without capacity use.
  • PITR restores to any second in the last 35 days. Data is encrypted at rest by default, and IAM controls access.

8. Knowledge Check

Answer each question in your own words before you open the model answer. The questions were written for this course.

Question 1: Explain what Amazon Keyspaces is and when you choose it.

Maps to: Objectives 1 and 2 (Comprehension).

Amazon Keyspaces is a serverless, managed, Apache Cassandra-compatible database that uses CQL and the existing Cassandra drivers. Choose it when an application already uses Cassandra, or needs a wide-column store with very high write throughput and low latency, and you do not want to manage servers. For a new serverless NoSQL workload without Cassandra, DynamoDB is usually simpler.

Question 2: Describe how to design a Keyspaces table for the query "readings of one device in a time range".

Maps to: Objective 3 (Application).

Use the device identifier as the partition key, so that all the rows of a device sit together, and the reading time as a clustering column, so that the rows are sorted by time and a range is one efficient read. Design the table around the query, because there are no joins, and spread the load evenly across partitions.

Question 3: Compare the capacity modes, and explain the consistency that Keyspaces uses.

Maps to: Objective 4 (Analysis).

On-demand mode scales automatically and charges per request, so it fits unpredictable traffic. Provisioned mode uses the capacity units that you set, optionally with auto scaling, and costs less for predictable traffic. All writes use LOCAL_QUORUM, and reads can use LOCAL_QUORUM for strong consistency in the Region, or LOCAL_ONE for lower cost with eventual consistency.

Question 4: Explain how Keyspaces provides availability, durability, and recovery.

Maps to: Objective 5 (Comprehension).

Keyspaces replicates the data three times across Availability Zones. Multi-Region replication adds fully managed active-active replication across chosen Regions, with availability up to 99.999 percent. Point-in-time recovery restores a table to any second in the previous 35 days. Data is encrypted at rest by default, and TTL deletes expired rows without using capacity.

Question 5: Choose between Keyspaces, DynamoDB, and DocumentDB for three different applications.

Maps to: Objective 6 (Evaluation).

Choose Keyspaces for an application that already uses Cassandra and CQL. Choose DynamoDB for a new serverless key-value or document workload with known access patterns. Choose DocumentDB for an application that uses MongoDB drivers and rich document queries. The compatibility with the existing interface is usually the deciding keyword.

Question 6: Explain how to protect a Keyspaces table against an accidental delete and against a Regional failure, and how to run Cassandra yourself if you must.

Maps to: Objective 5 (Application).

Turn on point-in-time recovery, which restores the table, or a table deleted within the last 35 days, to any second in the window, with the encryption settings of the source. For a Regional failure, use a multi-Region keyspace, which keeps replica keyspaces with the same schema in several Regions and lets you point the application to a healthy Region. To run Cassandra yourself on EC2, use a partition placement group so that a rack failure affects only one partition, and use Provisioned IOPS SSD volumes. Keyspaces removes this work.

Question 7: Compare Amazon Keyspaces with Apache Cassandra that you run yourself, and explain how a Keyspaces connection appears to the client.

Maps to: Objectives 1 and 2 (Analysis).

With Cassandra on your own servers you provision, patch, and manage the servers and the software, manage the cluster and node settings, configure the replication factor and the consistency level, add nodes to scale, and build multi-Region replication. Keyspaces is serverless: it needs no servers or control plane operations, configures the replication factor and consistency for you, scales tables and partitions automatically, and offers managed multi-Region replication. You pay only for what you use. Through a public service endpoint, Keyspaces appears to the client as a nine-node Cassandra 3.11.2 cluster, and through an interface VPC endpoint it appears as a three-node cluster. In both cases, the nodes map to load balancers that route the queries to many storage partitions on SSDs.

Question 8: A company wants to move its on-premises Cassandra cluster to Amazon Keyspaces with no downtime, give its ECS tasks access without passwords, control its own encryption key, and audit schema changes. Describe the solution.

Maps to: Objectives 5 and 6 (Synthesis).

Use an online migration: send new writes to both Cassandra and Keyspaces with dual writes, for example with the ZDM Dual Write Proxy, copy the historical data with AWS Glue, compare reads from both, and then switch the application. Check the functional differences first, such as the 1 MB row limit. Give the ECS tasks an IAM task role and add the SigV4 authentication plugin to the Cassandra driver, so they use short-term credentials over TLS on port 9142. Encrypt the tables with a customer managed AWS KMS key. Use CloudTrail to record the schema changes, and data events if data access must be audited, and CloudWatch alarms to watch for throttling.

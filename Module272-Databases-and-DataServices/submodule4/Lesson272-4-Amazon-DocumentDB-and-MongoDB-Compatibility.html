Introduction

Many applications keep a product, a user profile, or a piece of content as one nested JSON document. MongoDB is a popular database for that model. Running MongoDB yourself means managing replicas, sharding, backups, and patches. Amazon DocumentDB gives a managed alternative that keeps the MongoDB drivers. An architect has to know where DocumentDB fits, where it differs from MongoDB, and when DynamoDB is the better choice.

This lesson assumes that you know the Aurora cluster design from Lesson 272.2, because DocumentDB uses similar ideas. It follows FlashCart Inc. through the Problem Statement of each tab.

1. What Amazon DocumentDB Is

Problem Statement

The FlashCart product catalog is stored in many relational tables: products, specifications, reviews, and images. Every product page needs four joins, and every new product type means a schema change. The team already has application code and drivers for MongoDB, and it wants a managed database that stores a product as one JSON document and keeps that code.

1.1 What a Document Database Is

  • A document database stores data as JSON-like documents: nested key-value structures that can hold maps, lists, and other documents.
  • Each document can have its own fields, so there is no fixed schema to change when a product type changes.
  • You can query and index fields inside the documents.
  • Typical uses: user profiles, content management such as blogs and video metadata, and product catalogs and reviews in e-commerce.

A document can hold nested values. For example, a product document:

{
  "ProductID": "12345",
  "Category": "Mobile Phones",
  "Brand": "ExampleBrand",
  "Model": "ExampleModel X1",
  "Specifications": {
    "ScreenSize": "6.5 inches",
    "RAM": "8 GB",
    "Storage": "128 GB",
    "Camera": { "Rear": "48 MP + 8 MP + 5 MP", "Front": "16 MP" },
    "Dimensions": { "Height": "160 mm", "Width": "74 mm", "Depth": "8 mm" },
    "Connectivity": ["Wi-Fi", "Bluetooth 5.0", "NFC", "4G LTE"]
  },
  "Price": 699.99
}

1.2 What Amazon DocumentDB Is

  • Amazon DocumentDB (with MongoDB compatibility) is a fast, reliable, fully managed document database that stores, queries, and indexes JSON data.
  • It is the AWS implementation of a MongoDB-compatible database, in the way that Aurora is the AWS implementation of MySQL and PostgreSQL. It has similar deployment concepts to Aurora.
  • AWS handles the servers, the patching, the backups, and the recovery. The cluster is highly available, with replication across three Availability Zones.
  • Storage grows automatically, and the cluster supports millions of requests per second.
  • DocumentDB supports ACID transactions across several documents, so a group of changes succeeds or fails together.

1.3 MongoDB Compatibility

  • DocumentDB supports the MongoDB APIs through the MongoDB wire protocol, so you use MongoDB drivers and tools with it.
  • It is compatible with MongoDB 4.0, 5.0, and 8.0. The 8.0 version works with MongoDB drivers for API versions 6.0, 7.0, and 8.0.
  • DocumentDB is not MongoDB. It does not support every MongoDB feature, so check the supported APIs before you migrate.
  • Some newer capabilities, such as Serverless on 5.0, are not yet available in version 8.0, so check the version for each feature.

1.4 Relational or Document?

QuestionPoints to a relational databasePoints to a document database
Do you need ad hoc queries and joins?Yes.No. Each document holds the related data.
Is the schema mostly fixed?Yes.No. The schema is flexible.
What is the example?A flight booking system, and banking.A user profile, a content item, and an e-commerce product catalog.
  • An e-commerce product catalog can run on DocumentDB or on DynamoDB. The keywords decide: MongoDB drivers and rich document queries point to DocumentDB, and serverless key-value access at any scale points to DynamoDB.

2. Cluster Architecture and Failover

Problem Statement

FlashCart asks how DocumentDB keeps the catalog available if a data center fails, how the application connects to it, and how long an outage lasts when an instance breaks.

2.1 The Cluster

  • An instance-based DocumentDB cluster has one primary instance and up to 15 replica instances. A cluster has 0 to 16 instances and exactly one cluster volume.
  • The instances run only in an Amazon VPC. You create the cluster first, and then you create the instances in it.
  • All the instances, the primary and the replicas, support reads. Replicas do not take part in processing writes, so they are for read scaling.
  • All the instances share one cluster volume, so replicas read the same storage as the primary. They do not need to copy the data. This lowers the cost, and you can add replicas in minutes, regardless of the size of the storage volume.
  • You scale reads by adding replicas, and you scale writes by choosing a larger instance, or by using an elastic cluster (tab 3).

2.2 Storage

  • The volume spans three Availability Zones, with two copies of the data in each zone.
  • The storage handles the loss of up to two copies without losing write availability, and up to three copies without losing read availability.
  • It grows automatically in 10 GiB steps, up to 128 TiB for an instance-based cluster.
  • Recovery does not replay long redo logs, so an instance restart usually takes 30 seconds or less.

2.3 Endpoints and Failover

EndpointWhere it points
Cluster endpointThe current primary instance. Use it for writes.
Reader endpointLoad balances connections across the replicas. Use it for reads.
Instance endpointOne specific instance.
  • DocumentDB monitors the cluster. If the primary fails, it fails over to one of up to 15 replicas in the three Availability Zones, typically in under 30 seconds.
  • The cluster endpoint then points to the new primary.
  • DocumentDB continuously monitors the health of the cluster.
  • A cluster has exactly one cluster endpoint and one reader endpoint. All the instances listen on the same TCP port, which is 27017 by default, and the connection supports TLS.
  • A cluster with replicas in several Availability Zones has an availability of up to 99.99 percent.

  • C. Turn off automated backups.

  • The cluster volume keeps 6 copies in 3 zones, in the same way as Aurora.
  • Failover needs a replica. Without one, the cluster has no failover target.
  • The cluster endpoint follows the primary. The reader endpoint balances the replicas.

4. Security, Backup, and Migration

Problem Statement

The FlashCart security team asks how the catalog is protected and recovered. The migration team asks how the data moves from the self-managed MongoDB cluster to DocumentDB without a long outage.

4.1 Security

  • Encryption at rest uses AWS KMS keys. It covers the storage, the automated backups, the snapshots, and the replicas of the cluster.
  • Encryption in transit uses TLS.
  • The cluster runs in your VPC, in private subnets, and security groups control the access.
  • IAM controls who can manage the cluster. Database users are created in the database.

4.2 Backup and Restore

  • Automated backups are continuous and allow point-in-time recovery. You can restore the cluster to any second during the retention period, up to the last 5 minutes.
  • You can set the automatic backup retention period up to 35 days. DocumentDB stores the automated backups in Amazon S3, which is designed for 99.999999999 percent durability.
  • Manual snapshots stay until you delete them.
  • A restore creates a new cluster.
  • AWS Backup supports DocumentDB, so you can manage its backups with a central backup plan, together with other services, and copy them to another Region or account.

4.3 Migrating From MongoDB

  • AWS Database Migration Service (AWS DMS) can migrate from a MongoDB replica set or a sharded cluster to Amazon DocumentDB, with ongoing replication to keep the downtime short.
  • Check the list of supported MongoDB APIs, operations, and data types before you migrate, because DocumentDB does not support every MongoDB feature.
  • Applications keep the MongoDB drivers. They change the connection string and the TLS settings.
  • In AWS DMS, a MongoDB database is a supported source and DocumentDB is a supported target. DocumentDB can also be a source, for example to move data to another store.

5. DocumentDB Pricing

Problem Statement

The FlashCart finance team asks what DocumentDB costs and what the main levers are.

5.1 What You Pay For

Prices change often and differ by Region. Check the current rates on the Amazon DocumentDB pricing page, and estimate your own cost with the AWS Pricing Calculator.

  • Instances: instance hours for each primary and replica, or capacity units for Serverless.
  • Storage: a price per GB-month for the storage that you use.
  • I/O: a charge per request with standard storage, and none with I/O-optimized storage.
  • Backups: backup storage beyond the included amount, and snapshots.
  • Data transfer: for example, replication to other Regions in a global cluster.

5.2 Lowering the Cost

  • Use only the number of replicas that you need for reads and availability.
  • Choose I/O-optimized storage for a high-I/O workload, and standard storage otherwise.
  • Use Serverless for variable or intermittent workloads.
  • Delete old snapshots.

6.4 Lesson Summary

This lesson covered the following points:

  • A document database stores JSON documents with a flexible shape. Amazon DocumentDB is the managed, MongoDB-compatible service. It is compatible with MongoDB 4.0, 5.0, and 8.0, and it is not MongoDB.
  • The cluster has one primary and up to 15 replicas on a shared volume that keeps 6 copies in 3 zones and grows to 128 TiB. Failover typically takes under 30 seconds.
  • Replicas scale reads, elastic clusters scale reads and writes, Serverless follows the load, and global clusters reach other Regions.
  • KMS encryption, TLS, VPC isolation, and point-in-time recovery protect the data. AWS DMS migrates MongoDB data in.
  • I/O-optimized storage removes the I/O charge for a high-I/O workload.

Memory Hook

Documents in JSON, drivers from MongoDB, storage like Aurora, and DMS to move in.

7. Knowledge Check

Answer each question in your own words before you open the model answer. The questions were written for this course.

Question 1: Explain what a document database is, and what Amazon DocumentDB adds to it.

Maps to: Objectives 1 and 2 (Comprehension).

A document database stores data as JSON-like documents with a flexible shape, so a product with its specifications, reviews, and images can sit in one document that you query and index. Amazon DocumentDB is a fully managed, MongoDB-compatible service. AWS runs the servers, the patching, the backups, and the replication across three Availability Zones, and the application keeps its MongoDB drivers.

Question 2: Describe how a DocumentDB cluster stores data and handles a failure.

Maps to: Objective 3 (Comprehension).

An instance-based cluster has one primary and up to 15 replicas on a shared cluster volume. The volume keeps 6 copies of the data across 3 Availability Zones, grows in 10 GiB steps up to 128 TiB, and tolerates the loss of two copies for writes and three copies for reads. If the primary fails, DocumentDB promotes a replica, typically in under 30 seconds, and the cluster endpoint points to it.

Question 3: Compare the ways to scale a DocumentDB workload.

Maps to: Objective 4 (Analysis).

Replica instances add read throughput. A larger instance adds write capacity to an instance-based cluster. Elastic clusters shard the data, scale reads and writes, and store up to 4 PiB. Serverless adjusts capacity to a variable load. Global clusters add secondary clusters in other Regions for disaster recovery and local reads.

Question 4: Explain how to secure and recover a DocumentDB cluster, and how to migrate from MongoDB.

Maps to: Objective 5 (Application).

Use KMS encryption at rest, which also covers backups, snapshots, and replicas, TLS in transit, private subnets, and security groups. Automated backups allow point-in-time recovery, and manual snapshots stay until deleted. A restore creates a new cluster. AWS DMS migrates a MongoDB replica set or sharded cluster with ongoing replication, and the application keeps its drivers.

Question 5: Choose between DocumentDB and DynamoDB for a new catalog service.

Maps to: Objective 6 (Evaluation).

Choose DocumentDB when the application already uses MongoDB drivers and queries, or needs rich queries on documents. Choose DynamoDB when the access patterns are known, the workload needs serverless scaling with no servers, and single-digit millisecond latency at any size. DocumentDB is not MongoDB, so check the supported APIs.

Question 6: Explain how you back up and move data for DocumentDB with other AWS services.

Maps to: Objective 5 (Application).

DocumentDB has automated backups for point-in-time recovery and manual snapshots, and a restore creates a new cluster. AWS Backup supports DocumentDB, so a central backup plan can protect it with other services and copy the backups to another Region or account. AWS DMS migrates data into DocumentDB from a MongoDB replica set or sharded cluster, and DocumentDB can also be a source in DMS.

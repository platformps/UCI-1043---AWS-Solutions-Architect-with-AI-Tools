Introduction

Sensors, servers, and applications produce measurements every few seconds. Stored in a relational table, the readings grow by millions of rows per day, and the questions people ask, such as the average of the last hour or the trend over a year, become slow. A time series database is built for this data. An architect must recognize the keywords and know which Timestream engine is open to new customers.

1. Time Series Data and Amazon Timestream

Problem Statement

FlashCart installs temperature sensors in its warehouses and collects page-load times from its website. Each sensor and each page sends a reading every few seconds, and the operations team wants dashboards of the last hour and trends over a year. In a relational table, the readings grow by millions of rows per day, and the trend queries become slow.

1.1 What Time Series Data Is

  • Time series data is a sequence of measurements taken over time, such as a temperature every 10 seconds or the CPU use of a server every minute.
  • Each data point has a timestamp, one or more measures (the values), and dimensions that describe the source, such as the device ID or the Region.
  • The data arrives continuously and in large volume, and it is mostly appended, not updated.
  • Queries look at time windows: the last hour, the daily average, or the trend over a year.

1.2 What Amazon Timestream Is

  • Amazon Timestream is the AWS family of fully managed time series databases.
  • It has two engines. Amazon Timestream for InfluxDB runs open source InfluxDB. It is the AWS-recommended option for new workloads, with single-digit millisecond query response times for real-time analytics (tab 2).
  • Amazon Timestream for LiveAnalytics is the original serverless engine. It has been closed to new customers since June 20, 2025, and existing customers can keep using it (tab 3).
  • The course slides describe Timestream as up to 1,000 times faster and one-tenth of the cost of relational databases for time series. Treat these as marketing figures from the slides.

Kinesis Data Analytics for Apache Flink (lesson 273.6), as named on the slide, is now called Amazon Managed Service for Apache Flink.

2. Timestream for InfluxDB

Problem Statement

FlashCart chooses Timestream for InfluxDB for the warehouse sensors. The operations team already uses Telegraf agents and InfluxDB 2 queries on a server in its data center. The architects must choose a deployment that survives a zone failure and handles the read load of many dashboards.

2.1 What Timestream for InfluxDB Is

  • Amazon Timestream for InfluxDB is a fully managed time series database that runs open source InfluxDB.
  • It supports InfluxDB 3 Core and Enterprise for new workloads, and InfluxDB 2 for existing InfluxDB 2 workloads.
  • It is compatible with the open source InfluxDB APIs and tools, so you keep your query languages and your data collection agents. InfluxDB 2 uses Flux and InfluxQL. InfluxDB 3 uses SQL, its primary query language, and InfluxQL.
  • You can send data collected with open source Telegraf agents directly to it.
  • The building block depends on the version: a DB cluster for InfluxDB 3, and a DB instance for InfluxDB 2. In both, you choose an instance class, such as db.influx.large, like Amazon RDS.

2.2 Deployment Options

The deployment options depend on the InfluxDB version.

2.2.1 InfluxDB 3: DB Clusters (Recommended for New Workloads)

  • A DB cluster separates compute from storage, and it keeps the data in Amazon S3 for virtually unlimited, cost-effective storage.
EditionHow it worksUse it for
CoreSingle-node only. The node handles writes and reads. There is no compaction.Development, test, and near real-time monitoring of recent data.
Enterprise, single nodeOne node handles writes, reads, and compaction. It uses Single-AZ compute.Smaller production workloads that need compaction and long-term storage.
Enterprise, multi-nodeA 3-node configuration, or up to 15 nodes with a custom parameter group, spread across Availability Zones, with a dedicated compactor node.Production workloads that need high availability, scale, and long-term analytics.

2.2.2 InfluxDB 2: DB Instances (Existing InfluxDB 2 Workloads)

OptionHow it worksUse it for
Single-AZ DB instanceOne instance in one Availability Zone. AWS commits to 99.5 percent monthly uptime.Development, test, and workloads that tolerate downtime.
Multi-AZ DB instanceA primary and a standby in another zone, kept in sync. AWS commits to 99.9 percent monthly uptime.High availability without read scaling.
Multi-AZ read replica clusterA writer instance with read replicas. The writes are replicated asynchronously to the readers. It needs the InfluxData read replica add-on, which you subscribe to through AWS Marketplace.High availability and more capacity for read-heavy workloads, such as many dashboards.

2.3 Migration and Pricing

  • To move from a self-managed InfluxDB, restore a backup of the existing database into a Timestream for InfluxDB instance, with a few minutes of downtime. Then point the Telegraf agents at the new endpoint.
  • You pay for the instance hours of each instance or cluster node, by the instance class, and for the storage that you use. Billing starts when the instance is available.
  • Some options add a license charge: an InfluxDB 2 read replica cluster needs the read replica add-on subscription through AWS Marketplace, and InfluxDB 3 Enterprise adds a license charge per vCPU per hour. InfluxDB 3 Core has no license charge.
  • Check the Amazon Timestream pricing page for the current prices.

3. Timestream for LiveAnalytics

Problem Statement

A team in a FlashCart partner company has used the original Amazon Timestream for several years. Its engineers ask whether they can keep it, what makes it different, and how they would move if they had to.

3.1 Availability Change

  • Amazon Timestream for LiveAnalytics has been closed to new customers since June 20, 2025.
  • Existing customers can continue to use it as normal, and AWS continues to invest in its security, availability, and performance.
  • AWS recommends that new customers evaluate Timestream for InfluxDB, which has similar functionality.

Closed to New Customers

The course slides describe LiveAnalytics, so it can appear in exam questions and study material. For a new design, use Timestream for InfluxDB.

3.2 Features of LiveAnalytics

  • A fully managed, fast, scalable, serverless time series database that scales up and down automatically.
  • It can store and analyze trillions of events per day.
  • Storage tiering: recent data is kept in a memory store for fast queries, and historical data is kept in a cost-optimized magnetic store.
  • SQL compatibility, scheduled queries, multi-measure records, and built-in time series analytics functions that help find patterns in near real time.
  • Encryption in transit and at rest.

3.3 Moving Away From LiveAnalytics

The AWS migration guide recommends a target by workload:

  • Timestream for InfluxDB 3 for most workloads.
  • Timestream for InfluxDB 2 for low-latency operational workloads.
  • Amazon Aurora or Amazon RDS for PostgreSQL for use cases that are not time series.

The migration uses Amazon S3 as an intermediate layer:

  1. Export the data from Timestream for LiveAnalytics to Amazon S3.
  2. Make any required changes to the exported CSV files.
  3. Load the data into the target database.
  4. Point the writers and the dashboards at the new database.

4. Architecture and Integrations

Problem Statement

FlashCart must collect the sensor data from AWS IoT and from a data stream, run stream processing before storage, and show the results on dashboards in Grafana. The architects draw the end-to-end flow.

4.1 Timestream Architecture

Image 4a comes from the course slides. It shows the integrations of Timestream for LiveAnalytics, which is closed to new customers. Timestream for InfluxDB connects through the InfluxDB tools instead.

  • Timestream for InfluxDB (new workloads): data comes in from Telegraf agents and the InfluxDB APIs and client libraries. Dashboards use the InfluxDB UI, self-hosted Grafana, or Amazon Managed Grafana, pointed at the Timestream for InfluxDB endpoint with no other code changes.
  • Timestream for LiveAnalytics (existing customers), data in: AWS IoT rule actions, AWS Lambda (lesson 273.1), Prometheus, Telegraf, and stream processing with Amazon Managed Service for Apache Flink (formerly Kinesis Data Analytics) from Kinesis Data Streams or Amazon MSK (lesson 272.13).
  • Timestream for LiveAnalytics, data out: AWS Quick Sight (lesson 272.15) dashboards, Amazon SageMaker for machine learning, Grafana dashboards, and any JDBC connection.
  • Write the data in batches rather than one point at a time.

4.2 Timestream Compared With Other Databases for Time Data

ServiceWhen it fits time data
Amazon TimestreamPurpose-built for time series: time-window queries, built-in functions, and managed InfluxDB.
Amazon DynamoDBSimple lookups of recent readings by device key, with TTL to remove old items. No time series analytics.
Amazon KeyspacesHigh write throughput by a known key for an existing Cassandra application.
Amazon RedshiftLong-term analytics and BI on large history that is combined with other business data.

5.3 Lesson Summary

This lesson covered the following points:

  • Time series data is a sequence of timestamped measures with dimensions, such as sensor readings and metrics.
  • Amazon Timestream has two engines. Timestream for InfluxDB is recommended for new workloads. InfluxDB 3 runs as DB clusters, Core with a single node or Enterprise with one or more nodes, with storage in S3. InfluxDB 2 runs as DB instances, with Single-AZ, Multi-AZ, and read replica cluster options.
  • Timestream for LiveAnalytics is the serverless engine with memory and magnetic tiers and SQL. It has been closed to new customers since June 20, 2025.
  • Timestream for InfluxDB takes data from Telegraf and the InfluxDB APIs, and Grafana or Amazon Managed Grafana reads it. LiveAnalytics integrates with AWS IoT, Lambda, Managed Service for Apache Flink, AWS Quick Sight, and SageMaker.

Memory Hook

Timestream for time. InfluxDB for new work. LiveAnalytics for those already on it.

6.1 Practice Scenarios: AWS Databases

These scenarios review the database services of Module 272. Read each scenario, find the keywords, and choose a service before you open the answer.

6.1.1 Practice Scenario 1

From the course slides (Source: awswithchetan.com.)

Scenario: A global e-commerce company wants an active-active database across multiple Regions, so that customers can place orders from anywhere with low latency.

Show Answer and Explanation

Keywords: Active-active, multiple Regions, place orders, from anywhere, low latency.

Answer: Amazon DynamoDB global tables.

  • Placing an order is a write, and it must work in every Region. DynamoDB global tables accept writes in every replica Region.
  • Why not Aurora Global Database: its secondary Regions serve reads. With write forwarding, a secondary Region can forward writes, but every write is applied in the primary Region first, so it is not active-active.

6.1.2 Practice Scenario 2

From the course slides (Source: awswithchetan.com.)

Scenario: A ride-sharing app needs to cache frequently accessed data, such as driver locations, to reduce database load and achieve microsecond latency.

Show Answer and Explanation

Keywords: Cache.

Answer: Amazon ElastiCache or DynamoDB Accelerator (DAX).

  • If only one of them is among the options, it is an easy pick.
  • If both are options, look for more information: if the source database is DynamoDB, choose DAX. If the source database is RDS or Aurora, or the question mentions advanced cache features, choose ElastiCache.

6.1.3 Practice Scenario 3

From the course slides (Source: awswithchetan.com.)

Scenario: A streaming platform wants to store large volumes of user activity logs, but only needs them for occasional analytics queries.

Show Answer and Explanation

Keywords: Occasional, analytics queries.

Answer: The DynamoDB Standard-IA table class, or a DynamoDB export to Amazon S3.

  • It depends on the extra context. If the goal is to save storage cost, choose the DynamoDB Standard-Infrequent Access (Standard-IA) table class.
  • If the goal is to analyze the data with Athena (lesson 272.11) or other tools, choose an export to Amazon S3.

6.1.4 Practice Scenario 4

From the course slides (Source: awswithchetan.com.)

Scenario: A ride-sharing platform wants to quickly find the shortest path between drivers and riders, based on a complex graph of roads and connections.

Show Answer and Explanation

Keywords: Shortest path, graph, connections.

Answer: Amazon Neptune.

  • Relationships and paths between connected entities are what a graph database is built for.

6.1.5 Practice Scenario 5

From the course slides (Source: awswithchetan.com.)

Scenario: A team needs to quickly create a full copy of its production database to run performance tests and simulate heavy workloads, without affecting the live system. The copy must be ready within minutes.

Show Answer and Explanation

Keywords: Full copy of production, within minutes.

Answer: Aurora cloning.

  • A read replica might come to mind, but the scenario does not say that the copy is only read.
  • Aurora uses a copy-on-write protocol on its shared storage, so a clone is faster and more space-efficient than restoring a snapshot. You can create up to 15 clones with copy-on-write.

AWS references for the explanations: Using write forwarding in an Aurora global database and Cloning a volume for an Aurora DB cluster.

7. Knowledge Check

Answer each question in your own words before you open the model answer. The questions were written for this course.

Question 1: Explain what time series data is, and give two use cases for Amazon Timestream.

Maps to: Objectives 1 and 2 (Comprehension).

Time series data is a sequence of measurements over time. Each point has a timestamp, one or more measures, and dimensions that describe the source. It arrives continuously, is mostly appended, and is queried by time windows. Timestream fits IoT sensor data, application and server metrics, industrial telemetry, and real-time analytics of web traffic.

Question 2: Compare the two Timestream engines, and say which one a new customer should choose.

Maps to: Objective 2 (Analysis).

Timestream for InfluxDB is instance-based and runs open source InfluxDB 3, on DB clusters with SQL and InfluxQL, or InfluxDB 2, on DB instances with Flux and InfluxQL, with InfluxDB APIs, tools, and Telegraf. Timestream for LiveAnalytics is serverless, with a memory store, a magnetic store, SQL, and scheduled queries, but it has been closed to new customers since June 20, 2025. A new customer should choose Timestream for InfluxDB.

Question 3: Describe the deployment options of Timestream for InfluxDB 3 and InfluxDB 2, and when to use each one.

Maps to: Objective 3 (Application).

InfluxDB 3 runs as a DB cluster with storage in S3: Core is a single node for development, test, and recent data, and Enterprise runs as a single node or a multi-node cluster across Availability Zones, with compaction, for production. For InfluxDB 2, a Single-AZ instance is one DB instance, with a 99.5 percent uptime commitment, for development and test. A Multi-AZ instance adds a synchronized standby in another zone, with a 99.9 percent commitment, for availability without read scaling. A Multi-AZ read replica cluster has a writer and read replicas updated asynchronously, for availability and more read capacity.

Question 4: Explain how data flows into and out of Timestream in a typical architecture.

Maps to: Objective 4 (Application).

For Timestream for InfluxDB, Telegraf agents and the InfluxDB APIs write the data, and the InfluxDB UI, Grafana, or Amazon Managed Grafana read it. For LiveAnalytics, sources such as AWS IoT, Prometheus, and Lambda write the data, and AWS Quick Sight, Amazon SageMaker, and JDBC tools read it. In both cases, Managed Service for Apache Flink can process Kinesis or MSK streams before storage, and data should be written in batches.

Question 5: Design a time series solution for FlashCart warehouse sensors that keeps the existing Telegraf agents, survives a zone failure, and serves many dashboards.

Maps to: Objective 5 (Synthesis).

Because FlashCart already runs InfluxDB 2, use Amazon Timestream for InfluxDB 2 with a Multi-AZ read replica cluster: the writer takes the sensor data, and the readers serve the dashboards and give failover. Point the Telegraf agents at the managed endpoint, and restore the existing InfluxDB backup into it. For a new design, an InfluxDB 3 Enterprise multi-node cluster across Availability Zones is the recommended choice. Use Managed Service for Apache Flink if the streams need processing, and build dashboards in Grafana or Amazon Managed Grafana. Keep the instances in private subnets and encrypt the data.

Introduction

A database answers a query in milliseconds, but a popular query repeated thousands of times a minute still uses CPU, I/O, and connections. A cache answers the repeated request from memory, in under a millisecond. The cost is that the application must manage the cache: what to store, how long to keep it, and when to refresh it. An architect has to know the engines, the strategies, and which cache fits which source database.

This lesson assumes that you know the databases from Lessons 272.1 to 272.3, in particular RDS, Aurora, and DynamoDB with DAX. It follows FlashCart Inc. through the Problem Statement of each tab.

1. Caching and ElastiCache Basics

Problem Statement

The FlashCart product pages read the same popular products from the database thousands of times a minute. During the sale the database CPU is high and the page time grows. The engineers want to take the repeated reads off the database, and also keep the user sessions outside the web servers, so that any server can serve any user.

1.1 What a Cache Is

  • A cache keeps copies of frequently used data in fast storage, so that the next request is served faster and the source system has less work.
  • Applications use several cache layers: the browser, a content delivery network such as Amazon CloudFront, the application itself, a distributed in-memory cache, and the database buffer.
  • A database cache is an in-memory database with very high performance and very low latency. It relieves the database of read-heavy traffic.

1.2 What Amazon ElastiCache Is

  • Amazon ElastiCache is a fully managed in-memory data store and cache. It is to caches what RDS is to relational databases.
  • AWS handles the operating system, patching, setup, configuration, monitoring, failure recovery, and backups.
  • It gives sub-millisecond latency, so it speeds up read-heavy applications and helps make an application stateless.
  • It supports three engines: Valkey, Redis OSS, and Memcached.

1.3 Common Uses

UseHow ElastiCache helps
Database cacheThe application reads the cache first, and goes to the database only on a miss.
User session storeAny application instance reads the session from the cache, so a user stays logged in on any server.
LeaderboardsRedis-style sorted sets rank players in real time.
Counters, queues, and messagingFast atomic counters and publish/subscribe.

  • B. Increase the RDS storage.
  • C. Create a new RDS database for each user.
  • D. Use Amazon Glacier for the query results.

2. Engines and Deployment Options

Problem Statement

The FlashCart team must now choose an engine, and decide between a cache that AWS sizes and a cache that the team sizes. Some data needs a failover and a backup, and some is only a throwaway cache.

3. Caching Strategies

Problem Statement

The FlashCart engineers add the cache to the product service, and they must decide when the application puts data in the cache and when it removes it. A stale price on a product page is not acceptable, but a stale review count is fine.

3.1 Lazy Loading and Write-Through

Lazy loading (cache-aside)Write-through
How it worksRead the cache. On a miss, read the database and write the result to the cache.Write to the cache and to the database together on every write.
Stale dataPossible, until the item expires or is invalidated.No stale data for the written items.
Cache sizeOnly requested data is cached.Data that is never read also fills the cache.
CostA miss costs three trips.Every write costs an extra trip.

3.2 Time to Live (TTL)

  • Set a TTL on a cache key, so that it expires by itself. It limits how stale lazy-loaded data can become.
  • Combine lazy loading with a TTL, or lazy loading with write-through, for a balance of freshness and cost.

3.3 Session Store and Leaderboards

  • Session store: the application writes the session to the cache with a TTL. When the user hits another server, that server finds the session, so the user stays logged in.
  • Leaderboard: a Valkey or Redis OSS sorted set keeps each element unique and ordered, and ranks it in real time when it changes.

3.4 Exam-Style Question

Written for this course.

Scenario: An application caches product data from a database. A price must never be stale, but reading unused products into the cache should be avoided as much as possible. Which approach meets the requirements?

  • A. Write-through for the price, and lazy loading with a TTL for the rest.
  • B. Lazy loading with no TTL for everything.
  • C. Cache nothing.
  • D. Write-through for everything and never read the database.
Show Answer and Explanation

Correct answer: A. Write-through keeps the price in the cache current, and lazy loading with a TTL keeps the cache small for the rest of the data.

OptionResultReason
ACorrectIt matches freshness to the data that needs it.
BIncorrectLazy loading with no TTL can serve a stale price for a long time.
CIncorrectNo cache gives no relief to the database.
DIncorrectThe database must remain the source of truth.

Exam Trap

Remember these points:

  • Lazy loading can serve stale data. Write-through avoids it, but caches unread data.
  • A TTL bounds the age of cached data.
  • The strategy is in the application code.

Memory Hook

Lazy = fill on a miss. Write-through = fill on every write. TTL = expiry.

4. High Availability and Backups

Problem Statement

The FlashCart cache now holds sessions that customers cannot lose. If a cache node fails, or a whole zone or Region fails, the shop must keep working. The team also needs a way to restore the cache after an error.

4.1 High Availability

  • Valkey and Redis OSS use replication groups: a primary node and replica nodes.
  • Multi-AZ with automatic failover promotes a replica when the primary fails, or when its zone has a problem. For a sharded workload, use at least three shards and three zones.
  • For cluster mode enabled, Multi-AZ is automatic.
  • The application must handle the reconnection, and a cluster-aware client library detects changes in the topology.
  • Memcached has no replication or failover. If a node fails, the data on it is lost, and the application reads the database again.

4.2 Global Datastore

  • Global Datastore replicates a Valkey or Redis OSS cache across Regions, for low-latency global reads and for disaster recovery from a Regional failure.
  • Test the cross-Region failover before you need it in production.

4.3 Backups

  • Valkey and Redis OSS support automatic and manual backups (snapshots), and a restore creates a new cache.
  • Schedule the automatic backups for a period of low use, and review the retention period.
  • Memcached node-based clusters are not persistent and have no backups.

5. Security

Problem Statement

The FlashCart security team asks who can reach the cache and how the data in it is protected, because the cache holds session data.

5.1 Network and Access

  • An ElastiCache cache runs in your VPC, in private subnets. A security group controls which clients can connect.
  • IAM policies apply to the ElastiCache API, which creates, modifies, and deletes caches. They do not control the data commands inside the cache.
  • Valkey and Redis OSS support Redis AUTH (a password or token) as an extra layer on top of the security group, and IAM authentication for the data connection.
  • Memcached supports SASL-based authentication.

5.2 Encryption

  • Encryption in transit uses TLS (SSL) for Valkey and Redis OSS.
  • Encryption at rest uses AWS KMS for Valkey and Redis OSS.

6. ElastiCache Pricing

Problem Statement

The FlashCart finance team asks what ElastiCache costs, and whether serverless or nodes is cheaper.

6.1 What You Pay For

Prices change often and differ by Region. Check the current rates on the Amazon ElastiCache pricing page, and estimate your own cost with the AWS Pricing Calculator.

  • Node-based clusters: node hours for each node, by node type. Each replica is a node with its own cost, and reserved nodes lower the price of steady use.
  • Serverless: you pay for the data that you store and for the compute that your requests use.
  • Backups: backup storage beyond the included amount.
  • Data transfer: traffic between Availability Zones and Regions, including Global Datastore replication.

6.2 Lowering the Cost

  • Use Serverless for variable workloads, and reserved nodes for steady node-based ones.
  • Size the cache for the working set, not for the whole database.
  • Use a TTL so that unused data leaves the cache.
  • Keep the cache in the same Availability Zone as the application where possible, to lower the data transfer cost.

Exam Trap

Remember these points:

  • Each replica node adds a node cost.
  • A cache that is too small has a low hit rate, so the database still takes the load.

Memory Hook

Cache the working set. Reserved nodes for steady use. Serverless for variable use.

SAA-C03 Keyword Triggers

Trigger 1: “Variable cache workload with no nodes to choose”

Trigger 2: “Steady cache workload at the lowest cost”
→ Node-based cluster with reserved nodes

Trigger 3: “Remove unused data from the cache automatically”

7.4 Lesson Summary

This lesson covered the following points:

  • ElastiCache is a managed in-memory cache with sub-millisecond latency. It supports Valkey, Redis OSS, and Memcached, and it comes as Serverless or as node-based clusters.
  • Valkey and Redis OSS add rich data structures, replication, Multi-AZ automatic failover, backups, and Global Datastore. Memcached is simple and has none of those.
  • Lazy loading fills the cache on a miss and can serve stale data. Write-through updates the cache on every write. A TTL bounds the age of the data.
  • Security groups, Redis AUTH, IAM authentication, TLS, and KMS protect the cache. IAM policies cover the API.
  • DAX is for DynamoDB. ElastiCache is the general answer for RDS and Aurora, and for advanced features.

Memory Hook

Hit is fast, miss goes to the database. Lazy fills on a miss, write-through fills on a write, TTL expires. DAX for DynamoDB, ElastiCache for the rest.

8. Knowledge Check

Answer each question in your own words before you open the model answer. The questions were written for this course.

Question 1: Explain why an application uses a cache, and what ElastiCache provides.

Maps to: Objectives 1 and 2 (Comprehension).

A cache keeps frequently used data in fast memory, so repeated reads skip the database. This lowers the database load and the latency, and it helps make an application stateless by sharing session data. ElastiCache is a managed in-memory data store with sub-millisecond latency. AWS handles the patching, configuration, monitoring, failure recovery, and backups, and it supports Valkey, Redis OSS, and Memcached.

Question 2: Compare Valkey or Redis OSS with Memcached, and ElastiCache Serverless with a node-based cluster.

Maps to: Objective 3 (Analysis).

Valkey and Redis OSS offer rich data structures, replication, Multi-AZ automatic failover, backups, and Global Datastore. Memcached is simple and multi-threaded, with no replication, no failover, and no persistence on node-based clusters. Serverless needs no node choices and scales automatically, with Valkey and Redis OSS in cluster mode enabled only. A node-based cluster gives control over the node type, the count, and the cluster mode.

Question 3: Describe lazy loading, write-through, and TTL, and when to combine them.

Maps to: Objective 4 (Application).

Lazy loading reads the cache first, and on a miss reads the database and fills the cache, so only requested data is cached but it can be stale. Write-through updates the cache on every write, so there is no stale data for written items, but unread data fills the cache. A TTL expires keys automatically. A common design uses write-through for data that must be fresh and lazy loading with a TTL for the rest.

Question 4: Explain how to keep an ElastiCache cache available and protected across zones and Regions.

Maps to: Objective 5 (Application).

Use Valkey or Redis OSS with a primary and replicas in several Availability Zones and Multi-AZ automatic failover. Add Global Datastore for cross-Region replication and disaster recovery. Use backups and snapshots for recovery. Put the cache in private subnets, limit access with security groups, add Redis AUTH or IAM authentication, and turn on TLS and KMS encryption.

Question 5: Choose between DAX and ElastiCache for two different scenarios.

Maps to: Objective 6 (Evaluation).

Choose DAX when the source database is DynamoDB and the reads repeat, because it needs few code changes. Choose ElastiCache when the source is RDS or Aurora, or when the application needs advanced structures such as sorted sets, or one cache must serve many systems.

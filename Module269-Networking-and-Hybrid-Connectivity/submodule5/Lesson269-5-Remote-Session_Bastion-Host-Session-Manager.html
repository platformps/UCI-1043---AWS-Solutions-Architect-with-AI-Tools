Lesson 269.5 - Remote Session: Bastion Host, Session Manager

Reach private instances securely with bastion hosts, Session Manager, and EC2 Instance Connect Endpoint.

Overview and Objectives

Lesson Overview

This lesson covers how administrators securely reach instances in private subnets: the classic bastion host (jump box), how to secure and scale it, and the modern alternatives that remove it.

1. What Is a Bastion Host?

Problem Statement

Your application servers and databases run in private subnets, exactly as good design requires: they have no public IP addresses and cannot be reached from the internet. Then an application server misbehaves at 2 AM, and an administrator needs to log in with SSH to investigate.

Giving every server a public IP and opening port 22 to the internet would undo all that protection. You need one tightly controlled entry point that administrators can reach, and that can reach the private servers on their behalf.

1.1 What Is a Bastion Host?

  • A bastion host (also called a jump box or jump server) is an EC2 instance in a public subnet that acts as the single, hardened entry point for administrative access to instances in private subnets.
  • Administrators connect to the bastion first, using SSH for Linux or RDP for Windows, and then "jump" from it to the private instances.
  • The private instances never need a public IP, and they accept administrative connections only from the bastion.
  • Because it is exposed to the internet, the bastion is a target. It must run minimal software, be patched, and accept connections only from trusted IP addresses.

1.2 How It Works

  1. The bastion host runs in a public subnet, with a public IP or Elastic IP, and a route to the Internet Gateway.
  2. The administrator connects to the bastion over SSH (port 22), or RDP (port 3389) for Windows.
  3. From the bastion, the administrator opens a second SSH connection to the private instance, using its private IP.
  4. The private instances’ route tables have no route to the Internet Gateway, so nothing on the internet can reach them directly.

1.3 Security Groups: The Key Exam Topic

  • The bastion is in the public subnet, which is connected to all the other private subnets in the VPC through the local route.
  • The bastion host’s security group must allow inbound traffic from the internet on port 22, but only from a restricted CIDR, for example the public CIDR of your corporation.
  • The security group of the private EC2 instances must allow port 22 from the security group of the bastion host, or from the bastion host’s private IP.
Security Groups: The Key Exam Topic.
Security groupInbound ruleWhy
Bastion-SG (on the bastion)TCP 22 from the administrators’ public IP range only, for example 203.0.113.10/32Never 0.0.0.0/0. Only trusted networks can even try to log in.
App-SG (on the private instances)TCP 22 from Bastion-SG (a security group reference)Only the bastion can SSH in. Referencing the security group keeps working even if the bastion’s IP changes.

Exam Trap

0.0.0.0/0 on port 22.

An answer that opens the bastion’s port 22 to 0.0.0.0/0 is almost always wrong. The secure answer restricts it to the company’s public IP range (CIDR), and the private instances allow SSH only from the bastion’s security group.

1.4 Connecting Through the Bastion

The private instance needs your SSH key, but you should never copy your private key onto the bastion: if the bastion is compromised, the attacker gets the key to every server. Instead, keep the key on your laptop and use one of these:

Option 1: SSH ProxyJump (one command, recommended):

ssh -J ec2-user@<bastion-public-ip> ec2-user@10.0.2.15

Option 2: SSH agent forwarding:

ssh-add my-key.pem
ssh -A ec2-user@<bastion-public-ip>
# then, on the bastion:
ssh ec2-user@10.0.2.15

Both let the bastion pass your authentication along without the private key ever being stored on it. ProxyJump is safer, because the bastion never gets access to your SSH agent. For Windows instances, the same idea applies with an RDP bastion, often running Remote Desktop Gateway.

2. Securing & Designing a Bastion Host

Problem Statement

Your bastion host is now the front door to every private server. If an attacker gets in, they can reach everything behind it. If it crashes or its Availability Zone goes down, no administrator can reach anything during an incident. You need the bastion to be hard to break into, easy to audit, and still available when you need it most.

2.1 Hardening Checklist

Hardening Checklist.
PracticeWhy it matters
Restrict the source IPAllow port 22 (or 3389) only from your company’s IP range, never from 0.0.0.0/0.
Keep it minimalUse a minimal, up-to-date AMI. Run no applications or other software on it; it is only a jump point.
Never store private keys on itUse ProxyJump or agent forwarding (section 1.4).
Patch regularlyIt is internet-facing, so unpatched software is a direct risk. Systems Manager Patch Manager can automate this.
Use a small instance typeIt only forwards connections, so a small instance keeps cost low.
Use a network ACL as a second layerBlock known bad IP ranges at the subnet level.
Stop it when not neededLess time online means less exposure and less cost.

2.2 High Availability

A single bastion in one Availability Zone is a single point of failure. For production environments:

  • Run the bastion in an Auto Scaling group that spans public subnets in at least two AZs, so a failed instance is replaced automatically.
  • Put a Network Load Balancer in front, listening on port 22, so administrators always use the same address, or attach an Elastic IP that a startup script moves to the new instance.

2.3 Logging and Auditing

  • Send the bastion’s SSH logs to CloudWatch Logs, using the CloudWatch agent, to keep a record of who logged in and when.
  • Enable VPC Flow Logs to see every connection attempt to and from the bastion, including rejected ones.
  • Use AWS CloudTrail to audit changes to the bastion’s security groups and instance.

2.4 A Bastion That Also Does NAT

In low-cost, non-production environments, one EC2 instance in the public subnet can act as both the bastion host and a NAT instance. This is one of the few scenarios where the exam expects a NAT instance instead of a NAT Gateway (see lesson 269.2, NAT Instance and NAT Gateway).

SAA-C03 Keyword Triggers

Trigger 1: “The bastion host must remain available if an Availability Zone fails”→ Bastion in an Auto Scaling group across multiple AZs, with a Network Load Balancer or Elastic IP

Trigger 2: “Audit who connected to the bastion host”→ Ship SSH logs to CloudWatch Logs (and use Session Manager logging if allowed)

Trigger 3: “Combine SSH access and outbound internet access on one low-cost instance in a dev environment”→ A NAT instance that doubles as a bastion host

3. The Modern Alternative: AWS SSM Session Manager (Eliminates Bastion Host)

Problem Statement

Even a well-secured bastion is work: an internet-facing server to patch, SSH keys to distribute and rotate, a public IP to pay for, and an open port that attackers will keep scanning. Your security team asks: can we give administrators access to private instances with no bastion, no open inbound ports, and no SSH keys at all?

3.1 What Is Session Manager?

  • Session Manager allows you to start a secure shell on your EC2 instances and on-premises servers from the AWS console or CLI. (On-premises servers need the SSM Agent and must be registered with Systems Manager through a hybrid activation.)
  • No SSH access, bastion hosts, or SSH keys needed.
  • No port 22 needed, or any other open inbound port, for better security.
  • Supports Linux, macOS, and Windows.
  • The SSM Agent on the instance connects outbound to the Systems Manager service over HTTPS (443). Because the connection starts from inside, no inbound security group rule is needed.
  • Access is controlled with IAM policies, not SSH keys, so you can grant or revoke access per user and per instance.
  • Send session log data to Amazon S3 or CloudWatch Logs; session starts are also recorded in CloudTrail for auditing.
  • It also supports port forwarding, for example to reach a database or an RDP port through the session.

In the EC2 console, Session Manager is one of the options on an instance’s Connect page. If the instance is not set up for it yet, the console explains why:

3.2 How It Works

  1. The SSM Agent connects to Systems Manager. When the instance starts, the agent opens an outbound HTTPS connection to the Systems Manager service and keeps it open.
  2. The user connects to Session Manager from the console or CLI. IAM permissions decide which users can start sessions, and on which instances.
  3. The session starts over the agent’s channel. Because the agent already connected out, nothing on the internet ever connects in to the instance.

3.3 Required Setup Components

  1. The SSM Agent installed on the instance (it comes preinstalled on Amazon Linux and many other AWS-provided AMIs).
  2. An attached IAM role that lets the agent talk to Systems Manager, for example with the AmazonSSMManagedInstanceCore managed policy.
  3. Outbound HTTPS (port 443) from the instance to these three endpoints:
    • ec2messages.region.amazonaws.com
    • ssm.region.amazonaws.com
    • ssmmessages.region.amazonaws.com

Endpoints, Not Policies

The three addresses above are service endpoints: the hostnames of the Systems Manager services in your Region, which the SSM Agent connects to over HTTPS (443). They are not IAM policies.

EndpointWhat the agent uses it for
ssm.region.amazonaws.comThe main Systems Manager API: registering the instance and receiving its configuration
ec2messages.region.amazonaws.comThe messaging channel that delivers commands, for example from Run Command
ssmmessages.region.amazonaws.comThe session data channel that carries Session Manager’s interactive shell traffic

The instance needs both: network access to these endpoints (item 3), and permission to use them through the attached IAM role (item 2). Missing either one is the most common reason Session Manager fails to connect.

How the instance reaches those endpoints depends on its subnet:

3.3.1 EC2 in a Public Subnet

3.3.2 EC2 in a Private Subnet

Option 1 — with internet access, through a NAT Gateway. The agent reaches the Systems Manager endpoints through a NAT Gateway in a public subnet and the Internet Gateway.

Option 2 — with no internet access at all, through interface VPC endpoints. Create interface endpoints for ssm, ssmmessages, and ec2messages, so the traffic never leaves the AWS network (see lesson 269.3, Interface Endpoints). The endpoints’ security group must allow inbound HTTPS (443) from the instances.

In both cases, the security groups need no inbound rules for Session Manager, only outbound HTTPS.

Why This Matters for the Exam

Bastion hosts are still tested, but when a question stresses "no inbound ports," "no SSH keys," "no bastion," "least operational overhead," or "audit every session," the expected answer is usually Session Manager.

  • No inbound ports needed: eliminates the requirement to open inbound TCP port 22 (SSH) or port 3389 (RDP) in security groups or network ACLs. All management traffic originates outbound from the SSM Agent to the AWS Systems Manager service endpoints.
  • Private subnet remote management: connects directly to EC2 instances in isolated private subnets that have no public IP addresses or Internet Gateways (through interface VPC endpoints, section 3.3.2).

Trigger 3: “Session Manager works on some instances but not on instances in an isolated private subnet without internet access”→ Add interface VPC endpoints for ssm, ssmmessages, and ec2messages (and check the IAM instance profile)

4. EC2 Instance Connect Endpoint

Problem Statement

Your administrators like Session Manager, but some of them depend on their usual SSH and RDP clients and tools, and some instances cannot run the SSM Agent. They still need to reach private instances without a bastion, a public IP, or an Internet Gateway.

4.1 EC2 Instance Connect and EC2 Instance Connect Endpoint

  • EC2 Instance Connect pushes a temporary SSH public key to the instance for 60 seconds, controlled by IAM, so you do not manage long-lived keys. On its own, it needs the instance to be reachable, for example with a public IP.
  • EC2 Instance Connect Endpoint (launched June 2023) extends this to private instances. You create an endpoint in a subnet, and it tunnels SSH or RDP to instances in the same VPC.
  • It needs no public IP on the instance, no Internet Gateway in the VPC, no bastion, and no agent.
  • Access combines IAM permissions with security group rules, and connections are audited in CloudTrail.
  • There is no additional charge for the endpoint; standard data transfer charges apply.

4.2 Three Ways to Reach a Private Instance

6. Knowledge Check

No multiple choice. Answer each question in your own words first, then expand the model answer to compare.

Question 1. What is a bastion host, where does it live, and why do private instances need one?

Show the model answer

A bastion host (jump box) is a hardened EC2 instance in a public subnet that acts as the single entry point for administrative access. Private instances have no public IP and no route from the internet, so administrators connect to the bastion first and then jump to the private instances using their private IPs.

Question 2. Write the two security group rules that make a bastion design secure, and explain each.

Show the model answer

Bastion-SG: allow TCP 22 only from the company’s public IP CIDR (never 0.0.0.0/0), so only trusted networks can reach the bastion. App-SG: allow TCP 22 only from Bastion-SG (a security group reference), so only the bastion can SSH into the private instances, even if its IP changes.

Question 3. Why should not you copy your private SSH key onto the bastion host, and what should you do instead?

Show the model answer

If the bastion is compromised, the attacker would get a key that opens every private server. Keep the key on your own machine and use SSH ProxyJump (ssh -J) or agent forwarding, so the bastion passes the authentication along without ever storing the key. ProxyJump is safer because the bastion never gets access to your agent.

Question 4. How would you make a bastion host highly available?

Show the model answer

Run it in an Auto Scaling group that spans public subnets in at least two Availability Zones, so a failed instance or AZ is replaced automatically. Put a Network Load Balancer on port 22 in front, or move an Elastic IP to the replacement instance, so administrators keep using the same address.

Question 5. How does Session Manager give shell access without any inbound ports, and what does it need to work in a private subnet with no internet access?

Show the model answer

The SSM Agent on the instance makes an outbound HTTPS connection to the Systems Manager service, and sessions travel over that connection, so no inbound rule is needed. Access is controlled with IAM. It needs the SSM Agent, an IAM instance profile (for example with AmazonSSMManagedInstanceCore), and network access to Systems Manager; without internet access, that means interface VPC endpoints for ssm, ssmmessages, and ec2messages.

Question 6. When would you choose EC2 Instance Connect Endpoint over Session Manager?

Show the model answer

When administrators need to use standard SSH or RDP clients to reach private instances, without a public IP, Internet Gateway, bastion, or agent. EC2 Instance Connect Endpoint tunnels SSH and RDP to instances in the same VPC, controlled by IAM and security groups, at no extra charge. Session Manager is better when you want no SSH keys at all and built-in session logging.

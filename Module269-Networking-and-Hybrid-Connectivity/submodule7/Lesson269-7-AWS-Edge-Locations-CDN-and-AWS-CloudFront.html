Lesson 269.7 - AWS Edge Locations, CDN and AWS CloudFront

Deliver content close to users with AWS edge locations and Amazon CloudFront.

Lesson Overview

1. AWS Edge Locations

Problem Statement

Your application runs in one AWS Region in the United States. Users in Asia reach it over the public internet, crossing many networks that you do not control. Each hop adds delay and risk, so the experience is slow and inconsistent.

You want users to enter the AWS network close to where they are, and travel the rest of the way over AWS’s own network. You also need to know which AWS services run at the edge.

1.1 What Is an Edge Location?

  • A site in the AWS global edge network, close to end users.
  • Designed to deliver AWS services with the lowest latency.
  • Also called a point of presence (PoP).
  • There are many more edge locations than Regions: more than 400 edge locations in 90+ cities across 48 countries (check the AWS Global Infrastructure page for current numbers).
  • You do not launch EC2 instances or create VPCs in an edge location. It is where AWS edge services run.
  • Connected to the AWS Regions by the AWS backbone network, a redundant, high-bandwidth fiber network around the globe.
  • Each PoP is isolated from the others, so a failure in one does not affect the rest.

Exam Trap

An edge location is not a Region or an Availability Zone.

You cannot deploy your workloads in an edge location. Regions and Availability Zones host your resources. Edge locations serve content and network features close to users.

1.2 Edge Locations and Regional Edge Caches

  • Edge locations: closest to users. They cache popular content.
  • Regional edge caches: fewer and larger. They sit between the edge locations and your origin and keep content longer.
  • Content flow: user → edge location → regional edge cache → origin (your Region).

1.3 How Traffic Flows

  • The user connects to the nearest edge location over the internet.
  • From there, traffic travels to your Region over the AWS backbone, not the public internet.
  • The response returns the same way.

1.4 Without the AWS Edge Network

  • Traffic crosses many non-AWS networks, often across several continents.
  • Every hop adds latency.
  • The path is unpredictable and can change at any time.
  • More hops mean more points of failure.

1.5 With the AWS Edge Network

  • The user connects to a nearby edge location.
  • From there, traffic uses the AWS backbone network all the way to the Region.
  • Fewer hops over networks you do not control.

1.5.1 Benefits

  • Lower latency for users around the world.
  • More consistent performance, because most of the path is on the AWS network.
  • Higher reliability, thanks to a redundant backbone.
  • Less load on your origin when content is cached at the edge.

Memory Hook

Without the edge = many hops across the public internet. With the edge = enter AWS close to the user, then ride the AWS backbone.

  • Global Accelerator: does not cache. It routes traffic over the AWS backbone to your endpoint, such as an Application Load Balancer, a Network Load Balancer, or an EC2 instance.
  • Both use edge locations and the AWS backbone.

Exam Trap

Caching or no caching.

If the question says cache content close to users, choose CloudFront. If it asks for static IP addresses, non-HTTP traffic, or fast failover without caching, choose Global Accelerator.

2. What Is a CDN?

Problem Statement

Your website serves the same images, videos, and scripts to millions of users around the world, all from servers in one Region. Every request travels a long way, the origin is busy answering the same requests again and again, and the site slows down at peak times.

You need a way to serve popular content from a place close to each user, and take the load off your origin.

2.1 What Is a CDN?

  • CDN = Content Delivery Network.
  • A network of geographically distributed servers that cache content close to users.
  • The servers sit in edge locations (points of presence).
  • Users get content from the nearest server, not from the origin.
  • The origin is where the original content lives, such as an S3 bucket, a load balancer, or a web server.

2.2 How a CDN Works

  • The user’s request is routed to the nearest edge location.
  • Cache hit: the content is in the cache, so the edge location returns it right away.
  • Cache miss: the content is not there, so the edge location fetches it from the origin (through a regional edge cache), stores a copy, and returns it.
  • The next user nearby gets a cache hit.
  • Cached content stays for its TTL (time to live). After that, the CDN checks the origin again.

2.3 Cache Hit vs. Cache Miss

Cache Hit vs. Cache Miss.
AspectCache hitCache miss
Where the content comes fromThe edge locationThe origin, through a regional edge cache
SpeedFastestSlower, but the copy is cached for next time
Load on the originNoneOne request

2.4 What a CDN Delivers

  • Static content: images, CSS, JavaScript, downloads, and video files.
  • Streaming video to many viewers.
  • Dynamic content: not cached the same way, but still faster because the CDN reaches the origin over a fast, optimized network path.

2.5 Benefits of a CDN

  • Lower latency: content comes from a nearby server.
  • Less load on the origin: most requests never reach it.
  • Better availability: traffic spikes are absorbed at the edge.
  • Security at the edge: HTTPS, DDoS protection, and a web application firewall can run at the edge.
  • Lower cost: less traffic from the origin.

2.6 The AWS CDN: Amazon CloudFront

  • Amazon CloudFront is the AWS CDN. It uses AWS edge locations and regional edge caches.
  • Origins: an S3 bucket, an Application Load Balancer, an EC2 instance, or any HTTP server.
  • TTL: controls how long content stays cached. An invalidation removes content from the cache early.
  • Access control: signed URLs and signed cookies for private content, and geo restriction to allow or block countries.
  • Works with AWS WAF and AWS Shield for protection at the edge.

Exam Trap

A CDN caches, an accelerator does not.

A CDN such as CloudFront caches content at the edge. AWS Global Accelerator does not cache: it only routes traffic over the AWS backbone. If the question mentions caching or reducing load on the origin, choose CloudFront.

Memory Hook

CDN = copies of your content kept close to users. Hit = served at the edge. Miss = fetched from the origin, then cached.

3. Amazon CloudFront

Problem Statement

Your website keeps images and scripts in an S3 bucket, and its API runs behind an Application Load Balancer. Users around the world see slow pages, the origin is overloaded at peak times, and the bucket must stay private. The site also needs HTTPS on your own domain, and content must be blocked in some countries.

You need one service that caches content close to users, protects the origin, and secures delivery.

3.1 What Is Amazon CloudFront?

  • The AWS content delivery network (CDN).
  • Delivers static, dynamic, and streaming content with low latency and high transfer speeds.
  • Runs on the AWS global edge network: edge locations plus regional edge caches.
  • A global service: you create a distribution, not a Regional resource.
  • Integrates with S3, ALB, EC2, API Gateway, Route 53, ACM, AWS WAF, and AWS Shield.
  • Pay as you go, and data from AWS origins to CloudFront is free.
  • When a request is made for the content, the user is served from the nearest edge server.

3.2 A Practical Example of Amazon CloudFront

Scenario

A media company in San Francisco publishes digital journals on many topics and delivers them through a standard website. Most of its readers are in the US, a smaller share are in Europe, and some are in Asia.

The company hosts its content in the US West Region, in an S3 bucket, and readers have been served without any issues.

Then subscribers in Europe and Asia start to complain about lag. When they move to a new page, it takes a few seconds to load.

What should the company do?

Solution

Keep the content in US West as the origin, and put Amazon CloudFront in front of it.

CloudFront keeps copies of the content in edge locations near the readers in Europe and Asia. They now get pages from a nearby location instead of from San Francisco, so pages load much faster.

3.2.1 Tradeoffs of a CDN

  • Delay in updates (stale content): cached copies do not change the moment the origin does. Content of a critical nature can reach users near the origin before users served from other locations.
    • Reduce it with a shorter TTL, an invalidation, or versioned file names.
  • Extra cost: delivering content across Regions costs money for data transfer and requests. Without a CDN, you do not pay for a delivery network.
    • Offset it with a high cache hit ratio (fewer origin requests), price classes, and the free tier.
  • More to manage: cache behaviors, TTLs, and security settings need to be set up and monitored.

3.3 What Is a Distribution?

  • A configuration object that you create.
  • It tells CloudFront how to deliver your content.

3.3.1 Distribution Types

  • CloudFront used to have two distribution types:
    • Web distribution = regular web content. It supports streaming, which allows users to watch directly, without downloading the file first.
    • RTMP distribution = Flash-based video streaming.
  • RTMP is discontinued. Do not select it as an answer in the exam.

3.5 How a Request Flows

  • The user requests a URL on your distribution (or your own domain name).
  • DNS routes the request to the nearest edge location.
  • Cache hit: the edge location returns the cached copy.
  • Cache miss: CloudFront checks the regional edge cache, then fetches the content from the origin.
  • CloudFront caches the content and returns it to the user, using the AWS backbone for the origin leg.

3.6 Origins

  • Amazon S3 bucket: the common choice for static content. Keep the bucket private and use origin access control (OAC).
  • ALB, EC2, or any HTTP server: for dynamic content and APIs, in AWS or on premises.
  • API Gateway and media services can also be origins.
  • VPC origins: reach an ALB, NLB, or EC2 instance in a private subnet.
  • Origin groups: a primary and a secondary origin, so CloudFront fails over if the primary returns errors.
  • You can use several origins in one distribution, chosen by cache behavior.

CloudFront can route viewer requests to different origins based on request attributes.

  • A common method is path-based routing, where the URL path determines which origin should handle the request

3.7 Caching

A cache behavior defines how CloudFront processes requests that match a particular path pattern.

A cache behavior controls:

  • Path pattern
  • Target origin
  • Viewer protocol policy
  • Allowed HTTP methods
  • Cached HTTP methods
  • Cache policy
  • Origin request policy
  • Response headers policy
  • Content compression
  • Signed URL or signed cookie requirements
  • CloudFront Functions or Lambda@Edge associations
  • Cache behaviors let you cache /images/* for a long time and send /api/* to the ALB with little or no caching.
  • The cache key decides what makes two requests the same. It can include query strings, headers, and cookies, set in a cache policy.
  • TTL: by default content is cached for 24 hours unless the origin sends cache headers. You can set a minimum, a default, and a maximum.
  • Invalidation: removes content from the cache before the TTL ends.
  • Versioned file names (such as app-v2.js) avoid the need to invalidate.
  • Fewer origin requests means a higher cache hit ratio, a faster site, and lower cost.

3.8 Security

Security is another important part of CloudFront.

3.8.1 CloudFront and HTTPS

  • CloudFront supports HTTPS, so applications can encrypt traffic between users and the distribution.
  • A viewer protocol policy can redirect HTTP to HTTPS or allow only HTTPS.
  • AWS Certificate Manager (ACM) can provision and manage the SSL/TLS certificates for CloudFront distributions.
  • For a custom domain, request the ACM certificate in us-east-1, add the domain as an alternate domain name, and point it to the distribution with a Route 53 alias record.
  • Applications can then use secure URLs such as https://example.com instead of sending traffic over an unencrypted connection.

3.8.2 CloudFront and AWS WAF

  • CloudFront can work with AWS WAF (Web Application Firewall) to protect applications from common web attacks.
  • For example, WAF can filter malicious requests before they reach the application infrastructure.
  • A common architecture is: User → CloudFront (with AWS WAF attached) → Application. WAF inspects requests at the edge.
  • It adds an extra security layer for internet-facing applications.

3.8.3 CloudFront and DDoS Protection

  • CloudFront is integrated with AWS Shield, which helps protect applications against distributed denial-of-service (DDoS) attacks.
  • AWS Shield Standard is automatic and included at no extra cost.
  • Instead of exposing the application infrastructure directly to every request, CloudFront acts as a globally distributed front layer.
  • This is particularly useful for applications that handle large amounts of internet traffic.

3.8.4 Access Control for Content

  • OAC: only CloudFront can read a private S3 bucket. This replaces the older origin access identity (OAI).
  • Signed URLs and signed cookies: serve private content only to authorized users. Use a signed URL for a single file, and signed cookies for many files.
  • Geo restriction: allow or block countries.
  • Field-level encryption: protects chosen form fields with an extra layer of encryption.

3.8.5 CloudFront Signed URLs

  • A CloudFront signed URL grants temporary access to one private file through CloudFront.
  • See tab 6 for the setup, the policies, and examples.

3.10 CloudFront Geo Restriction

  • You can restrict who can access your distribution.
  • Allowlist: allow your users to access your content only if they are in one of the countries on a list of approved countries.
  • Blocklist: prevent your users from accessing your content if they are in one of the countries on a list of banned countries.
  • The "country" is determined using a third-party Geo-IP database.
  • Use case: copyright laws that control access to content.

3.11 Serverless Edge Computing: CloudFront Functions and Lambda@Edge

What distinguishes CloudFront from a simple caching layer is its ability to run compute logic at the edge.

  • Brings compute closer to users by running code at edge locations.
  • Serverless: automatically handles millions of requests per second.

CloudFront provides two options.

3.11.1 CloudFront Functions

  • CloudFront Functions run at the point of presence (PoP) in sub-millisecond time.
  • Lightweight JavaScript functions that run at CloudFront edge locations before cache lookup.
  • CloudFront Functions support two event triggers:
    • Viewer Request: before CloudFront checks the cache.
    • Viewer Response: before CloudFront returns the response to the viewer.
  • Use them for lightweight, high-volume operations: URL rewrites, header manipulation, cache key normalization, or simple redirect logic.
  • They are intentionally constrained: limited memory and no network access, so they are not suitable for external API calls.

The workflow below shows where CloudFront Functions run: on the viewer request, before CloudFront checks the cache, and on the viewer response, before CloudFront returns the response to the viewer.

3.11.2 Lambda@Edge

  • Lambda@Edge functions run at the regional edge cache locations globally.
  • They support longer execution times, network access, and the ability to generate or modify response bodies.
  • Use them to authenticate users against an external identity provider, resize images dynamically, or personalize content based on geolocation.
  • The trade-off is higher latency and cost than CloudFront Functions.

3.12 Pricing

  • Pay for data transfer out to viewers and for HTTP and HTTPS requests. Rates vary by Region.
  • Data from AWS origins to CloudFront is free.
  • An always-free tier gives you 1 TB of data transfer out and 10 million requests per month.
  • Price classes lower the cost by using fewer, cheaper edge locations (for example Price Class 100).
  • Flat-rate plans (introduced in November 2025) bundle CloudFront with WAF, DDoS protection, and DNS for one monthly price with no overage charges.
  • Always check the current CloudFront pricing page.

3.13 Common Use Cases

  • Static website in S3, delivered worldwide over HTTPS.
  • Dynamic sites and APIs in front of an ALB, with faster connections to the origin.
  • Video streaming and software downloads.
  • Protecting origins from DDoS attacks and traffic spikes.
  • Private content for paying or logged-in users, with signed URLs or cookies.

4. CloudFront: Cache Invalidations

Problem Statement

You updated index.html and the images at your origin, but users still see the old version. CloudFront keeps serving the cached copies until their TTL ends.

You need to remove the old copies now.

4.1 What Is a Cache Invalidation?

  • Removes objects from the CloudFront cache before the TTL ends.
  • CloudFront sends the invalidation to all edge locations.
  • The next request is a cache miss, so CloudFront fetches the new version from the origin and caches it.

4.2 How It Works

  • You update the files at the origin.
  • You create an invalidation for the paths to remove.
  • CloudFront removes them from the cache in every edge location.
  • The next GET fetches the fresh files from the origin.

4.3 Good to Know

  • Invalidate specific paths, such as /index.html, or use a wildcard, such as /images/* or /* for everything.
  • It is not instant. It takes a little time to reach all edge locations.
  • A monthly allowance of invalidation paths is free, and more cost extra. Check the pricing page.
  • To avoid invalidations, use versioned file names (such as app-v2.js) or a shorter TTL.

5. CloudFront: S3 as an Origin

Problem Statement

Your static website lives in an S3 bucket. If you make the bucket public so that users can reach it, anyone can bypass CloudFront. You lose HTTPS on your own domain, caching, and WAF protection.

You need the content to be served only through CloudFront, with the bucket kept private.

5.1 Why Use S3 as a CloudFront Origin?

  • An Amazon CloudFront S3 origin lets you securely speed up the delivery of static web assets (like images, HTML, CSS, and JS) by caching them globally at CloudFront edge locations.
  • S3 is durable, low-cost storage for static content: HTML, CSS, JavaScript, images, and video files.
  • CloudFront caches that content worldwide, so users get lower latency and S3 gets fewer requests.
  • Data from S3 to CloudFront is free. You pay for CloudFront delivery.
  • You add HTTPS, a custom domain, AWS WAF, geo restriction, and signed URLs on top of S3.

5.2 How It Works

  • The bucket is private, with Block Public Access turned on.
  • CloudFront sends signed requests to S3, using origin access control (OAC).
  • A bucket policy allows only that CloudFront distribution to read the objects.

5.3 Origin Access Control (OAC)

  • OAC lets CloudFront authenticate to an S3 origin using an IAM service principal.
  • Setup: create the distribution with the S3 origin, create an OAC, then add the bucket policy. The console can copy the policy for you.
  • The policy allows cloudfront.amazonaws.com, and the AWS:SourceArn condition limits it to your distribution.
  • To let CloudFront upload objects too, also allow s3:PutObject.
  • If the objects use SSE-KMS, the KMS key policy must also allow the CloudFront service principal.
{
  "Version": "2012-10-17",
  "Statement": [{
    "Sid": "AllowCloudFrontServicePrincipalReadOnly",
    "Effect": "Allow",
    "Principal": { "Service": "cloudfront.amazonaws.com" },
    "Action": "s3:GetObject",
    "Resource": "arn:aws:s3:::amzn-s3-demo-bucket/*",
    "Condition": { "StringEquals": {
      "AWS:SourceArn": "arn:aws:cloudfront::111122223333:distribution/<distribution ID>" } }
  }]
}

5.5 Settings for a Static Website

  • Default root object: set index.html, so that requests for the root of the site work. It applies to the root only.
  • Custom error responses: return a friendly page, or /index.html for a single-page app, when S3 answers with an error.
  • Viewer protocol policy: redirect HTTP to HTTPS.
  • Custom domain: an alternate domain name, an ACM certificate in us-east-1, and a Route 53 alias record.
  • Compression: turn on compression for text files.
  • Updates: use versioned file names or an invalidation after you deploy new files.
  • CORS: if your site needs it, forward the Origin header to S3.

5.6 Layers of Access Control

  • OAC and the bucket policy: who can reach the bucket (only CloudFront).
  • Signed URLs and signed cookies: who can reach CloudFront content (authorized users).
  • AWS WAF and geo restriction: which requests are allowed at the edge.
  • An S3 presigned URL is different: it gives temporary access straight to S3, not through CloudFront.

6. CloudFront Signed URLs

Problem Statement

An online training site sells course videos. Only customers who paid may watch them, and only for a limited time. If the video URL is public, anyone can share it.

You need private content that CloudFront serves only to authorized users.

6.1 What Is a Signed URL?

  • A CloudFront signed URL is a URL with a signature and an expiry added.
  • It grants temporary access to one private file through CloudFront.
  • Without a valid signed URL, CloudFront returns 403 Access Denied for that content.
  • Your application creates the URL with a private key, and CloudFront checks it with the matching public key.

6.2 Signed URLs vs. Signed Cookies

Signed URLs vs. Signed Cookies.
AspectSigned URLSigned cookies
Access toOne file per URLMany files, without changing their URLs
Best forA single download or video, or clients that do not support cookiesA members area or many streaming files
Carried inQuery string of the URLThree cookies sent with each request

6.3 How to Set It Up

  • Create a key pair.
  • Upload the public key to CloudFront and add it to a key group.
  • In the cache behavior, turn on restrict viewer access and choose the trusted key group.
  • Your application keeps the private key and signs each URL or cookie.

6.4 Canned Policy vs. Custom Policy

Canned Policy vs. Custom Policy.
AspectCanned policyCustom policy
ControlsExpiry time onlyExpiry, optional start time, and optional IP address range
One URL forOne fileOne file or many files, with a wildcard such as /reports/*
URL parametersExpires, Signature, Key-Pair-IdPolicy, Signature, Key-Pair-Id

6.5 Examples

6.5.1 Example 1: Paid Video (Canned Policy)

After a purchase, the application creates a signed URL for /private/video.mp4 that works until the Expires time, for example one hour from now.

https://d111111abcdef8.cloudfront.net/private/video.mp4
  ?Expires=1767225600
  &Signature=Ab12Cd34...(signature)
  &Key-Pair-Id=K2JCJMDEHXQW5F
  • Expires: when the link stops working.
  • Signature: proves the URL was signed with the private key.
  • Key-Pair-Id: tells CloudFront which public key to check the signature with.

6.5.2 Example 2: Report Download for an Office (Custom Policy)

A finance team shares reports only from the office network (203.0.113.0/24), during one day. A custom policy sets the time window and the IP range, and a wildcard covers every report.

{
  "Statement": [{
    "Resource": "https://d111111abcdef8.cloudfront.net/reports/*",
    "Condition": {
      "DateGreaterThan": { "AWS:EpochTime": 1767222000 },
      "DateLessThan":    { "AWS:EpochTime": 1767308400 },
      "IpAddress":       { "AWS:SourceIp": "203.0.113.0/24" }
    }
  }]
}
https://d111111abcdef8.cloudfront.net/reports/q3.pdf
  ?Policy=eyJTdGF0ZW1lbnQiOi4uLn0_(base64 policy)
  &Signature=Zx98Yw76...(signature)
  &Key-Pair-Id=K2JCJMDEHXQW5F
  • Policy carries the base64-encoded policy, instead of Expires.
  • Requests from another IP address, or outside the time window, get 403.

6.5.3 Example 3: Members Area (Signed Cookies)

A members area has hundreds of video files. Instead of a signed URL for each file, the site sets signed cookies after the member logs in, and every file URL stays unchanged.

Set-Cookie: CloudFront-Policy=eyJTdGF0ZW1lbnQiOi4uLn0_...
Set-Cookie: CloudFront-Signature=Ab12Cd34...
Set-Cookie: CloudFront-Key-Pair-Id=K2JCJMDEHXQW5F

6.5.4 Example 4: Creating a Signed URL in Code

import { getSignedUrl } from "@aws-sdk/cloudfront-signer";

const signedUrl = getSignedUrl({
  url: "https://d111111abcdef8.cloudfront.net/private/video.mp4",
  keyPairId: "K2JCJMDEHXQW5F",
  privateKey: process.env.CF_PRIVATE_KEY,
  dateLessThan: new Date(Date.now() + 60 * 60 * 1000).toISOString()  // valid for 1 hour
});
  • The code runs in your application, such as a backend or a Lambda function, and never in the browser.
  • Keep the private key secret, for example in AWS Secrets Manager.

OAC controls who can reach the S3 bucket (only CloudFront). Signed URLs and cookies control which users can reach the content through CloudFront. One file means a signed URL. Many files means signed cookies. Use both OAC and signed URLs to protect private S3 content.

7. CloudFront vs. S3 Cross-Region Replication

Problem Statement

Your content is in an S3 bucket in one Region, and users around the world need it with low latency. You can use CloudFront or S3 Cross-Region Replication (CRR). Which one fits your case?

7.1 CloudFront

  • Uses the global edge network.
  • Files are cached for a TTL (maybe a day).
  • Great for static content that must be available everywhere.

7.2 S3 Cross-Region Replication

S3 Cross-Region Replication (CRR) is a feature that automatically copies objects from a source bucket to a bucket in another Region, usually in near real time. It controls where your data is stored.

  • Must be set up for each Region where you want replication to happen.
  • Files are updated in near real time.
  • The copies are read only.
  • Great for dynamic content that needs to be available at low latency in a few Regions.

9. Knowledge Check

No multiple choice. Answer each question in your own words first, then expand the model answer to compare.

Question 1. What is an AWS edge location, and how does it differ from a Region and an Availability Zone?

Show the model answer

An edge location, also called a point of presence, is a site in the AWS global edge network that is close to end users and delivers AWS services with low latency. There are many more of them than Regions. A Region and its Availability Zones host your workloads, while an edge location does not: it serves content and network features close to users.

Question 2. What is a regional edge cache?

Show the model answer

A regional edge cache sits between the edge locations and your origin. There are fewer of them than edge locations, and each is larger, so content can be kept longer. A request goes from the user to an edge location, then to a regional edge cache, and then to the origin if the content is not cached.

Question 3. How does the path from a user to your application differ with and without the AWS edge network?

Show the model answer

Without it, traffic hops through many non-AWS networks, often across several continents, which adds latency, makes the path unpredictable, and adds points of failure. With it, the user connects to a nearby edge location and the traffic then travels over the AWS backbone network to the Region, with fewer hops over networks you do not control.

Question 4. Which AWS services use edge locations?

Show the model answer

Amazon CloudFront for caching and edge code (Lambda@Edge and CloudFront Functions), Amazon Route 53 for DNS, AWS Global Accelerator for routing over the AWS backbone with static anycast IP addresses, AWS WAF and AWS Shield for protection at the edge, and S3 Transfer Acceleration for faster uploads.

Question 5. When would you choose Global Accelerator instead of CloudFront?

Show the model answer

Choose CloudFront when you want to cache content close to users. Choose Global Accelerator when you need static anycast IP addresses, non-HTTP traffic such as TCP or UDP, or fast failover and better performance without caching. Both use edge locations and the AWS backbone.

Question 6. Can you run EC2 instances in an edge location? Explain.

Show the model answer

No. Edge locations run AWS edge services, such as CloudFront, Route 53, and Global Accelerator. You deploy EC2 instances and other workloads in a Region, in its Availability Zones.

Question 7. What is a CDN, and how does it improve performance?

Show the model answer

A CDN, or content delivery network, is a network of geographically distributed servers that cache content close to users. Users get content from the nearest server instead of the origin, which lowers latency and takes load off the origin. Amazon CloudFront is the AWS CDN.

Question 8. Explain a cache hit and a cache miss.

Show the model answer

On a cache hit, the content is already in the edge location’s cache, so it is returned right away. On a cache miss, the edge location fetches the content from the origin, through a regional edge cache, stores a copy, and returns it. The next nearby user then gets a cache hit. Cached content stays for its TTL.

Question 9. You updated a file at the origin, but users still see the old version from CloudFront. What can you do?

Show the model answer

The old copy stays in the cache until its TTL expires. You can create a CloudFront invalidation to remove it from the cache early, or set a shorter TTL. The next request then fetches the new version from the origin.

Question 10. What is a CloudFront distribution, an origin, and a cache behavior?

Show the model answer

A distribution is the CloudFront configuration, with its own domain name. An origin is where the original content lives, such as an S3 bucket, an ALB, EC2, or any HTTP server. A cache behavior is a rule matched by path pattern, such as /images/*, that chooses the origin and sets caching and security options for those requests.

Question 11. How do you serve a private S3 bucket only through CloudFront?

Show the model answer

Keep the bucket private, make it the CloudFront origin, and use origin access control (OAC), so only CloudFront can read the objects. This replaces the older origin access identity. Users can then reach the content only through the distribution.

Question 12. How do you restrict CloudFront content to authorized users, and when do you use signed URLs versus signed cookies?

Show the model answer

Require signed URLs or signed cookies. A signed URL gives access to a single file, and signed cookies give access to many files without changing each URL. You can also restrict by country with geo restriction.

Question 13. How do you use HTTPS with your own domain on CloudFront?

Show the model answer

Request a certificate in AWS Certificate Manager in the us-east-1 Region, add your domain as an alternate domain name on the distribution, attach the certificate, and point the domain to the distribution with a Route 53 alias record. Set the viewer protocol policy to redirect HTTP to HTTPS or to allow only HTTPS.

Question 14. Compare CloudFront Functions and Lambda@Edge.

Show the model answer

CloudFront Functions run JavaScript at the edge locations on viewer requests and responses, for simple and very fast tasks such as URL rewrites, redirects, and header changes. Lambda@Edge runs Node.js or Python at the regional edge caches on viewer and origin events, for more complex logic such as network calls or choosing an origin.

Question 15. A media company hosts its website in a US Region, and readers in Europe and Asia complain about slow page loads. What should it do, and what are the tradeoffs?

Show the model answer

Keep the content in the US Region as the origin and put CloudFront in front of it, so copies are cached at edge locations near the readers and pages load much faster. The tradeoffs are that cached copies can be out of date until the TTL ends or you invalidate them, and that delivering content across Regions adds cost. A shorter TTL, invalidations, versioned file names, a high cache hit ratio, and price classes help.

Question 16. How do you make sure an S3 bucket can be read only through CloudFront?

Show the model answer

Keep the bucket private with Block Public Access on, and use the bucket’s REST endpoint as the CloudFront origin with origin access control (OAC). Then add a bucket policy that allows the CloudFront service principal (cloudfront.amazonaws.com) to read the objects, with an AWS:SourceArn condition that limits it to your distribution. Direct requests to the S3 URL are then denied.

Question 17. Why cannot an S3 static website endpoint use OAC?

Show the model answer

CloudFront treats a website endpoint as a custom origin, and OAC works only with a regular S3 origin that uses the REST endpoint. A website endpoint also accepts HTTP only and requires a public bucket. To keep the bucket private, use the REST endpoint with OAC and set the default root object and custom error responses in CloudFront.

Question 18. Compare OAC and OAI.

Show the model answer

OAC is the recommended method. It authenticates with an IAM service principal and signed requests, supports SSE-KMS, works in all S3 Regions, and allows more granular policies. OAI is the legacy method and does not support SSE-KMS. Distributions that use OAI can migrate to OAC.

Question 19. The S3 objects are encrypted with SSE-KMS, and CloudFront returns access denied. What do you check?

Show the model answer

Check that the distribution uses OAC and not OAI, and that the KMS key policy allows the CloudFront service principal to use the key (decrypt and generate data key), limited to your distribution with the AWS:SourceArn condition. Also check the S3 bucket policy.

Question 20. When do you choose CloudFront, and when S3 Cross-Region Replication, to make content available worldwide?

Show the model answer

Choose CloudFront for static content that must be available everywhere: it uses the global edge network and caches files for a TTL. Choose S3 Cross-Region Replication for dynamic content that needs low latency in a few Regions: it must be set up for each Region, updates files in near real time, and the copies are read only.

Question 21. What is a CloudFront signed URL, and how is it created and checked?

Show the model answer

A signed URL grants temporary access to one private file through CloudFront. You upload a public key to CloudFront in a key group and turn on restricted viewer access in the cache behavior. Your application signs the URL with the private key, adding an expiry and a signature, and CloudFront checks it with the public key. Without a valid signed URL, CloudFront returns 403.

Question 22. When do you use a custom policy, and when signed cookies?

Show the model answer

Use a custom policy when you need more than an expiry time: a start time, an IP address range, or a wildcard that covers many files. Use signed cookies when users need access to many files and you do not want to change each URL, such as a members area.

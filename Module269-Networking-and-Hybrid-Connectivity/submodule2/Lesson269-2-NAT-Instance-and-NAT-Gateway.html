Lesson 269.2 - NAT Instance and NAT Gateway

Give private resources outbound internet access with NAT instances, NAT Gateways, and Regional NAT Gateways.

1. What Is NAT?

Problem Statement

Your app servers and databases sit in private subnets, exactly as good design requires. Then the operations team asks: how do these servers download security patches, pull container images, or call a payment provider’s API? They have no public IPs and no route to the Internet Gateway.

Making the subnet public would expose every server to the internet. You need a way for private resources to start connections out while the internet still cannot start connections in.

1.1 Network Address Translation

Network address translation (NAT) rewrites the source address of outgoing packets. A NAT device sits between your private subnets and the internet and replaces each private instance’s IP with its own public IP:

  • Many to one. Many private instances share a single public IP, the NAT device’s Elastic IP. The NAT device keeps their sessions apart by also translating the source port.
  • Outbound only. The NAT device records each outgoing connection in a translation table. Replies match an entry and are sent back to the right instance. A connection that starts from the internet matches no entry, so it is dropped.
  • The private instances stay private. They never get a public IP, and the internet only ever sees the NAT device’s address.

1.1.1 NAT vs. the Internet Gateway

The Internet Gateway also translates addresses, but differently. It maps one private IP to one public IP, in both directions, for instances in public subnets. A NAT device maps many private IPs to one public IP, for outbound traffic only. A NAT device in AWS still needs the Internet Gateway: it sends its translated traffic out through the IGW.

2. NAT Instance

Problem Statement

Before AWS offered a managed NAT service, teams solved the outbound-access problem the way they would on premises: run their own router. You launch an ordinary EC2 instance, turn it into a NAT device, and point your private subnets at it. It works, but now one EC2 instance carries all of your private subnets’ internet traffic, and keeping it patched, sized, and running is your job.

2.1 What Is a NAT Instance?

A NAT instance is an EC2 instance configured to perform NAT. It sits in a public subnet, and private subnets route their internet traffic to it. AWS now recommends NAT Gateways for almost every case, and the old Amazon-provided NAT AMI (built on the original Amazon Linux AMI) reached the end of its support. To build a NAT instance today, you configure your own AMI, for example Amazon Linux 2023 with IP forwarding and iptables rules.

So why learn it? Because the exam still asks about it, mostly as the wrong answer in scenarios that need availability or scale, and occasionally as the right answer when the question stresses the lowest cost for a small workload.

2.2 Building a NAT Instance

  1. Launch an EC2 instance in a public subnet from an AMI configured for NAT (IP forwarding enabled, iptables masquerade rules).
  2. Give it a public IP, ideally an Elastic IP so the address survives a stop and start.
  3. Disable the source/destination check on the instance (see below).
  4. Configure its security group to allow inbound traffic from your private subnets (for example HTTP and HTTPS from 10.0.11.0/24) and outbound traffic to the internet.
  5. Update the private subnet’s route table: 0.0.0.0/0 → the NAT instance (its instance ID or network interface).

2.2.1 Why the Source/Destination Check Must Be Disabled

By default, every EC2 instance checks that it is the source or the destination of every packet it sends or receives, and drops anything else. A NAT instance forwards other instances’ traffic, so it is neither the source nor the destination of those packets. With the check on, it silently drops everything it is meant to forward. Disabling the source/destination check is the single most tested NAT instance fact.

2.3 Limitations

  • Single point of failure. One instance in one AZ. If it fails, every private subnet using it loses internet access. High availability needs extra instances plus your own failover scripts.
  • Limited bandwidth. Throughput depends on the instance type you chose. To grow, you resize the instance yourself.
  • You manage everything: OS patches, software updates, monitoring, and scaling.
  • Security group required. It is an EC2 instance, so it has a security group you must maintain.

A NAT instance has one advantage a NAT Gateway does not: it is a full EC2 instance, so it can also act as a bastion host or do port forwarding. For a tiny dev environment, a small instance type can also cost less than a NAT Gateway.

2.4 SAA-C03 Exam Scenarios for NAT Instances

On the exam, a NAT Gateway is the default answer for outbound internet access. Choose a NAT instance only if the scenario specifically calls out one of these needs:

Note: Port Address Translation

Every NAT device, including a NAT Gateway, uses port address translation for outbound traffic, which is how many instances share one IP (Image 1a). What only a NAT instance can do is the reverse: forward an inbound port to a chosen private instance.

Exam Trap

The NAT instance "does not work".

A scenario where a NAT instance is running, routes are correct, but private instances still cannot reach the internet almost always has one answer: disable the source/destination check. Also check that its security group allows traffic from the private subnets and that it has a public or Elastic IP.

3. NAT Gateway

Problem Statement

The problem a NAT Gateway solves: EC2 instances in a private subnet have no route to the Internet Gateway, so they are not directly reachable from the internet. That is exactly what you want, until they need the internet for outbound requests, such as downloading OS patches or calling external APIs. The two obvious fixes both break your design:

  • Assign public IPs to the instances: this exposes them to the internet, which is a security violation.
  • Add an Internet Gateway route to the private subnet: this defeats the purpose of a private subnet, because it becomes public.

A NAT instance can solve this, but then you own it. When it goes down at 2 AM, every app server loses access to the payment API until someone launches a replacement, and when traffic doubles during a sale, it runs out of bandwidth.

The solution is a NAT Gateway: outbound-only internet access for private subnets that AWS runs, keeps available, and scales for you.

3.1 What Is a NAT Gateway?

A NAT Gateway is a fully managed NAT service. It does the same job as a NAT instance, letting resources in private subnets start connections to destinations outside their subnet using the NAT Gateway’s IP address, but AWS runs it, makes it redundant, and scales it.

3.2 A Common NAT Gateway Architecture

A typical NAT Gateway setup follows one path:

Private subnet → NAT Gateway → Internet Gateway → Internet

  1. Private subnet: an EC2 instance with only a private IP sends a request to the internet. Its route table matches 0.0.0.0/0 → nat-xxxx, so the packet goes to the NAT Gateway.
  2. NAT Gateway: it replaces the instance’s private source IP with its own Elastic IP, then forwards the packet using its public subnet’s route, 0.0.0.0/0 → igw-xxxx.
  3. Internet Gateway: it sends the packet out to the internet.
  4. The response comes back to the NAT Gateway’s Elastic IP. The NAT Gateway translates it back and delivers it to the private instance. A connection that starts from the internet has no matching entry, so it never reaches the instance.

3.3 How Does a NAT Gateway Work?

Follow the arrows in the diagram:

  1. The private EC2 instance sends a request to the internet, for example to download a patch. Its subnet’s route table sends 0.0.0.0/0 to the NAT Gateway. The instance’s security group must allow this outbound traffic (security groups allow all outbound by default).
  2. The NAT Gateway translates the address. It replaces the instance’s private IP with its own Elastic IP and keeps a record of the connection.
  3. The VPC router forwards the packet using the public subnet’s route table, which sends 0.0.0.0/0 to the Internet Gateway.
  4. The Internet Gateway sends it to the internet. The destination only ever sees the NAT Gateway’s Elastic IP.
  5. The response returns the same way. The NAT Gateway matches it to the original connection and delivers it to the private instance.

Compare the public EC2 instance: it has its own public IP, so its traffic goes straight from the router to the Internet Gateway, and it can also accept inbound connections. The private instance can only start connections out; nothing on the internet can reach it directly.

3.5 Scopes and Limitations

  • Availability Zone scope. A NAT Gateway is an AZ-specific resource. It is highly available within the AZ where it resides, built with redundant components inside that AZ, but it is not multi-AZ redundant on its own. For resilience across AZs, deploy one per AZ (below) or use a Regional NAT Gateway (tab 4).
  • IPv4 translation. NAT Gateways translate private IPv4 addresses to a public IPv4 address. For IPv6 traffic going out to the internet, AWS uses an egress-only Internet Gateway, a separate component. IPv6 addresses are already public, so no translation is needed; the egress-only gateway simply allows outbound connections and blocks inbound ones.

Note: Egress-Only Gateways and NAT64

  • An egress-only Internet Gateway is stateful: it remembers outbound connections so their responses can return, which is how it allows outbound traffic while blocking inbound.
  • NAT Gateways do have one IPv6 feature, NAT64, which lets IPv6-only workloads reach IPv4 destinations when used with DNS64. It is a niche case; for the exam, remember "outbound IPv6 = egress-only Internet Gateway."

Exam Tip

A NAT Gateway is placed in the PUBLIC subnet, not the private subnet it serves. It needs the public subnet’s route to the Internet Gateway to send traffic out. The private subnet’s route table then points 0.0.0.0/0 at the NAT Gateway. (This applies to the standard zonal NAT Gateway. A Regional NAT Gateway, covered in tab 4, does not need a subnet at all.)

A private NAT Gateway is useful when two networks have overlapping IP ranges and must still communicate. On the exam, "NAT Gateway" almost always means the public type.

3.6 High Availability: One NAT Gateway Per AZ

Because a NAT Gateway lives in one AZ, sharing a single NAT Gateway across AZs creates a hidden single point of failure. If its AZ goes down, private resources in the other AZs also lose internet access. You also pay cross-AZ data transfer for every request. The standard design is a NAT Gateway in each AZ, with routing that keeps traffic in the same AZ:

  1. Create a NAT Gateway in each AZ’s public subnet, each with its own Elastic IP.
  2. Make sure the public subnets route 0.0.0.0/0 to the Internet Gateway. The NAT Gateways send their traffic out this way.
  3. Create one private route table per AZ, each with 0.0.0.0/0 → the NAT Gateway in the same AZ.
  4. Associate each private subnet with its AZ’s route table.

3.7 Cost and Pricing Considerations

NAT Gateway pricing can include:

Cost and Pricing Considerations.
ChargeWhat it is forWhat drives it
Hourly NAT Gateway chargesEach hour a NAT Gateway existsThe number of NAT Gateways. You pay even when no traffic flows, so a one-per-AZ design in three AZs costs three times the hourly rate.
Data processing chargesEvery gigabyte that passes through the NAT GatewayHow much traffic your private subnets send through it, in both directions.
Data transfer-related chargesMoving data between AZs, or out to the internetYour architecture. Sending traffic to a NAT Gateway in another AZ adds cross-AZ transfer charges, and data going out to the internet is billed at standard rates.

The Elastic IP on a public NAT Gateway also counts toward AWS’s charge for public IPv4 addresses. Rates vary by Region, so check the Amazon VPC pricing page for current numbers.

Exam Trap

Cost trap: data processing adds up fast.

The hourly charge is predictable, but data processing scales with traffic. A private workload that pulls large files from S3 through a NAT Gateway pays processing charges on every gigabyte, which can cost far more than the NAT Gateway itself. That is why the first fix below matters so much.

3.7.1 Keeping NAT Costs Down

  • Use gateway endpoints for S3 and DynamoDB. They are free, and traffic to those services skips the NAT Gateway and its per-GB charge.
  • Keep traffic in the same AZ, as in Image 3d, to avoid cross-AZ data transfer charges.
  • Use interface endpoints for other heavily used AWS services, when they cost less than NAT processing.
  • For non-production environments where availability matters less, a single NAT Gateway can be an acceptable trade-off.

Exam Trap

Common mistakes.

  • Creating the NAT Gateway in a private subnet. A public NAT Gateway needs a subnet with a route to the Internet Gateway.
  • One NAT Gateway for all AZs in a production workload. It works until that AZ fails.
  • Trying to attach a security group to the NAT Gateway. It is not possible; filter with NACLs and instance security groups.

4. Regional NAT Gateway

Problem Statement

The one-per-AZ design works, but it adds up. Three AZs means three NAT Gateways, three Elastic IPs, three public subnets just to host them, and three private route tables. Every time your workloads move into a new AZ, you repeat the setup, and a missed route quietly sends traffic across AZs. Would not it be simpler to have one NAT Gateway that follows your workloads on its own?

4.1 What Is a Regional NAT Gateway?

  • New in November 2025: AWS added a regional availability mode for NAT Gateways.
  • One gateway, many AZs: a Regional NAT Gateway (sometimes abbreviated RNAT) is a single NAT Gateway that automatically expands and contracts across the Availability Zones in your VPC, based on where your workloads are.
  • Associated with the VPC: it is a highly available NAT Gateway tied to the VPC itself, not to a subnet or a single AZ.
  • No per-AZ deployments: because one gateway is shared across all AZs, you do not need a NAT Gateway, Elastic IP, and public subnet in each AZ.
  • New naming: the original kind is now called a zonal NAT Gateway.

4.2 How It Works

  • When you launch resources in a new AZ, the Regional NAT Gateway detects a network interface there and automatically expands into that AZ. When an AZ has no active workloads, it contracts from it.
  • Expansion to a new AZ can take up to 60 minutes. Until then, traffic from that AZ is processed in one of the AZs the NAT Gateway already covers.
  • AWS automatically creates a route table for the NAT Gateway, with a route to the Internet Gateway already in place. The VPC still needs an Internet Gateway.
  • Private subnets in every AZ can point 0.0.0.0/0 at the same NAT Gateway ID, so they can even share a route table.

4.2.1 Benefits

Benefits.
BenefitWhy it matters
Simplified setupOne NAT ID across all AZs, so the same route entry works in every subnet.
Enhanced securityNo public subnets are needed to host it, which reduces the chance of putting private resources in a subnet with public connectivity by mistake.
Automatic high availabilityIt follows your workloads into each AZ, so you get the one-per-AZ resilience without building it.
Higher IP and port limitsUp to 32 IP addresses per AZ, compared with 8 for a zonal NAT Gateway. Each IP adds 55,000 concurrent connections to a popular destination.

4.2.2 Automatic vs. Manual Mode

  • Automatic mode (recommended): AWS manages the IP addresses and the expansion across AZs.
  • Manual mode: you manage the IP addresses and control the translation for each AZ, so expanding and contracting across AZs is your responsibility.

4.2.3 Limitations

  • No private NAT. Regional NAT Gateways do not support private connectivity. For private NAT, use a zonal NAT Gateway.
  • Not available in constrained AZs, and not in the AWS GovCloud (US) or China Regions.
  • Its route table can use an AWS Transit Gateway as a route target, which supports designs with central traffic inspection.

AWS recommends considering Regional NAT Gateways for all use cases except those that need private connectivity.

4.3 How RNAT Solves NAT Cost and Complexity Issues

Let us compare the two architectures.

4.3.1 Traditional Zonal NAT vs Regional NAT

Traditional NAT (Before)

  • AZ-a → NAT A → IGW
  • AZ-b → NAT B → IGW
  • AZ-c → NAT C → IGW

Problems:

  • 3 NAT gateways minimum
  • 3 public subnets
  • Cross-AZ charges
  • AZ-specific routing
  • High cost

Regional NAT (Now)

  • ALL private subnets → 1 RNAT → IGW

Benefits:

  • Only 1 NAT required
  • No cross-AZ charges
  • No public subnets required
  • Auto-expands to new AZs
  • Greatly simplified routing

Note: while RNAT expands into a new AZ (up to 60 minutes), that AZ’s traffic is processed in another AZ, so cross-AZ charges can briefly apply.

4.4 Where RNAT Fits Best

RNAT is ideal for:

  • Modern multi-AZ microservices
  • Private-only VPC designs
  • Highly secure architectures
  • Environments with heavy S3/SSM usage
  • Teams wanting fewer moving parts
  • Cost-optimized cloud networks

Note: for heavy S3 traffic, add a free S3 gateway endpoint as well, so that traffic skips NAT data processing charges.

It simplifies almost everything.

4.5 Creating One

  1. In the VPC console, choose NAT gateways, then Create NAT gateway.
  2. For Availability mode, choose Regional. You do not specify a subnet.
  3. Choose the VPC, complete the remaining settings, and create it.
  4. Point your private route tables’ 0.0.0.0/0 route at the new NAT Gateway ID.

With the AWS CLI: aws ec2 create-nat-gateway --vpc-id vpc-12345678 --availability-mode regional

4.5.1 Moving From Zonal to Regional

Converting resets existing connections, so plan it for a maintenance window. There are two approaches:

  • New IP addresses are fine: create the Regional NAT Gateway, update the route tables to point to it, then delete the zonal NAT Gateways.
  • Keep the same IP addresses (for example, if partners allow-list them): delete the zonal NAT Gateways to release their IPs, create the Regional NAT Gateway with those IPs, then update the route tables. Traffic is interrupted during the switch.

Exam Note: A Very New Feature

The SAA-C03 exam guide was written before Regional NAT Gateways existed, so exam questions may not mention them yet. If a question asks how to keep outbound access available across AZ failures and does not mention regional mode, the classic answer, one NAT Gateway per AZ, is still correct. Know regional mode for real-world designs, and in case newer questions include it.

5.3.1 More Scenarios to Practice

7. Knowledge Check

No multiple choice. Answer each question in your own words first, then expand the model answer to compare.

Question 1. Explain how a NAT device lets many private instances share one public IP, and why it blocks connections that start from the internet.

Show the model answer

The NAT device rewrites each outgoing packet’s source to its own public IP and a unique source port, and records the mapping in a translation table. Replies come back to that IP and port, match the table, and are rewritten back to the original private IP. A connection that starts from the internet has no matching entry, so the NAT device has nowhere to send it and drops it.

Question 2. Why must the source/destination check be disabled on a NAT instance, and what happens if you forget?

Show the model answer

By default, an EC2 instance drops any packet for which it is not the source or destination. A NAT instance forwards other instances’ traffic, so it is neither. With the check enabled, it silently drops all the traffic it is meant to forward, and private instances cannot reach the internet even though routes and security groups look correct.

Question 3. List three reasons AWS recommends NAT Gateways over NAT instances, and one thing a NAT instance can do that a NAT Gateway cannot.

Show the model answer

NAT Gateways are fully managed (no patching or monitoring), redundant within their AZ (no single instance to fail), and scale automatically from 5 Gbps up to 100 Gbps. A NAT instance, being a full EC2 instance, can also act as a bastion host or do port forwarding, and it supports a security group.

Question 4. A company runs workloads in three AZs and uses a single NAT Gateway in AZ A. Describe the risk and two ways to fix it.

Show the model answer

A zonal NAT Gateway is only redundant within its AZ. If AZ A fails, private resources in AZs B and C also lose internet access, and every request from B and C already pays cross-AZ data transfer. Fix 1: create a NAT Gateway in each AZ’s public subnet and give each AZ a private route table pointing to its local NAT Gateway. Fix 2: replace them with a Regional NAT Gateway, which expands into every AZ that has workloads automatically.

Question 5. Name three differences between a zonal and a Regional NAT Gateway, and the one use case where you must still choose zonal.

Show the model answer

A zonal NAT Gateway lives in one AZ, needs a public subnet to host it, and needs its own route per AZ. A Regional NAT Gateway spans AZs automatically, needs no public subnet, uses one NAT ID for every AZ, and supports up to 32 IPs per AZ instead of 8. You must still choose zonal for private NAT, because regional mode does not support private connectivity.

Question 6. Your NAT Gateway data processing charges are high. Most of the traffic goes to Amazon S3 and DynamoDB. What do you change, and why does it lower the bill?

Show the model answer

Add gateway endpoints for S3 and DynamoDB to the private subnets’ route tables. Traffic to those services then follows the endpoint route instead of the NAT Gateway, so it no longer incurs NAT data processing charges, and gateway endpoints themselves are free. The traffic also stays on the AWS network.

Lesson 269.4 - VPC Traffic Monitoring - VPC Flow Logs and Traffic Mirroring

Capture, read, analyze, and troubleshoot VPC traffic with Flow Logs, and copy packets with Traffic Mirroring.

Overview and Objectives

Lesson Overview

This lesson covers how to capture information about the IP traffic in your VPC, read it, send it to the right destination, and use it to troubleshoot connectivity and spot security problems, plus how to copy actual packets for deep inspection.

  • Tab 1 covers VPC Flow Logs: what they capture, where you can enable them (VPC, subnet, or network interface), and what they do not capture.
  • Tab 2 covers flow log records: the default record format, how to read each field, and the custom fields you can add.
  • Tab 3 covers destinations and analysis: CloudWatch Logs, Amazon S3, and Amazon Data Firehose, how to query and alert on flow logs, and a hands-on lab on creating a flow log.
  • Tab 4 covers troubleshooting with flow logs: using ACCEPT and REJECT records to tell a security group problem from a network ACL problem, with two hands-on labs.
  • Tab 5 covers VPC Traffic Mirroring: copying actual packets from a network interface to security tools, with sources, targets, filters, sessions, and how it compares with flow logs.
  • Tab 6 compares flow logs with CloudTrail, Traffic Mirroring, Reachability Analyzer, and GuardDuty, and gives a cheat sheet for the AWS Certified Solutions Architect – Associate (SAA-C03) exam.
  • Tab 7 checks your understanding with open-ended questions.

1. What Are VPC Flow Logs?

Problem Statement

Users report that your application in a private subnet sometimes cannot reach its database. The security team also wants to know whether anyone on the internet is scanning your instances for open ports. You open the console, but nothing there shows you which connections were attempted, between which IP addresses and ports, and whether they were allowed or blocked.

You need a record of the IP traffic going to and from the network interfaces in your VPC, so you can troubleshoot connectivity and investigate suspicious activity.

1.1 What Are VPC Flow Logs?

  • VPC Flow Logs is a VPC feature that captures information about the IP traffic going to and from the network interfaces in your VPC.
  • Each record describes a flow: who talked to whom (source and destination IP and port), over which protocol, how many packets and bytes, and whether the traffic was ACCEPTed or REJECTed by security groups and network ACLs.
  • Flow logs capture metadata, not packet contents. To inspect the actual payload, you need Traffic Mirroring (tab 5).
  • Flow logs are collected outside the path of your traffic, so they do not affect network throughput or latency.

1.1.1 Why Use VPC Flow Logs?

Flow logs help you monitor and troubleshoot connectivity issues. Typical uses:

  • Troubleshooting connectivity issues, for example "Why cannot my EC2 instance talk to RDS?"
  • Identifying traffic blocked by security groups or network ACLs (REJECT records).
  • Detecting anomalous or suspicious traffic, for example unusually high egress, port scans, or connections to unexpected destinations.
  • Validating firewall rules and network configurations across subnets and VPCs.
  • Cost analysis, by finding the resources with high bandwidth usage (the "top talkers").

1.2 Where You Can Create a Flow Log

You can create a flow log for three kinds of resources. A flow log on a VPC or subnet covers every network interface inside it.

Where You Can Create a Flow Log.
LevelWhat it captures
VPCEvery network interface in the VPC
SubnetEvery network interface in that subnet
Network interface (ENI)Only that one interface

Because flow logs work at the network interface level, they also cover AWS services that create interfaces in your VPC, such as Elastic Load Balancing, Amazon RDS, Amazon ElastiCache, Amazon Redshift, NAT Gateways, Transit Gateway attachments, and Lambda functions connected to a VPC. Transit Gateways can also have their own flow logs.

1.3 Key Destinations for VPC Flow Logs

VPC Flow Logs can be published to three primary AWS services, depending on the operational requirement:

  • Amazon CloudWatch Logs: ideal for near real-time traffic monitoring, metric filter creation, and triggering CloudWatch alarms.
  • Amazon S3: best for long-term storage, cost-effective log retention, and running ad-hoc SQL queries using Amazon Athena.
  • Amazon Data Firehose: designed to stream log data directly to third-party destinations such as Splunk, Datadog, or custom HTTP endpoints.

Tab 3 compares the three destinations in detail, including permissions, cost, and how to analyze each one.

1.4 Flow Log Settings

Flow Log Settings.
SettingOptions
FilterAccepted, Rejected, or All traffic. "Rejected" alone is useful for security monitoring; "All" is best for troubleshooting.
Maximum aggregation interval10 minutes (default) or 1 minute. A flow is collected and summarized over this period before a record is written. 1 minute gives more detail but more records. For Nitro-based instances, the interval is always 1 minute or less.
DestinationCloudWatch Logs, Amazon S3, or Amazon Data Firehose (tab 3)
Record formatThe default format, or a custom format with extra fields (tab 2)

After you create a flow log, you cannot change its configuration, such as its record format. To change it, delete the flow log and create a new one. Records also are not instant: after each aggregation interval, it takes additional time to publish them to the destination.

1.5 What Flow Logs Do Not Capture

Flow logs do not record every kind of IP traffic. These are not captured:

  • Traffic to the Amazon DNS server (if you use your own DNS server, that traffic is logged)
  • Traffic generated by Windows instances for Amazon Windows license activation
  • Traffic to and from 169.254.169.254 for instance metadata
  • Traffic to and from 169.254.169.123 for the Amazon Time Sync Service
  • DHCP traffic
  • Traffic to the reserved IP address of the default VPC router
  • Mirrored traffic (the copy sent by Traffic Mirroring)
  • Traffic between an endpoint network interface and a Network Load Balancer network interface

Other Limitations to Know

  • You cannot enable flow logs for a peered VPC unless that VPC is in your account.
  • You will not see any records until there is active traffic on the resource.
  • Some records can be skipped during an aggregation interval because of internal capacity limits; these show SKIPDATA (tab 2).

2. Flow Log Records

Problem Statement

You have enabled flow logs, and now you are looking at thousands of lines like 2 123456789012 eni-0a1b2c3d4e5f6a7b8 203.0.113.12 10.0.1.25 49761 22 6 20 4249 1717000000 1717000060 REJECT OK. Unless you can read what each number means, the logs are useless. You need to understand the record format so you can turn these lines into answers.

2.1 The Default Record Format

A flow log record is a line of fields separated by spaces. The default format (version 2) has these 14 fields, in this order:

The Default Record Format.
#FieldMeaning
1versionThe flow log record version (2 for the default format)
2account-idThe AWS account that owns the network interface
3interface-idThe network interface the traffic was recorded on
4srcaddrSource IP address
5dstaddrDestination IP address
6srcportSource port
7dstportDestination port
8protocolIANA protocol number: 6 = TCP, 17 = UDP, 1 = ICMP
9packetsNumber of packets in the flow during the interval
10bytesNumber of bytes in the flow during the interval
11startTime of the first packet in the interval (Unix seconds)
12endTime of the last packet in the interval (Unix seconds)
13actionACCEPT — allowed by security groups and network ACLs; REJECT — blocked by a security group or network ACL
14log-statusOK — data logged normally; NODATA — no traffic in the interval; SKIPDATA — some records were skipped

Flow log examples: see Flow log record examples in the AWS documentation.

2.2 Reading a Record

2 123456789012 eni-0a1b2c3d4e5f6a7b8 203.0.113.12 10.0.1.25 49761 22 6 20 4249 1717000000 1717000060 REJECT OK

Field by field, this record says:

  • Someone at 203.0.113.12 (a public IP on the internet), using source port 49761,
  • tried to reach 10.0.1.25 on port 22 (SSH),
  • over protocol 6 (TCP), sending 20 packets and 4,249 bytes in one minute,
  • and the traffic was REJECTed by a security group or network ACL.

Many REJECT records like this, from one IP address to many ports, are a classic sign of a port scan.

2.3 Custom Record Format

Instead of the default format, you can choose a custom format: you pick which fields to include and their order. Newer versions added fields such as:

Custom Record Format.
FieldWhy it is useful
vpc-id, subnet-id, instance-idIdentify where the traffic was recorded without looking up the network interface
pkt-srcaddr, pkt-dstaddrThe original source and destination IPs in the packet. Useful behind a NAT Gateway or load balancer, where srcaddr and dstaddr show the intermediate interface.
tcp-flagsTCP flags such as SYN, helping to spot connection attempts and scans
flow-directionWhether the traffic is ingress or egress for the interface
traffic-pathThe path egress traffic took, such as through an Internet Gateway, NAT Gateway, or VPC endpoint
region, az-idWhere the network interface is located

SAA-C03 Keyword Triggers

Trigger 1: “Find the original client IP of traffic passing through a NAT Gateway in flow logs”→ Add pkt-srcaddr and pkt-dstaddr with a custom record format

Trigger 2: “Identify traffic blocked by security groups or network ACLs”→ Flow log records with action = REJECT (or a flow log filtered on Rejected traffic)

3. Destinations & Analysis

Problem Statement

The operations team wants an alert within minutes whenever rejected SSH attempts spike. The compliance team wants to keep a year of flow logs cheaply and occasionally run reports on them. One destination cannot do both jobs equally well. You need to know where flow logs can go and how each destination is analyzed.

3.1 Flow Log Destinations

Flow Log Destinations.
AspectAmazon CloudWatch LogsAmazon S3Amazon Data Firehose
Best forNear real-time search, metric filters, and alarmsLong-term, low-cost storage and large-scale analysisStreaming to other tools, such as OpenSearch, Splunk, or other partners
How you analyze itCloudWatch Logs Insights, metric filters, Contributor InsightsAmazon Athena (SQL), Amazon QuickSightWhatever tool receives the stream
PermissionsAn IAM role that lets the flow log service publish to the log groupA bucket policy that lets the service write to the bucketA role or permissions for the delivery stream
CostHigher (log ingestion and storage)Lowest for storing large volumesFirehose processing, plus the final destination

Each flow log publishes to one destination. To send the same traffic to two places, create two flow logs on the same resource. Data can also be published to a destination in another AWS account.

3.2 Analyzing Flow Logs

  • CloudWatch Logs Insights: run interactive queries, for example "top 10 source IPs with REJECTed traffic in the last hour."
  • Metric filter + CloudWatch alarm: turn matching records (such as REJECTs to port 22) into a metric, alarm when it crosses a threshold, and notify the team through Amazon SNS.
  • CloudWatch Contributor Insights: find the top talkers, such as the IP addresses sending the most traffic.
  • Amazon Athena: query flow logs stored in S3 with standard SQL, paying only for the data scanned. Visualize results with Amazon QuickSight.

3.3 Cost

  • Flow logs themselves have no extra charge for capturing traffic, but you pay data ingestion and storage charges at the destination, billed as vended logs.
  • Sending to S3 is generally the cheapest option for large volumes.
  • To reduce cost: log only rejected traffic if that is all you need, use the 10-minute interval, and set a retention period or S3 lifecycle rule.

4. Troubleshooting With Flow Logs

Problem Statement

An administrator cannot SSH into an instance. Both the security group and the network ACL look correct. Instead of guessing, you can use flow logs to see exactly which direction of the connection was blocked, and from that, which control is responsible.

4.1 Why Direction Matters

The key is the difference between the two firewall layers covered in lesson 269.1:

  • Security groups are stateful. If the inbound request is allowed, the response is automatically allowed out, whatever the outbound rules say.
  • Network ACLs are stateless. The response is checked separately against the outbound rules, and it usually goes to an ephemeral port (1024–65535) on the client.

So when a request is accepted coming in but its response is rejected going out, a security group cannot be the cause. It must be the network ACL.

4.2 Reading the Pattern

Reading the Pattern.
Inbound recordOutbound recordLikely cause
REJECT(none)The security group or the network ACL blocks the inbound request. Check both inbound rule sets.
ACCEPTREJECTThe network ACL blocks the response, usually a missing outbound rule for ephemeral ports.
ACCEPTACCEPTThe network allowed it both ways. Look elsewhere: the application, the OS firewall, or the route tables on the client side.
(no records)(no records)Traffic never reached the interface: check route tables, the Internet Gateway, the public IP, or DNS. Also confirm the flow log covers this interface.

The same logic works for outbound connections from an instance: if the request leaves (outbound ACCEPT) but the reply is rejected coming back in, the network ACL’s inbound rules are blocking the ephemeral ports.

4.3 Other Troubleshooting and Security Uses

  • Port scans: many REJECT records from one source IP to many destination ports.
  • Unexpected traffic: connections to unusual destinations or ports, which can indicate a compromised instance.
  • Top talkers: which instances send or receive the most traffic, for cost or capacity questions.
  • Amazon GuardDuty uses VPC flow logs (along with other sources) to detect threats automatically, without you enabling or managing the flow logs yourself.

5. VPC Traffic Mirroring

Problem Statement

Your security team’s intrusion detection system flags a suspicious pattern, and flow logs confirm that one instance is talking to an unusual IP address on port 443. But flow logs only show the envelope: who talked to whom, and whether it was allowed. To find out what was actually sent, the team needs the packets themselves, copied to their inspection tools, without slowing down or changing the production traffic.

5.1 What Is VPC Traffic Mirroring?

  • VPC Traffic Mirroring copies network traffic from an elastic network interface of Amazon EC2 instances and sends the copy to security and monitoring tools.
  • Unlike flow logs, it captures the actual packets, including their payload.
  • The copy is sent out of band: the original traffic continues unchanged.
  • Mirrored packets are wrapped in VXLAN encapsulation and sent on UDP port 4789.

5.1.1 Use Cases

  • Advanced troubleshooting that requires full payload visibility.
  • Deep packet inspection (DPI) for security appliances, such as intrusion detection and threat investigations.
  • Routing mirrored packets to third-party security tools, for example Palo Alto Networks or Check Point.

5.2 The Building Blocks

The Building Blocks.
ComponentWhat it is
Mirror sourceThe network interface (ENI) whose traffic you want to copy.
Mirror targetWhere the copies go: another ENI, a Network Load Balancer (with a UDP listener on port 4789), or a Gateway Load Balancer endpoint.
Mirror filterRules that choose which traffic to mirror, by protocol, source and destination port, CIDR, and inbound or outbound direction.
Mirror sessionConnects a source to a target, applies a filter, and starts the mirroring.

5.3 How to Set Up Traffic Mirroring (VPC Console)

5.4 Mirror Target Options

5.4.1 ENI As Target

The simplest setup: the copies go straight to the network interface of a single traffic analyzer instance.

5.4.2 Network Load Balancer As Target

For larger volumes and high availability, the copies go to a Network Load Balancer listening on UDP port 4789, which spreads them across a fleet of traffic analyzers. Here the source and the analyzers are in different VPCs.

AWS recommends a Network Load Balancer or a Gateway Load Balancer endpoint as the target when you need high availability.

5.5 Where the Source and Target Can Be

  • Source and target can be in the same VPC.
  • They can be in different VPCs, connected through VPC peering or a Transit Gateway.
  • The source and target VPCs can be in different AWS accounts.

Things to Know

  • Traffic Mirroring works only on supported instance types (Nitro-based instances).
  • Mirrored traffic counts toward the source instance’s network bandwidth.
  • You pay for each network interface with an active mirror session, so delete sessions you no longer need.

5.6 VPC Flow Logs vs. Traffic Mirroring

7. Knowledge Check

No multiple choice. Answer each question in your own words first, then expand the model answer to compare.

Question 1. What do VPC Flow Logs capture, what do not they capture, and at which three levels can you create them?

Show the model answer

They capture metadata about IP traffic to and from network interfaces: source and destination IPs and ports, protocol, packets, bytes, time, and whether the traffic was accepted or rejected. They do not capture packet contents, or certain traffic such as Amazon DNS, instance metadata (169.254.169.254), Time Sync, DHCP, and traffic to the VPC router’s reserved IP. You can create them for a VPC, a subnet, or a single network interface.

Question 2. Explain this record: 2 123456789012 eni-0a1b2c3d4e5f6a7b8 203.0.113.12 10.0.1.25 49761 22 6 20 4249 1717000000 1717000060 REJECT OK

Show the model answer

Version 2 record from account 123456789012 on that network interface. A client at 203.0.113.12, port 49761, tried to reach 10.0.1.25 on port 22 (SSH) over TCP (protocol 6), sending 20 packets and 4,249 bytes in one minute. The traffic was rejected by a security group or network ACL, and the record was logged normally (OK).

Question 3. Flow logs show an inbound request ACCEPTed and its response REJECTed. Which control is responsible, and why?

Show the model answer

The network ACL. Security groups are stateful, so if they allow the inbound request, the response is automatically allowed out. Network ACLs are stateless and check the response separately; here the outbound rules do not allow traffic to the client’s ephemeral port (1024–65535).

Question 4. Your operations team wants alerts on rejected SSH attempts, and your compliance team wants a year of logs at low cost. How would you design this?

Show the model answer

Create two flow logs on the VPC, since each flow log has one destination. Send one to CloudWatch Logs, with a metric filter on REJECT records for port 22, a CloudWatch alarm on that metric, and SNS notifications. Send the other to Amazon S3 with a lifecycle rule for retention, and query it with Athena when reports are needed.

Question 5. How do VPC Flow Logs differ from AWS CloudTrail and from Traffic Mirroring?

Show the model answer

Flow logs record network traffic metadata (who connected to whom, and whether it was allowed). CloudTrail records API calls, such as who changed a security group. Traffic Mirroring copies the actual packets, including their contents, for deep inspection.

Question 6. Traffic from private instances goes out through a NAT Gateway. In the NAT Gateway’s flow logs, how can you see which private instance started each connection?

Show the model answer

Use a custom record format that includes pkt-srcaddr and pkt-dstaddr. These fields show the original IP addresses in the packet, while srcaddr and dstaddr show the addresses of the interface the traffic passed through.

Question 7. What are the four building blocks of VPC Traffic Mirroring, and when would you choose a Network Load Balancer instead of an ENI as the mirror target?

Show the model answer

A mirror source (the ENI to copy), a mirror target (an ENI, a Network Load Balancer, or a Gateway Load Balancer endpoint), a mirror filter (which protocols, ports, CIDRs, and directions to copy), and a mirror session (which ties them together). Choose a Network Load Balancer, with a UDP listener on port 4789, when the volume is too large for one analyzer or you need high availability: it spreads the mirrored traffic across a fleet of analyzers.

1. AWS Security Token Service (STS)

Problem Statement

Your company relies on automated scripts and external developer applications to move data into Amazon Simple Storage Service (Amazon S3) buckets on a regular schedule. The team could create long-term AWS access keys and share them across environments. A key that is hardcoded, stored on a developer machine, or accidentally committed to a code repository stays valid until someone finds and revokes it.

How can you grant access to the buckets without storing permanent access keys?

1.1 What AWS STS Is

AWS STS is a service that provides temporary security credentials. Users, applications, and AWS services use them to access AWS resources. Instead of permanent credentials, STS generates credentials that expire automatically after a specified period. This reduces the risks of long-term credentials and shrinks the attack surface.

1.2 How AWS STS Works

1.2.1 Example: Cross-Account Access

A developer in AWS account A needs temporary access to an S3 bucket in account B.

  1. Account B creates an IAM role with permissions to access the S3 bucket.
  2. The role’s trust policy permits the appropriate principal from account A to assume it.
  3. The developer requests to assume the role.
  4. AWS STS returns temporary security credentials.
  5. The developer uses those credentials to access the permitted S3 resources.
  6. The credentials expire automatically.

1.3 Temporary Security Credentials

STS temporary credentials typically contain four components:

The components of STS temporary credentials.
ComponentPurpose
Access key IDIdentifies the temporary access key.
Secret access keySigns AWS API requests.
Session tokenIdentifies the temporary session. Required with the other two values.
Expiration timeThe time when the credentials stop working.

All three credential values (the access key ID, the secret access key, and the session token) are required when you make authenticated AWS API requests with an STS session.

A role session lasts one hour by default. With the AssumeRole operation, you can request a duration from 15 minutes up to the role’s maximum session duration, which is a setting from 1 hour to 12 hours.

1.4 Common STS Operations

The most common STS operations that return temporary credentials.
OperationUsed for
AssumeRoleAssuming a role within your account or across accounts, which is the usual choice for cross-account access.
AssumeRoleWithSAMLEnterprise sign-in with Security Assertion Markup Language (SAML) 2.0, for example through Active Directory Federation Services (AD FS), Okta, or Microsoft Entra ID.
AssumeRoleWithWebIdentityWeb and mobile identity providers (IdPs), for example Google, Facebook, or Amazon Cognito.

Other STS operations support web identity federation, SAML federation, session credentials, and retrieving information about the current caller.

1.5 Common Use Cases

  • Cross-account access: An identity in one AWS account assumes a role in another account without a separate IAM user there.
  • AWS service roles: AWS workloads use roles and temporary credentials instead of stored long-term access keys.
  • Federated access: Users who authenticate through external identity systems receive temporary AWS access.
  • Amazon Cognito: Cognito identity pools use roles and STS to give application users temporary AWS credentials.
  • AWS IAM Identity Center: Users reach AWS accounts through roles and temporary credentials instead of IAM user access keys.
  • Short-term access for third parties: External contractors and partners receive time-bound access to specific AWS resources.

1.6 STS Versus IAM

The main distinction between IAM and AWS STS is:

IAM compared with AWS STS.
IAMAWS STS
Defines identities, roles, policies, and permissionsIssues temporary security credentials
Determines what is allowedProvides credentials to exercise permitted access for a limited time
An IAM role defines permissionsAn STS session uses the role’s permissions, subject to applicable policy controls

  • Temporary credentials need all three values. A request that uses only the access key ID and secret access key from an STS session fails.

2. Amazon Cognito Overview and Core Components

Problem Statement

Imagine you are launching a new mobile or web application. The core business logic is ready, but before anyone can use the product you need user management. Building authentication from scratch means designing secure password storage, handling multi-factor authentication (MFA), supporting social sign-in, managing token refresh, and meeting security standards, while scaling from hundreds of users to millions.

Which AWS service can manage this for you?

2.1 What Amazon Cognito Is

  • Amazon Cognito is a fully managed identity service that adds user sign-up, sign-in, and access control to web and mobile applications. It acts as a managed identity provider.
  • It handles backend user management, authentication, and authorization at scale, so development teams can focus on the application instead of building identity systems.
  • It supports social identity providers, enterprise identity providers, and custom identity providers.
  • It scales to millions of users. It supports sign-in with social providers such as Apple, Facebook, Google, and Amazon, and with enterprise providers through SAML 2.0 and OpenID Connect (OIDC).

2.2 Core Components

Amazon Cognito has two primary identity-building blocks, user pools and identity pools, along with offline synchronization tools.

2.2.1 User Pools

A Cognito user pool is a user directory in AWS for customer-facing web and mobile applications.

  • Authentication (who you are): Provides sign-up and sign-in for application end users.
  • Built-in UI and customization: Provides a hosted user interface (UI) out of the box, or lets you integrate a custom UI with the AWS software development kits (SDKs).
  • Identity federation: Supports direct sign-in and federation through social identity providers (such as Facebook, Google, Apple, and Amazon) and enterprise SAML and OIDC providers.
  • Security and verification: Supports MFA, password policies, phone and email verification, and compromised credentials detection.
  • Tokens: After successful authentication, a user pool issues standard JSON Web Tokens (JWTs): an ID token, an access token, and a refresh token.

2.2.2 Identity Pools (Federated Identities)

Cognito identity pools provide authorization. They give application users temporary credentials to access AWS resources directly.

  • Authorization (what you can access): Exchanges tokens from an identity provider, such as a Cognito user pool, Google, or SAML, for temporary, limited-privilege AWS credentials.
  • Guest and unauthenticated access: Supports unauthenticated guest sessions, so people can use the app anonymously before they sign up.
  • Role mapping: Maps authenticated users to specific IAM roles and policies based on rules or user attributes.

2.2.3 Cognito Sync and AWS AppSync

  • Data synchronization: Lets applications save data locally on user devices for offline use.
  • Cross-device state: Synchronizes state and profile data across devices when connectivity returns.
  • Modern alternative: AWS AppSync (GraphQL) is often paired with Cognito for real-time and offline data syncing across mobile and web clients.

Current Service Note

Amazon Cognito Sync moves to maintenance mode and closes to new customers from July 30, 2026. Existing customers can continue to use it. AWS recommends AWS AppSync or Amazon DynamoDB for new applications. For details, see Amazon Cognito Sync availability change.

2.2.4 Adaptive Authentication

Cognito offers advanced security features that protect user accounts against compromised credentials and suspicious sign-ins. Tab 5 covers them.

Exam Trap

  • A user pool returns tokens. It does not return AWS credentials. Credentials come from an identity pool and AWS STS.
  • Do not build a new design on Cognito Sync. It is closed to new customers.

Memory Hook

User pool means who you are, with JWTs. Identity pool means what you can access, with AWS credentials.

Trigger 3: “Let enterprise users sign in with SAML 2.0 or OpenID Connect”→ Cognito user pools with enterprise identity provider federation

3. How User Pools and Identity Pools Work Together

Problem Statement

A photo-sharing mobile app lets users sign in with an email address or a social account, and then upload photos directly to an Amazon S3 bucket without routing uploads through your servers. The app must prove who the user is, and then receive permission to write to one bucket.

3.1 The Five Steps

In Amazon Cognito, the user pool and the identity pool are used together. The user pool authenticates the user. The identity pool then turns that proof into temporary AWS credentials.

  1. Authentication: The user logs in through a Cognito user pool (or an external social or SAML provider) and receives JWTs.
  2. Exchange: The client application passes the ID token to a Cognito identity pool.
  3. Token validation: The identity pool validates the token with the issuing identity provider.
  4. Assume role: The identity pool calls AWS STS to request temporary IAM credentials for the user’s role.
  5. Access AWS services: The client application uses the temporary credentials to work directly with services such as Amazon S3, Amazon DynamoDB, or Amazon API Gateway.

3.2 What Each Component Contributes

How the components of the flow fit together.
ComponentQuestion it answersWhat it returns
Cognito user poolWho are you?ID, access, and refresh JWTs
Cognito identity poolWhat AWS resources can your application access?Temporary AWS credentials, obtained through AWS STS
IAM roleWhat is allowed?The permissions that the credentials carry
AWS STSHow are short-lived credentials issued?Access key ID, secret access key, session token, and expiration time

4. Amazon Cognito Use Cases

Problem Statement

Four teams ask for four designs. One needs an API that only signed-in users can call. One needs custom checks while users sign up. One needs direct access to Amazon S3 after sign-in. One needs access for users who already sign in with another identity provider. Each design combines Amazon Cognito components in a different way.

4.1 UC1: Control Access to an API With a User Pool

A Cognito user pool can control who can call an API that Amazon API Gateway serves. This use case combines a user pool, API Gateway, and an AWS Lambda function.

  1. The application user signs in through a Cognito user pool and receives tokens.
  2. The application sends a request to the API and includes a token.
  3. API Gateway checks the token against the user pool by using a Cognito user pool authorizer.
  4. If the token is valid, API Gateway invokes the backend, such as a Lambda function.

4.2 UC2: AWS Lambda Triggers

Cognito user pools support Lambda triggers at key points in the sign-up and authentication workflows.

  • Pre Sign-up: Performs custom validation before a user is created. It can also automatically confirm users or verify email and phone attributes.
  • Post Confirmation: Runs after a user confirms an account. It can send welcome messages, log events, or update other systems.
  • Pre Token Generation: Customizes token claims before the JWT is issued, such as adding, modifying, or suppressing claims.
  • Custom Message: Customizes email and SMS messages for events such as account verification, password recovery, attribute verification, and MFA.

Key Takeaway

Lambda triggers let you customize Cognito authentication workflows without modifying the core authentication service.

4.3 UC3: Access Other AWS Services With a User Pool and an Identity Pool

This use case combines both Amazon Cognito components.

  1. The application user signs in through a Cognito user pool.
  2. After successful authentication, the application receives user pool tokens.
  3. The application presents the appropriate token to a configured identity pool.
  4. The identity pool exchanges the authenticated identity for temporary AWS credentials.
  5. The application uses those credentials to access permitted AWS services, such as Amazon S3 or DynamoDB.

IAM roles and policies that are associated with the identity pool control the permissions that the user has.

4.4 UC4: Authenticate With a Third-Party Identity Provider and Access AWS Services With an Identity Pool

Users can authenticate through a supported external identity provider and use a Cognito identity pool to obtain temporary AWS credentials. The general process is:

  1. The user authenticates with a supported third-party identity provider.
  2. The application receives a token from that provider.
  3. The application presents the token to the Cognito identity pool.
  4. The identity pool provides temporary AWS credentials based on configured IAM roles and permissions.
  5. The application uses those credentials to access authorized AWS services.

4.5 Summary of the Use Cases

The four use cases compared.
Use caseComponentsResult
UC1User pool, API Gateway, and LambdaOnly signed-in users can call the API
UC2User pool and Lambda triggersCustom logic during sign-up and authentication
UC3User pool and identity poolSigned-in users receive temporary AWS credentials
UC4Third-party identity provider and identity poolUsers from another provider receive temporary AWS credentials

Exam Trap

Authorizing calls to API Gateway with a user pool uses the token that the user pool issues. It does not need an identity pool. Use an identity pool when the application must call AWS services directly with AWS credentials.

Memory Hook

API calls use the user pool token. Direct AWS calls use identity pool credentials.

5. Cognito Advanced Security and Threat Protection

Problem Statement

Attackers are trying stolen username and password pairs against your application’s sign-in page, and abusive traffic is hitting your authentication endpoints. You need to detect risky sign-ins and leaked passwords, and you need to limit what a signed-in user can do in AWS.

5.1 Layers of Protection

For applications that need additional protection, Cognito provides features that detect and respond to suspicious authentication activity.

5.2 Security Features

Cognito security features.
FeatureWhat it does
Adaptive authenticationEvaluates sign-in risk by using signals such as IP address, device information, and sign-in behavior. Based on risk, Cognito can allow the request, require MFA, or block the sign-in.
Compromised credentials detectionIdentifies potentially compromised username and password combinations, and can allow or block the affected authentication attempts.
Threat protectionMonitors user authentication activity for signs of account takeover and can respond automatically. These capabilities belong to the Plus feature plan.
AWS WAF integrationAn AWS WAF web access control list (web ACL) can be associated with a user pool to inspect and control requests to Cognito authentication endpoints. This helps protect against unwanted or abusive traffic.
IAM least privilegeWhen identity pools provide temporary AWS credentials, the IAM roles and policies should grant users only the permissions that they need.

Key Takeaway

Amazon Cognito uses multiple layers of security to protect identities and control access: MFA, password policies, passkeys, and JWTs, plus adaptive authentication, threat detection, AWS WAF, and IAM.

6. Amazon Cognito Feature Plans and Costing

Problem Statement

A startup expects tens of thousands of monthly active users and wants to know which user pool plan it needs and how Amazon Cognito bills for it. The security team also wants to know whether threat protection is included.

6.1 The Pricing Model

Amazon Cognito uses pay-as-you-go pricing. For user pools, the main cost depends on the number of monthly active users (MAUs) and the feature plan that you choose: Lite, Essentials, or Plus. There are no minimum fees or upfront commitments. A feature plan applies to one user pool, so different user pools in the same account can use different plans.

6.2 Feature Plans

Amazon Cognito user pool feature plans and example prices.
PlanTypical usePricing highlights
LiteBasic registration, sign-in, MFA, federation, and Lambda triggersFirst 10,000 MAUs per month free for eligible usage. Paid MAUs use tiered pricing that starts at $0.0055 per MAU.
EssentialsAdds managed login, passwordless authentication, passkeys, email MFA, and enhanced token customizationFirst 10,000 MAUs per month free, then $0.015 per MAU.
PlusAdds advanced threat protection such as adaptive authentication and compromised credentials detectionNo MAU free tier. $0.020 per MAU.

New user pools default to the Essentials plan. The prices in the table are US East (N. Virginia) prices as of November 2026. For the most current information, see Amazon Cognito pricing.

Exam Trap

  • Threat protection (adaptive authentication and compromised credentials detection) needs the Plus plan.
  • The Plus plan has no free tier, so cost grows with every MAU.
  • Prices change. If a question gives no prices, answer with the plan whose features match the requirement.

Memory Hook

Lite is the basics, Essentials is the modern sign-in features, and Plus adds threat protection.

8. Knowledge Check

Answer each question in your own words, and then open the model answer to compare.

Question 1: STS and Long-Term Keys. A script in an external application uploads data to an Amazon S3 bucket with a long-term access key stored in its source code. Explain how AWS STS reduces the risk, and name the values that make up the credentials STS returns.

Show the model answer

A long-term access key in source code can be copied and used until someone revokes it. AWS STS issues temporary credentials that expire automatically, so a leaked credential stops working after a short time. The credentials contain an access key ID, a secret access key, a session token, and an expiration time.

Question 2: Sign-In and Upload Flow. Describe how a mobile app user signs in and then uploads a photo to Amazon S3. Name the role of the Cognito user pool, the Cognito identity pool, the IAM role, and AWS STS.

Show the model answer

The user signs in through a Cognito user pool, which returns JSON Web Tokens. The application passes the ID token to a Cognito identity pool, which validates it with the issuing identity provider and calls AWS STS to assume the IAM role mapped to that user. STS returns temporary credentials, and the application uploads the photo to Amazon S3 within the permissions of that role.

Question 3: Protecting Sign-In. A company wants to protect its application’s sign-in against stolen passwords and abusive traffic. Evaluate which Cognito security features you would recommend, and explain why.

Show the model answer

Recommend the Plus plan features: compromised credentials detection to flag or block leaked passwords, adaptive authentication to require MFA or block risky sign-ins, and threat protection to respond to account takeover. Associate an AWS WAF web ACL with the user pool to control abusive requests, and give identity pool roles only the permissions that users need. Plus has no free tier, so weigh the per-MAU cost.

Question 4: Choosing the Right Service. Explain the differences between AWS STS, Cognito user pools, Cognito identity pools, and AWS IAM Identity Center in terms of target audience, primary function, and returned credentials.

Show the model answer

AWS STS issues temporary credentials to IAM roles and sessions for AWS workloads, users, and federated identities. Cognito user pools serve external application users and return ID, access, and refresh JWTs. Cognito identity pools serve authenticated or guest application users and return temporary AWS credentials through STS. AWS IAM Identity Center serves the internal workforce and provides single sign-on sessions and temporary console or command line credentials for multiple AWS accounts.

Question 5: Guest Access. A mobile app lets guests download public content from Amazon S3 before they sign in, and gives signed-in users more access. Which Cognito components do you use, and why?

Show the model answer

Use a Cognito identity pool configured for guest (unauthenticated) access, so guests receive temporary credentials that an IAM role limits to the public content. Add a user pool for sign-in. After users authenticate, the identity pool maps them to a role with broader permissions.
